Foundation

The Storage Decision Tree

Every storage decision flows from access patterns, not data volume. Volume is an operational concern; the wrong engine for your access pattern is an architectural failure you'll spend years undoing.

STORAGE SELECTION FLOWCHART ──────────────────────────────────────────────────────────── Do you need ACID transactions across multiple entities? │ ├── YES ──► Do you need to scale writes beyond a single node? │ │ │ ├── NO ──► PostgreSQL / MySQL (single-leader SQL) │ │ │ └── YES ──► CockroachDB / Spanner / YugabyteDB (distributed SQL) │ └── NO ───► What is your PRIMARY access pattern? │ ├── Point lookups by key ──► DynamoDB / Redis / Cassandra │ ├── Flexible schema, rich queries ──► MongoDB / Firestore │ ├── Relationship traversal ──► Neo4j / Amazon Neptune │ ├── Append-only time-series ──► InfluxDB / TimescaleDB / Prometheus │ ├── Full-text / fuzzy search ──► Elasticsearch / OpenSearch / Typesense │ └── Large binary objects ──► S3 / GCS / Azure Blob
The Rule No One Tells You

Production systems almost always use multiple stores. PostgreSQL for authoritative state, Redis for hot reads, Elasticsearch for search, S3 for media. The decision tree helps you pick the right store per concern, not one store for everything.

Storage Engine 1

Relational Databases (SQL)

The default starting point for most backend systems. SQL gives you ACID guarantees, expressive JOINs, and battle-tested tooling. The penalty is write throughput at extreme scale and rigid schema evolution.

When SQL Wins

  • Financial transactions, order management — anywhere you need guaranteed consistency across related rows
  • Complex reporting queries with arbitrary JOINs (OLAP workloads favor Postgres over document stores)
  • Foreign key constraints, check constraints, enum types — data integrity enforced at the DB layer
  • Schema migrations are audited and versioned (Flyway / Liquibase)

ACID Unpacked

ACID PROPERTIES — what each actually guarantees: ────────────────────────────────────────────────────────── Atomicity "All or nothing." A transaction's writes either all commit or all roll back. No half-written state. Consistency Data only moves from one valid state to another. Constraints (FK, CHECK, UNIQUE) are always satisfied. Isolation Concurrent transactions don't see each other's partial state. (Levels: READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE) ↑ most DBs default to READ COMMITTED (PostgreSQL: READ COMMITTED) Durability Committed data survives crashes. Written to WAL (write-ahead log) before the client gets a success response. ────────────────────────────────────────────────────────── PostgreSQL isolation levels and what anomalies they prevent: Level Dirty Read Non-Repeatable Read Phantom Read ────────────────── ─────────── ──────────────────── ──────────── READ COMMITTED Protected Possible Possible REPEATABLE READ Protected Protected Possible (PG: Protected) SERIALIZABLE Protected Protected Protected

Storage Engine 2

Document Stores

Stores data as JSON/BSON documents. Schema-flexible — each document can have different fields. The sweet spot is hierarchical, self-contained data where you almost always retrieve the whole object.

🍃

Use when: Product catalogs, user profiles, content management, e-commerce. Rich query language + aggregation pipeline. Native sharding (mongos). Horizontal scale built-in.
🔥
Firestore

Use when: Mobile/web apps with real-time sync. Offline support. Automatic scaling. Limited query capabilities vs Mongo but zero ops overhead.
🛋️

Document Store
Apache CouchDB · Couchbase
Use when: Multi-master replication, offline-first apps. CouchDB's MVCC allows conflict resolution. Couchbase adds KV + N1QL query layer.
The JOIN Problem with Document Stores

Document stores have no native JOINs. If you frequently need to combine data from multiple collections, either embed the related data inside the parent document (denormalize) or reconsider whether SQL is a better fit. Embedding vs referencing is the core data modeling decision in MongoDB.

Storage Engine 3

Key-Value Stores

Pure hash-map semantics: get(key), set(key, value), delete(key). The simplest possible data model delivers the highest possible throughput. No schema, no query language beyond key lookups.

KEY-VALUE ACCESS PATTERNS vs WRONG USE CASES ────────────────────────────────────────────────────────── RIGHT FITS: Session storage user:{uuid} → {token, expiry, preferences} Feature flags feature:{name} → {enabled: true, rollout: 25} Rate limit counters ratelimit:{ip}:{window} → count (+ EXPIRE) Hot cache layer product:{id} → serialized product blob Distributed locks lock:{resource} → {holder, ttl} (with SETNX) WRONG FITS (reach for SQL/Document instead): "Find all sessions for user X" ← no secondary index, requires full scan "List products with price > 50" ← no range queries by value "Join user + orders" ← no relationship model Anything requiring aggregation ← no GROUP BY ────────────────────────────────────────────────────────── Redis vs DynamoDB vs Memcached: Redis → Rich data types (Sorted Set, List, Bitmap, HyperLogLog) Persistence optional (RDB snapshot + AOF log) Lua scripting for atomic multi-key ops Best for: leaderboards, queues, session, rate limiting DynamoDB → Serverless, infinite scale, SLA-backed Composite keys (PK + SK) enable range queries Global Secondary Indexes (GSI) for alternate access patterns Best for: serverless apps, IoT, gaming leaderboards Memcached → Pure caching only (no persistence, no types beyond string) Multi-threaded (Redis is single-threaded per shard) Best for: simple cache layer where you need maximum raw throughput
Storage Engine 4

Wide-Column Stores

Rows identified by a partition key. Each row can have a different set of columns. Built for write-heavy workloads at massive scale, with data physically sorted by clustering columns for efficient range reads.

Cassandra Data Model

CASSANDRA — Think "partitioned, sorted rows" ────────────────────────────────────────────────────────── TABLE: messages_by_conversation PRIMARY KEY: (conversation_id, sent_at, message_id) ↑ partition key ↑ clustering keys (sorted DESC) conversation_id sent_at message_id content sender ──────────────── ───────────────── ────────── ──────── ────────── "conv_abc" 2024-01-15 14:32 "msg_001" "Hello" "user_A" "conv_abc" 2024-01-15 14:31 "msg_000" "Hey!" "user_B" "conv_xyz" 2024-01-15 09:00 "msg_055" "Done" "user_C" → All messages for "conv_abc" are on the same node (same partition) → Time-ordered within the partition (clustering key) → Query: SELECT * FROM messages WHERE conversation_id='conv_abc' LIMIT 20 returns last 20 messages in O(1) with no full table scan ────────────────────────────────────────────────────────── Design Rule: Model queries first, schema second SQL: normalize data, then write arbitrary queries Cassandra: decide your queries, then design a table per query pattern

Storage Engine 5

Graph Databases

Stores entities as nodes and relationships as edges. Relationship traversal is O(1) per hop regardless of database size — exactly the opposite of recursive JOINs in SQL which get exponentially slower.

GRAPH DB vs SQL — Friend-of-friend query at depth 4 ────────────────────────────────────────────────────────── SQL (recursive CTE): at 1M users, depth-4 query = O(n^4) join explosion 10ms → 100ms → 1s → 10s... query times blow up Neo4j / Cypher: index-free adjacency — each node stores direct pointers to connected nodes, depth-4 traversal stays O(depth × avg_connections) regardless of total graph size → predictably fast ────────────────────────────────────────────────────────── Cypher query (Neo4j): MATCH (me:User {id: "alice"}) -[:FOLLOWS*2..4]->(suggested:User) WHERE NOT (me)-[:FOLLOWS]->(suggested) AND me <> suggested RETURN suggested.name, count(*) AS mutual_connections ORDER BY mutual_connections DESC LIMIT 20 → "People me might know" — 2-4 hops, not direct follows → Same query in SQL requires 3+ self-joins and becomes unusable at scale ────────────────────────────────────────────────────────── USE CASES: Social graphs · Fraud detection (ring networks) · Knowledge graphs · Recommendation engines · Network topology mapping · Access control / permissions
Storage Engine 6

NewSQL & Distributed SQL

Combines the ACID guarantees of SQL with the horizontal scalability of NoSQL. The tradeoff: higher latency per write (distributed consensus), higher operational complexity, and fewer ecosystem tools than PostgreSQL.

NEWSQL ARCHITECTURE — Raft consensus + distributed storage ────────────────────────────────────────────────────────── ┌─────────────────────────────────────────────┐ │ SQL Query Layer (PostgreSQL wire) │ └──────────────┬──────────────────────────────┘ │ distributed query planner ┌──────────────▼──────────────────────────────┐ │ Transaction Coordinator │ └────┬──────────────┬──────────────┬──────────┘ │ │ │ ┌────────▼───┐ ┌────────▼───┐ ┌────────▼───┐ │ Range 1 │ │ Range 2 │ │ Range 3 │ │ (Raft │ │ (Raft │ │ (Raft │ │ replicated│ │ replicated│ │ replicated│ │ 3-5 nodes)│ │ 3-5 nodes)│ │ 3-5 nodes)│ └────────────┘ └────────────┘ └────────────┘ CockroachDB · YugabyteDB · TiDB · Google Spanner (managed) Use when: ✓ Need global distribution with strong consistency (Spanner) ✓ Multi-region writes with no single SPOF ✓ Existing Postgres codebase that needs to scale out ✗ Avoid if single-region Postgres can handle your write volume ✗ Avoid if p99 latency is critical (consensus adds ~10-50ms)
Scaling Pattern

Sharding Strategies

Sharding partitions data across multiple database nodes. The strategy you choose determines your query patterns, hot spot risk, and how hard resharding will be two years from now.

Range Sharding

RANGE SHARDING — Shard by key ranges ────────────────────────────────────────────────────────── user_id range │ Shard ───────────────┼────────────────── 0 – 999,999 │ Shard A (DB node 1) 1M – 1,999,999 │ Shard B (DB node 2) 2M – 2,999,999 │ Shard C (DB node 3) Pros: Range queries efficient: "all users 500k–600k" goes to one shard Easy to reason about data location Supports ordered scans (time-series: all events from T1 to T2) Cons: Hot spot risk: new user IDs all land on the latest shard Temporal data (timestamps) → all writes hit the current range shard Uneven shard sizes as data grows non-uniformly

Hash Sharding

HASH SHARDING — shard = hash(key) % N ────────────────────────────────────────────────────────── user_id = "alice" → SHA256 → 0x3f2a... → mod 4 = Shard 2 user_id = "bob" → SHA256 → 0x9c41... → mod 4 = Shard 0 user_id = "charlie" → SHA256 → 0x71bd... → mod 4 = Shard 3 Pros: Even distribution regardless of key values No hot spots on new data Simple to implement Cons: Range queries impossible: "users 500k–600k" → must scan ALL shards Resharding = change N = rehash ALL keys → massive data migration No natural ordering for range scans Solution: Consistent Hashing (see Traffic Shaping pattern) → Virtual nodes on a ring → only 1/N keys remapped when adding a shard

Directory (Lookup) Sharding

DIRECTORY SHARDING — explicit mapping in a lookup service ────────────────────────────────────────────────────────── ┌────────────────────────┐ │ Shard Directory │ │ (Redis / Config DB) │ │ user_id → shard_id │ └──────────┬─────────────┘ │ ┌───────────────┼───────────────┐ ┌──────▼──────┐ ┌──────▼──────┐ ┌──────▼──────┐ │ Shard A │ │ Shard B │ │ Shard C │ └─────────────┘ └─────────────┘ └─────────────┘ Pros: Completely flexible — any shard assignment logic Resharding = update directory entries, move data incrementally Can co-locate related users (tenant-aware, same geography) Cons: Directory lookup on every read/write (extra network hop) Directory becomes a single point of failure (must be highly available) Directory can become stale during resharding windows

Availability Pattern

Replication Topologies

Replication keeps copies of your data on multiple nodes. The topology determines your consistency guarantees, failover behavior, and write scalability.

THREE REPLICATION TOPOLOGIES ────────────────────────────────────────────────────────── 1. SINGLE-LEADER (Master-Replica / Primary-Standby) Writes → Primary ──WAL stream──► Replica 1 (read traffic) └─────WAL stream──► Replica 2 (failover standby) Consistency: Strong (sync replication) or Eventual (async) Write scale: ✗ Single writer bottleneck Failover: Replica promoted to primary (seconds–minutes of downtime) Use: PostgreSQL read replicas, MySQL primary/replica, most RDBMS ────────────────────────────────────────────────────────── 2. MULTI-LEADER (Active-Active) US Primary ──► EU Primary (replication both ways) │ │ US Replicas EU Replicas Consistency: Eventual (conflict resolution required) Write scale: ✓ Writes accepted at any leader Conflict: Last-Write-Wins / CRDT / application-level merge Use: Multi-region writes (CouchDB, MySQL Group Replication) ────────────────────────────────────────────────────────── 3. LEADERLESS (Dynamo-style / Peer-to-Peer) Client writes to W of N replicas (quorum write) Client reads from R of N replicas (quorum read) When W + R > N → strong consistency guaranteed W=2, R=2, N=3 → W+R=4 > 3 → strong consistency W=1, R=1, N=3 → W+R=2 ≤ 3 → eventual consistency (higher throughput) Use: Cassandra, Amazon DynamoDB, Riak
Replication Lag is Not a Bug, It's a Feature Tradeoff

Synchronous replication = zero lag, but every write waits for replica acknowledgment → higher write latency. Async replication = lower write latency, but replicas may be seconds behind. Read-your-own-writes consistency requires routing reads to the primary or using sync replication for at least one replica.

Performance Pattern

Indexing Deep Dive

The wrong index (or missing one) is the #1 cause of database performance problems. Understanding the underlying data structure tells you exactly which index to reach for.

B-tree vs LSM tree vs Hash Index

B-TREE INDEX — PostgreSQL, MySQL default ────────────────────────────────────────────────────────── [50] / \ [20, 30] [70, 90] / | \ / | \ [10] [25] [35] [60] [80] [100] Reads: O(log n) — balanced tree, 3-4 disk reads for millions of rows Writes: O(log n) — insert in-place, rebalance if needed Range: Efficient — leaf nodes linked, range scan = sequential leaf walk Use: General purpose — most SQL indexes, equality + range queries ────────────────────────────────────────────────────────── LSM TREE — Cassandra, RocksDB, LevelDB, InfluxDB ────────────────────────────────────────────────────────── Write: MemTable (in-memory) → flush to SSTable (immutable on-disk) SSTables periodically compacted (merging sorted files) Read: Check MemTable → L0 SSTables → L1 → L2... (bloom filter skip) Reads: O(log n) but slower than B-tree on cold reads (multi-level check) Writes: Extremely fast — sequential append, never in-place update Range: Good (SSTables are sorted) Use: Write-heavy workloads — time-series, event log, Cassandra ────────────────────────────────────────────────────────── HASH INDEX — in-memory key→offset map ────────────────────────────────────────────────────────── Reads: O(1) — pure hash lookup Writes: O(1) average Range: Impossible — no ordering preserved Use: Exact-match lookups only — session store, KV cache

Composite & Covering Indexes

COMPOSITE INDEX — column order matters ────────────────────────────────────────────────────────── CREATE INDEX idx_orders ON orders(user_id, status, created_at DESC); Uses index: WHERE user_id = 42 WHERE user_id = 42 AND status = 'shipped' WHERE user_id = 42 AND status = 'shipped' ORDER BY created_at DESC Skips index: WHERE status = 'shipped' ← leading column missing WHERE created_at > '2024-01-01' ← leading columns missing Rule: Prefix rule — index only usable if leading columns are in WHERE/JOIN ────────────────────────────────────────────────────────── COVERING INDEX — index contains all SELECT columns ────────────────────────────────────────────────────────── Query: SELECT user_id, status, created_at FROM orders WHERE user_id = 42 Normal index: find row pointers → fetch rows from heap (random I/O) Covering idx: index already has user_id + status + created_at → index-only scan, never touch the actual table rows → 10-100× faster on I/O-bound queries PostgreSQL: CREATE INDEX INCLUDE (status, created_at) → explicit covering MySQL: All InnoDB secondary indexes automatically include PK column

Partial & Expression Indexes

PARTIAL INDEX — index only the rows you actually query ────────────────────────────────────────────────────────── -- Only active orders need fast lookup, not 5 years of history CREATE INDEX idx_active_orders ON orders(user_id) WHERE status IN ('pending', 'processing'); -- 10M orders total, 50k active → index size 200× smaller EXPRESSION INDEX — index a computed value ────────────────────────────────────────────────────────── -- Case-insensitive email lookup without touching application code CREATE INDEX idx_email_lower ON users(LOWER(email)); -- Query: SELECT * FROM users WHERE LOWER(email) = LOWER($1) -- Now uses the index instead of full table scan
Specialized Storage

Time-Series Databases

Optimized for append-only, timestamp-ordered data with high write throughput and efficient range aggregations. Using a general-purpose SQL DB for time-series data at scale leads to painful performance degradation over time.

TIME-SERIES ACCESS PATTERNS ────────────────────────────────────────────────────────── Write pattern: INSERT (sensor_id, timestamp, value) — billions/day Always monotonically increasing timestamp Bulk inserts common (batched from edge devices) Read pattern: "Last 5 minutes of CPU for host-042" "Average latency per service per hour, last 30 days" "Max temperature per zone, rolling 15-min window" Key optimization: Column-based storage [time, time, time, time] compressed → 90%+ savings [value, value, value...] delta-encoded (store diffs) ────────────────────────────────────────────────────────── RETENTION POLICIES — automatic data lifecycle ────────────────────────────────────────────────────────── Raw data (1s resolution) → keep 7 days → auto-delete 1-min rollup → keep 30 days → downsampled from raw 1-hour rollup → keep 1 year → downsampled from 1-min 1-day rollup → keep 5 years → downsampled from 1-hour Benefit: Storage grows O(log time) not O(time) Queries on old data hit pre-aggregated rollups → fast ────────────────────────────────────────────────────────── TSDB CHOICES: InfluxDB → Purpose-built TSDB, Flux query language, push model Best for: metrics, monitoring, IoT TimescaleDB → PostgreSQL extension (SQL queries work!) Best for: SQL ecosystem, complex joins with relational data Prometheus → Pull model, short retention, alerting-first Best for: Kubernetes metrics + Grafana dashboards ClickHouse → OLAP columnar store, SQL, petabyte-scale analytics Best for: log analytics, event analytics, not pure time-series
Specialized Storage

Blob & Object Storage

Immutable, flat-namespace storage for large binary objects: images, videos, backups, ML model artifacts, logs. Object storage is not a file system — there's no in-place editing, no rename, no directory structure (just prefixes).

OBJECT STORAGE ARCHITECTURE (S3 / GCS / Azure Blob) ────────────────────────────────────────────────────────── Namespace: bucket/key (flat — "folders" are just key prefixes) s3://my-bucket/users/alice/avatar.jpg s3://my-bucket/users/alice/bg.jpg s3://my-bucket/videos/2024/01/upload_abc.mp4 Operations: PUT → upload (atomic, versioned if enabled) GET → download (direct URL or pre-signed URL) DELETE → mark deleted (immediate or via lifecycle rule) LIST → list keys by prefix (paginated) ────────────────────────────────────────────────────────── LIFECYCLE POLICIES — automated tiering ────────────────────────────────────────────────────────── Day 0: Upload → S3 Standard (hot, immediate access) Day 30: Auto-transition → S3-IA (infrequent access, 40% cheaper) Day 90: Auto-transition → S3 Glacier (archive, minutes to hours retrieval) Day 365: Auto-transition → Deep Archive (12h retrieval, 75% cheaper) Day 2555: Auto-delete ────────────────────────────────────────────────────────── PRE-SIGNED URLs — secure direct uploads/downloads ────────────────────────────────────────────────────────── Client → Your API → "Give me URL to upload my avatar" Your API → S3: generate pre-signed PUT URL (expires in 15 min) Your API → Client: {url: "https://s3.amazonaws.com/...?sig=..."} Client → S3: PUT directly (bypasses your server, huge bandwidth saving) → Your backend never touches the binary data → S3 verifies signature, enforces max file size, CORS → After upload, client notifies your API → record metadata in DB
Specialized Storage

Search Engines

Full-text search, fuzzy matching, and relevance ranking require an inverted index — a fundamentally different data structure from B-trees. Elasticsearch is the default choice; Typesense is the simpler, faster alternative for most apps.

INVERTED INDEX — how Elasticsearch works ────────────────────────────────────────────────────────── Documents: Doc 1: "Distributed caching with Redis" Doc 2: "Redis cluster setup guide" Doc 3: "Cache invalidation strategies" Tokenize + normalize (lowercase, stem, remove stopwords): "distribut" → [Doc1] "cach" → [Doc1, Doc3] "redis" → [Doc1, Doc2] "cluster" → [Doc2] "setup" → [Doc2] "invalidat" → [Doc3] "strategi" → [Doc3] Query: "redis caching" "redis" → [Doc1, Doc2] "cach" → [Doc1, Doc3] Union → Doc1 ∩ Doc1 = Doc1 (highest score), Doc2, Doc3 ────────────────────────────────────────────────────────── ELASTICSEARCH vs TYPESENSE vs OPENSEARCH ────────────────────────────────────────────────────────── Elasticsearch → Most mature, complex, Java-based Powerful aggregations, geo-search, ML ranking High operational complexity and memory footprint Best for: log analytics (ELK stack), complex search Typesense → Rust-based, extremely fast, simple API Typo-tolerance built-in, instant search Simpler deployment (single binary) Best for: product search, autocomplete, most app search OpenSearch → AWS fork of Elasticsearch (open-source, no license risk) Compatible with ES tooling, AWS-managed (AOSS) Best for: AWS shops, ELK replacement without Elastic license ────────────────────────────────────────────────────────── SEARCH AS A SECONDARY INDEX — canonical pattern Source of truth: PostgreSQL (ACID writes) Search index: Elasticsearch (async sync via CDC or event) On write: INSERT into Postgres → publish event → ES indexer On read: Search → ES → get IDs → fetch full records from Postgres
Architecture Pattern

Multi-Store Architecture

Modern production systems routinely combine 3-5 storage engines. Each engine serves its natural access pattern. The architecture challenge is keeping these stores synchronized and knowing which is the source of truth.

SOCIAL PLATFORM — 5-store architecture ────────────────────────────────────────────────────────── [ Client ] │ [ API Gateway ] / | | | \ / | | | \ ┌─────────┐ │ │ │ ┌──────────┐ │Postgres │ │ │ │ │ Redis │ │Users │ │ │ │ │ Sessions│ │Posts │ │ │ │ │ Feeds │ │Follows │ │ │ │ │ Counts │ └─────────┘ │ │ │ └──────────┘ │ │ │ ┌──────┘ │ └──────────┐ ┌────────┐ │ ┌────────┐ │ Elastic│ │ │ S3 │ │ Search │ │ │ Images │ │ Users │ │ │ Videos │ │ Posts │ │ └────────┘ └────────┘ │ ┌──────────┐ │InfluxDB │ │ Analytics│ │ Events │ │ Metrics │ └──────────┘ Ownership rules: Postgres → source of truth for users, posts, social graph Redis → derived hot state (rebuilt from Postgres if lost) Elasticsearch → derived search index (rebuilt from Postgres via CDC) S3 → source of truth for binary objects (never duplicated) InfluxDB → derived analytics (append-only from event stream)
Change Data Capture (CDC) — the glue between stores

Debezium watches the Postgres WAL (write-ahead log) and publishes every INSERT/UPDATE/DELETE as a Kafka event. Elasticsearch consumers and Redis consumers subscribe and update their respective indexes. This keeps all stores eventually consistent without coupling application code to every storage system. Debezium → Kafka → Elasticsearch indexer is production-standard for search index sync.

9 Lenses

How Each Team Thinks About Storage

The same storage decision looks completely different depending on which concerns dominate your role.

🏗️ Infrastructure Engineer

We care about disk I/O, memory pressure, and operational footprint. A PostgreSQL cluster with streaming replication is something we can operate reliably. Adding MongoDB alongside it doubles our backup surface area, doubles our restore drill complexity, and requires separate expertise. Before adding a second database technology, we ask: does the application complexity justify the operational cost?

Our playbook is: managed services wherever possible (RDS, Cloud SQL, Atlas). Self-managed only when cost or compliance demands it — and then we size instances conservatively (database RAM = working set size) and set up automated failover before going to production.

For sharding, we prefer application-level sharding over Vitess or manual setup until we demonstrably need it. A Postgres read replica can scale you to 10× read traffic before you need to shard writes. We've seen teams shard prematurely and spend months migrating back to a simpler topology.

🌐 Network Engineer

Database connections are a network resource. Connection pooling (PgBouncer, ProxySQL) is not optional at scale — each open Postgres connection consumes ~5MB of memory and a file descriptor. At 1000 concurrent users, 1000 Postgres connections is a problem before you hit any query bottleneck.

Multi-region database topologies require careful latency accounting. A cross-region synchronous replication write adds 60-150ms of network RTT for every transaction. We help teams make the call between sync (zero data loss, higher latency) and async (data loss risk, lower latency) replication, because that's fundamentally a network latency problem, not a database problem.

Encryption in transit is always on — TLS for all database connections, never plaintext database sockets on public or shared network segments. We enforce this at the firewall and audit it monthly.

⚙️ Platform Engineer

Our job is to give product teams a "database as a service" experience — provision a Postgres instance with click or CLI, get connection strings injected into the service, migrations run via CI pipeline, and backups happen automatically. When teams bypass this for a self-hosted MongoDB because they want flexible schema, we lose auditability and backup guarantees.

We standardize on two or three approved database technologies for our platform. More than that, and we can't provide operator expertise, runbook coverage, or reliable SLAs for all of them. This means sometimes pushing back on "we need a graph database" and asking whether the team has actually tried modeling the problem in Postgres with recursive CTEs first.

Schema migration tooling is critical. Flyway or Liquibase runs in CI, every migration is reviewed and versioned, and we test all migrations against a production-sized dataset in staging. The number one cause of production incidents we see is a migration that ran fine on 1000 rows and locked the table for 10 minutes on 100M rows.

🔐 Security / Cyber Engineer

Every database is a data exfiltration target. Our concerns are: who can access what data, how is that access audited, and can we detect anomalous access patterns. Row-level security (Postgres RLS) lets us enforce tenant isolation in the database layer rather than relying on application code to be correct every time. Defense in depth — application bugs shouldn't expose other tenants' data.

Encryption at rest is baseline. Encryption of specific columns (PII, payment data) goes further — if someone exfiltrates the database dump, they still can't read SSNs or card numbers without the application key. We use envelope encryption: data encrypted with a data key, data key wrapped with a master key in KMS. Key rotation doesn't require re-encrypting all data.

Audit logging for all DDL changes and privileged queries is non-negotiable. We want to know: who ran `SELECT * FROM users`, when, and from which IP. In Postgres, pgaudit extension + centralized log shipping to a SIEM. Schema changes go through change management — no direct `ALTER TABLE` in production without a ticket and a change window.

📊 Data Engineer

The production database is the source of truth, but it's the wrong place to run analytics. Long-running analytical queries contend with OLTP traffic and can lock rows or consume connections needed for user-facing requests. We pull data to a warehouse (BigQuery, Snowflake, Redshift) via CDC or scheduled ETL, and analytics runs there — never on the production replica.

Schema design for analytics workloads favors star schema (fact + dimension tables) over normalized OLTP schemas. Denormalization is acceptable in the warehouse because you never write to it — you only read it. Wide tables with pre-joined data can answer 80% of business questions with a single table scan instead of a 5-way join.

We obsess over data types because storage engines treat them differently. In Postgres, `text` vs `varchar(255)` has no performance difference, but `integer` vs `bigint` vs `numeric` matters for index size and arithmetic precision. In Parquet (columnar analytics format), choosing the right type can halve storage size and halve query time through better compression.

🤖 ML / AI Engineer

Training data pipelines need immutable, versioned datasets. We don't train on the live production database — we snapshot it to object storage (Parquet files on S3) at specific points in time, and each training run references a fixed dataset version. This makes experiments reproducible and prevents training data leakage from future data.

Feature stores are a specialized storage layer for ML. They serve two purposes: offline storage (historical features for training, Parquet on S3) and online storage (low-latency feature serving at inference time, Redis or DynamoDB). The hard problem is keeping offline and online features consistent so that what you trained on matches what you serve at prediction time.

Vector databases (Pinecone, Weaviate, pgvector) are the newest storage category we care about. Embedding vectors for semantic search, RAG pipelines, and recommendation systems need approximate nearest-neighbor (ANN) search — something no SQL index can do. pgvector in Postgres handles most use cases up to ~10M vectors; dedicated vector DBs are for larger scale or more complex similarity metrics.

⚡ Backend Engineer

I care about query performance, connection management, and ORM behavior. The most common mistakes I see: SELECT * queries that return 50 columns when you need 3 (unnecessary data transfer and memory), missing indexes on foreign keys (every JOIN becomes a sequential scan), and N+1 query patterns hidden inside ORMs (fetch a list of users, then loop and fetch each user's orders separately — 1 + N queries).

Database transactions should be short. Long transactions hold locks and inflate MVCC bloat in Postgres. The pattern I follow: acquire data → do any computation outside the transaction → open transaction → write → commit. Never make API calls or do heavy processing inside a transaction. If the HTTP call hangs, you're holding a lock for the duration.

Connection pooling is always on. SQLAlchemy's pool_size + max_overflow matches PgBouncer's pool settings. I test connection pool behavior explicitly under load — a pool exhaustion bug hides until you have real traffic, then it causes cascading timeout failures across all endpoints simultaneously.

🎨 Frontend Engineer

From the frontend perspective, the storage technology itself is mostly invisible — I care about the API response shape, response time, and consistency guarantees. But storage choices bleed through. If the backend uses MongoDB with flexible schema, I might get inconsistent field presence across different documents and have to null-check everything. If it uses an eventually consistent store, I might see stale data immediately after my own writes.

Optimistic updates require understanding storage guarantees. If I update a post optimistically in the UI before the API call completes, and the backend uses eventual consistency, my next page load might show the old value. This means the frontend needs to either manage local state carefully or understand when to trust the server response vs the local cache.

For offline-first apps (PWA, mobile), I'm implementing a client-side store (IndexedDB, SQLite via Expo) that syncs with the backend. The sync protocol has to handle conflicts — what wins when the user edits offline and someone else edits the same record? The storage technology on the backend determines whether conflict resolution is possible (CRDTs, last-write-wins, versioned fields) or painful.

📡 SRE / Site Reliability Engineer

Storage is where the most catastrophic and hardest-to-reverse incidents happen. Our golden rules: every database has automated backups tested weekly with a full restore drill. Backup untested is no backup. We've seen teams discover their Postgres backups were corrupted only when they tried to restore after a failure — the backup job was silently failing for months.

Our SLOs for storage depend on the tier. User-facing reads: p99 < 20ms (served from cache), p99 < 100ms (from DB with index). Analytics queries: p95 < 5s. Write SLO: p99 < 50ms for OLTP. When these drift, we alert and treat it as an incident — database performance degradation is always a leading indicator of something worse.

Schema migrations in production require a runbook. For tables over 1M rows, we use online DDL tools (pt-online-schema-change for MySQL, pg_repack or pg_partman for Postgres). We test migrations against a production-sized snapshot, measure lock duration, and set a rollback plan before touching production. A migration that seemed fast in staging can take hours and lock the table on production-scale data.

Problem 01
Design the Storage Layer for a Social Platform (Instagram-scale)
Multi-store Sharding Replication Blob Storage

Requirements

500M users. Users post photos/videos. Follow graph (up to 100M edges). 2B daily active sessions. Search users and hashtags. Prioritize: availability over strict consistency for social data, strict consistency for payment/billing.

Storage Architecture

USER WRITES (photo upload flow): Client ──► POST /media/upload API server generates pre-signed S3 URL Client ──► PUT image.jpg directly to S3 (bypass API server) API server called back: POST /media/confirm API server ──► Postgres: INSERT INTO media (user_id, s3_key, ...) ──► Redis: invalidate user feed cache ──► Event bus: publish "media.uploaded" event CDC stream ──► Elasticsearch: index media for hashtag search ────────────────────────────────────────────────────────── SHARDING STRATEGY: Postgres → Shard on user_id (hash mod 64 shards) Each shard: 1 primary + 2 async replicas User data never crosses shards (no cross-shard joins) S3 → No sharding needed (S3 is infinite scale by design) Key structure: {bucket}/{user_id_prefix}/{date}/{uuid}.jpg Elasticsearch → Index per content type (users, posts, hashtags) Sharded internally by ES (5 primary shards default) Redis → Feed cache: user:{id}:feed → sorted set of post IDs Sessions: session:{token} → user_id (with TTL) Sharded Redis Cluster (consistent hashing, 16k hash slots) ────────────────────────────────────────────────────────── CONSISTENCY DECISIONS: Follow relationship: Eventual OK — if you follow someone and their posts appear 500ms later, users don't notice Payment / billing: Strict required — dedicated Postgres + sync replica Session tokens: Strict required — Redis with sync replication Photo metadata: Eventual OK — async replica lag acceptable

Schema Key Tables

-- Sharded user table (each shard holds a user_id range)
CREATE TABLE users (
  user_id     BIGINT PRIMARY KEY,   -- shard key
  username    TEXT UNIQUE NOT NULL,
  email       TEXT UNIQUE NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT now(),
  profile     JSONB                  -- flexible metadata, avoid nullable columns
);

-- Media table, co-located with user on same shard
CREATE TABLE media (
  media_id    BIGINT PRIMARY KEY,
  user_id     BIGINT NOT NULL,       -- same shard as user
  s3_key      TEXT NOT NULL,
  media_type  TEXT CHECK (media_type IN ('photo','video','reel')),
  caption     TEXT,
  created_at  TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_media_user_time ON media(user_id, created_at DESC);

-- Follow graph: keep on a dedicated graph shard or use Cassandra
CREATE TABLE follows (
  follower_id BIGINT NOT NULL,
  followee_id BIGINT NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (follower_id, followee_id)
);
-- Covering index for "who does user X follow?" and "who follows user X?"
CREATE INDEX idx_follows_followee ON follows(followee_id, follower_id);
Problem 02
Design Storage for IoT Sensor Platform (10M Devices)
Time-Series Wide-Column Retention Policy Write-Heavy

Problem Shape

10M IoT devices each send a reading every 10 seconds: device_id, timestamp, sensor_type, value. Peak write rate: 1M events/second. Queries: recent readings per device, aggregates per device class per hour, anomaly detection on rolling windows. Data older than 90 days is rarely queried.

Why Not PostgreSQL?

Postgres with a naive schema hits a wall at ~5M rows/day: VACUUM overhead grows, B-tree indexes get bloated from sequential inserts, and range-aggregate queries on billions of rows become multi-second scans. This is exactly what time-series databases were built to solve.

Architecture

IOT INGESTION PIPELINE 10M devices │ MQTT / CoAP (binary protocol, low overhead) ▼ [ MQTT Broker / Kafka ] (buffer — handles bursty device reconnects) │ stream partitioned by device_id ▼ [ Ingest Service ] (stateless, horizontally scaled) │ batch writes (1000 events per write) ▼ [ TimescaleDB hypertable ] — raw data, 7-day retention │ continuous aggregate job (every 1 minute) ▼ [ TimescaleDB 1-min rollup ] — 30-day retention │ continuous aggregate job (every 1 hour) ▼ [ TimescaleDB 1-hour rollup ] — 1-year retention ────────────────────────────────────────────────────────── WHY TIMESCALEDB (not pure InfluxDB): → Standard SQL (team knows it, BI tools connect to it) → Continuous aggregates = materialized views that auto-update → TimescaleDB chunks = automatic partitioning by time → Can JOIN with relational device metadata in Postgres → pgvector available if we want ML anomaly detection

TimescaleDB Schema

-- Regular Postgres table, converted to hypertable
CREATE TABLE sensor_readings (
  device_id   TEXT        NOT NULL,
  time        TIMESTAMPTZ NOT NULL,
  sensor_type TEXT        NOT NULL,
  value       DOUBLE PRECISION NOT NULL
);

-- Creates 1-day chunks internally (auto-managed)
SELECT create_hypertable('sensor_readings', 'time', chunk_time_interval => INTERVAL '1 day');

-- Compress chunks older than 7 days (typically 95%+ compression ratio)
ALTER TABLE sensor_readings SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'device_id, sensor_type'
);
SELECT add_compression_policy('sensor_readings', INTERVAL '7 days');

-- Auto-drop raw data after 90 days
SELECT add_retention_policy('sensor_readings', INTERVAL '90 days');

-- Continuous aggregate for 1-minute rollups (auto-updated)
CREATE MATERIALIZED VIEW readings_1min
WITH (timescaledb.continuous) AS
SELECT
  device_id, sensor_type,
  time_bucket('1 minute', time) AS bucket,
  avg(value)  AS avg_val,
  min(value)  AS min_val,
  max(value)  AS max_val,
  count(*)    AS sample_count
FROM sensor_readings
GROUP BY device_id, sensor_type, bucket;

SELECT add_continuous_aggregate_policy('readings_1min',
  start_offset => INTERVAL '10 minutes',
  end_offset   => INTERVAL '1 minute',
  schedule_interval => INTERVAL '1 minute');
Problem 03
E-commerce Product Search & Catalog Storage
Elasticsearch PostgreSQL CDC Search Relevance

The Problem with Search in SQL

LIKE '%laptop%' performs a full table scan. ILIKE is case-insensitive but still full scan. PostgreSQL's built-in full-text search (tsvector/tsquery) is good but lacks: typo tolerance, synonym expansion, personalized ranking, and faceted aggregations. For an e-commerce search box, Elasticsearch wins clearly.

Dual-Store Architecture

E-COMMERCE STORAGE SPLIT Source of Truth: PostgreSQL products (id, name, description, price, inventory_count, category_id) orders (id, user_id, total, status, created_at) inventory (product_id, warehouse_id, quantity, reserved) → All transactional writes go here, ACID guaranteed Search Index: Elasticsearch products index with: name, description, category, brand, price, attributes (color, size, material), avg_rating, sales_rank (for popularity boost) → Denormalized, pre-joined, ready for instant query → Updated asynchronously via CDC (Debezium) Session & Cart: Redis cart:{user_id} → Hash {product_id: quantity} session:{token} → user_id recently_viewed:{user_id} → List of product_ids (LRANGE for display) ────────────────────────────────────────────────────────── SYNC PIPELINE (Postgres → Elasticsearch) Postgres WAL │ Debezium connector reads WAL ▼ Kafka topic: products.changes │ Kafka Connect ES Sink writes to Elasticsearch ▼ Elasticsearch products index Lag: typically <500ms (eventual consistency) Conflict: Postgres always wins — ES is rebuilt from Postgres at any time

Decision Guide

Trade-offs Table

Decision Option A Option B When to Choose A
Consistency vs Throughput Synchronous replication (strong) Async replication (eventual) Financial, auth, inventory — any data where staleness causes wrong decisions
SQL vs Document Store PostgreSQL MongoDB When you need JOINs, FK constraints, or complex transactions. Default choice unless access pattern is clearly document-shaped
Hash vs Range Sharding Hash sharding Range sharding When writes are random (user IDs). Use range when recent data is always hot (time-series)
Normalize vs Denormalize Normalized (3NF) Denormalized / embedded Normalized for OLTP (smaller writes, consistent updates). Denormalized for read-heavy or document stores
B-tree vs LSM index B-tree (Postgres default) LSM tree (Cassandra, RocksDB) B-tree for mixed read/write OLTP. LSM for write-heavy, time-series, append-only workloads
Self-hosted vs Managed Managed (RDS, Atlas, Cloud SQL) Self-hosted Managed unless cost at scale or compliance (data residency) requires control. The ops savings outweigh the cost premium at most companies
Single store vs Multi-store Postgres for everything Postgres + Redis + Elasticsearch Single store for early stage. Add specialized stores only when you hit a concrete limitation: search quality, read throughput, or latency
TimescaleDB vs InfluxDB TimescaleDB (SQL) InfluxDB (Flux) TimescaleDB when you need SQL compatibility, JOINs with relational data, or BI tool integration. InfluxDB for pure IoT/monitoring workloads at massive scale
What Not to Do

Anti-patterns

  • Choosing the database before defining access patterns "MongoDB is flexible, let's use it." Schema flexibility is irrelevant if your query patterns require JOINs. Always enumerate your top 5 queries before picking a storage engine — the queries determine the engine, not the other way around.
  • Using a relational DB as a document store Storing all data in a single JSON column in Postgres to get "schema flexibility." You lose query ability (can't index inside JSON efficiently beyond JSONB), lose FK constraints, and get none of the actual benefits of either approach. Pick SQL with a schema, or pick a document store — not a hybrid that's worse than both.
  • Sharding prematurely (before you hit a real limit) Sharding adds enormous complexity: no cross-shard joins, harder schema migrations, complex backup/restore, connection multiplexing. A well-indexed Postgres on a c6g.8xlarge with read replicas can handle 50k+ TPS. Shard when you have concrete evidence of the bottleneck, not as speculative architecture.
  • Indexing every column "just in case" Each index is a write penalty (must be updated on every INSERT/UPDATE/DELETE) and consumes disk. An over-indexed table with 20 indexes can have worse write throughput than one with 3 well-chosen indexes. Use EXPLAIN ANALYZE to find which indexes are actually used, then drop the ones that aren't.
  • No data retention policy — letting the database grow forever Every database needs a retention strategy. Time-series data that never ages out will eventually exhaust disk and slow queries. Decide at schema design time: what's the max data age we'll ever query? Implement retention policies before launch, not after the disk fills up.
  • Running analytics on the production OLTP database Analytics queries (GROUP BY, COUNT, window functions over millions of rows) compete with user-facing OLTP traffic. A slow analytics query can lock rows and cause cascading timeouts. Use a read replica at minimum, a data warehouse (Redshift, BigQuery) for anything serious.
  • Treating the search index as the source of truth Elasticsearch can lose data on improper shutdown, has eventual consistency, and doesn't support ACID transactions. It's a derived index, not a source of truth. Postgres is the source of truth; Elasticsearch is rebuilt from it. If they diverge, Postgres wins and you re-index from Postgres — not the other way around.
  • Long transactions in high-throughput OLTP A transaction that takes 5 seconds holds locks for 5 seconds. In Postgres, long transactions also prevent VACUUM from reclaiming dead rows (MVCC bloat). Keep transactions under 100ms. Move computation, external API calls, and file I/O outside transaction boundaries. If a business flow truly requires a long transaction, consider a saga pattern with compensating transactions instead.
Interview Strategy

Interview Tips for Storage Questions

The Storage Interview Trap

Interviewers want to hear you ask about access patterns before picking a database. Jumping straight to "I'll use MongoDB" or "I'll use PostgreSQL" signals that you're cargo-culting. Always say: "Before I pick the storage engine, let me understand the read/write ratio and the primary query patterns."

Tip 01

Lead with access patterns, not with engines. Ask: "What are the top 3 queries?" before you name a database. Then map those queries to the access pattern → engine matrix.

Tip 02

Always mention the primary-replica pattern. Even for basic SQL setups, say "primary for writes, read replicas for read traffic" — this shows you think about scale even at lower complexity.

Tip 03

Explain sharding only when prompted by scale. Don't shard speculatively. Say: "A single Postgres instance handles X TPS. If we grow past that, we'd shard on user_id using consistent hashing." Then stop unless the interviewer pushes further.

Tip 04

Name the source of truth explicitly. In multi-store designs, interviewers want to hear: "Postgres is the source of truth. Elasticsearch is a derived index rebuilt from Postgres. Redis is a derived cache." This shows you understand data ownership.

Tip 05

Mention EXPLAIN ANALYZE for performance questions. When asked "how do you optimize this query?", say: "First, I'd run EXPLAIN ANALYZE to see if it's using the index, check for sequential scans, and look at estimated vs actual rows." This is exactly what senior engineers do.

Tip 06

For time-series, always mention retention and rollups. Raw data at 1s resolution forever is never the right answer. Say: "I'd keep raw data for 7 days, 1-minute rollups for 30 days, hourly rollups for a year — this keeps storage bounded and historical queries fast."

Clarifications
+
ACID Explained
A = Atomicity: all steps of a transaction succeed or all fail (no partial updates). C = Consistency: the DB moves from one valid state to another — no constraint violations. I = Isolation: concurrent transactions don't interfere (a read doesn't see a half-written transaction). D = Durability: once committed, data survives crashes. ACID is what makes banks trust databases.
+
OLTP vs OLAP
OLTP (Online Transaction Processing): many small, fast read/write operations — your app's main database (users logging in, orders being placed). Optimized for row-based access. OLAP (Online Analytical Processing): complex queries scanning millions of rows (monthly revenue by region). Optimized for column-based access. Never run analytics queries on your OLTP DB in production — use a separate warehouse.
+
BASE (vs ACID)
NoSQL databases often trade ACID for BASE: BA = Basically Available (the system always returns a response, even if stale), S = Soft state (data may change over time without input, due to eventual consistency), E = Eventual consistency (replicas will converge to the same value eventually). BASE allows higher availability and performance at the cost of strict consistency.
+
Document vs Relational
Relational: data in rigid tables with foreign keys. Changing schema requires migrations. Document (MongoDB, Firestore): data stored as JSON-like documents. Flexible schema — each document can have different fields. Great for hierarchical data (a post with nested comments). Bad for: highly relational data (many-to-many relationships are awkward without JOINs).
+
Wide-Column: Cassandra Basics
Cassandra stores data like a table, but you design the schema around your queries. The partition key determines which server stores the data. The clustering key determines sort order within a partition. You must know your access patterns upfront — Cassandra is optimized for specific queries, not flexible ad-hoc queries. Used by Netflix, Instagram, Apple for massive write throughput.
+
Shard Key Selection
The shard key determines how data is distributed across shards. Bad shard key = hotspot (one shard handles 80% of traffic). Example of a bad key: user status (most users are "active" → one shard overloaded). Good key: user_id with consistent hashing → even distribution. Rule: shard key should have HIGH cardinality (many unique values) and be frequently used in queries.
+
WAL (Write-Ahead Log)
WAL = Write-Ahead Log. Before PostgreSQL writes data to disk, it first logs the intended change to the WAL. If the server crashes mid-write, it replays the WAL on restart to recover. Replication works by streaming the WAL from primary to replicas — replicas apply the same log entries. This is why "streaming replication" is fast and consistent.
+
MVCC (Multi-Version Concurrency Control)
MVCC lets readers and writers not block each other. Instead of locking a row when reading, the DB keeps multiple versions of each row. A read transaction sees the snapshot from when it started. A write creates a new version. Readers never block writers; writers never block readers. PostgreSQL and MySQL InnoDB use MVCC — it's why you can do SELECT while a transaction is updating the same rows.
+
B-Tree vs LSM Tree
B-Tree (PostgreSQL, MySQL): tree structure optimized for reads. Data stored in sorted order on disk. Fast reads and point lookups. Writes update in place — can cause write amplification. LSM Tree (Cassandra, RocksDB, LevelDB): writes go to memory first (fast), then flush to disk sorted. Reads may need to check multiple levels. Excellent write throughput. Used when write-heavy workloads dominate.
+
Composite & Covering Index
Composite index: index on multiple columns — (user_id, created_at) speeds up "WHERE user_id = X ORDER BY created_at". The order of columns matters. Covering index: the index contains ALL columns needed by the query — the DB never reads the actual table row (index-only scan). Example: index on (user_id, email, name) covers SELECT email, name WHERE user_id = X without touching the table.
+
Time-Series Databases
Time-series data = measurements over time: CPU usage every 10s, stock prices every millisecond. Regular databases struggle because: data arrives in time order (good for append), queries always filter by time range, and you need to downsample (store per-second for a day, per-minute for a month). InfluxDB, TimescaleDB (PostgreSQL extension), Prometheus (for metrics) are purpose-built for this.
+
Object vs Block vs File Storage
Object storage (S3, GCS): store files as objects with metadata. Cheap, infinitely scalable, HTTP-accessible. Cannot edit in place — must overwrite the whole object. Perfect for images, videos, backups. Block storage (EBS): acts like a hard drive attached to a server. Fast random access. Used for databases. File storage (EFS, NFS): shared file system mounted by multiple servers. Used for shared config files, media processing.
