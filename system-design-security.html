Foundation

Zero Trust Architecture

Old security assumed a hard perimeter — anything inside the network was trusted. Zero Trust flips that: never trust, always verify. Every request must be authenticated and authorized regardless of where it originates.

🏰

Castle-and-Moat (Old)

Perimeter firewall protects the "inside." Once you're in, you're trusted. A single breach compromises everything.

🔍

Zero Trust (New)

Every request verified every time. No implicit trust for internal traffic. Micro-segmentation limits blast radius.

🔑

Identity is the Perimeter

Users, devices, services all have cryptographic identities. Access decisions are based on identity + context, not network location.

📦

Least Privilege

Grant the minimum access required. Time-bound credentials. No standing elevated permissions. JIT (just-in-time) access.

Zero Trust Request Flow User / Service Policy Engine Resource │ │ │ │──── Request (with identity token) ─────►│ │ │ │ Verify: Who are you? │ │ │ Check: Device posture? │ │ │ Evaluate: RBAC/ABAC policy? │ │ │ Log: audit trail │ │◄─── ALLOW / DENY decision ──────────────│ │ │ │ │ │──── (if ALLOW) Request + short-lived token ──────────────────────────►│ │ │ │ │◄───────────────────────────── Response ──────────────────────────────│ Principles: verify explicitly · least privilege · assume breach

Google's BeyondCorp was the pioneering real-world Zero Trust implementation — employees access corporate apps over the internet with no VPN, just strong device and user verification.

Core Concepts

Authentication vs. Authorization

These terms are often confused. Authentication (AuthN) asks "who are you?" — it verifies identity. Authorization (AuthZ) asks "what are you allowed to do?" — it enforces access policy. They are separate concerns.

MFA (Multi-Factor Auth)

Something you know (password) + something you have (TOTP app) + something you are (biometric). Each factor independently verified.

SSO (Single Sign-On)

One login gives access to multiple apps. Implemented via SAML (enterprise) or OIDC (modern web/mobile). IdP (Identity Provider) issues tokens.

Service-to-Service AuthN

Services authenticate with mTLS certificates or short-lived tokens (Workload Identity). No passwords — cryptographic proofs only.

Identity Protocols

OAuth 2.0 & OpenID Connect (OIDC)

OAuth 2.0 is a delegation framework — it lets users grant apps access to their data without sharing passwords. OIDC is built on top of OAuth 2.0 and adds authentication (who the user is), not just authorization (what they can access).

OAuth 2.0 Authorization Code Flow (most secure, for web/mobile apps) User Your App Auth Server Resource API │ │ │ │ │──Click Login───►│ │ │ │ │──Redirect to /auth──►│ │ │ │ (client_id, scope, │ │ │ │ redirect_uri, │ │ │ │ code_challenge) │ │ │◄────────────────│ Login UI ───────────│ │ │──Username/Pwd──►│──────────────────────► │ │ │◄─ auth code ─────────│ │ │ │ │ │ │ │──POST /token ────────►│ │ │ │ (code + code_verifier) │ │ │◄─ access_token ───────│ │ │ │ + refresh_token │ │ │ │ + id_token (OIDC) │ │ │ │ │ │ │ │──Bearer access_token────────────────────────►│ │ │◄──────────────────────────────── user data ──│ PKCE (code_challenge/code_verifier) prevents authorization code interception attacks id_token (JWT) = OIDC layer: contains user identity claims (sub, email, name) access_token = OAuth layer: used to call APIs on user's behalf

Scopes

Fine-grained permissions the app requests: openid profile email read:documents. Users see and consent to these. APIs check the scope on the access token.

Client Credentials Flow

For machine-to-machine (no user). Service authenticates directly to auth server with client_id + client_secret → gets access_token. Used for backend services and daemons.

Token Refresh

Access tokens are short-lived (15 min). Refresh tokens (days/weeks) let apps get new access tokens without re-login. Refresh tokens must be stored securely — rotation invalidates old ones.

Token Introspection

APIs can call the auth server's /introspect endpoint to validate opaque tokens. Slower than JWT validation but tokens can be instantly revoked.

Token Format

JSON Web Tokens (JWT)

A JWT is a self-contained token — it carries claims (user ID, roles, expiry) and a cryptographic signature. APIs can validate it locally without calling the auth server, making JWTs fast for distributed systems.

JWT Structure: three base64url-encoded parts separated by dots Header Payload (Claims) Signature eyJhbGciOiJ . eyJzdWIiOiJ1c2VyX . SflKxwRJSMeKKF2Q Header (decoded): Payload (decoded): { { "alg": "RS256", "sub": "user_123", ← subject (user ID) "typ": "JWT" "iat": 1716700000, ← issued at } "exp": 1716700900, ← expiry (15 min) "iss": "auth.acme.com", ← issuer Signature = RSA-SHA256( "aud": "api.acme.com", ← audience base64(header) + "." + "roles": ["admin"], ← custom claim base64(payload), "email": "u@acme.com" private_key } ) Validation: decode header → get alg → fetch public key → verify signature → check exp/iss/aud RS256 = asymmetric: auth server signs with private key, APIs verify with public key (JWKS endpoint) HS256 = symmetric: same secret everywhere — avoid in distributed systems

JWT Cannot Be Revoked

Once issued, a JWT is valid until expiry. You can't "delete" it from the server. Mitigation: short TTL (15 min) + token blocklist for logout or compromise events.

JWKS Endpoint

Auth server publishes public keys at /.well-known/jwks.json. APIs cache and rotate these keys. Allows key rotation without redeploying services.

Claims vs. Database Queries

Encode stable, slow-changing attributes in JWT claims (roles, tenant ID). Don't encode fast-changing data — stale tokens would carry wrong values.

Credentials & Keys

Secrets Management

Data Protection

Encryption: TLS, mTLS, At-Rest

Encryption protects data in two states: in transit (TLS/mTLS) and at rest (disk encryption, field-level encryption). These are complementary — you need both.

Access Control Models

RBAC vs. ABAC

RBAC assigns permissions to roles, then roles to users. Simple and auditable. ABAC grants access based on attributes of the user, resource, and environment — more flexible but harder to reason about.

RBAC: Role-Based Access Control User Roles Permissions Alice ──────► [engineer] ─────────► read:metrics, deploy:staging Bob ──────► [engineer] ─────────► read:metrics, deploy:staging Bob ──────► [team-lead] ─────────► deploy:production, manage:users Carol ──────► [viewer] ─────────► read:metrics Simple, predictable. "What can an engineer do?" — easy to answer. Common in AWS IAM, K8s RBAC. ABAC: Attribute-Based Access Control Request Policy Decision { ALLOW IF: │ user.dept = "finance", user.dept == resource.owner │ resource.class = "finance", AND resource.class != "secret" resource.owner = "finance", AND env.time BETWEEN 9am-6pm env.time = "14:00", AND user.clearance >= resource.sensitivity action = "read" } │ } ▼ ALLOW Handles "contractors can only access projects they're assigned to during business hours" OPA (Open Policy Agent) and AWS Cedar are popular ABAC policy engines

When to Use RBAC

Small to medium permission sets. Clear role taxonomy. Teams or products with stable access patterns. K8s, AWS IAM, database access.

When to Use ABAC

Multi-tenant SaaS (users can only see their tenant's data). Fine-grained data ownership. Context-sensitive access (time, location, device). Large organizations with many dynamic rules.

OPA (Open Policy Agent)

Policy-as-code engine. Write Rego policies that evaluate JSON inputs. Used as a sidecar in K8s admission control, API gateways, and microservices. Decisions are auditable and testable.

Defense in Depth

API Security

APIs are the most-attacked surface in modern systems. A defense-in-depth strategy layers multiple controls — no single mechanism is sufficient.

API Security Layers Internet │ ▼ WAF (Web Application Firewall) │ Blocks: SQLi, XSS, OWASP Top 10 │ Tools: AWS WAF, Cloudflare WAF, ModSecurity │ ▼ DDoS Protection (Cloudflare Magic Transit, AWS Shield) │ Absorbs volumetric attacks before they hit origin │ ▼ API Gateway │ Rate limiting (per IP, per API key, per user) │ Auth token validation (JWT, API keys) │ TLS termination │ Request/response transformation │ Tools: Kong, AWS API Gateway, Apigee, Nginx │ ▼ Service Mesh (optional, for internal traffic) │ mTLS between services │ Authorization policies (deny by default) │ Traffic observability │ ▼ Application │ Input validation (reject malformed inputs) │ Parameter binding (no raw SQL) │ Output encoding (prevent XSS) │ Business logic authorization (can this user do this action?) Attack types: injection · BOLA (broken object-level auth) · BFLA (broken function-level auth) BOLA = "I can access /orders/12345 even though that's not my order" (IDOR)

API Keys vs. Bearer Tokens

API keys: simple, for server-to-server. No user context. Must be rotated. Store hashed in DB. Bearer tokens (JWT): carry user identity and scopes. Short-lived. Validate signature on each request.

Input Validation

Validate type, format, length, range at the boundary. Reject unexpected fields. Use allowlists, not denylists. Parameterized queries prevent SQL injection entirely — never concatenate user input into SQL.

Security Headers

Strict-Transport-Security (force HTTPS), Content-Security-Policy (prevent XSS), X-Frame-Options (prevent clickjacking), X-Content-Type-Options: nosniff.

9 Viewpoints

Engineer Perspectives

Security Engineer

Threat model first. What's the crown jewel? Who are the adversaries? Build controls proportional to risk, not to compliance checkbox length.

Backend Engineer

Validate JWT claims in middleware before any handler runs. Never trust the payload without verifying the signature — base64 decoding is not validation.

SRE

Secret rotation must be zero-downtime. Test rotation runbooks quarterly. Cert expiry alerts at 30/14/7 days — certificate expiry is the #1 cause of preventable outages.

Platform Engineer

Integrate auth into the platform primitives. Inject Vault secrets via init containers. Sidecar proxies handle mTLS. Developers shouldn't need to think about certificates.

Architect

Centralized identity provider (Okta, Auth0, Cognito) beats rolling your own. The auth server is security-critical infrastructure — use a battle-tested implementation.

Data Engineer

Column-level access in data warehouses (Redshift/BigQuery). PII masking for analytics. Audit logs must be immutable — write to append-only storage (S3 WORM).

ML Engineer

Training data access is often overly permissive. Apply RBAC to feature stores. Model APIs need auth too — an open prediction endpoint leaks your model.

Frontend Engineer

Store tokens in memory (not localStorage) to prevent XSS theft. Implement PKCE for SPAs. Never store client secrets in browser code — they're not secret.

Mobile Engineer

Use the OS keychain (iOS Keychain, Android Keystore) for token storage. Certificate pinning adds an extra layer against MITM on mobile networks.

Security Design Problems

Problem 01 · OAuth + JWT
Design an auth service with OAuth 2.0, OIDC, and JWT for a multi-tenant SaaS platform
JWTOAuth 2.0OIDCMulti-tenant

Requirements

Support Google/GitHub social login, enterprise SAML SSO, and service-to-service auth. JWTs must carry tenant ID and roles. Tokens expire in 15 min, refresh tokens in 7 days.

Key Implementation

import jwt, time
from cryptography.hazmat.primitives import serialization

# Load RSA private key (kept in Vault, never in code)
with open("private_key.pem", "rb") as f:
    private_key = serialization.load_pem_private_key(f.read(), password=None)

def issue_access_token(user_id: str, tenant_id: str, roles: list[str]) -> str:
    now = int(time.time())
    payload = {
        "sub": user_id,
        "iss": "auth.acme.com",
        "aud": "api.acme.com",
        "iat": now,
        "exp": now + 900,          # 15 minutes
        "tenant_id": tenant_id,    # custom claim for multi-tenancy
        "roles": roles,
    }
    # RS256: sign with private key, APIs verify with public key from JWKS
    return jwt.encode(payload, private_key, algorithm="RS256")

def validate_token(token: str, public_key) -> dict:
    try:
        return jwt.decode(
            token,
            public_key,
            algorithms=["RS256"],
            audience="api.acme.com",
            issuer="auth.acme.com",
        )
    except jwt.ExpiredSignatureError:
        raise AuthError("Token expired")
    except jwt.InvalidTokenError as e:
        raise AuthError(f"Invalid token: {e}")

# Middleware: FastAPI dependency
from fastapi import Depends, HTTPException, Security
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

bearer_scheme = HTTPBearer()

def get_current_user(
    creds: HTTPAuthorizationCredentials = Security(bearer_scheme),
    public_key = Depends(get_jwks_public_key),
):
    claims = validate_token(creds.credentials, public_key)
    return {
        "user_id": claims["sub"],
        "tenant_id": claims["tenant_id"],
        "roles": claims["roles"],
    }

# Tenant isolation: every DB query scoped by tenant_id
def get_documents(user = Depends(get_current_user), db = Depends(get_db)):
    return db.query(Document).filter(
        Document.tenant_id == user["tenant_id"]  # never skip this filter
    ).all()

Multi-tenant Gotchas

Always filter by tenant_id in every query — a missing filter is a data leak. Test with two tenants in every integration test. Use row-level security in Postgres for an extra safety net.

Problem 02 · Secrets & Rotation
Build a zero-downtime secrets rotation system for database credentials
VaultDynamic SecretsZero-Downtime

Challenge

Rotating a DB password while services are running causes connection failures if not coordinated. Dynamic secrets solve this — no rotation needed because each lease is short-lived.

import hvac, psycopg2, time, threading

class VaultManagedDB:
    """DB connection pool that auto-renews Vault leases before expiry."""

    def __init__(self, vault_addr: str, role: str):
        self.client = hvac.Client(url=vault_addr)
        self.client.auth.kubernetes.login(role="app", jwt=self._k8s_token())
        self.role = role
        self._conn = None
        self._lease_id = None
        self._refresh_timer = None

    def connect(self):
        secret = self.client.secrets.database.generate_credentials(name=self.role)
        creds = secret["data"]
        lease_id = secret["lease_id"]
        ttl = secret["lease_duration"]  # e.g., 900 seconds

        self._conn = psycopg2.connect(
            host="db.internal", dbname="app",
            user=creds["username"], password=creds["password"]
        )
        self._lease_id = lease_id
        # Renew at 80% of TTL to avoid gap
        self._schedule_renewal(ttl * 0.8)

    def _schedule_renewal(self, delay: float):
        if self._refresh_timer:
            self._refresh_timer.cancel()
        self._refresh_timer = threading.Timer(delay, self._renew_lease)
        self._refresh_timer.daemon = True
        self._refresh_timer.start()

    def _renew_lease(self):
        try:
            result = self.client.sys.renew_secret(self._lease_id)
            new_ttl = result["lease_duration"]
            self._schedule_renewal(new_ttl * 0.8)
        except Exception:
            # Lease renewal failed — get fresh credentials
            self.connect()

    def _k8s_token(self) -> str:
        with open("/var/run/secrets/kubernetes.io/serviceaccount/token") as f:
            return f.read()

    def execute(self, query: str, params=None):
        cur = self._conn.cursor()
        cur.execute(query, params)
        return cur.fetchall()

Key Insight

Dynamic secrets mean there's never a long-lived password to rotate. If a pod is compromised, its credentials expire within 15 minutes automatically. No breach notification lag, no rotation coordination.

Problem 03 · RBAC + OPA
Design a fine-grained authorization system using OPA for a document management platform
OPARBACPolicy-as-Code

Requirements

Users can view/edit/delete their own documents. Managers can view all documents in their department. Auditors can view but never edit. Policies change frequently without code deploys.

# OPA Rego policy (document_policy.rego) — deployed to OPA sidecar
# ---------------------------------------------------------------
# package authz.documents
#
# default allow = false
#
# allow {
#   input.action == "read"
#   doc_readable
# }
# allow {
#   input.action in {"write", "delete"}
#   doc_writable
# }
#
# doc_readable {
#   input.user.id == input.resource.owner_id  # own document
# }
# doc_readable {
#   input.user.role == "auditor"               # auditors read all
# }
# doc_readable {
#   input.user.role == "manager"
#   input.user.department == input.resource.department
# }
# doc_writable {
#   input.user.id == input.resource.owner_id
#   input.user.role != "auditor"               # auditors can never write
# }
# ---------------------------------------------------------------

import requests

OPA_URL = "http://localhost:8181/v1/data/authz/documents/allow"

def check_permission(user: dict, action: str, resource: dict) -> bool:
    """Call OPA sidecar to evaluate policy."""
    response = requests.post(OPA_URL, json={
        "input": {
            "user": user,
            "action": action,
            "resource": resource,
        }
    })
    return response.json().get("result", False)

# FastAPI endpoint with OPA authorization
from fastapi import HTTPException

def get_document(doc_id: str, user = Depends(get_current_user), db = Depends(get_db)):
    doc = db.get(Document, doc_id)
    if not doc:
        raise HTTPException(404)

    resource = {
        "id": doc.id,
        "owner_id": doc.owner_id,
        "department": doc.department,
    }
    if not check_permission(user, "read", resource):
        raise HTTPException(403, "Access denied")

    return doc

Why OPA

Policy changes are deployed to OPA as data, not code. The application doesn't need to be redeployed when access rules change. Policies are unit-testable with opa test. Bundle policies from Git for GitOps-style governance.

What Not to Do

Security Anti-patterns

Secrets in Source Code

Hardcoding API keys, DB passwords, or private keys. Git history is permanent. Use a secrets manager and environment injection.

JWT Without Signature Verification

Calling jwt.decode(token, options={"verify_signature": False}). The payload is just base64 — anyone can forge it. Always verify the signature.

Long-Lived Tokens

Access tokens valid for days or weeks. A stolen token is valid until expiry. Short TTL (15 min) + refresh token rotation limits exposure.

Missing Tenant Isolation

Forgetting WHERE tenant_id = ? in multi-tenant queries. One missing filter exposes all tenant data. Use Postgres RLS as a backstop.

Rolling Your Own Crypto

Implementing custom encryption or hashing. Use industry-standard libraries: bcrypt/Argon2 for passwords, AES-GCM for symmetric, RSA/ECDSA for asymmetric.

Over-Permissive IAM

Giving services * access to S3 or AdministratorAccess because it's easy. Apply least privilege. Use IAM Analyzer to detect excessive permissions.

No Audit Logs

Security events (login failures, privilege escalations, secret access) not logged. You can't detect or investigate breaches without audit trails. Logs must be tamper-proof.

Security as Afterthought

Adding auth and encryption after the architecture is set. Security constraints change data models, API contracts, and service boundaries. Design in from day one.

Interview Prep

Interview Tips

Lead with Threat Modeling

Start any security discussion with: "What are we protecting? From whom? What's the impact of a breach?" Interviewers want to see systematic thinking, not jumping to solutions.

Know the 401 vs 403 Distinction

401 = not authenticated (token missing or invalid). 403 = authenticated but not authorized. Getting this wrong suggests shallow understanding of auth flows.

Mention Defense in Depth

No single control is sufficient. WAF + API gateway auth + application-level AuthZ + audit logs. Show you understand layered security.

Explain JWT Trade-offs Clearly

JWTs can't be instantly revoked — this is a common follow-up. Explain: short TTL + token blocklist (Redis) for logout/revocation. Or switch to opaque tokens if instant revocation is required.

Dynamic Secrets > Rotation

If asked about credential rotation, pivot to dynamic secrets as the superior solution. Rotating a static password is a band-aid. Dynamic secrets eliminate the rotation problem entirely.

Least Privilege Everywhere

Apply this principle to IAM roles, DB users, API scopes, network rules. The blast radius of any single compromised component is bounded by its minimum necessary permissions.

Clarifications
+
What is a VPN and why doesn't Zero Trust use one?
A VPN (Virtual Private Network) creates an encrypted tunnel from your device to a corporate network, making you appear "inside." Once inside, old systems trusted you. Zero Trust eliminates this — your location doesn't matter. You must prove identity and authorization on every single request regardless of whether you're on the corporate network or a coffee shop WiFi.
+
What is an Identity Provider (IdP)?
An IdP is the system that verifies who you are and issues proof of your identity. Examples: Okta, Auth0, Azure AD, Keycloak, Google Identity. Think of it as the DMV — you prove your identity there, they give you a license (token), and other services trust that license without calling the DMV again.
+
OAuth 2.0 vs OIDC: what's the difference?
OAuth 2.0 answers "what can this app do on your behalf?" — it's a delegation protocol for authorization. OIDC (OpenID Connect) adds "and who are you?" on top of OAuth. When you click "Sign in with Google," Google uses OIDC: OAuth 2.0 for the token flow, plus an id_token that tells the app your name, email, and Google user ID.
+
What is PKCE (Proof Key for Code Exchange)?
PKCE is a security add-on for OAuth in mobile/SPA apps. Before redirecting to login, the app generates a random secret (code_verifier) and sends a hash of it (code_challenge). When exchanging the auth code for a token, the app proves it has the original secret. This prevents an attacker who intercepts the auth code from using it, because they don't have the verifier.
+
Base64 is not encryption
JWT payloads are base64url-encoded, which is just encoding — anyone can decode them instantly. The security comes from the signature: if you change any byte in the payload, the signature breaks. Never put secrets in JWT claims — they're readable by anyone who has the token.
+
What is a Hardware Security Module (HSM)?
An HSM is a physical device that stores cryptographic keys and performs crypto operations in tamper-resistant hardware. The private key never leaves the device — the HSM does the signing/decryption internally. AWS CloudHSM and Azure Dedicated HSM provide this as a service. Used for root CA keys, payment signing keys, and regulatory requirements.
+
What is a Certificate Authority (CA)?
A CA is a trusted third party that signs TLS certificates, vouching that "yes, this cert really belongs to api.example.com." Browsers and operating systems ship with a list of trusted root CAs. Let's Encrypt is a free, automated CA. For internal services, companies run a private CA (AWS Private CA, cert-manager with Vault) to issue mTLS certificates.
+
What is OPA (Open Policy Agent)?
OPA is a general-purpose policy engine you embed in your system. You write access rules in a language called Rego, and OPA evaluates them against JSON input (user, action, resource). It runs as a sidecar container or library. The key benefit: policies are code you can test and version-control, and they change without redeploying your application.
+
What is a WAF and what does it block?
A WAF (Web Application Firewall) sits in front of your APIs and inspects HTTP traffic for attack patterns. It blocks: SQL injection (adding SQL to form fields), XSS (injecting JavaScript), path traversal (../../etc/passwd), and OWASP Top 10 attacks. It's not a replacement for input validation in your code — it's an additional layer.
