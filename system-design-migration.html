Foundation

Why Migration is Hard

Migrating a live system is like rebuilding a plane while flying it. You cannot take production offline, you have years of implicit behavior in the old system, and data must remain consistent throughout. The goal is incremental, reversible steps.

✈️

No Big Bang Rewrites

Full rewrites fail 90% of the time. The new system has to replicate years of undocumented edge cases. Incremental migration preserves working behavior while replacing internals.

🔁

Data is the Hard Part

Code can be rewritten quickly. Data — its schema, its relationships, its history — must migrate safely with zero loss and zero corruption. This is the bottleneck in every migration.

↩️

Always Have Rollback

Every migration step must be reversible. If step 3 goes wrong, you need to roll back to step 2 without losing data written after step 2. Design every step with rollback in mind.

🐢

Incremental over Atomic

Atomic migrations ("switch everything at once") maximize risk. Incremental migrations move one slice at a time — one service, one table, one endpoint — and validate before moving on.

Core Pattern

Strangler Fig Pattern

Named after the strangler fig vine, which grows around a tree until it replaces it. A proxy sits in front of the legacy system. New functionality is built in the new system. Traffic is gradually routed from legacy to new until the legacy dies off.

Migration complete.

Facade / Proxy Layer

The proxy is the key — it lets you reroute traffic without changing clients. Can be an API gateway (Kong, Nginx), a BFF, or a dedicated routing service. Routing rules change with feature flags.

Anti-Corruption Layer (ACL)

When new service calls old service, the ACL translates between old and new data models. Prevents the old model's concepts from leaking into the new design. Delete the ACL when the old service is gone.

Branch by Abstraction

Create an interface in the monolith. Old code → old implementation. New code → new implementation behind the same interface. Toggle which implementation is active via feature flag.

Controlled Rollouts

Feature Flags

Feature flags decouple deployment from release. Code is deployed to production but behind a flag — disabled by default. The flag is enabled for specific users/groups/percentages without a new deployment.

Feature flag types and use cases Release flags: ship code before it's ready to release if flag("new_checkout_flow").enabled_for(user): return new_checkout() return old_checkout() Experiment flags: A/B testing variant = flag("pricing_display").variant_for(user) if variant == "B": show_yearly_price_first() # test if conversion improves Ops flags: kill switch for performance/emergencies if flag("use_redis_cache").enabled(): return cache.get(key) or fetch_and_cache(key) return db.fetch(key) # if Redis dies, disable flag instantly Permission flags: beta features for specific users/tenants if flag("advanced_analytics").enabled_for(tenant_id): return analytics_v2() Flag services: LaunchDarkly, Unleash (open-source), GrowthBook, Flagsmith Key: flags must be evaluated fast (< 1ms). Client-side SDK caches flag state locally. Flag cleanup: set a cleanup date when creating. Flags that aren't deleted accumulate as tech debt.
from launchdarkly_client import LDClient, Context

def checkout(user_id: str, cart: Cart):

    if use_new_flow:
        return new_checkout_v2(cart)
    return legacy_checkout(cart)

Schema Evolution

Database Migration

The expand/contract pattern (also called parallel change) is the safest way to change a database schema on a live system. It separates schema changes from code changes into multiple deployable steps.

Expand/Contract: renaming a column (users.full_name → first_name + last_name) Step 1: EXPAND — add new columns (non-breaking) ALTER TABLE users ADD COLUMN first_name VARCHAR(100); ALTER TABLE users ADD COLUMN last_name VARCHAR(100); Deploy: app writes to BOTH old full_name AND new first_name/last_name Reads still come from full_name Step 2: BACKFILL — populate new columns for existing rows UPDATE users SET first_name = SPLIT_PART(full_name, ' ', 1), last_name = TRIM(SUBSTRING(full_name FROM POSITION(' ' IN full_name))) WHERE first_name IS NULL; Run in batches (1000 rows at a time) to avoid lock escalation Step 3: MIGRATE READS — app reads from new columns Deploy: reads switch to first_name + last_name Writes still go to BOTH columns (backward compatibility) Monitor for a week: if rollback needed, reads still work on full_name Step 4: CONTRACT — remove old column Deploy: app no longer writes to full_name ALTER TABLE users DROP COLUMN full_name; Only safe to do after all read traffic has moved away Each step is independently deployable and reversible. Never combine steps into one deployment.
Migration TypeSafe?Technique
Add nullable column✅ SafeDeploy anytime — existing rows get NULL, no lock
Add NOT NULL column⚠️ RiskyAdd nullable first, backfill, add NOT NULL constraint after
Add index on large table⚠️ RiskyUse CREATE INDEX CONCURRENTLY (Postgres) — no table lock
Rename column❌ BreakingExpand/contract: add new, backfill, migrate reads, drop old
Change column type❌ BreakingAdd new column with new type, dual-write, migrate, drop old
Delete column❌ BreakingRemove from app first (deploy), then ALTER TABLE DROP
Split table❌ BreakingCreate new tables, dual-write with triggers, migrate reads, drop old
API Evolution

Backward Compatibility

During a rolling or canary deployment, old and new versions of a service run simultaneously and must interoperate. API changes must be backward-compatible, or you create a deployment window where the system is broken.

Rules for backward-compatible API changes SAFE (additive) changes: ✅ Add new optional request field (old clients don't send it → default used) ✅ Add new response field (old clients ignore unknown fields) ✅ Add new API endpoint (old clients never call it) ✅ Add new enum value (if old clients handle unknown values gracefully) BREAKING changes (require versioning or expand/contract): ❌ Remove or rename field (old clients break) ❌ Change field type (int → string) ❌ Make optional field required (old clients not sending it fail) ❌ Change behavior of existing call (old clients get unexpected results) Postel's Law (Robustness Principle): "Be conservative in what you send, liberal in what you accept." → Accept unknown fields silently (don't error) → Never send fields that old consumers can't handle Versioning strategies when breaking change is unavoidable: URI versioning: /v1/orders vs /v2/orders ← most common Header versioning: Accept: application/vnd.acme.v2+json Query param: GET /orders?api_version=2024-01-01 Run both versions simultaneously until all consumers migrate
Architecture Evolution

Breaking Up a Monolith

Microservices decomposition is often more about organizational structure than technical need. Don't split prematurely — a well-structured monolith beats a poorly-designed microservices architecture every time.

When to split: signals that a monolith is ready Signs a monolith needs splitting: • Deploy friction: one team's change blocks another team's deploy • Scale mismatch: one component needs 10× more resources than the rest • Technology constraint: one part needs GPU, another needs fast GC • Team autonomy: 8+ engineers blocked on the same codebase • Fault isolation: one bug crashes the entire system How to split safely: 1. Identify a bounded context (clear domain ownership) 2. Extract to a library / internal module first (no network calls) 3. Apply strangler fig: route new traffic to extracted service 4. Migrate the database last (data is hardest) 5. Decommission monolith code once 100% traffic migrated Martin Fowler: "Don't start with microservices. Start with a modular monolith." Sam Newman: split on team ownership boundaries, not technical layers
9 Viewpoints

Engineer Perspectives

Architect

The strangler fig requires a proxy layer from day one. If you can't intercept traffic, you can't redirect it. Negotiate the proxy into the initial architecture before the migration begins.

Backend Engineer

Dual-write is more complex than it looks. Write order matters: write to new system first (if it fails, don't write to old). Validate data consistency between both systems daily during the migration window.

SRE

Feature flag rollbacks are your fastest safety net. During a migration, keep the flag at 5% for a day, watch error rates, then advance. Each increment is a checkpoint.

Data Engineer

Database migrations are the riskiest step. Always run the migration on a production replica first. Time the backfill on real data volume — 1M rows might take 10 minutes; 1B rows might take 3 days.

Platform Engineer

Canary deployments need infrastructure support: weighted load balancing in the service mesh or load balancer, automated rollback triggers tied to SLO alerts, and separate log streams per version.

Security Engineer

Feature flags that gate security controls (auth, encryption) need tighter review. A flag accidentally left off could disable auth for 5% of traffic. Require security flags to default to the secure state.

Frontend Engineer

Frontend feature flags can be evaluated client-side (fast) but the flag state must be treated as untrusted for anything security-sensitive. Always enforce access control server-side.

Mobile Engineer

Mobile clients can't be forced to update. Old app versions can persist for months. API changes must be backward compatible for at least 2 major versions back. Don't remove fields — mark deprecated and add new ones.

ML Engineer

Shadow deployment is perfect for model migrations. Run the new model on all traffic, log its predictions, compare against ground truth, then flip the switch when confident in its quality.

Problem 01 · DB Migration
Rename a column in a 500M-row table with zero downtime
Expand/ContractPostgresZero-Downtime

Scenario

Table orders has column total_amount. We want to rename it to amount_cents (also converting from dollars to cents). 500M rows, 10K requests/sec. Cannot have downtime.

import psycopg2, time

# Step 1: EXPAND - Add new column (takes seconds, no table lock)
# Run this SQL directly, no app deploy needed
"""
ALTER TABLE orders ADD COLUMN amount_cents BIGINT;
CREATE INDEX CONCURRENTLY idx_orders_amount_cents ON orders(amount_cents);
"""

# Step 2: Deploy app v2 - dual-write to BOTH columns
class OrderRepository:
    def create_order(self, amount_dollars: float) -> dict:
        amount_cents_val = int(amount_dollars * 100)
        self.db.execute("""
            INSERT INTO orders (total_amount, amount_cents)
            VALUES (%s, %s)
            RETURNING id
        """, (amount_dollars, amount_cents_val))

    def update_order(self, order_id: int, amount_dollars: float):
        amount_cents_val = int(amount_dollars * 100)
        self.db.execute("""
            UPDATE orders
            SET total_amount = %s, amount_cents = %s
            WHERE id = %s
        """, (amount_dollars, amount_cents_val, order_id))

# Step 3: BACKFILL old rows in batches (don't lock the table)
def backfill_amount_cents(conn, batch_size=10_000):
    last_id = 0
    while True:
        with conn.cursor() as cur:
            cur.execute("""
                UPDATE orders
                SET amount_cents = (total_amount * 100)::BIGINT
                WHERE id > %s
                  AND amount_cents IS NULL
                ORDER BY id
                LIMIT %s
                RETURNING id
            """, (last_id, batch_size))
            rows = cur.fetchall()
            conn.commit()

            if not rows:
                break
            last_id = rows[-1][0]
            time.sleep(0.05)  # throttle to avoid overwhelming DB

# Step 4: Deploy app v3 - READS switch to amount_cents, still write both
# Step 5: Monitor for 1 week. Confirm no reads touch total_amount.
# Step 6: Deploy app v4 - stop writing to total_amount
# Step 7: DROP COLUMN (safe now — no reads or writes)
"""
ALTER TABLE orders DROP COLUMN total_amount;
"""

Key Invariants

Each step is deployed independently. Rollback at any step is possible: step 3 → drop amount_cents, redeploy app v1. The backfill runs on the production replica first to measure duration.

import httpx
from launchdarkly_client import LDClient, Context

ld = LDClient("sdk-key")
PAYMENT_SVC = "http://payment-svc:8080"
MONOLITH = "http://monolith:3000"

async def route_payment(user_id: str, payload: dict):
    ctx = Context.builder(user_id).build()
    use_new_svc = ld.variation("payment_service_v2", ctx, default=False)

    target = PAYMENT_SVC if use_new_svc else MONOLITH
    async with httpx.AsyncClient() as client:
        resp = await client.post(f"{target}/v1/payments/charge", json=payload)
        return resp.json()

Anti-Corruption Layer

The new payment service uses different data models (snake_case, cents instead of dollars). The ACL in the gateway translates between formats so neither service knows about the other's conventions.

Problem 03 · Feature Flags
Design a safe migration of a pricing algorithm using shadow mode + flags
Feature FlagsShadow ModeA/B Test

Scenario

New ML-based pricing algorithm replaces rule-based system. Shadow mode: run both, compare outputs, don't show new prices to users yet. Validate for 2 weeks, then canary.

import asyncio, logging
from dataclasses import dataclass

log = logging.getLogger("pricing")

@dataclass
class PriceResult:
    price: float
    algorithm: str
    latency_ms: float

async def get_price(user_id: str, item_id: str) -> PriceResult:
    use_ml = feature_flags.variation("ml_pricing", user_id, default=False)

    if use_ml:
        # Production: use ML model
        return await ml_pricing.calculate(user_id, item_id)

    # Default: rule-based (still live)
    rule_price = await rule_based_pricing.calculate(user_id, item_id)

    # Shadow mode: also run ML in background, log discrepancy
    if feature_flags.variation("ml_pricing_shadow", user_id, default=False):
        asyncio.create_task(
            _shadow_compare(user_id, item_id, rule_price)
        )

    return rule_price

async def _shadow_compare(user_id: str, item_id: str, rule_result: PriceResult):
    try:
        ml_result = await ml_pricing.calculate(user_id, item_id)
        discrepancy_pct = abs(ml_result.price - rule_result.price) / rule_result.price * 100

        log.info("shadow_comparison",
            user_id=user_id,
            item_id=item_id,
            rule_price=rule_result.price,
            ml_price=ml_result.price,
            discrepancy_pct=round(discrepancy_pct, 2),
            ml_latency_ms=ml_result.latency_ms,
        )
        # After 2 weeks: analyze logs.
        # If avg discrepancy < 5% and p99 latency < rule-based: promote to canary
    except Exception as e:
        log.warning("shadow_ml_failed", error=str(e))

What Not to Do

Migration Anti-patterns

The Big Bang Migration

Switching everything at once on a Friday night. No incremental validation, no rollback. The most common cause of catastrophic production incidents. Always migrate incrementally.

Forgetting the ACL

Letting the legacy data model bleed into the new service. Now you have two systems with the same bad design. The Anti-Corruption Layer is the investment that lets you build the right model independently.

ALTER TABLE on a Hot Table

Running a blocking ALTER TABLE on a table receiving 10K writes/sec. Takes a table lock, queues all writes, cascades to downtime. Use CONCURRENTLY, expand/contract, or pg_repack.

Flag Accumulation

Creating feature flags without a cleanup date. After 2 years, the codebase has 200 flags, nobody knows which are active, and removing them is feared. Set a TTL when creating every flag.

Dual-Write Without Validation

Writing to old and new systems but never checking they're consistent. Data diverges silently. Add a reconciliation job that compares both systems daily and alerts on discrepancies.

Decommissioning Too Early

Deleting the old system while some clients still depend on it. Always wait for 100% traffic to be confirmed on the new system, plus a buffer period, before decommissioning.

No Rollback Plan

Designing migrations assuming they'll succeed. Every migration step needs a documented, tested rollback procedure. Practice the rollback on staging before production.

Microservices Too Early

Splitting a 2-person team's monolith into 12 microservices. Distributed systems overhead (network failures, distributed transactions, operational complexity) far exceeds any benefit at small scale.

Interview Prep

Interview Tips

Propose Incremental Steps

Never say "we'll migrate everything at once." Break it into phases with validation checkpoints. This shows maturity and risk awareness that interviewers are specifically looking for.

Mention the Expand/Contract Pattern

When database schema changes come up, describe expand/contract by name. Knowing this pattern demonstrates real production experience — it's not in most textbooks.

Feature Flags Separate Deploy from Release

This is the key insight. Code goes to production but is invisible until the flag is turned on. Rollback doesn't require a re-deploy — just flip the flag. Interviewers love this.

Know When NOT to Use Microservices

Saying "actually a modular monolith would serve this team better" at the right moment impresses senior interviewers. It shows you optimize for outcomes, not architecture trends.

Ask About the Team Size

The right migration strategy depends on team structure. 5 engineers on one codebase? Modular monolith. 50 engineers with deployment conflicts? Time to split. Team topology drives architecture.

Data Migration is the Hard Part

When asked about system migration, always address data first. Code migration is fast and reversible. Data migration is slow, risky, and harder to undo. The questioner wants to see that you know this.

Clarifications
+
What is a bounded context?
From Domain-Driven Design (DDD): a bounded context is a well-defined area of the codebase where a specific model applies. "Order" means one thing in the order service and something slightly different in the billing service. Bounded contexts define natural seams where you can split services without coupling them together.
+
What is a load balancer?
A load balancer distributes incoming requests across multiple server instances. For blue-green deploys, the load balancer is the switch — it points 100% of traffic to Blue, then you flip it to point to Green. AWS ALB, Nginx, HAProxy, and Envoy are common load balancers.
+
What is LaunchDarkly?
LaunchDarkly is a feature flag management SaaS. You define flags in their dashboard, their SDK evaluates them in your app in under 1ms (cached locally). You can target flags to specific users, percentages, or attributes — without redeploying code. Unleash is the popular open-source alternative.
+
What is a table lock and why is it dangerous?
Many ALTER TABLE operations acquire an exclusive lock on the entire table, blocking all reads and writes until the operation completes. On a table with millions of rows and active traffic, this can take minutes — causing a full outage. Postgres's CREATE INDEX CONCURRENTLY and tools like gh-ost (for MySQL) avoid this by building the new structure in the background.
+
What is Postel's Law?
Jon Postel wrote in RFC 793 (TCP spec): "Be conservative in what you do, be liberal in what you accept from others." For APIs: accept unknown fields gracefully (don't error), but only send fields that consumers are known to handle. This makes APIs more resilient to change over time.
+
What is Conway's Law?
Melvin Conway observed in 1967: "Organizations which design systems are constrained to produce designs which are copies of the communication structures of those organizations." In practice: your microservices boundaries will mirror your team structure. This is why "team topology" matters — design teams and services together, not independently.
