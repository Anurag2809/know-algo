Foundation

SLO, SLI, and SLA — Measuring Reliability

You cannot improve what you don't measure. SLOs (Service Level Objectives) are the internal reliability targets that drive engineering decisions. SLAs are the contractual commitments to customers. SLIs are the actual measurements.

THE THREE CONCEPTS ────────────────────────────────────────────────────────── SLI (Service Level Indicator): The metric you measure. Raw data. Examples: Request success rate = (successful requests) / (total requests) Latency p99 = 99th percentile response time Availability = (uptime minutes) / (total minutes in period) SLO (Service Level Objective): Your internal target for the SLI. What you're engineering toward. Examples: "Availability SLO: 99.9% of requests succeed in a 30-day window" "Latency SLO: p99 < 200ms for /search endpoint" "Error rate SLO: < 0.1% of API calls return 5xx" SLA (Service Level Agreement): Legal/contractual commitment to customers. Usually more conservative than SLO (buffer for when you miss SLO). Example: SLO = 99.9%, SLA = 99.5% (gives you 4 nines of buffer) Violation → financial penalty, credits, contract clauses ────────────────────────────────────────────────────────── ERROR BUDGET — the key concept SRE teams use SLO: 99.9% availability over 30 days Total minutes in 30 days: 43,200 Allowed downtime: 43,200 × 0.001 = 43.2 minutes Error budget = 43.2 minutes per month Current downtime this month: 15 minutes Remaining error budget: 28.2 minutes Budget remaining → can deploy risky changes Budget exhausted → freeze deployments, focus on reliability This creates a data-driven conversation between product (wants features) and SRE (wants stability). Both are valid — the budget decides.

The Compounding Problem with Dependencies

If your service depends on 3 external services, each at 99.9% availability, your availability is 99.9% × 99.9% × 99.9% = 99.7% — even if your own code is perfect. Every dependency erodes your SLO. This is why graceful degradation (serving reduced functionality when a dependency is down) is not optional in distributed systems.

Risk Taxonomy

Failure Modes in Distributed Systems

TAXONOMY OF FAILURES ────────────────────────────────────────────────────────── Fail-stop: Service crashes and stops responding. Easiest to detect (health check fails, circuit breaker trips). Example: Out-of-memory crash, disk full. Fail-slow: Service responds, but very slowly. Hardest to detect — looks like high load, not failure. Timeouts are the only defense. Example: DB with 90% CPU, GC pause, lock contention. Fail-partial: Some operations succeed, some fail unpredictably. Very hard to detect pattern — requires per-operation metrics. Example: S3 region degradation, partial network partition. Fail-corrupt: Service responds correctly but returns wrong data silently. No timeout or circuit breaker helps — requires data validation. Example: Bug in serialization, bit rot, cache returning stale data. ────────────────────────────────────────────────────────── CASCADING FAILURE — the most dangerous pattern Without protection: Upstream traffic ──► Service A ──► (slow) Service B │ │ Threads pile up Threads pile up waiting for B waiting for DB │ Service A OOM → crashes │ Load shifts to Service A' │ Service A' also crashes │ Full stack outage With circuit breaker + bulkhead: Upstream traffic ──► Service A ──► Circuit Breaker ──► (slow) Service B │ │ Fast failure ◄──── Open circuit (fallback response) after 5 failures │ Service A healthy, B isolated
Core Pattern

Circuit Breaker

Named after the electrical circuit breaker: when a circuit overloads, the breaker trips and prevents current from flowing until the overload is resolved. Applied to service calls: when failures exceed a threshold, stop calling the failing service and fail fast (returning a cached/fallback response), giving the failing service time to recover.

CIRCUIT BREAKER STATE MACHINE ────────────────────────────────────────────────────────── [ CLOSED ] ← normal operation Requests flow through. Track failure count in rolling window. │ failures > threshold │ ← e.g., 5 failures in 10s │ [ OPEN ] ← failing fast Immediately return error/fallback. No calls to downstream service. Timer starts (e.g., 30 seconds). │ timer expires │ │ [ HALF-OPEN ] ← probing Allow 1 test request through. │ ├── Success → back to CLOSED ✓ └── Failure → back to OPEN, reset timer ────────────────────────────────────────────────────────── PARAMETERS TO TUNE: Failure threshold: 5 failures in last 10 seconds (count-based) 50% error rate in 60-second window (rate-based) Open duration: 30 seconds before half-open probe Success threshold: 3 consecutive successes in half-open → close

Python Implementation

import time
from enum import Enum

class CircuitState(Enum):
    CLOSED = "closed"
    OPEN = "open"
    HALF_OPEN = "half_open"

class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=30, success_threshold=3):
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.success_count = 0
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.success_threshold = success_threshold
        self.last_failure_time = None

    def call(self, func, *args, fallback=None, **kwargs):
        if self.state == CircuitState.OPEN:
            # Check if recovery timeout has elapsed → half-open
            if time.time() - self.last_failure_time >= self.recovery_timeout:
                self.state = CircuitState.HALF_OPEN
                self.success_count = 0
            else:
                # Fast fail — return fallback without calling downstream
                if fallback:
                    return fallback(*args, **kwargs)
                raise CircuitOpenError("Circuit is open")

        try:
            result = func(*args, **kwargs)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise

    def _on_success(self):
        if self.state == CircuitState.HALF_OPEN:
            self.success_count += 1
            if self.success_count >= self.success_threshold:
                self.state = CircuitState.CLOSED
                self.failure_count = 0
        else:
            self.failure_count = max(0, self.failure_count - 1)  # decay

    def _on_failure(self):
        self.failure_count += 1
        self.last_failure_time = time.time()
        if self.failure_count >= self.failure_threshold:
            self.state = CircuitState.OPEN

# Usage:
recommendation_cb = CircuitBreaker(failure_threshold=5, recovery_timeout=30)

def get_recommendations_with_fallback(user_id):
    return recommendation_cb.call(
        recommendation_service.get,
        user_id,
        fallback=lambda uid: get_popular_items()  # show trending if CB open
    )
Libraries Over Hand-Rolled: Resilience4j, Hystrix, Polly

Resilience4j (Java/Kotlin), Polly (.NET), and the deprecated Netflix Hystrix all provide battle-tested circuit breaker implementations with metrics hooks, thread pool isolation, and configurable ring buffer tracking. In service meshes (Istio/Envoy), circuit breaking is configurable at the proxy layer without any application code. Production systems should use proven libraries, not hand-rolled state machines.

Isolation Pattern

Bulkhead Pattern

Named after ship bulkheads that divide a ship's hull into waterproof compartments — a hull breach floods one compartment, not the whole ship. Applied to services: isolate failure domains so that one failing integration can't exhaust the resources of the whole service.

BULKHEAD — THREAD POOL ISOLATION ────────────────────────────────────────────────────────── WITHOUT BULKHEAD: Single thread pool (200 threads) shared by all downstream calls Recommendation Service (slow) ──► 180 threads stuck waiting Payment Service (fast) ──► 20 threads available → queued Search Service (critical) ──► 0 threads → timeout, user-facing failure One slow dependency starves all others. WITH BULKHEAD: Recommendation pool: 30 threads (slow OK, isolated) Payment pool: 50 threads (critical, dedicated) Search pool: 40 threads (user-facing, dedicated) Internal API pool: 30 threads Recommendation Service hangs → 30 threads stuck Payment Service unaffected → 50 threads still available ✓ Search Service unaffected → 40 threads still available ✓ ────────────────────────────────────────────────────────── BULKHEAD — CONNECTION POOL ISOLATION User DB pool: max 50 connections Orders DB pool: max 30 connections Analytics DB pool: max 10 connections Analytics query spikes → analytics pool exhausted User and Order DBs unaffected ✓ BULKHEAD — KUBERNETES RESOURCE ISOLATION Namespace: payments → resource limits: 4 CPU, 8GB RAM Namespace: analytics → resource limits: 2 CPU, 4GB RAM Namespace: web-api → resource limits: 8 CPU, 16GB RAM Analytics job spikes → hits namespace CPU limit, throttled Payments and web-api unaffected ✓
Core Mechanism

Retry & Timeout Strategies

Retries and timeouts are complementary but often misconfigured together. Retries amplify load on a failing service — without timeouts, retries can make cascading failures worse.

RETRY STRATEGIES ────────────────────────────────────────────────────────── BAD: Immediate retry (thundering herd) Service A calls B, B fails. Immediately retry → B still failing All Service A instances retry simultaneously B is hit with 3× the load while already struggling → death spiral GOOD: Exponential backoff with jitter Attempt 1: immediate Attempt 2: wait 1s Attempt 3: wait 2s Attempt 4: wait 4s (cap at some max, e.g., 32s) + Jitter: wait = random(0, base_delay) → desynchronizes retriers Multiple clients don't all retry at the same second ────────────────────────────────────────────────────────── WHAT TO RETRY (and what NOT to retry) Safe to retry: GET requests (idempotent by HTTP spec) PUT/DELETE (idempotent by HTTP spec) Network errors (connection refused, DNS timeout) 5xx errors ONLY if you know they're transient (503 Retry-After) Do NOT retry: POST without idempotency key (creates duplicates) 400 Bad Request (retrying won't fix a malformed request) 401/403 (auth error — retry is pointless) 409 Conflict (application logic error, not transient) 500 from your own code logic (not a transient network error) ────────────────────────────────────────────────────────── TIMEOUT HIERARCHY — set at each call boundary User browser: 30s connection timeout, 60s read timeout │ API Gateway: 25s request timeout (shorter than browser → explicit error page) │ Service A: 20s deadline propagated via context │ Service B call: 15s timeout (leaves buffer for retry + response) │ DB query: 5s statement timeout Rule: Each timeout shorter than the caller's timeout. Buffer enough for at least one retry. Propagate deadlines (gRPC context) so services don't work past client timeout.
Resilience Pattern

Graceful Degradation

When a non-critical dependency fails, serve a reduced but still useful response rather than failing completely. This requires upfront design decisions about what's core functionality vs what's enhancement.

DEGRADATION TIERS — product design for resilience ────────────────────────────────────────────────────────── E-commerce product page: Tier 1 (always available — core): Product name, description, price, add-to-cart Served from: Postgres primary + CDN cache SLO: 99.99% — any downtime is P0 Tier 2 (usually available — important): Customer reviews and ratings Served from: Reviews service + Redis cache Fallback: "Reviews temporarily unavailable" + cached rating from last hour Tier 3 (nice to have — enhancement): Personalized recommendations ("You might also like") Served from: ML recommendation service Fallback: Popular items in same category (from Redis, no ML needed) Circuit breaker: if ML service fails, instantly return popular items Tier 4 (optional — enrichment): Real-time inventory count ("12 left in stock!") Served from: Inventory service WebSocket Fallback: Static "In Stock" text from cached data User barely notices. ────────────────────────────────────────────────────────── FEATURE FLAGS — runtime degradation control ENABLE_RECOMMENDATIONS = true ENABLE_REVIEWS = true ENABLE_LIVE_INVENTORY = false ← disabled during inventory service incident → Ops can disable non-critical features instantly during incidents → No deploy required → 30-second toggle vs 5-minute deploy → Launchdarky, Unleash, or simple Redis key
Proactive Reliability

Chaos Engineering

Chaos engineering is the practice of deliberately injecting failures in a controlled way to verify your resilience assumptions before they fail in production uncontrolled. The hypothesis: "The system maintains SLO when X fails." The experiment: make X fail, observe.

CHAOS EXPERIMENT PROCESS ────────────────────────────────────────────────────────── 1. Define steady state: "p99 latency < 200ms, error rate < 0.1%" 2. Hypothesis: "Killing one of 3 database replicas won't violate steady state" 3. Inject failure (in staging first, then production with small blast radius): Kill 1 of 3 DB replicas via: kill -9 {postgres_pid} 4. Observe: Does error rate spike? Does p99 exceed 200ms? Did automatic failover occur within 30 seconds? Did any alerts fire? 5. Analyze and fix: Found: connection pool exhaustion during replica promotion (15s) Fix: add retry logic during failover window Re-run experiment → confirm fix ────────────────────────────────────────────────────────── FAILURE INJECTION CATALOG Network failures: tc netem: add 200ms latency to all packets to DB subnet iptables: drop 10% of packets to payment service toxiproxy: inject latency, jitter, timeout on specific connections Process failures: kill -9 on specific service processes chaos-monkey randomly terminates VMs in production (Netflix) Resource exhaustion: stress-ng: fill memory, saturate CPU, exhaust file descriptors disk-fill: fill disk to trigger space errors Service failures: Gremlin, Chaos Mesh: Kubernetes-native chaos injection AWS Fault Injection Simulator: managed chaos for AWS services
Geographic Resilience

Multi-Region Failover

A single-region service is unavailable during that region's outage — no circuit breaker or retry helps when AWS us-east-1 has a regional failure. Multi-region architectures survive AZ and region failures at the cost of significant complexity and data replication concerns.

MULTI-REGION TOPOLOGIES ────────────────────────────────────────────────────────── ACTIVE-PASSIVE (Warm Standby): us-east-1 (active) eu-west-1 (passive/warm) All traffic → here No user traffic Primary DB (writes) Read-only replica (continuous sync) Warm app servers (auto-start on failover) Failover: update DNS (Route53 health check) → 60-300s RTO RPO: seconds (async replication lag) to zero (sync replication) Use for: DR requirements, lower cost than active-active ACTIVE-ACTIVE (Multi-region writes): us-east-1 (active) eu-west-1 (active) US users → here EU users → here Primary DB (writes) Primary DB (writes) │ ←──── sync ────► │ └──── conflict resolution needed ────┘ Complexity: write conflicts (last-write-wins or CRDT) RTO: near-zero (traffic rerouted instantly via DNS/anycast) Use for: global latency SLOs, financial services, gaming ────────────────────────────────────────────────────────── DNS FAILOVER (AWS Route53 example): Primary record: us-east-1 load balancer Health check: HTTPS GET /healthz every 10s, must return 200 Failover record: eu-west-1 load balancer Routing policy: FAILOVER (secondary only if primary health check fails) Failover trigger: 3 consecutive health check failures → 30s DNS TTL: 60s (lower = faster failover, higher cache invalidation cost) Total failover time: ~60-90s (health check failure + TTL expiry)

9 Lenses

How Each Team Thinks About Reliability

🏗️ Infrastructure Engineer

We think in availability zones. Every compute resource, database, and load balancer has to span at least 2 AZs — preferably 3. A single-AZ deployment is a single point of failure that AWS's own AZ outages will eventually hit. Our baseline IaC template deploys auto-scaling groups across 3 AZs with cross-zone load balancing enabled, and we code-review any deviation from this pattern.

Instance replacement is our reliability mechanism for compute. We don't patch production servers — we replace them. Every EC2 instance or Kubernetes node is immutable: when a CVE requires patching, we spin up new instances with the patched AMI and terminate the old ones. This means we test deployment and startup paths constantly, not just during incidents, so we know they work.

Runbooks for every alert are not bureaucracy — they're reliability infrastructure. When an alert fires at 3 AM, a clear runbook with diagnosis steps, escalation paths, and rollback procedures is the difference between a 15-minute incident and a 2-hour one. We require every new service to have runbooks before it goes to production, and we run quarterly runbook drills to verify they're still accurate.

🌐 Network Engineer

Network partitions are the failure mode that most software engineers don't design for because they're rare in a single datacenter. In multi-region or multi-cloud systems, they're a regular occurrence. We design routing policies assuming the inter-region link is unreliable: anycast routing that falls back automatically, BGP health checks that redirect traffic away from degraded regions, and client-side failover logic that doesn't wait for DNS TTL expiry.

TCP connection limits are a reliability concern people ignore until they hit them. A load balancer processing 100k concurrent WebSocket connections has 100k open TCP connections — each consuming kernel resources. We monitor TCP connection table utilization and set alerts at 70% of the configured max. Connection exhaustion looks like random timeouts, which is a very difficult failure mode to diagnose without pre-configured metrics.

DDoS resilience is part of reliability engineering, not just security. A volumetric DDoS attack that exhausts your network bandwidth has the same effect as a catastrophic failure: service unavailable. We deploy AWS Shield / Cloudflare / rate limiting at the network edge, and we've tested our response to synthetic volumetric traffic to verify that legitimate traffic still gets through during an attack.

⚙️ Platform Engineer

Platform reliability is about making reliability the path of least resistance for product teams. We provide a service template with circuit breakers, retries with backoff, health check endpoints, and structured logging pre-configured. A team that starts from our template has reliability built in — a team that starts from scratch has to consciously add each of these, and they often don't until they have their first incident.

Deployment reliability is platform reliability. We require blue-green deployments or canary releases through our CI/CD pipeline. A bad deploy that's caught at 5% canary traffic is an incident that 95% of users never experienced. Our canary automation watches error rate and p99 latency during the rollout — automatic rollback triggers if either exceeds baseline by more than 20% for 5 minutes.

SLO dashboards are a platform product we maintain. Every service registered in our catalog gets an auto-generated SLO dashboard in Grafana, fed from Prometheus. SLO burn rate alerts are pre-configured: fast burn (consuming 5% of error budget in 1 hour) pages immediately; slow burn (consuming 10% in 6 hours) sends a Slack notification. Teams don't have to set this up — it just works when they register the service.

🔐 Security / Cyber Engineer

Availability is a security property — the A in CIA (Confidentiality, Integrity, Availability). A DDoS attack targeting availability is a security incident, not just an ops incident. We treat sustained traffic patterns that look like DoS (single IP, single ASN, single user agent) as security events and engage incident response, not just infrastructure auto-scaling.

Failover systems must be hardened the same way as primary systems. We've seen incident post-mortems where the DR site was less secured than production — it ran old versions, had open security groups, and missed authentication on admin endpoints. When you fail over to DR, you can't trade availability for security. Our runbook requires security controls validation as a pre-failover checklist item.

Chaos engineering includes security failure scenarios. We test: what happens if the certificate authority we use for mTLS is temporarily unreachable? Does service-to-service communication fail open (dangerous) or fail closed (correct)? What happens if the secrets manager is down during a service restart? Fail closed is almost always correct for security dependencies. We verify this with injected chaos, not by assuming the code is right.

📊 Data Engineer

Data pipeline reliability has a different failure taxonomy than service reliability. A pipeline that produces wrong results silently is worse than one that fails loudly — wrong data influences business decisions and may not be noticed for weeks. Our SLOs include data quality metrics: freshness (data lag), completeness (row count vs expected), and schema conformance. A "green" pipeline that produces stale or corrupt data violates our SLO as much as a crashed pipeline.

We design pipelines for idempotent re-runs. If the pipeline fails at step 3 of 5, we should be able to re-run from the beginning and get the same result. This means: never overwrite output in-place (write to a versioned path, then atomic rename), use database UPSERT not INSERT (so re-runs don't duplicate rows), and track pipeline execution state in a metadata table so we know which steps completed.

Backfill is our recovery mechanism. When a data pipeline produces wrong output for 3 days (maybe due to a schema change we didn't catch), we fix the pipeline, then reprocess the 3 days of raw events from Kafka (using Kafka's replay capability) through the corrected pipeline. The Kafka retention period is our data reliability window — once an event ages out of Kafka, we can't backfill from it without raw source data archives.

🤖 ML / AI Engineer

ML model reliability has a unique failure mode: gradual degradation (model drift) rather than sudden failure. A model trained on last year's data serving this year's traffic produces increasingly incorrect predictions — but no circuit breaker trips, no error rate spikes. Our SLI for ML systems includes prediction quality metrics (click-through rate, conversion rate, user satisfaction scores) measured via A/B test, not just infrastructure metrics.

Model serving must degrade gracefully when the inference service is unavailable. For recommendation systems, the fallback is "popular items" from Redis — no ML needed, always available, acceptable quality. For safety classifiers (content moderation), the fallback must be fail-safe: if the classifier is down, treat all content as potentially unsafe and queue for human review. Fail-open for safety systems is unacceptable.

Model rollback is our most important reliability mechanism. Every model deployment is versioned. If a new model causes a measurable decrease in business metrics (measured via shadow mode or canary), we roll back to the previous model version within minutes. The rollback procedure is tested monthly — we practice it in staging so it's not improvised during a live incident. "We can't roll back the model" is a statement that means you haven't designed for reliability.

⚡ Backend Engineer

Every external call I make gets a timeout. This is not negotiable — a hanging HTTP client with no timeout is a thread leak in disguise. I set connect timeout (2s — fast fail if host is unreachable), read timeout (10s — give the service time to respond but not forever), and I propagate deadlines from incoming gRPC context so I never work past the caller's deadline. When the client has given up, continuing work server-side is waste.

Retry logic is in every outgoing call, but only for idempotent operations and only for transient errors. I distinguish between retryable (network timeout, 503 with Retry-After header, connection reset) and non-retryable (400, 401, 409, 422). Retrying a 400 is wasting capacity on guaranteed failures. Retrying a 503 without exponential backoff is DDoS-ing the recovering service. These details matter and I document them in the code.

Graceful shutdown is an often-forgotten reliability concern for backend services. When Kubernetes sends SIGTERM before terminating a pod, I catch it: stop accepting new requests, drain in-flight requests with a 30-second grace period, close DB connections cleanly, commit any pending async work. A pod that's killed mid-request without graceful shutdown causes a spike of user-visible errors during every rolling deploy. One developer's missed graceful shutdown handler causes thousands of user errors per deployment.

🎨 Frontend Engineer

Frontend resilience starts with not making the full page dependent on every API call. I architect pages with a primary data requirement (must succeed) and secondary data requirements (show skeleton if unavailable). React Suspense boundaries with fallback UI let me declare these dependencies explicitly — a failed recommendation API shows a fallback component, not a broken page. Users shouldn't see a white screen because the recommendations service had a hiccup.

Offline-capable design is the extreme version of graceful degradation. Service workers can cache critical UI assets and the last-known API responses — users can view content even with no network. Writes that happen offline are queued and replayed when connectivity returns. This is more engineering effort, but for apps used in unreliable network conditions (mobile, rural, emerging markets), it's the difference between functional and unusable.

Loading states must accurately reflect what's happening. "Loading..." shown for 30 seconds while an API hangs is not graceful degradation — it's just a different flavor of bad UX. I set frontend timeouts on API calls (10-15 seconds), show meaningful error states after timeout ("This is taking longer than expected. Try again?"), and let users retry without refreshing the page. Frontend reliability includes communicating failure honestly and giving users agency to recover.

📡 SRE / Site Reliability Engineer

Our primary reliability metric is error budget burn rate. The burn rate alert pattern I use: page immediately if we're burning 5% of our monthly error budget in any 1-hour window (fast burn = likely active incident). Alert to Slack if we're burning 10% of budget in any 6-hour window (slow burn = something degraded, not critical yet). This catches both the acute incidents and the gradual reliability decay before it becomes a crisis.

Post-incident reviews (PIRs) are our reliability learning loop. After every P0/P1 incident, we conduct a blameless PIR within 48 hours: timeline reconstruction, contributing factors, what worked, what didn't, and 3-5 concrete action items with owners and deadlines. We publish the PIR internally so other teams learn from it. The action items get tracked and followed up — a PIR with no follow-through is theater, not engineering.

Chaos engineering is part of our quarterly reliability program. We run 2-3 targeted experiments per quarter per critical service, always starting in staging and promoting to production only after staging validates the hypothesis. We've found real bugs this way that our code review and load testing missed — a failover procedure that worked in theory but caused 4 minutes of partial unavailability in practice, caught via chaos before users experienced it in a real failure.

Problem 01
Design an API Gateway with Full Resilience Patterns
Circuit Breaker Bulkhead Retry Timeout Degradation

The Resilient Gateway Pipeline

RESILIENT REQUEST LIFECYCLE Client │ timeout: 30s ▼ [ API Gateway ] │ ├── Auth Check: JWT verify (timeout: 100ms, no retry) │ └── fail: 401 immediately │ ├── Rate Limit: Redis token bucket (timeout: 50ms) │ └── fail: serve from local in-memory cache (degraded, eventually consistent) │ ├── Request routing (4 downstream services, each in own bulkhead): │ │ ┌─── User Service (pool: 50 threads, timeout: 3s, retry: 2×) │ │ CB threshold: 5 failures/10s → open 30s │ │ Fallback: cached user data from Redis (5min TTL) │ │ │ ├─── Product Service (pool: 100 threads, timeout: 5s, retry: 2×) │ │ CB threshold: 10 failures/20s → open 60s │ │ Fallback: CDN-cached product page │ │ │ ├─── Inventory Service (pool: 30 threads, timeout: 2s, retry: 1×) │ │ CB threshold: 3 failures/5s → open 20s │ │ Fallback: show "Check availability" instead of live count │ │ │ └─── Recommendation Engine (pool: 20 threads, timeout: 1s, NO retry) │ CB threshold: 2 failures/5s → open 10s │ Fallback: popular items from Redis (always available) │ ← strictest CB: slowest, least critical, fails fast │ └── Response aggregation → client

Why Per-Service Bulkheads

The recommendation engine regularly takes longer than 1 second during ML model evaluation. Without a bulkhead, this would exhaust the shared thread pool and starve inventory lookups (which users actually need for checkout). With a dedicated 20-thread pool, the recommendation engine can be slow without impacting checkout. The tight circuit breaker (2 failures in 5s → open) ensures a slow recommendation service is immediately bypassed, not retried.

Problem 02
Design a Multi-Region Failover System for a Financial App
Active-Passive RTO <60s RPO ~0 DNS Failover

Requirements

  • RTO (Recovery Time Objective): <60 seconds of user-visible downtime during region failure
  • RPO (Recovery Point Objective): near-zero — no financial transaction data can be lost
  • Normal operation: all traffic to us-east-1, EU region is warm standby

Architecture

FINANCIAL APP MULTI-REGION FAILOVER us-east-1 (primary, all traffic) App servers (ECS tasks, 3 AZs) RDS PostgreSQL primary (Multi-AZ: sync replica in same region) │ synchronous replication to standby (same region, different AZ) │ asynchronous replication (seconds lag) → │ eu-west-1 (warm standby) App servers (pre-warmed, 1 task per AZ, no user traffic) RDS PostgreSQL read replica (async from us-east-1 primary) Lag: typically <5 seconds, monitored continuously FAILOVER TRIGGER: Route53 health check: HTTPS /healthz every 10s Failure condition: 3 consecutive failures (30s detection) FAILOVER PROCEDURE (automated, ~60s total): T+0: 3rd health check failure detected T+30: Route53 fails over DNS to eu-west-1 load balancer T+30: EU app servers receive first traffic T+35: RDS promotion: eu-west-1 read replica promoted to primary (automated via EventBridge rule triggering Lambda) T+60: EU primary accepting writes, full service restored RPO WINDOW: Replication lag at failover: 0-10 seconds (async lag) Transactions in that window: potentially lost Mitigation: synchronous replication to same-region standby (zero loss within region), async to cross-region (small window)
Problem 03

Prometheus SLO Recording Rules

# prometheus/rules/payment_slo.yml
groups:
  - name: payment_slo
    interval: 30s
    rules:
      # SLI: success rate (5xx are bad events)
      - record: payment:request_success_rate:5m
        expr: |
          1 - (
            sum(rate(http_requests_total{service="payment",code=~"5.."}[5m]))
            /
            sum(rate(http_requests_total{service="payment"}[5m]))
          )

      # Error budget burn rate (30-day window)
      - record: payment:error_budget_burn_rate:1h
        expr: |
          (1 - payment:request_success_rate:5m) / (1 - 0.9995)
          # burn_rate = 1 means consuming error budget at exact SLO rate
          # burn_rate = 6 means burning 6× faster than allowed

# Alert: fast burn (will exhaust monthly budget in ~5 days at this rate)
- alert: PaymentSLOFastBurn
  expr: payment:error_budget_burn_rate:1h > 14.4
  for: 5m
  labels:
    severity: critical
    team: payments
  annotations:
    summary: "Payment SLO fast burn rate: {{ $value }}×"
    description: "At this rate, monthly error budget exhausted in < 50 hours"

# Alert: slow burn (will exhaust monthly budget in ~10 days)
- alert: PaymentSLOSlowBurn
  expr: payment:error_budget_burn_rate:1h > 3
  for: 30m
  labels:
    severity: warning
Decision Guide

Trade-offs Table

Decision Option A Option B When to Choose A
Active-passive vs active-active Active-passive (warm standby) Active-active (multi-region writes) Active-passive when RPO of seconds is acceptable and you want to avoid write conflict complexity. Active-active for near-zero RPO and global users who need low latency
Circuit breaker vs retry-only Circuit breaker + retry Retry only Always prefer circuit breaker. Retry without CB during a failing service multiplies load on the already-struggling downstream, accelerating the cascade
Fail fast vs wait for retry Fail fast (tight timeout) Aggressive retry Fail fast for user-facing requests where UX matters. Aggressive retry for background jobs where eventual success is more important than latency
SLO 99.9% vs 99.99% 99.9% (single-region) 99.99% (multi-region) 99.9% is achievable with careful single-region design (Multi-AZ). 99.99% almost always requires multi-region and costs significantly more in both infra and engineering complexity
Graceful degradation vs full availability Graceful degradation (tiered) All-or-nothing Graceful degradation almost always wins. All-or-nothing means every non-critical service dependency can cause a full outage. Degradation requires upfront design effort
Chaos in staging vs production Staging first, then production Production directly Always staging first. Production chaos requires: small blast radius, feature flags to limit scope, immediate rollback, and on-call SRE standing by. Never chaos production cold
Liveness vs readiness checks Separate liveness and readiness Single health check Always separate. Liveness failure → restart (nuclear option). Readiness failure → remove from load balancer (graceful). Conflating them causes unnecessary pod restarts during startup
Tight vs loose error budget 99.9% SLO (44 min/month) 99.99% SLO (4.4 min/month) Set SLO to match actual user expectations, not aspirational targets. An overly tight SLO depletes budget on noise, freezes deployments constantly, and erodes team trust in SLOs as a tool
What Not to Do

Anti-patterns

  • Retry without exponential backoff and jitter Immediate retries on a failing service add load at the worst possible moment. Without jitter, all clients retry simultaneously, creating thundering herd spikes. Exponential backoff with jitter desynchronizes retriers and gives the recovering service breathing room. This pattern is specifically what AWS SDK, gRPC, and most HTTP client libraries implement — use their built-in retry logic, don't write your own without jitter.
  • Shared thread pool across all downstream calls (no bulkhead) One slow or hanging service will eventually exhaust all available threads, blocking every other service call. Isolate each major dependency in its own bounded thread pool or connection pool. The cost is slightly higher memory and configuration; the benefit is blast-radius containment — one service failure can't bring down your whole service.
  • Setting SLAs tighter than SLOs Your SLA is what you promise customers. Your SLO is what you achieve internally. If SLA = SLO = 99.9%, you have zero buffer — any SLO miss immediately breaches the customer contract. Set SLA conservatively below your SLO. The gap is your margin for measurement imprecision, external factors, and the occasional bad week.
  • Circuit breaker that never closes (stuck open) A circuit breaker that opens but never half-opens means the downstream service can recover fully and your CB still rejects all calls. Verify your CB implementation transitions to HALF_OPEN after the recovery timeout. Also ensure the half-open probe doesn't itself time out too quickly — give the probe enough time to reflect actual service health.
  • Chaos engineering without defined steady state Running chaos experiments without knowing what "normal" looks like means you can't tell if the experiment revealed a problem. Define your steady state metrics (error rate, p99 latency) before injecting failure. "Let's see what happens" is exploration, not engineering. "Hypothesis: killing one DB replica won't change error rate" is chaos engineering.
  • Single health check for both liveness and readiness Liveness checks that include dependency checks (DB, Redis) will restart the pod if those dependencies are temporarily unavailable — even if the pod itself is fine. A DB blip causes every pod to restart simultaneously. Liveness should check only the process health. Readiness can check dependencies — it removes from load balancer, which is reversible.
  • Designing failover but never testing it A DR runbook that hasn't been executed in 12 months is theoretical. DNS failover that hasn't been tested may have outdated IP ranges, wrong IAM permissions, or a missed dependency. Run quarterly failover drills. The first time you execute a failover should not be during an actual production incident. "We have DR" without regular drills means you have false confidence.
  • Error budget = 0 → full deployment freeze for the whole month Exhausting error budget once doesn't mean all reliability-improving work stops. The freeze should cover risky feature deploys, not all deploys. Bug fixes, security patches, and reliability improvements should continue. An overly broad freeze causes safety patches to pile up, which itself becomes a risk.
Interview Strategy

Interview Tips for Reliability Questions

The Reliability Interview Trap

Interviewers ask "how would you make this highly available?" Many candidates list infrastructure (multiple AZs, replicas, CDN). The signal interviewers are looking for is pattern knowledge: circuit breakers, bulkheads, graceful degradation, and SLOs. Infrastructure redundancy is necessary but not sufficient — the resilience patterns are what separate senior engineers from juniors.

Tip 01

Always define your SLO first. Before drawing any architecture, say "What's our availability target? 99.9% or 99.99%?" This shows you know the target determines the design — single-region for 99.9%, multi-region for 99.99%.

Tip 02

Name the circuit breaker when discussing service calls. Any time you draw a service-to-service call, say "I'd put a circuit breaker here with a fallback response." Name the states: closed, open, half-open. This signals you know the pattern, not just the concept.

Tip 03

Separate critical from non-critical dependencies. Explicitly tier your dependencies: "Recommendations are nice-to-have, so they have a tight circuit breaker and fall back to popular items. Payments are critical and must succeed." This shows product thinking alongside technical design.

Tip 04

Mention error budgets when discussing SLOs. "Our SLO is 99.9% availability, which gives us 43 minutes of downtime per month as our error budget. We freeze risky deploys when the budget is exhausted." This shows you've internalized how SLOs drive engineering decisions.

Tip 05

Distinguish RTO from RPO for DR questions. "RTO is how quickly we recover (how long is the service down). RPO is how much data we can afford to lose (how far back do we restore from)." These two numbers drive the entire failover architecture and few candidates can define both clearly.

Tip 06

Mention chaos engineering as a verification strategy. "I'd validate our circuit breaker and fallback behavior with chaos experiments — inject failure into the recommendation service and verify the fallback works without affecting user-facing checkout." This shows reliability thinking beyond design into verification.

Clarifications
+
MTTR vs MTBF
MTBF (Mean Time Between Failures): average time between incidents. Higher = more reliable. MTTR (Mean Time To Recovery/Repair): average time to restore service after an incident. Lower = faster recovery. Both matter: a system with MTBF of 1 year but MTTR of 3 days is worse than one with MTBF of 1 month but MTTR of 5 minutes. Optimize both; don't just prevent failures — also get fast at recovering.
+
RTO vs RPO
RTO (Recovery Time Objective): maximum acceptable downtime. "We must be back online within 4 hours." Drives: hot standby vs cold standby, replication strategy. RPO (Recovery Point Objective): maximum acceptable data loss. "We can lose at most 1 hour of data." Drives: backup frequency, replication lag limits. Lower RTO/RPO = more expensive infrastructure. Define these before designing your disaster recovery plan.
+
Error Budget
Error budget = 100% − SLO. If your SLO is 99.9%, your error budget is 0.1% = 8.7 hours/year. This budget belongs to engineering — spend it on risky deployments, experiments, and new features. If the budget is exhausted (too many incidents), freeze deployments until it refills. If the budget is underused, you're being too conservative — ship more. Error budgets turn SLOs into a management tool, not just a metric.
+
Four Golden Signals
From Google's SRE book: Latency (how long requests take — track p50, p99, p999, not just averages), Traffic (how many requests per second), Errors (rate of failed requests — 5xx, timeouts), Saturation (how "full" your service is — CPU %, memory %, queue depth). Monitor all four. An anomaly in any one is a leading indicator of an incident.
+
Circuit Breaker States
CLOSED (normal): requests pass through, failures counted. OPEN (failing): requests immediately rejected without trying the downstream service — fast failure instead of slow failure. After a timeout, moves to HALF-OPEN. HALF-OPEN (testing recovery): a few test requests pass through. If they succeed, circuit CLOSES again. If they fail, circuit OPENS again. Libraries: Resilience4j (Java), polly (.NET), pybreaker (Python).
+
Thread Pool Isolation
Without bulkheads: one slow downstream service exhausts the shared thread pool, blocking ALL other requests too. With bulkheads: each downstream service gets its own bounded thread pool (e.g., 20 threads for payments, 20 for inventory). If payments is slow and all 20 payment threads are waiting, inventory threads are unaffected. Hystrix (Netflix, now deprecated) popularized this. Now done with Resilience4j or Envoy.
+
Retry Storms
Retry storms happen when many clients simultaneously retry failed requests, multiplying load on an already struggling service. Example: 1000 clients fail, all retry after 1 second → service gets 1000 simultaneous retries → overwhelmed again → all retry → cascading failure. Fix: exponential backoff (1s, 2s, 4s, 8s...) + jitter (add random 0–1s to each delay so retries spread out in time).
+
Liveness vs Readiness vs Startup Probes
Kubernetes has three probe types. Liveness: is the pod alive? If it fails, Kubernetes kills and restarts the pod. Readiness: is the pod ready to receive traffic? If it fails, the pod is removed from the load balancer (but not restarted). Startup: is the app still initializing? Prevents liveness from killing pods that take a long time to start. Always implement all three in production services.
+
Blast Radius
Blast radius = how much of your system can break if an experiment or change goes wrong. Chaos engineering principle: start small. First test: kill one pod in staging. Later: kill one availability zone in prod. Never: kill all instances globally. Keep blast radius small and increase gradually as confidence builds. Use feature flags to limit impact and have a kill switch ready before starting any experiment.
+
Active-Passive vs Active-Active
Active-passive: one region handles all traffic; the other is a standby that takes over if primary fails. Simpler, but failover takes time (DNS propagation, database promotion) and standby capacity is wasted. Active-active: both regions handle traffic simultaneously. Zero downtime failover. Harder: need to handle data consistency across regions, avoid double-writes, and route users to the right region.
+
DNS Failover
DNS failover: your DNS record points to Region A. If Region A health checks fail, the DNS record automatically updates to point to Region B. Challenge: DNS TTL. If TTL is 300 seconds, users who cached the old IP are stuck pointing at the failing region for up to 5 minutes. Use low TTL (30–60s) for services that need fast failover. AWS Route 53 health checks can trigger failover within 1 minute.
