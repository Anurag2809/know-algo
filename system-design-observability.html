Foundation

The Three Pillars of Observability

Observability is the ability to understand what a system is doing from its external outputs, without modifying the system. The three pillars — logs, metrics, and traces — each answer different questions about system behavior.

Three pillars: what question each answers LOGS METRICS TRACES "What happened?" "How is it performing?" "Why is this slow?" Timestamped events Numeric time-series Request flow across services Unstructured or JSON Aggregatable, queryable Spans with timing + context High volume, expensive Low cardinality, cheap Sampled (1% or adaptive) Example: 2026-01-15T14:23:01Z http_request_duration_p99 TraceID: abc123 level=ERROR = 450ms Order → Payment → DB msg="DB timeout" error_rate = 0.5% ├─ order-svc: 5ms user_id=123 active_connections = 847 ├─ payment-svc: 420ms ← slow! order_id=789 └─ postgres: 380ms ← root cause Tools: Elasticsearch/Loki Prometheus/Datadog Jaeger/Zipkin/Tempo CloudWatch Logs InfluxDB/VictoriaMetrics AWS X-Ray/GCP Cloud Trace
📋

Logs — Events

Discrete timestamped records of things that happened. Use structured JSON (not free text) so logs are machine-parseable. Include trace_id to correlate with traces.

📊

Metrics — Numbers

Aggregated numeric measurements over time. Four types: Counter (always increases), Gauge (up/down), Histogram (distribution), Summary (quantiles).

🔍

Traces — Flows

A trace follows a single request across multiple services. Each service creates a span with start time, duration, and metadata. Parent-child relationships form a tree.

🔗

Correlation

The real power: correlate all three. A metric alert fires → find the trace_id from that time window → look up the log lines from that trace. Tools: Grafana unified view.

Instrumentation Standard

OpenTelemetry (OTel)

OpenTelemetry is the open-source standard for instrumentation. It provides vendor-neutral APIs and SDKs to generate traces, metrics, and logs. You instrument once, then export to any backend (Jaeger, Prometheus, Datadog, etc.).

OpenTelemetry Architecture Your Application ├─ OTel SDK (Python/Go/Java/JS) │ ├─ Auto-instrumentation (HTTP, DB, gRPC — no code changes) │ └─ Manual spans for business logic │ ▼ OTel Collector (sidecar or daemonset) ├─ Receivers: OTLP, Prometheus, Jaeger, Zipkin ├─ Processors: batching, sampling, PII scrubbing, tail-sampling └─ Exporters: (fan out to multiple backends) ├─► Jaeger / Tempo (traces) ├─► Prometheus (metrics) └─► Elasticsearch / Loki (logs) OTel Collector is the key: centralize sampling/routing decisions, not in each app Tail-based sampling: decide to keep/drop a trace AFTER it completes (knows if it had errors) Head-based sampling: decide at trace start (doesn't know outcome yet)

Numeric Telemetry

Metrics & Prometheus

Prometheus is the de-facto standard for metrics in cloud-native systems. It scrapes metrics from HTTP endpoints, stores them in a time-series database, and provides PromQL for querying. Grafana visualizes PromQL queries as dashboards.

Prometheus Scrape Architecture Services Prometheus Server Grafana order-svc:8080/metrics ◄──── scrape every 15s ─────────────────────────────── payment-svc:8080/metrics ◄── scrape every 15s ── store TSDB ──► PromQL ─────► postgres-exporter:9187/metrics ◄ scrape 15s ────────────────────────────────► Prometheus pulls (scrapes) — apps expose metrics on /metrics endpoint Alternative: pushgateway for short-lived jobs that may not exist when Prometheus scrapes Metric types: Counter: http_requests_total{method="GET",status="200"} ← always goes up Gauge: active_connections{service="db"} ← can go up/down Histogram: http_request_duration_seconds_bucket{le="0.1"} ← counts by bucket Summary: http_request_duration_seconds{quantile="0.99"} ← client-side quantile PromQL: rate(http_requests_total[5m]) → requests per second over 5-minute window histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) → p99 latency

Cardinality Problem

High-cardinality labels (like user_id or order_id) create millions of time series, crashing Prometheus. Labels should be low-cardinality: status code, endpoint, region — not individual IDs.

Alertmanager

Routes Prometheus alerts to PagerDuty, Slack, email. Handles deduplication (same alert from 3 instances = 1 notification), grouping, and silencing during maintenance.

Long-Term Storage

Prometheus keeps ~2 weeks locally. For longer retention: Thanos or Cortex (S3-backed, multi-region PromQL), or VictoriaMetrics (high-performance, compression). Grafana Mimir is CNCF-native.

Request Flow

Distributed Tracing

When a request touches 10 microservices, a single log line can't tell you where 400ms went. A trace reconstructs the full call graph: each service adds a span with start time, duration, and metadata.

Trace: user clicks checkout → trace spans the entire flow TraceID: 7f3a8b2c... │ ├─ api-gateway [0ms → 2ms] routing, auth check │ ├─ order-service [2ms → 8ms] validate cart, create order │ │ │ ├─ postgres [3ms → 7ms] INSERT order │ │ │ └─ inventory-service [5ms → 8ms] reserve items │ └─ redis [5ms → 6ms] decrement stock │ ├─ payment-service [8ms → 430ms] ← 422ms spent here! │ │ │ ├─ stripe-api [8ms → 420ms] ← root cause: external API slow │ │ http.status=200, latency=412ms │ │ │ └─ postgres [420ms → 430ms] INSERT payment record │ └─ notification-service [430ms → 432ms] send confirmation email (async) Total trace: 432ms. Root cause: Stripe API. Order service itself: 6ms. Without tracing: you'd see "checkout is slow" but have no idea where.

Context Propagation

Trace context (trace_id, span_id) must be forwarded in HTTP headers (traceparent in W3C format) or gRPC metadata. Auto-instrumentation handles this, but custom async jobs need manual propagation.

Sampling Strategies

At 1000 req/s, storing every trace is expensive. Head sampling: keep 1% randomly. Tail sampling (preferred): keep 100% of error traces, 1% of success traces. OTel Collector's tail-sampling processor handles this.

Tools

Jaeger: CNCF, self-hosted, Elasticsearch/Cassandra backend. Tempo: Grafana's trace backend, object-storage-based (S3), cheap. Zipkin: older but simpler. AWS X-Ray, GCP Cloud Trace: managed options.

Event Records

Structured Logging

Unstructured logs ("Error connecting to database") are hard to query at scale. Structured logging emits JSON with consistent fields, enabling fast queries and aggregations.

import structlog, logging
from opentelemetry import trace

# Configure structlog with JSON output
structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,     # adds request context
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso"),
        structlog.processors.JSONRenderer(),          # structured JSON output
    ],
    logger_factory=structlog.PrintLoggerFactory(),
)
log = structlog.get_logger()

# Middleware: inject trace context into all log lines
async def logging_middleware(request: Request, call_next):
    span = trace.get_current_span()
    ctx = span.get_span_context()
    structlog.contextvars.bind_contextvars(
        trace_id=format(ctx.trace_id, '032x'),
        span_id=format(ctx.span_id, '016x'),
        user_id=request.state.user_id if hasattr(request.state, 'user_id') else None,
        path=request.url.path,
        method=request.method,
    )
    response = await call_next(request)
    log.info("request_completed", status=response.status_code)
    structlog.contextvars.clear_contextvars()
    return response

# Log output (each line is a JSON object):
# {"event":"request_completed","level":"info","timestamp":"2026-01-15T14:23:01Z",
#  "trace_id":"7f3a8b2c...","span_id":"a1b2...","user_id":"u123",
#  "path":"/checkout","method":"POST","status":200}

Log Aggregation Stacks

ELK: Elasticsearch + Logstash + Kibana. Powerful but resource-intensive. Loki: Grafana's log store, index-free (just labels), much cheaper than Elasticsearch. CloudWatch Logs: AWS-native, simple but expensive at scale.

Log Levels

ERROR: system failure requiring immediate attention. WARN: unexpected but recovered. INFO: normal significant events. DEBUG: detailed developer info (never in production). Use sampling for high-frequency INFO logs.

Log Volume Management

Log what you need to debug incidents, not everything. Rate-limit noisy log lines. Sample INFO logs at 10%. Never log PII (passwords, SSNs, credit cards) — you'll get a compliance violation.

Reliability Targets

SLO / SLI / SLA & Error Budgets

SRE (Site Reliability Engineering) uses concrete reliability targets instead of vague promises. The framework: define what "reliability" means (SLI), set a target (SLO), and track your remaining budget for risk (error budget).

SLI → SLO → SLA hierarchy SLI (Service Level Indicator) = the metric you measure Examples: • Availability: successful_requests / total_requests • Latency: % of requests under 200ms • Throughput: messages processed per second • Error rate: errors / total_requests SLO (Service Level Objective) = your internal target for the SLI Examples: • 99.9% of requests succeed over a rolling 30-day window • 95% of requests complete in under 200ms • p99 latency under 1 second SLA (Service Level Agreement) = contractual commitment to customers • SLA is always MORE lenient than SLO (buffer for you to act before breach) • SLO: 99.9%, SLA: 99.5% → if you miss SLO, you still have time before SLA penalty Error Budget = 1 - SLO = allowable downtime • 99.9% SLO over 30 days = 0.1% of 30 days = 43.2 minutes of allowed downtime • If error budget is exhausted → freeze new feature deployments until budget refills • Error budget is a contract between product team and SRE: spend budget on features vs. reliability Burn rate: if budget burns 14x faster than normal, you'll exhaust it in 1hr → page immediately

Choosing Good SLIs

SLIs must reflect user experience, not internal signals. "Database connection pool healthy" is a poor SLI. "% of checkout requests completing in under 3 seconds" directly measures user impact.

Error Budget Policies

When budget is exhausted: halt all risky deployments. When budget is healthy: prioritize new features. Budget tracking creates shared incentive — engineers care about reliability because it affects their velocity.

Uptime Math

99% = 87.6 hr/yr down. 99.9% = 8.7 hr/yr. 99.95% = 4.4 hr/yr. 99.99% = 52 min/yr. 99.999% = 5.2 min/yr. Each nine requires significantly more investment.

On-Call Intelligence

Alerting & On-call

Bad alerting is worse than no alerting — alert fatigue causes engineers to ignore pages, missing real incidents. Good alerts are actionable, symptom-based, and rare enough to demand attention.

Alert tiers: who gets woken up and when Severity │ Response Time │ Channel │ Example ──────────┼───────────────┼─────────────────┼──────────────────────────────────── P1/SEV-1 │ 5 minutes │ Page (wake up) │ Error rate > 10% for 2 minutes P2/SEV-2 │ 30 minutes │ Page (business) │ Error budget burn rate > 5x P3/SEV-3 │ 1 business day│ Slack/ticket │ p95 latency trending up P4/SEV-4 │ Next sprint │ Ticket │ Disk usage > 70% Alert on symptoms, not causes: GOOD: "error_rate > 1% for 5 minutes" ← user impact BAD: "CPU > 80%" ← maybe fine, maybe not BAD: "deployment in progress" ← not actionable Multi-window burn rate alerting (Google SRE Book): 1h window: burn_rate > 14x → exhaust budget in 2 hours → PAGE immediately 6h window: burn_rate > 6x → exhaust budget in 5 hours → PAGE (ticket) 3d window: burn_rate > 1x → on track to exhaust budget → Slack ticket

Alert Fatigue

Too many alerts = oncall ignores them. Target: < 5 pages/shift, each requiring real investigation. Track alert volume and actionability. Noisy alerts get a bug filed to fix or delete them.

Runbooks

Every alert must have a linked runbook: what does this alert mean, how do I diagnose it, common fixes, escalation path. Oncall should be able to handle incidents without waking up the original author.

PagerDuty / OpsGenie

On-call rotation management. Escalation policies (if primary doesn't ack in 5 min, page secondary). Schedules. Incident management. Postmortem tracking. Alertmanager routes to these tools.

SRE Framework

The Four Golden Signals

Google's SRE book distilled the essential metrics for any service into four signals. If you can only monitor four things, monitor these.

SignalDefinitionPromQL ExampleAlert Threshold
LatencyHow long requests take. Distinguish success vs. error latency — slow errors can mask fast successes in averages.histogram_quantile(0.99, rate(duration_bucket[5m]))p99 > SLO target for 5 min
TrafficDemand on the system. Requests/sec, messages/sec. Sudden drops can indicate an issue just as much as spikes.rate(http_requests_total[5m])Drop > 50% from baseline
ErrorsRate of failed requests. Count both explicit (5xx) and implicit (wrong data, slow degraded).rate(http_requests_total{code=~"5.."}[5m])Error rate > 1% for 2 min
SaturationHow full is the service? CPU, memory, connections, queue depth. Predict problems before they happen.db_connections_active / db_connections_max> 80% saturation

USE method (for resources): Utilization, Saturation, Errors. RED method (for services): Rate, Errors, Duration. Golden signals combine both perspectives.

9 Viewpoints

Engineer Perspectives

SRE

SLOs are a negotiation tool, not just a number. Negotiate SLO with product before launch. Tight SLO = less feature velocity. Loose SLO = angry customers.

Backend Engineer

Add trace context to every log line from day one. Retrofitting tracing into a running system is painful. Use structlog and OTel auto-instrumentation — it's a one-time setup cost.

Platform Engineer

Standardize the observability stack. One Prometheus, one Grafana, one OTel collector daemonset. Teams should only worry about what to measure, not how to ship it.

Data Engineer

Pipelines need metrics too. Track: lag (how far behind are we?), throughput (records/sec), and data quality (null rate, schema violations). Treat pipeline observability like service observability.

Architect

Design observability into the architecture. Agree on trace context propagation format (W3C traceparent) before teams build. Retrofitting spans into async event systems is especially painful.

ML Engineer

Model serving needs latency percentiles (inference is often p99-sensitive), input data drift metrics, and prediction distribution monitoring. Use Prometheus + custom metrics.

Security Engineer

Observability data can be sensitive. Logs may contain PII. Traces reveal system topology to attackers. RBAC on Grafana. Scrub PII before shipping logs to Elastic.

Frontend Engineer

Real User Monitoring (RUM) tracks what actual users experience: Core Web Vitals, LCP, FID, CLS. Synthetic monitoring (Playwright tests on a schedule) catches issues before users do.

Mobile Engineer

Mobile crash reporting (Firebase Crashlytics, Sentry) is your logs. Instrument app startup time, screen render times, and API call latency from the client perspective. Client sees different p99s than server.

Observability Design Problems

Problem 01 · SLO Dashboard
Build a multi-window error budget burn rate alert for a 99.9% SLO
SLOPrometheusError Budget

Requirements

Service has a 99.9% success rate SLO (30-day rolling window). Need alerts at three burn rates: immediate page (P1), ticket (P2), and tracking (P3). Alert fatigue must be minimized.

# Prometheus alerting rules (alerts.yaml)
# Error ratio = errors / total requests over a window
# Burn rate = how fast we're consuming the error budget (1x = exactly on track)

# error budget = 0.1% (1 - 0.999 SLO)
# If we burn at 14x rate over 1h: 14 * 1h = consume 14h of budget in 1h
#   → exhausts 30-day budget in 30*24/14 ≈ 51 hours → PAGE NOW

groups:
  - name: slo_alerts
    rules:
      # P1: Fast burn — 14x rate for 1h OR 14x rate for 5min
      - alert: SLO_ErrorBudgetFastBurn
        expr: |
          (
            rate(http_requests_total{status=~"5.."}[1h])
            / rate(http_requests_total[1h])
          ) > (14 * 0.001)
          and
          (
            rate(http_requests_total{status=~"5.."}[5m])
            / rate(http_requests_total[5m])
          ) > (14 * 0.001)
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Error budget burning 14x faster than target"
          runbook: "https://wiki/runbooks/api-error-budget"

      # P2: Slow burn — 6x rate over 6h window
      - alert: SLO_ErrorBudgetSlowBurn
        expr: |
          (
            rate(http_requests_total{status=~"5.."}[6h])
            / rate(http_requests_total[6h])
          ) > (6 * 0.001)
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "Error budget burning 6x faster than target"

# Python: calculate current error budget remaining
def error_budget_remaining(success_rate_30d: float, slo: float = 0.999) -> dict:
    budget_total = 1 - slo           # 0.001 (0.1%)
    budget_used = slo - success_rate_30d
    budget_remaining = budget_total - budget_used
    pct_remaining = budget_remaining / budget_total * 100

    return {
        "slo": f"{slo*100}%",
        "actual": f"{success_rate_30d*100:.4f}%",
        "budget_used_min": (budget_used * 30 * 24 * 60),
        "budget_remaining_min": (budget_remaining * 30 * 24 * 60),
        "pct_remaining": f"{pct_remaining:.1f}%",
        "status": "OK" if pct_remaining > 50 else "WARNING" if pct_remaining > 0 else "EXHAUSTED"
    }

# Example: actual = 99.92% vs SLO 99.9%
print(error_budget_remaining(0.9992))
# {'budget_remaining_min': 28.8, 'pct_remaining': '20.0%', 'status': 'WARNING'}

Key Insight

Multi-window alerting reduces false positives. A single bad second doesn't exhaust your budget. The 1h + 5m dual condition catches sustained fast burns without alerting on momentary spikes.

Problem 02 · Distributed Tracing
Trace a slow checkout request across 6 microservices with OTel + Jaeger
OpenTelemetryJaegerDistributed Tracing

Challenge

Checkout p99 is 2.3 seconds. Average is 150ms. The 99th percentile outliers are mysterious — they don't leave obvious error logs. We need to find which service is slow for these specific requests.

from opentelemetry import trace, context
from opentelemetry.propagate import inject, extract
import httpx

tracer = trace.get_tracer("checkout-service")

async def checkout(cart_id: str, user_id: str):
    with tracer.start_as_current_span("checkout") as span:
        span.set_attribute("cart.id", cart_id)
        span.set_attribute("user.id", user_id)

        # Each downstream call propagates trace context via HTTP headers
        headers = {}
        inject(headers)  # adds 'traceparent' header with current trace/span IDs

        async with httpx.AsyncClient() as client:
            # These calls are sequential — each span shows where time was spent
            with tracer.start_as_current_span("validate_inventory"):
                inventory = await client.post(
                    "http://inventory-svc/validate",
                    headers=headers,
                    json={"cart_id": cart_id}
                )

            with tracer.start_as_current_span("calculate_pricing"):
                pricing = await client.post(
                    "http://pricing-svc/calculate",
                    headers=headers,
                    json={"cart_id": cart_id, "user_id": user_id}
                )
                span.set_attribute("pricing.total", pricing.json()["total"])

            with tracer.start_as_current_span("process_payment"):
                payment = await client.post(
                    "http://payment-svc/charge",
                    headers=headers,
                    json={"amount": pricing.json()["total"]}
                )

            with tracer.start_as_current_span("create_order"):
                order = await client.post(
                    "http://order-svc/create",
                    headers=headers,
                    json={"cart_id": cart_id, "payment_id": payment.json()["id"]}
                )

        span.set_attribute("order.id", order.json()["id"])
        return order.json()

# In Jaeger: filter traces where duration > 1000ms
# The waterfall view immediately shows which span is slow:
# If payment-svc span = 2100ms → look at payment-svc's internal spans
# If the payment-svc DB span = 2100ms → N+1 query or missing index

Tail Sampling Config

Keep 100% of slow traces (duration > 1s), 100% of error traces, 0.1% of fast successful traces. This dramatically reduces storage while preserving all the interesting traces for debugging.

Design a Grafana SLO dashboard for an API service with RED metrics

Dashboard Layout

Top row: SLO status (% remaining budget, days until exhaustion). Second row: RED metrics (rate, errors, duration) as time-series. Third row: per-endpoint breakdown. Fourth row: upstream dependencies.

# Key PromQL queries for each dashboard panel

# 1. Request rate (RED: Rate)
rate(http_requests_total{service="checkout"}[5m])

# 2. Error rate % (RED: Errors)
100 * rate(http_requests_total{service="checkout",status=~"5.."}[5m])
    / rate(http_requests_total{service="checkout"}[5m])

# 3. p99 latency (RED: Duration)
histogram_quantile(0.99,
  rate(http_request_duration_seconds_bucket{service="checkout"}[5m])
)

# 4. SLO compliance (30-day rolling)
1 - (
  rate(http_requests_total{service="checkout",status=~"5.."}[30d])
  / rate(http_requests_total{service="checkout"}[30d])
)

# 5. Error budget remaining (%)
100 * (
  1 - (
    rate(http_requests_total{service="checkout",status=~"5.."}[30d])

) / 0.001

(
  rate(http_requests_total{service="checkout",status=~"5.."}[1h])

What Not to Do

Observability Anti-patterns

Alert on Every Metric

Alerts for CPU > 80%, disk > 70%, all at once. Creates alert fatigue. Only alert on user-facing symptoms — latency, errors, availability.

Missing Trace Context in Logs

Log lines without trace_id are useless during an incident — you can't correlate what happened in service A with what happened in service B for the same request.

Storing All Traces

At 1000 req/s, 100% trace storage is terabytes/day. Use sampling. Tail-based sampling keeps what matters (errors, slow requests) and drops the rest.

High-Cardinality Labels

Adding user_id or order_id as Prometheus labels creates millions of time series. Prometheus will OOM. Use histograms for per-request data, not counters.

SLO Without Error Budget Policy

Having an SLO number but no policy for when budget is exhausted. The policy is the point — it drives behavior: freeze deploys, fix reliability, update runbooks.

Unstructured Logs

Free-text log messages that can't be parsed or queried. Impossible to aggregate at scale. Use JSON with consistent field names from the start.

No Dashboards Before Launch

Instrumenting after an incident instead of before. You have no baseline to compare against. Build dashboards during development, not after the first outage.

Treating Average as Truth

Monitoring p50 latency misses the tail. Users who hit p99 are real users having a bad experience. Always alert on p99, and check p99.9 for critical paths.

Interview Prep

Interview Tips

Explain the Pillars and When to Use Each

Logs for event details, metrics for trends/alerts, traces for latency attribution. The interviewer wants to know you understand when each tool is appropriate.

Know the SLI→SLO→SLA Chain

Define the SLI (what you measure), set the SLO (your internal target), and the SLA is more lenient (buffer for the customer contract). Error budget = 1 - SLO.

Mention Error Budget Trade-offs

Error budget policy is the sophisticated part. When budget is healthy, ship features. When exhausted, freeze risky changes and invest in reliability. This is the SRE model in practice.

Criticize Metric Averages

If you mention "average latency," immediately correct yourself to p99 or p99.9. Interviewers notice this — averages hide the worst user experience and are rarely actionable.

Explain Cardinality

High-cardinality labels (user_id, trace_id as Prometheus labels) is a common mistake. Show you know the difference between metric labels (low-cardinality) and trace/log fields (can be high-cardinality).

Mention the Golden Signals

Latency, Traffic, Errors, Saturation — Google's SRE framework. Knowing these by name shows you've internalized SRE thinking beyond just "add Prometheus."

Clarifications
+
What is a time-series database?
A time-series database (TSDB) stores data indexed by time: (timestamp, metric_name, labels, value). It's optimized for queries like "give me CPU usage over the last hour." Prometheus uses its own TSDB. InfluxDB, VictoriaMetrics, and TimescaleDB are other examples.
+
What is a sidecar container?
In Kubernetes, a Pod can run multiple containers. A sidecar is a helper container that runs alongside your app container, sharing the same network and volumes. The OTel Collector sidecar receives telemetry from the app, processes it (batching, sampling), and ships it to backends — so the app doesn't need to know about the observability infrastructure.
+
What is a histogram vs average?
Averages hide the distribution. If 90% of requests take 10ms and 10% take 1000ms, the average is 109ms — misleading. A histogram buckets requests: "how many took 0-10ms? 10-100ms? 100ms-1s?" From histograms, you can compute percentiles: p99 = 1000ms reveals the problem. Always use histograms for latency.
+
What is context propagation?
When service A calls service B, the trace context (which trace this request belongs to) must be passed along in HTTP headers. The W3C standard header is `traceparent: 00-traceid-spanid-flags`. Without propagation, service B's spans become orphaned — not connected to the original trace. Auto-instrumentation handles this for HTTP and gRPC; you must handle it manually for Kafka messages and async jobs.

What does "nine nines" mean?
"Five nines" = 99.999% availability = 5.26 minutes of downtime per year. Each additional "nine" is 10x more reliable and 10x harder to achieve. Most internet services target 99.9% (three nines = 8.7 hours/year). Financial transaction systems might target 99.99% (four nines = 52 minutes/year). 100% uptime is impossible — maintenance, deployments, and unexpected failures always happen.

What is PagerDuty?
PagerDuty is an on-call management platform. It receives alerts from monitoring systems (Prometheus, Datadog) and pages the on-call engineer via phone call, SMS, or app push. It manages escalation (if you don't respond in 5 min, wake up your backup), on-call rotation schedules, and incident timelines. OpsGenie is a similar alternative.

What is the USE vs RED method?
USE (Brendan Gregg) focuses on infrastructure resources — Utilization (how busy?), Saturation (how much backlog?), Errors (failure count). Good for CPU, disk, network. RED (Tom Wilkie) focuses on services — Rate (requests/sec), Errors (failed requests), Duration (latency). Good for APIs and microservices. Golden Signals combines both approaches.
