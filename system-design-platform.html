Foundation

Platform Engineering

Platform engineering builds the "paved road" — opinionated, self-service infrastructure that makes the right things easy and the wrong things hard. Instead of every team solving the same infrastructure problems, the platform team solves them once and exposes them as simple APIs.

🛣️

Paved Road

Curated path of tools, patterns, and templates that work well together. Teams can go off-road, but the paved road is the easiest and most supported path. Reduces cognitive load for product engineers.

🔧

Internal Developer Platform (IDP)

A self-service portal where developers provision services, databases, CI pipelines, and environments — without filing tickets or waiting for ops. Backstage is the most popular open-source IDP framework.

📏

Golden Paths

Pre-configured templates for "how we create a new service here." Includes: Dockerfile, Helm chart, CI pipeline, monitoring dashboards, and Terraform module. Spin up a new service in 10 minutes, not 10 days.

📊

Developer Experience (DevEx)

Measured by DORA metrics: deployment frequency, lead time for changes, change failure rate, time to restore. Platform teams optimize these metrics as their primary KPIs.

Continuous Delivery

CI/CD Pipelines

CI (Continuous Integration) validates every code change automatically. CD (Continuous Delivery/Deployment) takes validated code to production automatically or with one click. The goal is to make deployment a boring, frequent, low-risk event.

Container Orchestration

Kubernetes Fundamentals

Kubernetes (K8s) is a container orchestration platform. It schedules containers across a cluster of machines, handles restarts, scales replicas, routes traffic, and manages configuration — without manual server management.

K8s core objects and how they relate Cluster ├─ Node (VM or physical machine) │ └─ Pod (smallest deployable unit — 1+ containers sharing network/storage) │ ├─ app container │ └─ sidecar containers (OTel collector, Envoy proxy) │ ├─ Deployment: manages a set of identical Pods │ "keep 3 replicas of order-service:v2 running" │ Handles rolling updates, rollbacks │ ├─ Service: stable network endpoint for a set of Pods │ ClusterIP: internal only │ NodePort: expose on each node's port │ LoadBalancer: provision cloud LB (ALB, GLB) │ ├─ Ingress: HTTP routing rules (path-based, host-based) │ "api.example.com/orders → order-svc" │ Implemented by Ingress controller (Nginx, Traefik, ALB controller) │ ├─ ConfigMap: non-secret config (env vars, config files) │ Secret: sensitive config (base64, or external via ESO) │ └─ HorizontalPodAutoscaler (HPA) "scale order-service to 2-20 replicas based on CPU/custom metric" Helm: package manager for K8s. Chart = templated collection of K8s manifests. helm install order-svc ./charts/order --set image.tag=v2.3.1 --namespace prod
Declarative Deployments

GitOps & ArgoCD

GitOps uses Git as the single source of truth for infrastructure and application state. The desired state is declared in Git; a controller continuously reconciles the actual cluster state to match Git. No more manual kubectl apply — Git is the deployment mechanism.

GitOps workflow: Git is the only way to deploy Developer GitHub ArgoCD K8s Cluster │ │ │ │ │── PR: update ─────►│ │ │ │ image.tag: v2 │ │ │ │ │── merge to main ──►│ │ │ │ │ detect diff │ │ │ │ (Git vs cluster) │ │ │ │── sync ──────────►│ │ │ │ kubectl apply │ │ │ │ rolling update │ │ │ │◄─ healthy ────────│ │ │ │ │ │ │ │ continuous reconcile every 3min │ │ │ if cluster drifts from Git → fix it Benefits: • Full audit trail: every deploy is a Git commit with author • Rollback: git revert → ArgoCD reverts the cluster • Disaster recovery: cluster dies → recreate from Git state • PR reviews for prod changes: infra change = code review Flux is an alternative to ArgoCD. Both implement the GitOps operator pattern. Image Updater: ArgoCD plugin that auto-updates image tags in Git when new image pushed to registry
Service-to-Service

Service Mesh

A service mesh adds a transparent proxy (sidecar) to every service. The proxy handles mTLS, load balancing, retries, timeouts, circuit breaking, and traffic splitting — without application code changes. The mesh provides observability across all service-to-service calls.

Service mesh: sidecar proxies handle cross-cutting concerns Order Service Payment Service ┌─────────────────────┐ ┌──────────────────────┐ │ App (Go) │ │ App (Python) │ │ │ │ │ │ Envoy Sidecar ─────┼──── mTLS ─────────┼─── Envoy Sidecar │ │ • retries (3x) │ │ • circuit breaker │ │ • timeout (500ms) │ │ • rate limiting │ │ • traces │ │ • traces │ └─────────────────────┘ └──────────────────────┘ │ │ └──────────── Control Plane ───────────────┘ (Istio / Linkerd) • Push config to all sidecars • Collect telemetry • Enforce policies App code makes plain HTTP/gRPC calls — sidecar transparently encrypts, retries, traces Traffic splitting: route 5% to v2, 95% to v1 at sidecar level (no code change) Istio: powerful but complex (CNI, CRDs). Linkerd: simpler, lower overhead, Rust proxies.
Infrastructure as Code

Terraform & IaC

Infrastructure as Code means provisioning cloud resources (VPCs, databases, K8s clusters) through code rather than clicking in a UI. Changes are version-controlled, reviewed, and applied automatically — the same discipline as application code.

State Management

Terraform tracks what it created in a state file. Store in S3 with DynamoDB locking (prevents two engineers running apply simultaneously). Never edit state manually.

Terraform vs Pulumi

Terraform: HCL declarative language, massive ecosystem. Pulumi: write infrastructure in Python/TypeScript/Go — same language as your app code. Both are excellent; Pulumi is preferred when logic gets complex.

Modules

Reusable Terraform packages. Company internal modules standardize how VPCs, EKS clusters, RDS instances are created. Teams use modules, not raw resources, to enforce security and tagging standards.

Engineer Perspectives

Platform Engineer

Treat platform features like product features. Measure adoption, not just existence. If engineers aren't using the golden path, find out why — maybe it's not actually golden.

SRE

CI pipelines must run integration tests against real dependencies (testcontainers), not mocks. Mocked tests that pass while prod fails are worse than no tests — they create false confidence.

Backend Engineer

Kubernetes resource limits are mandatory, not optional. A Pod without limits can starve neighbors on the same node. Set both requests (scheduling) and limits (enforcement) for CPU and memory.

Security Engineer

Shift security left: SAST in CI, container scanning before push, IaC security checks (Checkov, tfsec). Catching a CVE in CI costs minutes; catching it post-deploy costs hours of incident work.

Data Engineer

Data pipelines need CI/CD too. dbt models should have CI tests (schema checks, row counts). Deploy pipeline changes with the same rigor as application code — data bugs are often invisible until downstream.

ML Engineer

ML training jobs run in Kubernetes with GPU node pools. Use KubeFlow Pipelines or Argo Workflows for training orchestration. Model serving deploys like a regular service — same CI/CD, same Helm chart pattern.

Frontend Engineer

Preview environments (one per PR, auto-deployed) are a killer platform feature. Reviewers can see the feature live without setting up locally. Netlify/Vercel do this natively; internal platforms replicate it with ArgoCD + Ingress rules.

Mobile Engineer

Mobile CI/CD differs: builds take 20+ minutes, and distribution goes to TestFlight/Play Store, not K8s. Fastlane automates signing and distribution. Platform teams often own mobile CI lanes to standardize codesigning.

Architect

Platform maturity is a competitive advantage. Teams that deploy 10× per day beat teams that deploy once a week. The platform team's ROI is measured in every team's shipping velocity.

Problem 01 · GitOps
Design a zero-downtime deployment pipeline with ArgoCD and automated rollback
ArgoCDKubernetesGitOps

Requirements

Every merge to main deploys to staging automatically, then to production with canary. If error rate exceeds 1% during rollout, auto-rollback to previous version.

# kind: Application

# spec:
#   source:
#     repoURL: https://github.com/acme/k8s-config
#     path: apps/order-service
#     targetRevision: HEAD

# Argo Rollouts: canary strategy with auto-rollback
# rollout.yaml
# apiVersion: argoproj.io/v1alpha1
# kind: Rollout
# spec:
#   strategy:
#     canary:
#       steps:
#         - setWeight: 5          # 5% canary
#         - pause: {duration: 5m}
#         - setWeight: 25
#         - pause: {duration: 10m}
#         - setWeight: 50
#         - pause: {duration: 10m}
#         - setWeight: 100
#       analysis:                 # auto-rollback on metric failure
#         templates:
#           - templateName: success-rate
#         args:
#           - name: service-name

# Analysis template: watch error rate during canary
# analysistemplate.yaml
# spec:
#   metrics:
#     - name: success-rate
#       interval: 1m
#       failureLimit: 3          # 3 consecutive failures → rollback
#       provider:
#         prometheus:
#           address: http://prometheus:9090
#           query: |
#             sum(rate(http_requests_total{service="{{args.service-name}}",

#             / sum(rate(http_requests_total{service="{{args.service-name}}"}[5m]))
#       successCondition: result[0] >= 0.99  # 99%+ success rate required

# Auto-rollback flow:
# canary at 5% → error rate 2% (> 1% threshold) →

What Not to Do

Platform Anti-patterns

Snowflake Servers

Servers configured by hand, not reproducible. When they fail, recovery is a mystery. IaC enforces reproducibility — every server is defined in code and can be rebuilt identically.

No Resource Limits

Kubernetes Pods without CPU/memory limits. A runaway pod consumes all node resources and starves neighbors. Always set requests (for scheduling) and limits (for enforcement).

kubectl apply in CI

Directly applying manifests from CI without GitOps. No audit trail. No reconciliation loop to fix drift. Upgrade to ArgoCD/Flux — Git becomes the source of truth.

Mocking Everything in Tests

Unit tests that mock the database, the cache, and every external call. They test nothing real. Use Testcontainers to run real dependencies. Mocks should be exceptions, not the default.

Long-Lived Feature Branches

Branches that diverge from main for weeks. Merge conflicts become a project themselves. Trunk-based development with feature flags eliminates this — everyone commits to main, flags hide incomplete features.

Platform Without Users

Building elaborate internal tools that engineers don't use because they're slower than the old way. Measure adoption. If no one uses the golden path, the platform team has a product problem, not a technical one.

Secrets in ConfigMaps

Kubernetes ConfigMaps are not encrypted. Putting passwords or API keys there exposes them to anyone with cluster read access. Use Secrets + External Secrets Operator pulling from Vault/AWS Secrets Manager.

One Giant Pipeline

A 45-minute sequential CI pipeline that runs everything. Fast feedback is the point of CI. Parallelize: lint + unit tests in 2 minutes, integration tests next, E2E only on main branch.

Interview Prep

Interview Tips

Know the DORA Metrics

Deployment frequency, lead time for changes, change failure rate, time to restore. These are the industry-standard measure of DevOps maturity. Citing them shows you understand the business value of CI/CD.

Explain GitOps vs Push-Based

Push-based (CI runs kubectl apply) vs pull-based (ArgoCD watches Git and applies). Pull-based is more secure (cluster doesn't need external credentials) and self-healing. Know the trade-off.

Mention Testcontainers

Integration tests with real databases instead of mocks. This is a maturity signal. Most candidates know about unit testing with mocks; fewer know about real-dependency integration testing in CI.

Service Mesh is a Layer, Not a Requirement

Don't recommend a service mesh for a 3-service system. It adds significant operational complexity. Recommend it when: mTLS between all services is required, or traffic management (canary, retries) is needed at the network level.

IDP = Product Thinking for Platform

The best platform teams think of engineers as users. NPS surveys for internal tools, adoption metrics for golden paths. This is the differentiator between a good platform team and a great one.

Trunk-Based Development

Most high-performing teams use trunk-based development (all changes to main, short-lived branches). Pair it with feature flags. This eliminates merge conflicts and enables continuous delivery.

Clarifications
+
What is CI vs CD?
CI (Continuous Integration): automatically build and test every code commit. Goal: catch bugs before they reach production. CD has two meanings — Continuous Delivery: every commit is releasable (but human triggers deploy). Continuous Deployment: every passing commit automatically deploys to production. Most companies do Continuous Delivery, not full Continuous Deployment.
+
What is a container and how does K8s use them?
A container (Docker) packages an app and all its dependencies into an isolated unit that runs the same everywhere. Kubernetes manages containers across many machines: it decides which machine runs each container, restarts them when they fail, and balances load. Think of K8s as the operating system for a cluster of machines.
+
What is a Git merge vs Git rebase?
Merge: combines two branches by creating a new "merge commit" that has both as parents — preserves history. Rebase: moves your branch's commits onto the tip of another branch — creates a linear history. GitOps doesn't care about this distinction — it watches the resulting state of the main branch, not how commits were integrated.
+
What is Envoy proxy?
Envoy is a high-performance network proxy written in C++, originally built at Lyft. It handles HTTP/1.1, HTTP/2, gRPC, and TCP. In a service mesh, Envoy is the sidecar proxy — it runs alongside each app container and transparently intercepts all network traffic. Istio's data plane uses Envoy. It's also used standalone as an API gateway and in AWS App Mesh.
+
What is idempotence in IaC?
An operation is idempotent if running it multiple times produces the same result as running it once. Terraform is idempotent: running `terraform apply` on an already-provisioned infrastructure changes nothing (or only what changed in the config). This is essential for automation — you can safely re-run the pipeline without fear of double-creating resources.
+
What are DORA metrics?
DORA (DevOps Research and Assessment) identified four metrics that predict software delivery performance: Deployment Frequency (how often?), Lead Time for Changes (commit → production, how long?), Change Failure Rate (what % of deploys cause incidents?), Time to Restore (when an incident happens, how fast to recover?). Elite performers deploy multiple times per day with sub-1-hour lead time.
