Batch vs. Stream Processing

Every data pipeline sits somewhere on the spectrum between processing finite bounded datasets (batch) and processing infinite unbounded event streams (stream). The right choice depends on your freshness requirement — how stale is the data allowed to be when consumers read it?

Bounded (Batch) Input Unbounded (Stream) Input Database / S3 / HDFS Kafka / Kinesis / Pub/Sub │ │ ▼ ▼ ┌─────────────────────┐ ┌─────────────────────────┐ │ Batch Job (Spark) │ │ Stream Job (Flink/Spark) │ │ reads ALL records │ │ processes per event │ │ per run │ │ or micro-batch │ └────────┬────────────┘ └──────────┬──────────────┘ │ │ ▼ ▼ Warehouse / Data Lake Sink: Kafka / DB / Cache / Dashboard Latency: minutes → hours milliseconds → seconds Throughput: very high (GBs→TBs) medium (tunable) Cost: low (spot instances) higher (always-on) Fault tol.: re-run entire job checkpointing + exactly-once

Batch Processing

  • Process all data up to time T in one run
  • High throughput, low operational cost
  • Nightly ETL, monthly billing aggregations
  • Retry is cheap — just re-run the job
  • Simple programming model

Stream Processing

  • Process each event or micro-batch as it arrives
  • Low latency (sub-second possible)
  • Fraud detection, live dashboards, alerting
  • Fault tolerance via checkpointing
  • Out-of-order events & watermarks required

Micro-Batch (Spark Streaming)

  • Batches of 100ms–30s treated as mini-batch
  • Simpler semantics than pure streaming
  • Latency: seconds (not milliseconds)
  • High throughput via batch optimizations
  • Trigger: fixed interval or processingTime

Incremental Batch

  • Process only new records since last run
  • Watermark column: updated_at, event_time
  • Reduces compute cost vs full batch
  • Late data handled by re-processing window
  • Common in data warehouse refresh patterns

Time Semantics

Three time concepts matter in stream processing, and confusing them causes incorrect aggregations:

Time TypeDefinitionUse CasePitfall
Event TimeWhen the event actually occurred (in the source system)Analytics, billing, complianceOut-of-order arrival; must buffer
Processing TimeWhen the pipeline processes the eventSimple alerting, real-time feedsResults differ on retry / replay
Ingestion TimeWhen the message arrives at the message brokerCompromise when event time missingNetwork delay skews it

Watermarks: A watermark W(t) tells the engine "all events with event_time < t have arrived." Events arriving after the watermark are late data — you must decide: drop them, update results, or route to a side output for reconciliation. Flink's BoundedOutOfOrdernessWatermarks lets you configure max lateness (e.g., 5 minutes).

Lambda & Kappa Architecture

These are two competing blueprints for building systems that serve both historical analytics and low-latency results.

Lambda Architecture

Raw Events (Kafka / S3 event store) │ ├──────────────────────────────────┐ │ │ ▼ ▼ ┌──────────────────────┐ ┌──────────────────────┐ │ Batch Layer │ │ Speed Layer │ │ (Spark on S3/HDFS) │ │ (Flink / Spark SS) │ │ Recomputes from raw │ │ Processes real-time │ │ Every N hours/days │ │ Last N minutes/hrs │ └──────────┬───────────┘ └──────────┬───────────┘ │ │ ▼ ▼ Batch Views (DWH) Realtime Views (Redis) │ │ └────────────┬────────────────┘ ▼ ┌───────────────────┐ │ Serving Layer │ │ Merges batch + │ │ realtime views │ └───────────────────┘ Pros: high accuracy (batch), low latency (speed) Cons: TWO codebases to maintain — same logic implemented twice

Kappa Architecture

Raw Events (Kafka — permanent log retention) │ ▼ ┌─────────────────────────────────────────────┐ │ Single Stream Processing Layer │ │ (Flink / Spark SS) │ │ │ │ Normal mode: process live events │ │ Reprocessing: replay Kafka from offset 0 │ │ Run v2 job in parallel → swap output │ └───────────────────┬─────────────────────────┘ │ ▼ Serving Layer (DB / Cache) Pros: single codebase, simpler operations Cons: Kafka must retain full history (expensive); reprocessing is slow

Which to Choose?

  • Lambda: When batch accuracy > operational complexity. Legacy teams often have Spark batch already. Good for compliance reports that must match exactly.
  • Kappa: When you can keep Kafka logs forever (or object-store offloading). Best for teams with strong Flink/Spark Streaming skills. Simpler DevOps.
  • Modern trend: Kappa with Lakehouse. Store raw events in S3/GCS with Iceberg/Delta, replay from object store instead of Kafka for reprocessing. Best of both worlds.

dbt (Data Build Tool)

dbt is the de-facto ELT transformation layer. It runs SQL SELECT statements in your warehouse, materializing them as tables or views, with lineage, testing, and documentation built in.

-- models/marts/fct_orders.sql
-- dbt model: one SELECT → materialized as table in warehouse

{{ config(
    materialized='incremental',          -- only process new rows
    unique_key='order_id',               -- merge on this key
    on_schema_change='sync_all_columns'
) }}

WITH source_orders AS (
    SELECT *
    FROM {{ ref('stg_orders') }}         -- ref() builds the DAG
    WHERE status != 'cancelled'
    {% if is_incremental() %}
        AND created_at > (SELECT MAX(created_at) FROM {{ this }})
    {% endif %}
),
enriched AS (
    SELECT
        o.order_id,
        o.user_id,
        o.created_at,
        o.total_amount,
        u.country,
        u.plan_tier,
        -- surrogate key for SCD Type 2 tracking
        {{ dbt_utils.generate_surrogate_key(['order_id', 'created_at']) }} AS sk
    FROM source_orders o
    LEFT JOIN {{ ref('dim_users') }} u USING (user_id)
)
SELECT * FROM enriched

dbt Tests: Add schema.yml with tests: [unique, not_null, accepted_values, relationships]. Run dbt test in CI to catch data quality regressions before they reach dashboards.

Apache Spark

Spark is the dominant batch and micro-batch engine. Its key insight is keeping intermediate data in memory across stages rather than writing to disk after each MapReduce step.

Execution Model

DataFrame API — Key Patterns

from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window

spark = SparkSession.builder \
    .appName("UserEventAggregation") \
    .config("spark.sql.adaptive.enabled", "true")   \  # AQE: auto tune joins
    .config("spark.sql.adaptive.coalescePartitions.enabled", "true") \
    .getOrCreate()

# Read from S3 with partition pruning
events = spark.read.parquet("s3://data-lake/events/year=2024/month=*/") \
    .filter(F.col("event_type").isin(["purchase", "refund"])) \
    .filter(F.col("country") == "US")

# Avoid shuffle: broadcast small dimension table
users = spark.read.parquet("s3://data-lake/users/").cache()
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 50 * 1024 * 1024)  # 50MB

enriched = events.join(F.broadcast(users), "user_id", "left")

# Window function — running total per user per day
window = Window.partitionBy("user_id", "date") \
               .orderBy("event_ts") \
               .rowsBetween(Window.unboundedPreceding, Window.currentRow)

result = enriched.withColumn(
    "running_spend",
    F.sum("amount").over(window)
).groupBy("date", "country", "plan_tier") \
 .agg(
    F.count("order_id").alias("order_count"),
    F.sum("amount").alias("revenue"),
    F.approx_count_distinct("user_id").alias("unique_buyers")  # HLL
 )

# Write with partitioning — downstream pruning
result.write \
    .mode("overwrite") \
    .partitionBy("date", "country") \
    .parquet("s3://data-warehouse/fct_daily_revenue/")

Apache Flink

Flink is the leading true stream processing engine. Unlike Spark's micro-batch model, Flink processes each event individually with exactly-once guarantees via distributed snapshots (Chandy-Lamport algorithm).

Windows & State

Kafka Source ──▶ Flink JobManager ──▶ Kafka/DB Sink │ ┌───────────┼───────────┐ ▼ ▼ ▼ TaskManager TaskManager TaskManager (slots) (slots) (slots) │ ┌────┴─────┐ │ State │ ← RocksDB (large) or heap (small) │ Backend │ └────┬─────┘ │ checkpoint every N seconds ▼ S3 / HDFS (checkpoint storage) Window Types: Tumbling: [0–5min] [5–10min] [10–15min] — no overlap Sliding: [0–5min] [1–6min] [2–7min] — overlap (every 1min) Session: events grouped by inactivity gap (e.g., 30min idle) Global: one window, custom trigger (count-based, etc.) 
from pyflink.datastream import StreamExecutionEnvironment
from pyflink.datastream.connectors.kafka import FlinkKafkaConsumer, FlinkKafkaProducer
from pyflink.datastream.window import TumblingEventTimeWindows, Time
from pyflink.common.watermark_strategy import WatermarkStrategy, Duration

env = StreamExecutionEnvironment.get_execution_environment()
env.set_parallelism(4)
env.enable_checkpointing(60_000)  # checkpoint every 60s (ms)

# Source with watermark strategy (5 min max lateness)
watermark_strategy = WatermarkStrategy \
    .for_bounded_out_of_orderness(Duration.of_minutes(5)) \
    .with_timestamp_assigner(lambda event, _: event["event_ts"])

stream = env.add_source(FlinkKafkaConsumer(
    topics="user-events",
    deserialization_schema=...,
    properties={"bootstrap.servers": "kafka:9092", "group.id": "flink-agg"}
)).assign_timestamps_and_watermarks(watermark_strategy)

# Stateful aggregation: count purchases per user per 10-min tumbling window
result = stream \
    .filter(lambda e: e["event_type"] == "purchase") \
    .key_by(lambda e: e["user_id"]) \
    .window(TumblingEventTimeWindows.of(Time.minutes(10))) \
    .reduce(lambda a, b: {
        "user_id": a["user_id"],
        "count": a["count"] + b["count"],
        "revenue": a["revenue"] + b["revenue"],
        "window_end": b["window_end"]
    })

# Late data side output (events arriving after watermark)
late_tag = OutputTag("late-events")
# ... configure allowed lateness and side output sink

result.add_sink(FlinkKafkaProducer("purchase-aggregates", ...))
env.execute("PurchaseAggregationJob")

Data Lakehouse

A lakehouse combines the low-cost object storage of a data lake with the ACID transactions, schema enforcement, and query performance of a data warehouse. The key innovation is an open table format layer sitting on top of Parquet files in S3/GCS.

Data Sources CDC (Debezium) + Kafka + App Logs + Click Events │ ▼ ┌───────────────────────────────────────────────────┐ │ Raw / Bronze Layer │ │ S3: s3://lake/raw/{source}/{date}/ │ │ Format: Parquet + Iceberg/Delta table format │ │ No transforms — append-only, full history │ └─────────────────────┬─────────────────────────────┘ │ dbt / Spark transform ▼ ┌───────────────────────────────────────────────────┐ │ Cleaned / Silver Layer │ │ Deduplicated, validated, joined dimensions │ │ Partition by (date, region, event_type) │ └─────────────────────┬─────────────────────────────┘ │ aggregation ▼ ┌───────────────────────────────────────────────────┐ │ Business / Gold Layer │ │ Fact + Dimension tables (star schema) │ │ Served to: BI tools, dashboards, ML features │ └───────────────────────────────────────────────────┘ Open Table Formats (choose one): Apache Iceberg — Netflix origin, best time-travel, hidden partitioning Delta Lake — Databricks, tight Spark integration, MERGE support Apache Hudi — Uber origin, upsert-optimized, two table types (CoW/MoR)

Iceberg Table Features

-- Create Iceberg table with hidden partitioning
CREATE TABLE catalog.db.events (
    event_id     BIGINT,
    user_id      BIGINT,
    event_type   STRING,
    amount       DECIMAL(12,2),
    event_ts     TIMESTAMP,
    country      STRING
)
USING iceberg
PARTITIONED BY (days(event_ts), country)  -- hidden partitioning by day
TBLPROPERTIES (
    'write.target-file-size-bytes' = '134217728',  -- 128MB files
    'write.delete.mode'            = 'merge-on-read',
    'history.expire.max-snapshot-age-ms' = '604800000'  -- 7 days
);

-- MERGE (upsert) — atomic, no duplicate risk
MERGE INTO catalog.db.events AS target
USING new_events AS source ON target.event_id = source.event_id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

-- Time travel: audit or reprocess
SELECT * FROM catalog.db.events
TIMESTAMP AS OF '2024-01-15 00:00:00';

-- Snapshot rollback after bad write
CALL catalog.system.rollback_to_snapshot('db.events', 8170963818875623621);

Z-Ordering for query performance: OPTIMIZE table ZORDER BY (user_id, event_type) co-locates related data in the same Parquet files. Query filters on user_id skip 90%+ of files via Iceberg's min/max statistics per file.

Pipeline Orchestration

Orchestrators schedule, monitor, and retry pipeline tasks. They manage DAG (Directed Acyclic Graph) dependencies — task B runs only after task A succeeds.

Apache Airflow

  • Most widely deployed orchestrator
  • Python-defined DAGs
  • Rich operator ecosystem
  • Backfill: airflow dags backfill
  • Weakness: scheduler bottleneck, no dynamic tasks in older versions
  • Managed: MWAA (AWS), Cloud Composer (GCP)

Prefect

  • Python-native, dynamic workflows
  • Tasks are decorated functions
  • Hybrid execution (cloud + local agents)
  • Better error messages than Airflow
  • Flows can be parameterized at runtime
  • Good for ML training pipelines

Dagster

  • Asset-centric (not task-centric)
  • Data-aware: knows schema of each asset
  • Built-in data quality testing
  • Lineage graph out of the box
  • Partitioned assets for incremental loads
  • Best for data platform teams

dbt + orchestrator

  • dbt Cloud has built-in scheduling
  • Or trigger dbt from Airflow/Prefect
  • Slim CI: only run changed models
  • State: compare to production artifacts
  • Integration: dbt-airflow operators

from airflow.providers.amazon.aws.operators.emr import EmrServerlessStartJobRunOperator
from airflow.providers.common.sql.operators.sql import SQLCheckOperator

    "owner": "data-platform",
    "retries": 3,

    # Step 1: Run Spark job on EMR Serverless

        task_id="run_spark_aggregation",
        application_id="{{ var.value.emr_app_id }}",
        execution_role_arn="{{ var.value.emr_role_arn }}",
        job_driver={
            "sparkSubmit": {
                "entryPoint": "s3://scripts/revenue_aggregation.py",
                "entryPointArguments": [
                    "--date", "{{ ds }}",  # Airflow template: execution date
                    "--env", "prod",
                ],
            }
        },
        configuration_overrides={
            "monitoringConfiguration": {
                "s3MonitoringConfiguration": {"logUri": "s3://logs/emr/"}
            }
        },
    )

    # Step 2: Data quality check
    quality_check = SQLCheckOperator(
        task_id="check_row_count",

    # Step 3: dbt transformation (downstream models)

        task_id="dbt_mart_models",

Data Quality & Lineage

In complex pipelines, bad data propagates silently and corrupts downstream models. Proactive quality gates and complete lineage are essential.

Data Quality Dimensions: Completeness — are expected rows and columns present? Freshness — how old is the latest partition? Accuracy — does it match source-of-truth (reconciliation)? Consistency — does it agree across tables? (referential integrity) Uniqueness — are primary keys truly unique? Validity — are values within expected domain/range? Tools: dbt tests — schema.yml: unique, not_null, accepted_values, relationships Great Expectations — Python-native, rich expectation library Soda Core — SQL-based checks, push alerts to Slack/PagerDuty Monte Carlo — ML-based anomaly detection (row count, distribution drift)

Data Lineage

Lineage tracks data from source to sink — "which source tables feed dashboard X?" — enabling impact analysis when upstream schemas change.

Lineage Stack

  • Column-level lineage: OpenLineage standard (facets), consumed by Marquez or DataHub
  • dbt lineage: dbt docs generate produces a full DAG; integrated in dbt Cloud
  • Spark lineage: Spark Listener emits OpenLineage events per job
  • Flink lineage: Flink SQL lineage with OpenLineage Flink integration
  • Data catalog: DataHub (LinkedIn), Apache Atlas, Google Dataplex — search + govern

Schema Evolution Strategy: Use backward-compatible schema changes (add nullable columns, never remove/rename). Enforce with Schema Registry (Confluent) for Kafka topics. Set avro.evolution.allow = BACKWARD in registry to block breaking changes.

Engineer Perspectives

Infrastructure Engineer

Right-size your compute separately from storage. EMR Serverless or Databricks serverless lets you pay per job rather than maintaining always-on clusters. Use spot instances for batch jobs (2–10× cheaper) with on-demand fallback. Store intermediate shuffle data on local NVMe SSDs, not EBS — shuffle spills to EBS kill performance by 5–10×. Set up auto-termination on clusters (30 min idle) to prevent bill creep.

Network Engineer

Shuffle traffic is the dominant intra-cluster network cost. Keep Spark executors in the same Availability Zone to avoid cross-AZ data transfer charges (which add up to thousands of dollars/month at petabyte scale). Place Kafka brokers in the same VPC as Flink TaskManagers. Use VPC endpoints for S3 to avoid NAT gateway costs for high-throughput jobs reading from object storage.

Platform / DevEx Engineer

Standardize on one orchestrator and enforce it. Rogue cron jobs running on EC2 are the #1 cause of data freshness incidents — they fail silently. Provide a pipeline template repository: one git repo per pipeline, standard CI that runs dbt test on PR, auto-deploys to staging, requires data quality gate before prod deploy. The best platform makes the right way the easy way.

Security / Compliance Engineer

PII flows through pipelines invisibly until it lands in a BI dashboard accessible to 1,000 employees. Tag PII columns at the source (DataHub tags or BigQuery column-level policy tags), propagate tags through transformations, and enforce masking at query time for non-privileged roles. For GDPR right-to-erasure: either delete the raw partition and re-derive, or use Iceberg's Row-Level Deletes (merge-on-read) with periodic compaction.

Data Engineer

Choose your partitioning strategy before launch — repartitioning a petabyte table later is expensive. Partition by the column most frequently in WHERE clauses (usually date + a high-cardinality key). Never partition by a boolean or low-cardinality column — you'll have two giant partitions and Spark won't skip anything. Use Z-ordering (Iceberg/Delta) to cluster within partitions for point lookups on user_id.

ML / AI Engineer

Feature pipelines have unique requirements: point-in-time correct joins (no data leakage), feature freshness SLAs (stale features degrade model performance), and reproducibility (same data for training and serving). Use a feature store (Feast, Tecton, Vertex AI Feature Store) to centralize feature computation. Stream features require exactly-once writes — use Flink + Kafka + Redis for sub-second feature freshness in online serving.

Backend Engineer

Operational databases are not analytics engines — avoid complex analytics queries on Postgres/MySQL in production. Instead, use CDC (Debezium → Kafka) to stream changes to the lakehouse in near real-time. Use the read replica only as a short-term bridge, not a permanent analytics solution. Design your source schemas with analytics in mind: include created_at and updated_at on every table — these are mandatory for incremental ingestion.

Frontend / Product Engineer

Dashboard users confuse freshness with correctness. A daily batch pipeline that says "data as of yesterday 4AM" is not wrong — it just needs to be clearly labeled. Work with the data team to add a data freshness indicator to dashboards. If business users demand real-time, quantify the cost: a streaming pipeline replacing a $50/month batch job typically costs $500–2000/month in always-on infrastructure. Make the tradeoff visible before committing.

SRE / Reliability Engineer

Define SLOs for pipeline freshness: "fct_daily_revenue must be available by 6AM UTC with ≤1% row count deviation from yesterday." Alert on freshness lag (Airflow SLA missed) and data quality (row count anomaly). Set up dead-man's switch alerts: if no successful run in 26 hours, page on-call. Budget for reprocessing capacity — keep 20% headroom so backfills don't starve production jobs during incident recovery.

Real Applied Problems

Problem 1: Real-Time Fraud Detection Pipeline

Process 500K payment events/second, detect fraud within 200ms, 99.9% uptime requirement

Architecture: Flink stateful stream processing with keyed state per user.

Payment Service │ Kafka topic: payments (100 partitions) ▼ Flink Fraud Detection Job │ ├─ Key by user_id ├─ ValueState: last_5_txn_amounts, last_country, velocity_count │ ├─ Rule Engine (stateless): │ velocity: >5 txn in 60s → SUSPICIOUS │ geo_jump: country changed in <10min → SUSPICIOUS │ amount: >3σ from user 30-day avg → SUSPICIOUS │ └─ ML Score (Flink async I/O → model serving endpoint) │ latency: p99 <50ms via async I/O ▼ Decision Stream (APPROVE / DECLINE / REVIEW) │ ├──▶ Payment Processor (approve/decline) └──▶ Review Queue (Kafka → fraud analyst UI) 
from pyflink.datastream import StreamExecutionEnvironment, KeyedStream
from pyflink.datastream.state import ValueStateDescriptor, ListStateDescriptor
from pyflink.common import Types
import asyncio, aiohttp

class FraudDetector(KeyedProcessFunction):
    """Stateful per-user fraud detection with 60s velocity window."""

    def open(self, ctx):
        # Per-user state — stored in RocksDB for large state
        self.velocity_count = self.runtime_context.get_state(
            ValueStateDescriptor("velocity_60s", Types.INT())
        )
        self.last_country = self.runtime_context.get_state(
            ValueStateDescriptor("last_country", Types.STRING())
        )
        self.last_txn_ts = self.runtime_context.get_state(
            ValueStateDescriptor("last_txn_ts", Types.LONG())
        )
        self.running_avg = self.runtime_context.get_state(
            ValueStateDescriptor("avg_amount", Types.FLOAT())
        )

    def process_element(self, event, ctx):
        now = ctx.timestamp()
        velocity = self.velocity_count.value() or 0
        last_ts = self.last_txn_ts.value() or 0
        avg_amt = self.running_avg.value() or event["amount"]

        flags = []

        # Velocity: decay counter if >60s since last txn
        if now - last_ts > 60_000:
            velocity = 0
        velocity += 1
        if velocity > 5:
            flags.append("VELOCITY_EXCEEDED")

        # Geo jump
        if self.last_country.value() and \
           self.last_country.value() != event["country"] and \
           (now - last_ts) < 600_000:   # 10 min
            flags.append("GEO_JUMP")

        # Amount anomaly: simple z-score
        z_score = abs(event["amount"] - avg_amt) / (avg_amt * 0.3 + 1)
        if z_score > 3:
            flags.append("AMOUNT_ANOMALY")

        # Update state
        self.velocity_count.update(velocity)
        self.last_country.update(event["country"])
        self.last_txn_ts.update(now)
        # EMA of amount
        self.running_avg.update(0.95 * avg_amt + 0.05 * event["amount"])

        # Register cleanup timer (TTL after 24h of inactivity)
        ctx.timer_service().register_event_time_timer(now + 86_400_000)

        event["fraud_flags"] = flags
        event["decision"] = "REVIEW" if flags else "APPROVE"
        yield event

    def on_timer(self, timestamp, ctx):
        # Clean up state for inactive users
        self.velocity_count.clear()
        self.last_country.clear()
        self.last_txn_ts.clear()

# Run as a long-running streaming job

# 1. Define Kafka CDC source (Debezium JSON format)
CREATE TABLE kafka_users_cdc (
    op          STRING,       -- 'c' create, 'u' update, 'd' delete, 'r' read
    before      ROW<user_id BIGINT, email STRING, plan STRING, updated_at TIMESTAMP>,
    after       ROW<user_id BIGINT, email STRING, plan STRING, updated_at TIMESTAMP>,
    source      ROW<db STRING, table STRING, lsn BIGINT>,
    ts_ms       BIGINT,
    PRIMARY KEY (source.lsn) NOT ENFORCED
) WITH (
    'connector'                     = 'kafka',
    'topic'                         = 'pg.public.users',
    'properties.bootstrap.servers'  = 'kafka:9092',
    'properties.group.id'           = 'flink-iceberg-sink',
    'format'                        = 'debezium-json',
    'scan.startup.mode'             = 'earliest-offset'
);

-- 2. Define Iceberg sink table
CREATE TABLE iceberg_catalog.bronze.users (
    user_id     BIGINT,
    email       STRING,
    plan        STRING,
    updated_at  TIMESTAMP(6),
    _cdc_op     STRING,       -- track operation type
    _ingested_at TIMESTAMP(6) NOT ENFORCED,
    PRIMARY KEY (user_id) NOT ENFORCED
) WITH (
    'connector'    = 'iceberg',
    'catalog-name' = 'iceberg_catalog',
    'database-name'= 'bronze',
    'table-name'   = 'users',
    'write.upsert.enabled' = 'true'   -- MERGE mode
);

-- 3. Streaming INSERT: flatten CDC events
INSERT INTO iceberg_catalog.bronze.users
SELECT
    COALESCE(after.user_id, before.user_id) AS user_id,
    after.email,
    after.plan,
    after.updated_at,
    op AS _cdc_op,
    TO_TIMESTAMP_LTZ(ts_ms, 3) AS _ingested_at
FROM kafka_users_cdc
WHERE op IN ('c', 'u', 'r');  -- ignore deletes (soft-delete in warehouse)

Problem 3: ML Feature Pipeline with Point-in-Time Correctness

Compute user features for a fraud model — training data must reflect what the model would have seen at prediction time, not future data

The training data leakage problem: If you naively join user features as they are today with historical labels, your model trains on information that wasn't available at prediction time (future leakage). This creates optimistic training metrics that don't hold in production.

Wrong (leaky join): label_ts=2024-01-10 joined with feature computed_at=2024-01-15 ← LEAK Correct (point-in-time join): label_ts=2024-01-10 joined with feature.as_of(2024-01-10) ← SAFE Implementation: ┌──────────────────────────────────────────────────────────┐ │ Feature Store (Feast / Tecton) │ │ │ │ Historical feature values stored per (entity, ts) │ │ │ │ get_historical_features( │ │ entity_df = label_df[["user_id", "event_timestamp"]], │ │ features = ["user_stats:txn_count_7d", │ │ "user_stats:avg_amount_30d", │ │ "device:is_new_device"] │ │ ) → snapshot of features AT each event_timestamp │ └──────────────────────────────────────────────────────────┘ 
import pandas as pd
from feast import FeatureStore

store = FeatureStore(repo_path="feature_repo/")

# Label dataset: fraud labels with the timestamp of the event
labels = pd.read_parquet("s3://ml-data/fraud_labels_2024.parquet")
# Columns: user_id, event_timestamp, is_fraud

# Point-in-time correct feature retrieval
# Feast looks up the latest feature value BEFORE event_timestamp for each row
training_df = store.get_historical_features(
    entity_df=labels,
    features=[
        "user_transaction_stats:txn_count_7d",
        "user_transaction_stats:avg_amount_30d",
        "user_transaction_stats:unique_merchants_14d",
        "user_device_features:is_new_device",
        "user_device_features:device_count_30d",
        "user_geo_features:countries_visited_7d",
    ]
).to_df()

# No data leakage: features are as they were at event_timestamp
print(training_df.head())

Anti-Patterns

1. Overusing Streaming

Building a Flink job when a nightly Spark batch job would satisfy requirements. Streaming pipelines are 10× harder to operate and 5× more expensive. Only stream when latency truly requires it.

2. SELECT * From Kafka

Reading all fields from wide Kafka messages when only 3 are needed. Deserializes the entire payload on every event. Project only required fields at the source operator to reduce GC pressure and memory.

3. No Partitioning Strategy

Writing all data into a single Parquet file or unpartitioned table. Downstream queries scan 100% of data for any filter. Always partition by the most common query filter (date, region). Profile before writing.

4. Tight Coupling to Source Schema

Pipeline that breaks when a source column is renamed. Use schema registry with BACKWARD compatibility checks. Add integration tests that validate pipeline against real source data in staging.

5. No Idempotency

Pipeline that produces duplicate rows on retry. Every write must be idempotent: use MERGE/upsert (Iceberg), deduplication by message ID, or INSERT OVERWRITE for partition-level idempotency.

6. Skipping Data Quality Checks

"We'll add tests later." Bad data in a warehouse corrupts months of downstream models and dashboards. Add basic not_null, unique, range checks on every pipeline output before it reaches consumers.

7. Fan-out Without Back-Pressure

One pipeline feeding 20 downstream consumers directly. When one consumer slows down, it backs up the entire pipeline. Use Kafka as the fan-out buffer — each consumer maintains its own offset.

8. Training Data Leakage

Joining ML training labels with "current" feature values rather than features as-of the label timestamp. Models appear highly accurate in training but fail in production. Always use point-in-time correct joins.

Interview Tips

Start with freshness requirements

Before designing any pipeline, ask: "How stale can the data be?" This immediately determines batch vs stream and budget. A 1-hour SLA is 100× cheaper than a 1-second SLA — make the interviewer confirm which they actually need.

Name the layers explicitly

Use Bronze/Silver/Gold (or Raw/Cleaned/Business) language. Interviewers at data-heavy companies (Meta, Airbnb, Lyft) expect you to know Medallion architecture. Describe what changes at each layer and why.

Address the late data problem

Every stream processing question should mention watermarks and late data handling. What's your max lateness tolerance? What happens to events that arrive after the watermark — drop, side output, or allowed lateness? Shows you understand real-world stream complexity.

Mention exactly-once semantics

Explain: at-most-once (simplest, data loss possible), at-least-once (duplicates possible, handle with idempotent writes), exactly-once (most expensive, Flink checkpointing + transactional sink). Production systems usually target at-least-once + idempotent writes rather than true exactly-once.

Quantify the schema evolution risk

Describe backward vs forward compatibility. Say: "I'd put all Kafka topics behind Schema Registry with BACKWARD_TRANSITIVE compatibility — producers can add nullable fields, but removing or renaming fields requires a breaking change process." This signals production experience.

Always mention monitoring

A pipeline without observability is a black box. Mention: consumer lag alerts (Kafka), freshness SLO checks (Airflow SLA), row count anomaly detection, data quality scores trending. Ask: "What's our SLO for pipeline freshness and who gets paged when it misses?"

Clarifications
+
Batch vs Stream
"Bounded" data has an end (a file, yesterday's logs). "Unbounded" data is a live stream with no end. Watermarks tell the engine "time has advanced this far" — without them, you'd wait forever to close a time window. Streaming is ~10× more expensive to operate than batch.
+
Lambda vs Kappa
Lambda ≠ AWS Lambda. Named after lambda calculus (combining two functions). The problem: you implement the same business logic twice — once in Spark batch, once in Flink stream. Kappa simplifies to one stream job that replays Kafka from offset 0 for historical reprocessing.
+
ETL vs ELT
ETL transforms before loading (separate compute cluster). ELT loads raw data first, transforms inside the warehouse using SQL. ELT won because cloud warehouses (BigQuery, Snowflake) have cheap compute. dbt = "data build tool" — just SQL SELECT statements materialized as tables.
+
Apache Spark
Spark's breakthrough: keep intermediate data in memory between processing steps instead of writing to disk (unlike Hadoop MapReduce). A "shuffle" = data moving across machines for GROUP BY or JOIN. Shuffles are the #1 bottleneck — they send data over the network.
+
Apache Flink
Flink processes one event at a time, not micro-batches. "Windows" group events by time (all purchases in 10 minutes). "State" is per-key memory between events (running count per user). "Checkpoint" = save state to S3 so recovery restarts without reprocessing all history from scratch.
+
Data Lakehouse
A lakehouse = data lake (cheap S3 storage) + warehouse features (ACID transactions, time travel, schema enforcement). Parquet is a columnar file format — reads only the columns you need. Iceberg/Delta add a metadata layer so S3 files behave like a proper database table.
+
Orchestration & DAGs
DAG = Directed Acyclic Graph — a task dependency map with no loops: "task B runs after task A." Airflow doesn't run your computation; it schedules and monitors it. Backfill = re-running past dates after adding a new pipeline that needs years of history computed.
+
Data Lineage
Data lineage = the family tree of a dashboard number. "This metric → this warehouse table → built from these raw tables → loaded from this database." Without lineage, when a number looks wrong you can't trace where it came from. The data equivalent of a stack trace.
