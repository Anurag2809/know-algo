When to Go Async

Async processing trades immediacy for decoupling and resilience. Not every operation benefits from it — but certain patterns make synchronous calls actively harmful.

SYNC vs ASYNC DECISION FLOWCHART ────────────────────────────────────────────────────────── Does the client need the result before it can proceed? │ ├── YES → Synchronous (gRPC / REST) │ "Create order and return order_id to client" │ └── NO → Can be async. Now ask: │ ├── Is the work time-sensitive? │ ├── YES (SLA <5s) → Task queue with fast workers (Celery, SQS) │ └── NO → Batch processing acceptable │ ├── Do multiple services need this event? │ ├── YES → Pub/Sub (Kafka topic, SNS fan-out) │ └── NO → Point-to-point queue (SQS, RabbitMQ) │ ├── Do you need event replay / historical reads? │ ├── YES → Event stream (Kafka, Kinesis — log retention) │ └── NO → Message queue (delete-on-consume, SQS/RabbitMQ) │ └── Do you need ordered processing? ├── YES → Kafka (partition-level ordering) └── NO → SQS standard (no ordering, higher throughput) ────────────────────────────────────────────────────────── PRIME USE CASES FOR ASYNC: ✓ Email / notification sending (user doesn't wait for email) ✓ Image / video processing (encode after upload acknowledged) ✓ Charging a payment (confirm order, charge asynchronously) ✓ Search index updates (ES reindex after DB write) ✓ Analytics event ingestion (never block on analytics) ✓ ML inference jobs (batch scoring overnight) ✓ Cross-service fan-out (order.created → 5 downstream services) ✗ Auth checks (must be synchronous — every request needs it) ✗ Inventory reservation before order confirmation (need result) ✗ Payment capture when user is waiting on checkout page
Core Distinction

Message Queue vs Event Stream

These two patterns solve different problems. Confusing them is the root cause of most async architecture mistakes.

MESSAGE QUEUE — work distribution ────────────────────────────────────────────────────────── Producer Queue Consumer Pool │ │ │ ├── msg A ────────►│ ┌─────┤ Worker 1 ├── msg B ────────►│ │ │ processes msg A ├── msg C ────────►│ │ │ deletes msg A from queue │ │ └─────┤ Worker 2 │ │ processes msg B └─────┤ Worker 3 │ processes msg C Key properties: • Each message consumed by exactly one consumer • Message deleted after successful processing (ack) • Consumer pool scales horizontally to drain queue • No replay — consumed messages are gone • Ordering not guaranteed (SQS standard) Use when: Task distribution, job queues, work parallelism Tools: SQS, RabbitMQ, Redis Lists (LPUSH/BRPOP) ────────────────────────────────────────────────────────── EVENT STREAM — event log ────────────────────────────────────────────────────────── Producer Topic/Partition (append-only log) │ │ ├── event A ──────►│ offset 0: order.created {id:1} ├── event B ──────►│ offset 1: order.created {id:2} ├── event C ──────►│ offset 2: payment.captured {id:1} Consumer groups (each gets all events independently): Shipping Service → reads from offset 0, processes all 3 events Inventory Service → reads from offset 0, processes all 3 events Analytics Service → reads from offset 0, processes all 3 events Key properties: • Each consumer group reads all events independently • Events retained for configurable period (hours to forever) • Replay: new consumer can read from offset 0 to replay history • Ordered within partition (not across partitions) • Consumers track own offset (commit on success) Use when: Audit log, fan-out to multiple consumers, replay, CDC Tools: Kafka, AWS Kinesis, Google Cloud Pub/Sub
Deep Dive

Apache Kafka

Kafka is a distributed, durable, ordered log. It's not a message queue — it's a commit log that multiple consumers can independently read. This distinction changes everything about how you design with it.

Kafka Architecture

KAFKA INTERNALS ────────────────────────────────────────────────────────── Topic: orders (4 partitions, replication factor 3) Partition 0: [msg0][msg1][msg4][msg7]... → Broker 1 (leader) → Broker 2 (follower) → Broker 3 (follower) Partition 1: [msg2][msg5]... → Broker 2 (leader) → Broker 3 (follower) → Broker 1 (follower) Partitioning key: Producer sends {key: "order_123", value: {...}} Kafka: partition = hash("order_123") % 4 → always same partition Guarantee: All events for the same order_id are in the same partition Guarantee: Partition is consumed in-order by one consumer in the group ────────────────────────────────────────────────────────── CONSUMER GROUP — parallel processing Topic: orders (4 partitions) Consumer Group: shipping-service (4 consumers) Consumer 1 ──► Partition 0 Consumer 2 ──► Partition 1 Consumer 3 ──► Partition 2 Consumer 4 ──► Partition 3 Scaling rule: max parallelism = number of partitions If consumers > partitions → some consumers idle (set partitions high) If consumers < partitions → one consumer handles multiple partitions ────────────────────────────────────────────────────────── RETENTION & REPLAY Default retention: 7 days (configurable: hours to permanent) New consumer group: start from beginning → processes all 7 days of events Existing group: resumes from last committed offset Use case: Add new analytics service → reprocess last 30 days of events Bug in consumer → fix bug, reset offset → reprocess Disaster recovery → replay all events to rebuild state

Producer Guarantees: acks Setting

PRODUCER ACKNOWLEDGMENT LEVELS ────────────────────────────────────────────────────────── acks=0 (fire and forget): Producer sends, doesn't wait for any ack Fastest — maximum throughput Risk: message lost if broker crashes before write Use for: high-volume metrics, analytics (some loss acceptable) acks=1 (leader ack): Leader broker writes to disk, acks to producer Medium — good balance of throughput and safety Risk: message lost if leader crashes BEFORE followers replicate Use for: most general-purpose use cases acks=all (−1) (full quorum ack): Leader + all in-sync replicas write, then ack Strongest — no message loss as long as one ISR survives Latency: adds follower replication time to every write Use for: financial events, user actions requiring guaranteed delivery Pair with: min.insync.replicas = 2 → Kafka rejects write if fewer than 2 replicas are in-sync → Prevents data loss even if one broker fails during write

Kafka Consumer: Offset Management

from confluent_kafka import Consumer, KafkaError

consumer = Consumer({
    'bootstrap.servers': 'kafka-broker:9092',
    'group.id':          'shipping-service-v1',
    'auto.offset.reset': 'earliest',          # start from beginning if no offset saved
    'enable.auto.commit': False,              # CRITICAL: manual commit for exactly-once
})

consumer.subscribe(['orders'])

while True:
    msg = consumer.poll(timeout=1.0)
    if msg is None:
        continue
    if msg.error():
        # Handle partition EOF, broker errors, etc.
        handle_kafka_error(msg.error())
        continue

    try:
        order = json.loads(msg.value())
        # Process BEFORE committing offset
        create_shipment(order)

        # Commit AFTER successful processing
        # If we crash here, this message will be reprocessed — idempotency required
        consumer.commit(asynchronous=False)

    except Exception as e:
        # Do NOT commit — message will be redelivered after rebalance
        log.error(f"Failed to process {msg.offset()}: {e}")
        # Dead letter queue or retry logic here
The Commit Placement Problem

Commit BEFORE processing → at-most-once (message lost on crash). Commit AFTER processing → at-least-once (message reprocessed on crash). There is no "exactly-once" without idempotent consumers (checking if message was already processed). The standard choice is at-least-once with idempotent consumers — simplest to implement correctly.

Task Queue Pattern

SQS & Task Queues

Amazon SQS and similar task queue systems (Celery + Redis/RabbitMQ) are designed for work distribution, not event streaming. The message is deleted after consumption — there's no replay, no consumer groups, just workers competing for tasks.

SQS VISIBILITY TIMEOUT — how at-least-once works ────────────────────────────────────────────────────────── Worker calls ReceiveMessage │ SQS returns message, sets visibility timeout (30s default) │ Message is HIDDEN from other workers (not deleted) │ ├── Worker processes successfully │ Worker calls DeleteMessage │ Message permanently deleted ✓ │ └── Worker crashes / timeout expires Message becomes VISIBLE again after timeout Another worker picks it up → reprocessed Visibility timeout tuning: Set to 2× your max processing time If job takes 60s max → visibility timeout = 120s Too short → multiple workers process same message Too long → failed messages take a long time to retry ────────────────────────────────────────────────────────── DEAD LETTER QUEUE (DLQ) — handling poison messages Message processed, fails, requeued. Message processed again, fails again. (maxReceiveCount = 5) After 5 failures → message moved to Dead Letter Queue DLQ benefits: • Failed messages don't block the main queue indefinitely • Inspect DLQ to debug why messages are failing • Replay from DLQ after bug fix (SQS DLQ redrive) ────────────────────────────────────────────────────────── SQS STANDARD vs FIFO Standard: unlimited throughput, at-least-once, no ordering guarantee Best for: most use cases, parallelizable work FIFO: exactly-once, strict ordering per MessageGroupId Max 3000 msg/s with batching (300/s per group) Best for: financial transactions, sequential job steps

Celery Task Queue Pattern

# tasks.py — Celery with Redis broker
from celery import Celery
from celery.utils.log import get_task_logger

app = Celery('tasks', broker='redis://localhost:6379/0',
                       backend='redis://localhost:6379/1')

app.conf.task_routes = {
    'tasks.send_email':    {'queue': 'email'},
    'tasks.resize_image':  {'queue': 'image_processing'},
    'tasks.charge_payment': {'queue': 'payments'},  # dedicated high-priority queue
}

logger = get_task_logger(__name__)

@app.task(bind=True, max_retries=3, default_retry_delay=60)
def send_email(self, user_id, template_id, context):
    try:
        user = fetch_user(user_id)
        email_service.send(user.email, template_id, context)
    except EmailServiceTemporaryError as exc:
        # Exponential backoff: 60s, 120s, 240s
        raise self.retry(exc=exc, countdown=60 * (2 ** self.request.retries))
    except EmailServicePermanentError:
        # Don't retry — log and alert
        logger.error(f"Permanent email failure for user {user_id}")
        send_alert(f"Email permanently failed: user {user_id}")

# Caller — fire and forget:
send_email.delay(user_id=42, template_id='welcome', context={'name': 'Alice'})

# Caller — chain (sequential tasks):
from celery import chain
chain(resize_image.s(image_id), generate_thumbnail.s(), update_cdn.s()).delay()
Fan-out Pattern

Pub/Sub Architecture

Publish/Subscribe decouples event producers from consumers completely. Producers don't know who subscribes. New consumers can be added without touching producer code. This is the core pattern for event-driven microservices.

PUB/SUB FAN-OUT — one event, many consumers ────────────────────────────────────────────────────────── Order Service │ publishes: order.created {order_id: "ord_123", user_id: 42, total: 99.99} ▼ Kafka Topic: order.created │ (no knowledge of who subscribes) │ ├──► Inventory Service reserves stock ├──► Shipping Service creates shipment ├──► Email Service sends confirmation email ├──► Fraud Service runs fraud analysis └──► Analytics Service records conversion event Adding a new consumer (Loyalty Points Service): → Subscribe to order.created topic → Deploy Loyalty Points Service → Order Service untouched, no downtime → New service can replay history from offset 0 ────────────────────────────────────────────────────────── AWS SNS + SQS FAN-OUT (serverless pattern) Order Service │ SNS Publish: order.created ▼ [ SNS Topic ] │ fan-out to subscribed SQS queues │ ├──► SQS Queue: inventory → Lambda or ECS worker ├──► SQS Queue: shipping → Lambda or ECS worker └──► SQS Queue: email → Lambda Benefits: • SQS provides buffering + retry per consumer independently • Consumer A failing doesn't affect consumer B • Each queue has its own DLQ • Lambda auto-scales per queue depth
Core Guarantee

Delivery Semantics

THREE DELIVERY GUARANTEES ────────────────────────────────────────────────────────── AT-MOST-ONCE: Ack first, process after. If processing crashes after ack → message LOST. Benefit: No duplicates, low overhead Use for: High-volume metrics where losing 0.1% is acceptable AT-LEAST-ONCE (standard choice): Process first, ack after. If crash after process but before ack → redelivered → DUPLICATE. Benefit: No message loss Requirement: Consumers MUST be idempotent Use for: 99% of production async systems EXACTLY-ONCE: Process and ack atomically. Kafka: Transactional API + idempotent producer SQS FIFO: MessageDeduplicationId within 5-min dedup window Complexity: High, performance overhead Use for: Financial transactions, billing events ────────────────────────────────────────────────────────── IDEMPOTENCY IMPLEMENTATION (at-least-once consumers) Pattern 1: Unique constraint in DB DB: INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT (event_id) DO NOTHING If duplicate: INSERT fails silently → skip processing Pattern 2: Check-then-act IF event_id IN processed_events_cache THEN return ELSE process AND record event_id Pattern 3: Idempotent operations "Set inventory to 50" is idempotent (applied twice = same result) "Decrement inventory by 1" is NOT (applied twice = wrong result) Design operations to be inherently idempotent where possible
Flow Control

Backpressure

Backpressure is how a slow consumer tells a fast producer to slow down. Without it, producers overwhelm consumers, queues grow unboundedly, and the system eventually crashes with OOM errors or timeout cascades.

BACKPRESSURE STRATEGIES ────────────────────────────────────────────────────────── 1. BOUNDED QUEUES — reject when full Queue max depth: 10,000 messages Producer tries to enqueue when queue is full → Reject: producer receives error, slows down or retries → Never infinite memory growth 2. CONSUMER LAG MONITORING — scale consumers dynamically Kafka consumer lag = (latest offset) - (consumer current offset) Alert if lag > 10,000 messages Auto-scale: add consumer replicas when lag exceeds threshold Scale-in: remove consumers when lag < 1,000 for 10 min 3. RATE LIMITING PRODUCERS Producer checks queue depth before sending If queue_depth / queue_max > 0.8 → producer pauses 500ms Reactive backpressure vs proactive backpressure 4. LOAD SHEDDING Drop lowest-priority messages when overloaded Example: analytics events dropped, payment events never dropped Requires message priority classification upfront 5. TOKEN BUCKET at queue ingestion Queue accepts max 5000 msg/s from a single producer Burst allowed up to bucket size, then throttle Smooth producer bursts, protect consumers ────────────────────────────────────────────────────────── CONSUMER LAG SLO EXAMPLE SLO: email notifications delivered within 30s of event Average event processing: 10ms/message Consumer throughput: 100 msg/s If lag = 50,000 messages: Time to clear lag: 50,000 / 100 = 500 seconds → SLO violated Solution: scale consumers until throughput > producer rate + drain rate
Distributed Transactions

Saga Pattern

In microservices, you can't use a database transaction that spans multiple services. The saga pattern achieves distributed consistency without distributed transactions by decomposing a business flow into a sequence of local transactions, each with a compensating action on failure.

SAGA — E-COMMERCE ORDER FLOW ────────────────────────────────────────────────────────── Happy path: Step 1: Order Service creates order (status: PENDING) Step 2: Inventory Service reserves stock (status: RESERVED) Step 3: Payment Service charges card (status: CHARGED) Step 4: Shipping Service creates shipment (status: SHIPPED) Step 5: Order Service marks order CONFIRMED Failure at Step 3 (payment declined): Step 3 fails → trigger compensating transactions in reverse: Step 2 rollback: Inventory Service releases reservation Step 1 rollback: Order Service marks order FAILED ────────────────────────────────────────────────────────── TWO SAGA IMPLEMENTATIONS Choreography (event-driven, no central coordinator): Each service publishes success/failure events Other services react to events autonomously OrderService → "order.created" → InventoryService InventoryService → "stock.reserved" → PaymentService PaymentService → "payment.failed" → InventoryService ("release.stock") Pros: Decoupled, no SPOF Cons: Hard to track overall saga state, difficult to debug Orchestration (central saga orchestrator): Saga Orchestrator calls each service in sequence Orchestrator tracks state, calls compensations on failure SagaOrchestrator → call InventoryService.reserve() → call PaymentService.charge() → if fail: call InventoryService.release() → call ShippingService.ship() Pros: Single place to see full saga state, easier debugging Cons: Orchestrator becomes coupling point Production recommendation: Orchestration for <5 steps, choreography for fan-out
Reliability Pattern

Transactional Outbox

The hardest problem in async systems: how do you atomically save to your database AND publish an event to Kafka? If you do them separately, you can save to DB but fail to publish the event — or publish the event but have the DB write rollback. The transactional outbox solves this without two-phase commit.

THE DUAL-WRITE PROBLEM ────────────────────────────────────────────────────────── WRONG approach: BEGIN TRANSACTION INSERT INTO orders (...) COMMIT kafka.publish("order.created", ...) ← crash here → event lost! OR: kafka.publish("order.created", ...) ← if DB transaction rolls back → ghost event! BEGIN TRANSACTION INSERT INTO orders (...) COMMIT CORRECT: Transactional Outbox Pattern ────────────────────────────────────────────────────────── BEGIN TRANSACTION INSERT INTO orders (id, status, ...) VALUES (...) INSERT INTO outbox (event_type, payload, status) VALUES ('order.created', '{...}', 'pending') COMMIT ← atomic! Either both succeed or both rollback [ Outbox Worker ] (separate process): SELECT * FROM outbox WHERE status = 'pending' LIMIT 100 FOR each event: kafka.publish(event.event_type, event.payload) UPDATE outbox SET status='published' WHERE id=event.id ────────────────────────────────────────────────────────── DEBEZIUM (CDC-based outbox): Instead of a worker, use Debezium to watch the outbox table's WAL Debezium reads Postgres WAL → publishes to Kafka automatically Zero application code for outbox polling → simpler, more reliable Production standard for high-volume event publishing
Decision Guide

Tool Selection

Apache Kafka
  • Best for: Event streaming, fan-out to multiple consumers, audit log, CDC, replay
  • Throughput: Millions of messages/second
  • Retention: Days to forever
  • Ordering: Per partition
  • Managed: Confluent Cloud, MSK (AWS), Aiven
  • Avoid when: Simple task queue (overkill), need strict routing per message
Amazon SQS
  • Best for: Task queues, work distribution, serverless Lambda triggers
  • Throughput: Unlimited (standard), 3000/s (FIFO)
  • Retention: Up to 14 days
  • Ordering: FIFO only with SQS FIFO
  • Cost: Pay per message, serverless
  • Avoid when: Fan-out to many consumers (SNS+SQS combo), replay needed
RabbitMQ
  • Best for: Complex routing (topic, fanout, direct exchanges), RPC pattern
  • Throughput: Hundreds of thousands/second
  • Routing: Flexible exchange types
  • Protocol: AMQP (richer than HTTP-based queues)
  • Avoid when: Need replay, high throughput >1M/s
Redis Streams / Lists
  • Best for: Simple queues, low-latency task dispatch, real-time pub/sub
  • Throughput: Very high (in-memory)
  • Streams: Consumer groups, persistent log (unlike Redis Lists)
  • Pub/Sub: Ephemeral (not persisted) — fan-out only
  • Avoid when: Need durable multi-consumer streaming (use Kafka)
9 Lenses

How Each Team Thinks About Async

🏗️ Infrastructure Engineer

Kafka clusters are complex to operate. Broker sizing, disk throughput, JVM heap tuning, Zookeeper (now KRaft) quorum, partition reassignment during broker replacement — these are non-trivial operational concerns. We almost always recommend Confluent Cloud or MSK over self-managed Kafka unless there's a compelling cost or compliance reason. The managed service cost is worth it in engineering time saved.

Consumer lag dashboards are our primary operational signal for async systems. We set alerts: p95 consumer lag under 1 minute for critical queues, under 5 minutes for non-critical. When lag grows faster than it's drained, something is wrong — either a processing bottleneck, a poison message causing retry loops, or a consumer crash. We don't wait for users to report problems; lag is the leading indicator.

Kafka partition count is a one-way door. You can increase partition count, but partitions cannot be decreased without recreating the topic (which means losing existing messages or migrating them). We set initial partition counts conservatively high (e.g., 24) to allow future consumer scaling without topology changes.

🌐 Network Engineer

Kafka's inter-broker replication traffic is substantial. For a 3-replica Kafka cluster receiving 100 MB/s of messages, inter-broker replication generates another 200 MB/s (each message replicated to 2 followers). We size network interfaces accordingly and place Kafka brokers on dedicated network segments with guaranteed bandwidth, separate from application traffic.

Consumer batch fetching (fetch.min.bytes, fetch.max.wait.ms) is a network efficiency tuning knob. Small batch sizes mean many small TCP segments — lots of overhead. Large batch sizes mean higher latency but fewer round trips. We tune this based on the latency SLO of each consumer: email notifications (SLO: 30s) can batch aggressively, real-time fraud detection (SLO: 200ms) cannot.

Cross-region Kafka replication (MirrorMaker 2 or Confluent Replication) adds meaningful latency and bandwidth cost. We model this explicitly: 10 MB/s of events × cross-region replication = ~$300/month in data transfer costs. We help teams decide whether they need true multi-region Kafka or whether regional Kafka clusters per region with eventual consistency is sufficient.

⚙️ Platform Engineer

We provide a "queue as a service" abstraction. Teams declare a queue in a config file, our platform creates the SQS queue + DLQ + IAM policy + Datadog dashboard + PagerDuty alert. They don't touch AWS console. This standardization means every queue in the company has a DLQ, monitoring, and alerting — not just the ones where a senior engineer remembered to set it up.

Schema registry is the platform artifact that enables async evolution. When teams publish Kafka events with Avro schemas registered in Confluent Schema Registry, adding a new field is backward-compatible (consumers that don't know the new field ignore it). Removing a required field is a breaking change and triggers a schema compatibility check failure in CI. This is the async equivalent of API contract testing.

We've standardized on CloudEvents (CNCF spec) as our event envelope format. Every event has: specversion, type (e.g., "com.company.orders.created"), source, id, time, and data. The standard envelope means our event routing, tracing, and schema tooling works uniformly across all event types, regardless of which team published them.

🔐 Security / Cyber Engineer

Message queues are a data exfiltration vector. A compromised consumer service that subscribes to a Kafka topic with PII can silently exfiltrate all user data. We enforce topic-level ACLs: each service gets read access only to the topics it explicitly needs, and write access only to topics it owns. No wildcard subscriptions, no "subscribe to everything" service accounts.

Encryption in transit for Kafka is mandatory: TLS on all broker connections. Encryption at rest depends on the sensitivity of the data — payment events and PII events are on encrypted EBS volumes, high-volume analytics events can use unencrypted storage for cost. We document this per topic in our data classification registry.

Message replay is a security concern people overlook. If an attacker gains temporary access to a Kafka consumer and resets the consumer offset, they can replay all historical events — including password reset tokens, one-time payment links, or auth codes that were previously consumed. We treat Kafka ACLs with the same rigor as database access controls, not as a secondary concern.

📊 Data Engineer

Kafka is our data backbone. Every user action, system event, and service state change flows through Kafka, and we read it in real time for analytics, monitoring, and ML feature computation. The key pattern is: application writes to Kafka → Kafka Streams job aggregates → results land in the data warehouse or feature store. We're the team that cares most about event schema stability — a producer changing field names without notice breaks our pipelines silently.

Event time vs processing time is a subtle but critical distinction for streaming analytics. An IoT sensor event with timestamp "2024-01-15 10:00:00" might arrive at Kafka at 10:05 due to network delay. If we aggregate by event time (the actual occurrence), we need to handle late arrivals with a watermark (e.g., accept events up to 2 minutes late). If we aggregate by processing time (arrival time), the results are simpler but inaccurate for out-of-order data.

We love the transactional outbox pattern because it makes CDC-based pipelines fully reliable. Debezium watching the outbox table gives us exactly-once event delivery to Kafka, which means our downstream analytics are consistent with the source-of-truth database. We've been burned by producers that publish to Kafka and then fail the DB write — we spent days reconciling analytics that diverged from production data.

🤖 ML / AI Engineer

Real-time feature computation is an async processing problem. User behavior events (clicks, purchases, search queries) flow through Kafka → Flink/Kafka Streams → feature store (Redis). The online feature store serves these computed features at inference time. The challenge is keeping the real-time features aligned with the batch features used in training — feature skew is the silent killer of ML model performance in production.

Async batch inference is the workload we use Celery for. Users upload documents → we enqueue an "analyze_document" task → Celery workers with GPU access process the document in 30 seconds → result stored in DB, user notified via WebSocket. This decouples the user-facing API from the ML inference latency — users get immediate acknowledgment, wait for the async result.

Model training pipelines are large-scale async workflows. We use Airflow (workflow orchestrator) to schedule DAGs: extract training data from Kafka → preprocess → train → evaluate → if metrics pass: deploy. Each step is a Celery task or a Kubernetes job. The saga pattern applies here: if model evaluation fails, we trigger a rollback (keep the previous model serving). We never deploy a failing model synchronously during user traffic.

⚡ Backend Engineer

The most important async design decision is: what's the user contract when something fails? If I queue an email and the email service is down, does the user know? For most async work, the answer is: they get an acknowledgment that the action was accepted, and if it eventually fails permanently, they get a notification (email failed to send, payment couldn't process). Designing this failure notification path is as important as the happy path.

I treat every Celery task as potentially being run multiple times. Idempotency keys in the task payload, check-then-act patterns in the task body, and unique constraints in the database are my three layers of defense against duplicate processing. A task that's safe to run twice is a task I can deploy confidently knowing retries won't corrupt state.

The choice between Celery chains and Saga choreography depends on coupling tolerance. Celery chains are centralized — the caller defines the full workflow. Kafka choreography is decoupled — each service reacts independently to events. For internal workflows where I control all services, I prefer Celery chains (simpler, easier to trace). For cross-team event propagation where coupling is undesirable, Kafka choreography is cleaner.

🎨 Frontend Engineer

Async processing shifts the UX challenge from "how to show loading" to "how to show progress." When a user submits a form that triggers an async job (video upload, data export, background analysis), I can't show a spinner that resolves in 200ms — the job takes 30 seconds. My options: polling (GET /jobs/{id} every 2s), WebSocket push from job completion, or Server-Sent Events from the job service.

Job status pages are the standard UX pattern for long async operations. The user is redirected to /jobs/abc123 immediately after submission. That page polls or subscribes to the job status and shows a progress indicator. When the job completes, the page refreshes with results. This is how Netlify shows deploy status, how Vercel shows build logs — it's a proven pattern that users understand intuitively.

Optimistic UI for async operations requires careful thought about rollback. I can optimistically show "email sent!" and then handle the rare case where the async email fails by showing a retry button or notification. But for irreversible async operations (deduct credits, send payment), I don't optimistically show success — I wait for at least the queue acknowledgment before updating UI, and show a clear pending state.

📡 SRE / Site Reliability Engineer

Consumer lag is my primary SLO for async systems. For the order processing pipeline, my SLO is: 99th percentile order processing lag under 30 seconds. I alert at 2 minutes (warning) and 5 minutes (critical, page on-call). Consumer lag is a leading indicator — by the time users notice delayed notifications, lag has been growing for minutes. We catch it before users do.

Dead letter queue depth is my second alert. If DLQ messages are accumulating, a class of messages is consistently failing processing. This is different from consumer lag (which can indicate overload) — DLQ growth indicates bugs (poison messages, schema mismatches, downstream service failures). I alert at 100 DLQ messages and page at 1000. DLQ messages should be investigated within hours, not left to accumulate for days.

Kafka broker disk is the most operationally painful alert to deal with urgently. Kafka writes log segments to disk, and a broker with a full disk stops accepting writes and can cause partition leader elections. We set log retention based on disk capacity (not arbitrarily), monitor disk fill rate, and pre-provision at 60% utilization. Kafka disk filling up at 3 AM with 30 minutes to fix it is an incident we've lived and never want again.

Real Problems

Applied Async Design

Problem 01
Design the Notification System for a Social Platform (1B users)
Fan-out on Write Kafka Priority Queues Multi-Channel

Problem

A celebrity with 10M followers posts a photo. Each follower may need a push notification, email digest, and in-app notification. That's up to 30M notification events from a single action. At the same time, a regular user's post to 100 followers needs to notify in under 2 seconds (real-time feel).

Architecture

TWO-TIER NOTIFICATION SYSTEM User posts │ ▼ [ Post Service ] │ → Kafka: "post.created" {user_id, follower_count, post_id} ▼ [ Fan-out Service ] │ ├── Celebrity path (follower_count > 100k): │ → Write "notify user X about post Y" to Kafka: fan-out-jobs │ → Worker processes batch (500 followers per Kafka message) │ → Priority: LOW — eventual delivery acceptable (minutes) │ └── Regular user path (follower_count <= 100k): → Write all follower IDs directly to Kafka: notifications-high-priority → Priority: HIGH — deliver within 2 seconds [ Notification Router ] Reads from Kafka, routes to channel queues: ├── SQS: push-notifications → FCM / APNs workers ├── SQS: email-notifications → Email service workers └── SQS: in-app → WebSocket push to connected clients Backpressure: Push SLO 2s, Email SLO 30min — different worker pool sizes Deduplication: Redis SET per user per post (SETEX 1h) → skip if already notified

Fan-out Strategy

For users with <100K followers: fan-out on write (write to each follower's notification queue immediately). For celebrities with >100K followers: fan-out on read (store the post, generate notifications lazily as followers open their apps). The hybrid avoids generating 30M notifications instantly while maintaining real-time feel for regular users.

Decision Guide

Trade-offs Table

Decision Option A Option B When to Choose A
Kafka vs SQS Kafka SQS Multiple independent consumer groups need the same events, or replay is required. SQS when task distribution to a single consumer pool is the goal
At-least-once vs exactly-once At-least-once Exactly-once At-least-once + idempotent consumers covers 95% of cases with less complexity. Exactly-once for financial events where duplicates cause real money errors
Choreography vs Orchestration Orchestration Choreography Orchestration when you need to track saga state and debug easily (<5 steps, one team). Choreography for decoupled cross-team event propagation

What Not to Do

Anti-patterns

  • Non-idempotent consumers with at-least-once delivery If your consumer does "charge card X for amount Y" without idempotency checks, a redelivered message (due to consumer crash after processing but before commit) charges the user twice. Every at-least-once consumer must be idempotent. This is not optional — it's the foundational invariant of reliable async systems.
  • No Dead Letter Queue A message that consistently fails processing will be retried indefinitely, consuming worker capacity and hiding the underlying bug. Every queue needs a DLQ with a retry limit (maxReceiveCount). DLQ alerts tell you that a class of messages is broken — without them, the queue just silently grows and workers spin.
  • Unbounded queues without backpressure Accepting work faster than you process it means your queue grows indefinitely. A 10M-message backlog takes 3 hours to drain at 1000 msg/s. During those 3 hours, all messages are delayed, your SLO is violated, and the system is effectively down for that workload. Set max queue depths and reject producers when limits are hit.
  • Putting too much data in the message payload Kafka messages should be small (ideally <1MB). A message containing a full 10MB JSON document means 10MB per consumer replica, per message — this hits Kafka broker memory limits and increases replication overhead. Store the large data in S3 or the database and put only the ID in the message. Consumers fetch the full data when they process the event.
  • Dual-write (DB + Kafka) without transactional outbox Publishing to Kafka in application code after a DB commit is a race condition. If the process crashes between the commit and the publish, the event is lost forever. If you publish before the commit and the commit fails, you have a ghost event. Use the transactional outbox pattern — it's not optional if correctness matters.
  • Storing mutable business logic in event schemas A Kafka event schema published to 10 consumers is a public API. Renaming a field breaks all 10 consumers simultaneously. Events should be versioned (envelope with schema version), and consumers should be written to handle unknown fields gracefully. Never silently break consumers with a "quick schema fix."
  • Using a queue when you need a stream (or vice versa) Using SQS (queue) when you need multiple services to independently consume the same events means you need one SQS queue per consumer — which you then have to manually fan-out to. Use Kafka (stream) instead and let consumer groups handle fan-out naturally. Conversely, using Kafka for a simple task queue where one worker pool processes each message is overkill — SQS is simpler and cheaper.
  • Coupling Saga steps synchronously inside a transaction Calling Payment Service inside a database transaction while waiting for the HTTP response keeps the DB transaction open for the duration of the network call. A 500ms payment API call holds a DB lock for 500ms — at 1000 concurrent checkouts, this is table-lock disaster. Saga steps must be asynchronous and transactionless at the orchestration level.
Interview Strategy

Interview Tips for Async Questions

The Async Interview Signal

Any time you hear "user doesn't need to wait for this" or "this could spike 100×," that's your cue to propose an async pattern. Interviewers reward candidates who correctly identify when decoupling and queueing is necessary — not just those who can describe how Kafka works.

Tip 01

Lead with the distinction: queue vs stream. "Does each event need to be processed by one consumer, or multiple independent consumers?" One consumer = SQS. Multiple = Kafka. This single question shows you understand the paradigm difference.

Tip 02

Always mention the DLQ. Every queue discussion should include "and a Dead Letter Queue with an alert." This shows operational thinking — not just happy-path design but what happens when things fail.

Tip 03

Raise idempotency proactively. When proposing async processing, say "consumers must be idempotent because we use at-least-once delivery." Then briefly describe how: idempotency key in DB, check-then-act, or inherently idempotent operations.

Tip 04

For distributed transactions, name the Saga pattern. "We can't use a 2-phase commit across microservices, so we'd use a saga — either choreography via events or orchestration with a saga coordinator." Naming the pattern signals seniority.

Tip 05

Mention consumer lag as your SLO metric. "I'd set an SLO on consumer lag — say, p99 lag under 30 seconds — and alert when it exceeds 2 minutes." This shows you think about measuring async system health, not just building it.

Tip 06

For notification fan-out, discuss the celebrity problem. Distinguishing "fan-out on write for regular users" vs "fan-out on read for celebrities" shows you've thought about the extreme case. Interviewers asking about notification systems almost always probe this.

Clarifications
+
Message Broker vs Event Broker
Message broker (RabbitMQ, SQS): focus on routing messages to consumers. Message deleted after acknowledged. Good for task queues where each task is done by one worker. Event broker (Kafka, Kinesis): focus on durable, replayable event logs. Messages kept for days/weeks. Multiple consumer groups read independently. Good for event sourcing, audit logs, and feeding multiple systems.
+
Kafka Partitions & Consumer Groups
A Kafka topic is split into N partitions. Each partition is an ordered, append-only log on one broker. Consumer groups: a group of consumers that jointly consume all partitions — each partition is assigned to exactly one consumer in the group. Scale throughput: add partitions → add consumers. Rule: you can have AT MOST as many consumers as partitions (extra consumers are idle).
+
Kafka Offset & Acknowledgment
Offset = the position of a message in a partition (like line number in a file). Consumers track their offset to know what they've processed. acks=0: producer doesn't wait for broker confirmation (fastest, data loss possible). acks=1: leader broker acknowledges (fast, leader crash = data loss). acks=all: all replicas must acknowledge (slowest, strongest guarantee). acks=all is required for "at-least-once" delivery.
+
SQS: Visibility Timeout & DLQ
SQS Visibility Timeout: when a consumer receives a message, it's hidden from other consumers for N seconds (default 30). If the consumer doesn't delete it within that time, SQS makes it visible again (assumes the consumer crashed). Set timeout slightly longer than your max processing time. DLQ (Dead Letter Queue): if a message fails N times (maxReceiveCount), SQS moves it to the DLQ for investigation instead of endlessly retrying.
+
Idempotent Consumer
At-least-once delivery means duplicates happen. Your consumer MUST be idempotent — processing the same message twice must produce the same result as processing it once. Strategies: check if message ID was already processed (deduplication table), use upsert instead of insert (UPDATE ... ON CONFLICT), or design operations that are naturally idempotent (setting a value vs incrementing it).
+
Dead Letter Queue (DLQ)
A DLQ is a separate queue that receives messages that fail processing after N retries. Instead of infinite retries (which can block the main queue), failed messages are moved to the DLQ for human investigation. Every production queue should have a DLQ. Set up alerts for DLQ depth > 0. Common cause of DLQ accumulation: schema change in producer that breaks the consumer.
+
Fan-Out Pattern
Fan-out: one event triggers multiple independent consumers. Example: user signup → send welcome email + create billing record + set up analytics profile. Pub/sub: producer publishes to a topic; N consumers subscribe independently. In AWS: SNS (notification service) + SQS (one queue per subscriber). In Kafka: one topic, multiple consumer groups. Each consumer group reads all messages independently.
+
Consumer Lag
Consumer lag = how far behind the consumer is from the latest message in the queue/topic. In Kafka, lag = latest offset − consumer's current offset. Lag of 0 = consumer is keeping up. Lag growing = consumer is too slow. Alert on lag > some threshold. Root causes: consumer too slow (add consumers/partitions), message size too large, downstream service too slow. Tools: Kafka consumer lag metrics, Burrow.
+
Choreography vs Orchestration
Choreography (event-driven): each service listens for events and publishes its own events. No central coordinator. Pros: services are loosely coupled. Cons: hard to see the overall flow, distributed tracing needed. Orchestration (saga orchestrator): one service coordinates all steps explicitly, calling each service in order. Pros: easy to see the flow. Cons: orchestrator becomes a dependency. Choreography for simple flows; orchestration for complex business processes.
+
Dual-Write Problem
Dual-write: updating a database AND publishing a message in the same operation. Problem: what if the DB write succeeds but the Kafka publish fails? Or vice versa? Data is now inconsistent. Fix: Transactional Outbox — write the event to an "outbox" table in the same DB transaction as the business data. A separate process (Debezium/CDC) reads the outbox and publishes to Kafka. Now both are always in sync.
+
CDC (Change Data Capture)
CDC = Change Data Capture. Instead of your application explicitly publishing events, CDC reads the database's internal change log (WAL in PostgreSQL, binlog in MySQL) and automatically publishes every INSERT/UPDATE/DELETE to a stream. Debezium is the most common CDC tool — it tails the DB log and publishes changes to Kafka. Useful for syncing databases, building event streams without modifying application code.
