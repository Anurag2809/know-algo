Foundation

Event-Driven Architecture

In event-driven systems, components communicate by emitting and reacting to events rather than calling each other directly. This decouples producers from consumers, allows multiple consumers to react independently, and creates a natural audit log of everything that happens.

Request-response vs event-driven Request-Response (tight coupling): Order Service ──► Payment Service (direct call — waits for response) ──► Inventory Service (blocks, sequential) ──► Notification Service (blocks more) If any service is slow: Order Service waits. Coupling: Order knows about all 3 services. Event-Driven (loose coupling): Order Service ──► Kafka: "order.placed" │ ┌──────────┼──────────────────┐ ▼ ▼ ▼ Payment Svc Inventory Svc Notification Svc (processes (reserves (sends email, independently) stock) SMS) Order Service doesn't know who consumes the event. New consumers add with zero code change. Events are durable (Kafka retains for 7 days) — consumers can replay if they fail.
📤

Event vs Message vs Command

Event: "something happened" (past tense, fact). Message: data sent to a specific recipient. Command: "do this" (imperative, synchronous intent). Events are the foundation of event-driven systems — they're facts, not instructions.

⏱️

Eventual Consistency

In event-driven systems, state updates propagate asynchronously. After "order.placed" fires, inventory may not be updated for 50ms. The system eventually reaches consistency — design UX to tolerate this.

🔄

Idempotency

Events may be delivered more than once (Kafka "at least once"). Consumers must handle duplicate events safely. Use idempotency keys (event_id) and check-before-apply patterns.

State as Events

Event Sourcing

Instead of storing current state, event sourcing stores the history of events that led to the current state. Current state is derived by replaying events. This gives you a complete audit log, the ability to time-travel to any past state, and the ability to add new projections from historical events.

Traditional vs Event Sourced state Traditional (mutable state): orders table: { id: 123, status: "shipped", total: $150 } → History is gone. Can't answer "when was it paid? who approved it?" Event Sourced (immutable event log): event_store: { event_id: 1, type: "OrderPlaced", order_id: 123, total: $150, ts: 10:00 } { event_id: 2, type: "PaymentReceived",order_id: 123, amount: $150, ts: 10:01 } { event_id: 3, type: "ItemShipped", order_id: 123, tracking: "UPS-99", ts: 10:05 } { event_id: 4, type: "OrderDelivered", order_id: 123, ts: 11:30 } Current state = replay events 1-4: → status: "delivered", total: $150, paid: true, tracking: "UPS-99" State at 10:02 = replay events 1-2: → status: "paid", total: $150 Benefits: ✅ Complete audit trail (regulatory: financial, healthcare) ✅ Time-travel debugging ("what was the state at 10:03?") ✅ New read models: add a "monthly revenue" projection by replaying all PaymentReceived events ✅ Event replay for new microservice: replay all events to build its initial state Costs: ⚠️ Complexity: reading state requires replaying events (mitigated by snapshots) ⚠️ Schema evolution: old events must still be deserializable ⚠️ Not every system needs this — use where audit trail is core, not everywhere
from dataclasses import dataclass, field
from datetime import datetime
import json

# Events are immutable facts
@dataclass
class OrderEvent:
    event_id: str
    order_id: str
    event_type: str
    data: dict
    timestamp: datetime = field(default_factory=datetime.utcnow)

# Aggregate: rebuilds state from events
class Order:
    def __init__(self, order_id: str):
        self.order_id = order_id
        self.status = None
        self.total = 0
        self.items = []
        self._version = 0
        self._pending_events = []

    # Command handlers emit events
    def place(self, items: list, total: float):
        if self.status is not None:
            raise ValueError("Order already placed")
        self._apply(OrderEvent("e1", self.order_id, "OrderPlaced",
                               {"items": items, "total": total}))

    def receive_payment(self, amount: float):
        if self.status != "placed":
            raise ValueError("Invalid state transition")
        self._apply(OrderEvent("e2", self.order_id, "PaymentReceived",
                               {"amount": amount}))

    # Event application is the source of truth for state changes
    def _apply(self, event: OrderEvent):
        if event.event_type == "OrderPlaced":
            self.status = "placed"
            self.items = event.data["items"]
            self.total = event.data["total"]
        elif event.event_type == "PaymentReceived":
            self.status = "paid"
        self._version += 1
        self._pending_events.append(event)

    @classmethod
    def from_events(cls, order_id: str, events: list[OrderEvent]) -> "Order":
        order = cls(order_id)
        for event in events:
            order._apply(event)
        order._pending_events.clear()  # historical events, not new
        return order

# Snapshot pattern: store state every 100 events to speed up replay
class OrderRepository:
    def save(self, order: Order):
        for event in order._pending_events:
            self.event_store.append(event)
        if order._version % 100 == 0:
            self.snapshot_store.save(order.order_id, order._version, order.__dict__)

    def load(self, order_id: str) -> Order:
        snapshot = self.snapshot_store.get_latest(order_id)
        if snapshot:
            order = Order(order_id)
            order.__dict__.update(snapshot["state"])
            events = self.event_store.get_since(order_id, snapshot["version"])
        else:
            events = self.event_store.get_all(order_id)
            order = Order.from_events(order_id, events)
        return order
Read/Write Separation

CQRS (Command Query Responsibility Segregation)

CQRS separates write operations (commands that change state) from read operations (queries that return data). This lets you optimize the write model for consistency and the read model for query performance — using different data stores if needed.

CQRS with event sourcing (common pairing) Commands (writes) Queries (reads) │ │ ▼ ▼ Write Model Read Models (projections) Event Store (append-only) ┌── Order Summary Table (Postgres) Consistency guaranteed │ { id, status, total, user_id } Strong validation ├── User Activity Feed (Redis) Complex domain logic │ { user_id: [event1, event2...] } └── Analytics Cube (Redshift) Events published to Kafka ──────────────► { day, revenue, order_count } Projection processors: consume events, update read models Read models are eventual consistent (lag: 10ms - 1s depending on consumer) Read model can be rebuilt: replay all events from Kafka to recreate any projection Scaling: write model (1 node, strong consistency) vs read models (scale-out horizontally)
Real-Time Protocols

WebSockets & Server-Sent Events

HTTP is request-response: the client asks, the server answers. For real-time updates where the server needs to push to clients, we need persistent connections.

WebSocket vs SSE vs Long Polling WebSocket (full-duplex, bidirectional) Client ←────────────────────────── Server ────────────────────────────► Single TCP connection, both sides can send anytime Protocol: ws:// or wss:// (TLS) Best for: chat, gaming, collaborative editing, live trading Server-Sent Events (SSE) (server → client only) Client ◄────────────────────────── Server HTTP/1.1 persistent connection, server streams events Client uses EventSource API, automatic reconnection Best for: notifications, live feeds, dashboards (no client → server needed) Simpler than WebSocket, works through HTTP/2 multiplexing Long Polling (simulates push with HTTP) Client: GET /events (holds connection open) Server: waits until there's data to send, then responds Client: immediately sends next GET /events Highest latency (new connection per event), works everywhere Best for: fallback when WebSocket/SSE unavailable Decision: Bidirectional? → WebSocket Server pushes only? → SSE (simpler, HTTP/2 friendly) Need to work everywhere, low volume? → Long Polling
from fastapi import FastAPI, WebSocket, WebSocketDisconnect
from fastapi.responses import StreamingResponse
import asyncio, json, redis.asyncio as aioredis

app = FastAPI()

# WebSocket: bidirectional chat
class ConnectionManager:
    def __init__(self):
        self.rooms: dict[str, set[WebSocket]] = {}

    async def connect(self, ws: WebSocket, room_id: str):
        await ws.accept()
        self.rooms.setdefault(room_id, set()).add(ws)

    async def disconnect(self, ws: WebSocket, room_id: str):
        self.rooms.get(room_id, set()).discard(ws)

    async def broadcast(self, room_id: str, message: str, sender: WebSocket):
        for ws in list(self.rooms.get(room_id, set())):
            if ws != sender:
                try:
                    await ws.send_text(message)
                except Exception:
                    await self.disconnect(ws, room_id)

manager = ConnectionManager()

@app.websocket("/ws/{room_id}")
async def websocket_endpoint(ws: WebSocket, room_id: str, user_id: str):
    await manager.connect(ws, room_id)
    try:
        while True:
            data = await ws.receive_text()
            msg = json.dumps({"user": user_id, "text": data})
            await manager.broadcast(room_id, msg, sender=ws)
    except WebSocketDisconnect:
        await manager.disconnect(ws, room_id)

# SSE: server pushes notifications to client
@app.get("/events/notifications")
async def notifications_stream(user_id: str):
    redis = aioredis.Redis()

    async def event_generator():
        pubsub = redis.pubsub()
        await pubsub.subscribe(f"notifications:{user_id}")
        try:
            async for msg in pubsub.listen():
                if msg["type"] == "message":
                    yield f"data: {msg['data'].decode()}\n\n"
        finally:
            await pubsub.unsubscribe(f"notifications:{user_id}")

    return StreamingResponse(event_generator(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache",
                                     "X-Accel-Buffering": "no"})
Delivery at Scale

Fan-out Patterns

When one event (a tweet, a post, a stock price update) must be delivered to many subscribers, fan-out is the challenge. At scale, naive approaches fail — delivering to 1M followers cannot happen in a single database transaction.

Fan-out on write vs fan-out on read Fan-out on Write (Twitter model for non-celebrities) User A posts tweet ──► Kafka "tweet.created" │ Fan-out Worker │ (background, async) │ for each of A's followers: │ append tweet_id to follower's timeline cache ▼ [Redis timeline cache per user] user_B_timeline: [tweet_99, tweet_55, tweet_23...] user_C_timeline: [tweet_99, tweet_67...] Reading B's timeline: O(1) Redis read Downside: celebrity with 50M followers → 50M writes per tweet (expensive) Fan-out on Read (Twitter model for celebrities) Celebrity (50M followers) → don't pre-populate timelines When user B loads feed: 1. Load B's following list 2. Query latest tweets from each (cache with Redis) 3. Merge and rank Expensive at read time, but avoids 50M writes Hybrid (Twitter's actual approach) Non-celebrity (< 100K followers) → fan-out on write Celebrity (> 100K followers) → injected at read time Timeline = pre-computed (non-celebs) + injected (celebs) at read time Notification fan-out: Event → Kafka → Fan-out service → per-user notification queue (SQS/Redis) → delivery channels: WebSocket push (online users) / APNs (iOS) / FCM (Android)
Collaborative Systems

Collaborative Editing & CRDTs

When multiple users edit the same document simultaneously (Google Docs, Figma), their changes must be merged without conflicts. Two approaches: Operational Transformation (OT) — used by Google Docs — and CRDTs (Conflict-free Replicated Data Types).

Operational Transformation (OT): transform concurrent operations Initial doc: "hello" User A (offline): insert "world " at position 0 → "world hello" User B (offline): delete "h" at position 0 → "ello" Naive merge: apply A then B → delete at position 0 of "world hello" → "orld hello" (WRONG) OT: transform B's operation against A's operation: B intended to delete position 0 of "hello" A inserted 6 chars at position 0 Transform B: delete at position 0+6=6 of "world hello" → "world ello" (CORRECT) CRDT (Conflict-free Replicated Data Type): no coordination needed Assign unique ID to each character position Characters are ordered by their IDs, not absolute positions Insertions always commute (any order of merge → same result) Yjs and Automerge: production CRDT libraries for text, JSON, rich text Used by: Figma (multiplayer canvas), Linear, Notion Real-time sync infrastructure: WebSocket server → receives operations → broadcasts to room participants Operations stored in Kafka/Redis → new participants replay to get current state Server stores authoritative state (snapshot) + recent delta log
Low-Latency Systems

Multiplayer Gaming Architecture

Multiplayer games require sub-50ms latency, authoritative game state, anti-cheat, and match servers close to players. The architecture is fundamentally different from web services — UDP is preferred over TCP for real-time game state.

Online multiplayer game server architecture Game Client Match Server Game Services │ (stateful, UDP) │ │── UDP: player_input ────────►│ │ │◄─ UDP: world_state ──────────│ │ │ (30 updates/sec) │◄─ Matchmaking ───────────│ │ │ (queue players) │ │ │◄─ Leaderboard ───────────│ │ │◄─ Anti-cheat ────────────│ │ │ (validate moves) │ Why UDP over TCP for game state? TCP guarantees delivery (retransmits lost packets) → head-of-line blocking If packet 5 is lost, TCP waits before delivering 6, 7, 8 Game state is time-sensitive: old state is useless — new state supersedes it UDP: send and forget, application handles "last known state" logic Techniques: Client prediction: apply input locally immediately, reconcile with server state Lag compensation: server rewinds time to validate shots at player's reported time Delta compression: only send what changed since last ack (not full world state) Interpolation: smooth rendering between received state snapshots Infrastructure: Match servers: bare-metal or C3 instances near players (AWS GameLift, Agones/K8s) Anycast routing: player connects to nearest server by IP geography DDoS protection: UDP flood protection (AWS Shield Advanced)
9 Viewpoints

Engineer Perspectives

Backend Engineer

WebSocket connections are long-lived stateful resources. A pod restart drops all active connections. Design clients to reconnect automatically with exponential backoff + state resync.

Architect

Event sourcing adds significant complexity. Only adopt it where audit history and time-travel are core requirements (financial transactions, medical records). For a simple CRUD app, it's overengineering.

SRE

Real-time systems are latency-sensitive. Monitor p99.9, not just p99. A single slow message broker partition can cascade. Set consumer lag alerts — lag growing means consumers can't keep up with producers.

Data Engineer

Event logs are gold for analytics. Store raw events in S3 (Iceberg) in addition to processing them. Events you don't store now can't be replayed for future analytics use cases.

Frontend Engineer

EventSource (SSE) auto-reconnects but loses messages during the gap. Implement a "last-event-id" header so the server can replay missed events. Same principle for WebSocket reconnection.

Platform Engineer

WebSocket servers need sticky sessions in the load balancer — a client must reconnect to the same pod (or a shared pub/sub like Redis) or it loses its room subscription. AWS ALB supports sticky sessions for WebSocket.

Security Engineer

WebSocket connections bypass many HTTP-layer security controls (WAF, rate limiting per request). Add authentication at upgrade handshake (check JWT before upgrading HTTP → WS). Rate-limit messages per connection.

Mobile Engineer

Mobile apps can't hold persistent WebSocket connections indefinitely — OS kills background apps. Use push notifications (APNs/FCM) to wake the app, then establish a short-lived connection to sync state.

ML Engineer

Real-time event streams are valuable training data. Use Kafka Connect to mirror production events to your data lake (S3/Iceberg) for offline training, while Flink processes the same stream for online features.

Problem 01 · Live Chat
Design a chat system like Slack with 10M concurrent WebSocket connections
WebSocketRedis Pub/SubFan-out

Requirements

10M concurrent users, message delivery < 200ms, message history, presence indicators (online/offline), read receipts. Messages delivered exactly once.

import asyncio, json
import redis.asyncio as aioredis
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

# Architecture: each server handles ~50K connections
# Total: 200 WebSocket servers for 10M connections
# Redis pub/sub for cross-server message routing

class ChatServer:
    def __init__(self):
        self.redis = aioredis.Redis.from_url("redis://redis-cluster")
        self.local_connections: dict[str, set[WebSocket]] = {}  # channel_id → {ws}
        self.user_ws: dict[str, WebSocket] = {}  # user_id → ws

    async def connect(self, ws: WebSocket, user_id: str):
        await ws.accept()
        self.user_ws[user_id] = ws

        # Register presence: user is online
        await self.redis.setex(f"presence:{user_id}", 30, "online")  # 30s TTL, heartbeat refreshes

        # Subscribe to user's channels
        channels = await self.get_user_channels(user_id)
        for ch in channels:
            self.local_connections.setdefault(ch, set()).add(ws)

    async def handle_message(self, user_id: str, raw: str):
        msg = json.loads(raw)
        channel_id = msg["channel_id"]

        # Persist to DB (append-only messages table)
        msg_id = await self.db.insert_message(
            channel_id=channel_id, user_id=user_id, text=msg["text"]
        )
        event = json.dumps({
            "type": "message", "id": msg_id,
            "channel": channel_id, "user": user_id,
            "text": msg["text"], "ts": msg["ts"]
        })

        # Publish to Redis channel → all servers subscribed to this channel get it
        await self.redis.publish(f"channel:{channel_id}", event)

    async def redis_subscriber(self, channel_id: str):
        pubsub = self.redis.pubsub()
        await pubsub.subscribe(f"channel:{channel_id}")
        async for message in pubsub.listen():
            if message["type"] == "message":
                # Deliver to all local WebSocket connections in this channel
                event = message["data"].decode()
                for ws in list(self.local_connections.get(channel_id, set())):
                    try:
                        await ws.send_text(event)
                    except Exception:
                        self.local_connections[channel_id].discard(ws)

# Scaling: 200 WebSocket pods (50K connections each) + Redis cluster
# Sticky load balancing: client stays on same pod (ALB cookie-based)
# Message deduplication: msg_id in DB, client deduplicates on msg_id

Problem 03 · Event Sourcing
Design an event-sourced ledger for a fintech payment system
Event SourcingCQRSIdempotency

Requirements

Financial transactions must be immutable, auditable, and replayable. Support: view balance (current), view statement (historical), regulatory replay of any period.

from decimal import Decimal
from datetime import datetime
import uuid

# Event types (immutable facts)
EVENTS = ["MoneyDeposited", "MoneyWithdrawn", "TransferInitiated",
          "TransferCompleted", "TransferFailed"]

class LedgerService:
    def __init__(self, event_store, idempotency_store):
        self.event_store = event_store        # append-only (Postgres partitioned table)
        self.idempotency = idempotency_store  # Redis: idempotency_key → event_id

    def deposit(self, account_id: str, amount: Decimal, idempotency_key: str) -> str:
        # Idempotency: same key → same event (safe to retry)
        if existing := self.idempotency.get(idempotency_key):
            return existing

        event_id = str(uuid.uuid4())
        self.event_store.append({
            "event_id": event_id,
            "account_id": account_id,
            "event_type": "MoneyDeposited",
            "amount": str(amount),
            "currency": "USD",
            "timestamp": datetime.utcnow().isoformat(),
            "idempotency_key": idempotency_key,
        })
        self.idempotency.set(idempotency_key, event_id, ex=86400)  # 24h TTL

        # Publish to read model updater
        self.kafka.publish("ledger.events", {"event_id": event_id, "account_id": account_id})
        return event_id

    def get_balance(self, account_id: str) -> Decimal:
        # Read model: balance maintained in Redis by projection consumer
        # O(1) read — don't replay events for every balance check!
        return Decimal(self.redis.get(f"balance:{account_id}") or "0")

    def get_statement(self, account_id: str, from_ts: datetime, to_ts: datetime) -> list:
        # Read from event store — exact historical replay
        return self.event_store.query(
            "SELECT * FROM ledger_events WHERE account_id = %s AND timestamp BETWEEN %s AND %s",
            (account_id, from_ts, to_ts)
        )

# Projection consumer: maintains balance in Redis
# Kafka consumer group: "balance-projection"
# On MoneyDeposited: INCRBYFLOAT balance:{account_id} amount
# On MoneyWithdrawn: DECRFLOAT balance:{account_id} amount
# On TransferCompleted: atomic: DECR source, INCR destination

What Not to Do

Real-Time Anti-patterns

Polling Instead of Push

Polling /api/messages every second when you have 1M users = 1M req/sec unnecessary load. WebSocket or SSE push reduces this to near-zero (connections are idle between events).

No Reconnection Logic

WebSocket disconnects happen (pod restart, network blip). Clients must reconnect with exponential backoff + replay missed messages using a cursor/sequence number.

Event Sourcing Everywhere

Applying event sourcing to user profiles, product catalog, and settings. The complexity of replaying events and evolving schemas is justified only where audit trails are truly necessary.

Storing Mutable State in Events

Events must be immutable. Never update an event record — if you need to correct, emit a compensating event ("OrderCancelled" doesn't modify "OrderPlaced"). The log is append-only.

Recomputing Projections Synchronously

Replaying all events to get the current balance on every request is O(N) per read. Use snapshots (store state every 100 events) and maintain a precomputed read model for frequent queries.

No Backpressure for WebSockets

Flooding a slow client with messages faster than it can consume. Implement per-connection send queues with max depth. If queue overflows, close the connection — the client reconnects and re-syncs.

WebSocket Without Auth

Upgrading any HTTP connection to WebSocket without validating the JWT first. Validate credentials during the HTTP upgrade handshake before the WS connection is established.

Same Server for Game State and API

Game state servers need UDP, stateful connections, and are latency-sensitive. API servers need HTTP, are stateless, and optimize for throughput. Run them on separate infrastructure with different scaling policies.

Interview Prep

Interview Tips

WebSocket vs SSE Decision

Interviewers often ask "how would you push updates to clients?" Know the tradeoffs: SSE for one-way (simpler), WebSocket for bidirectional. Don't default to WebSocket for everything.

Fan-out Math

If asked "design Twitter," calculate: 300M users, avg 200 followers = fan-out at write is fine. But Katy Perry (150M followers) × 1 tweet = 150M writes. That's the celebrity problem — hybrid approach.

Event Sourcing is a Trade-off

Don't present event sourcing as always superior. Present it as a specific tool for specific needs (audit, regulatory). Say "I'd use it for the payment ledger but not the user profile service."

Idempotency in Event Systems

Kafka delivers events "at least once." Consumers must be idempotent — processing the same event twice has the same result as processing it once. Show you know this and have a pattern (check event_id before applying).

Mention Sticky Sessions for WS

WebSocket pods are stateful (hold open connections). Load balancers must use sticky routing — a reconnecting client must reach the same pod or be re-subscribed. This is a common scaling pitfall.

CQRS without Event Sourcing

CQRS and event sourcing are often paired but independent. You can have CQRS (separate read/write models) with a traditional relational database. Interviewers appreciate knowing the distinction.

Clarifications
+
What is eventual consistency?
Eventual consistency means that if no new updates are made, all replicas will eventually agree on the same value — but there's a window where they disagree. Example: you post a tweet, and for 100ms your follower's feed doesn't show it, then it appears. This is fine for social feeds but not for bank balances (which need strong consistency).
+
What is TCP vs UDP?
TCP (Transmission Control Protocol) guarantees reliable, ordered delivery — lost packets are retransmitted. Good for web, email, databases. UDP (User Datagram Protocol) is "fire and forget" — packets may be lost, arrive out of order, and there's no retransmission. Games use UDP because an old game state (lost packet) is worse than a new one (next packet). Speed over reliability.
+
What is an idempotency key?
An idempotency key is a unique ID the client generates and sends with a request. If the server processes the request (or has already processed it), it stores the result under that key. If the client retries (after a network failure), the server returns the same result without processing twice. Stripe uses this for payments — retrying "charge $100" with the same key doesn't double-charge.
+
What is a projection in event sourcing?
A projection is a read model built by consuming and transforming events. Example: consume all "PaymentReceived" events → maintain a "total_revenue_per_day" table. Projections are always derived — you can delete and rebuild them by replaying the event log. This means you can add new reporting requirements without touching the write model.
+
What is APNs and FCM?
APNs (Apple Push Notification service) is Apple's system for delivering push notifications to iOS/macOS devices. FCM (Firebase Cloud Messaging) is Google's system for Android. When an app is backgrounded, you can't send WebSocket messages — instead you push a notification via these services, which the OS delivers to the device, waking the app if needed.
