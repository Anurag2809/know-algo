Foundation

Paradigm Decision Tree

There is no universally superior API style. Each paradigm optimizes for a different set of constraints. The decision is about which constraints your problem has, not which technology is fashionable.

API PARADIGM SELECTION FLOWCHART ────────────────────────────────────────────────────────── Who are the consumers? │ ├── External / public / mobile clients │ │ │ ├── Need flexible queries (different clients need different fields)? │ │ ├── YES → GraphQL (mobile: fetch exactly what you need) │ │ └── NO → REST (standard, cacheable, well-understood) │ │ │ └── Need real-time push from server? │ ├── YES → WebSocket or SSE (Server-Sent Events for one-way push) │ └── NO → REST │ ├── Internal microservices (service-to-service) │ │ │ ├── Low-latency, high-throughput, strict schema? │ │ └── YES → gRPC (binary protobufs, multiplexed HTTP/2) │ │ │ ├── Fire-and-forget, decoupled, async? │ │ └── YES → Message Queue (Kafka, SQS) → see Async pattern │ │ │ └── Casual internal REST is fine for low-traffic internal services │ └── Server-to-server event notification (3rd party) └── Webhooks (HTTP POST callbacks, no persistent connection)
REST
Stateless, resource-based, HTTP verbs + status codes. The universal default. Best for: Public APIs, CRUD services, cacheable data, any client that speaks HTTP. Avoid when: Many small related queries (over-fetching/under-fetching), binary payloads, real-time.
GraphQL
Single endpoint, client-specified query shape. Schema-first, type-safe. Best for: Mobile apps (bandwidth-sensitive), heterogeneous clients, rapid frontend iteration. Avoid when: Simple CRUD, file uploads, heavy caching (per-resource cache invalidation is hard).
gRPC
Binary protobuf over HTTP/2. Strongly typed, code-generated clients. Best for: Internal microservices, streaming (bidirectional), polyglot environments. Avoid when: Browser clients (needs gRPC-web proxy), external public APIs (tooling friction).
WebSocket
Persistent full-duplex TCP connection. Server pushes without client polling. Best for: Chat, live dashboards, collaborative editing, multiplayer games. Avoid when: Infrequent updates (SSE is simpler), request-response pattern (REST is better).
Webhook
HTTP POST to a URL you register. Event-driven, no persistent connection. Best for: Third-party integrations (Stripe, GitHub, Twilio), async notifications. Avoid when: High-frequency events (polling is more efficient), delivery guarantees needed without retry logic.
Paradigm 1

REST API Design

REST is not just "HTTP with JSON." A well-designed REST API is self-documenting through resource names, predictable through consistent verb semantics, and performant through HTTP-native caching. A poorly designed one is just RPC wrapped in HTTP.

Resource Design & HTTP Verbs

RESOURCE-ORIENTED DESIGN ────────────────────────────────────────────────────────── CORRECT — nouns for resources, verbs via HTTP method: GET /users → list users (paginated) GET /users/{id} → get specific user POST /users → create user (returns 201 + Location header) PUT /users/{id} → full replace (all fields required) PATCH /users/{id} → partial update (only changed fields) DELETE /users/{id} → delete user (returns 204 No Content) GET /users/{id}/orders → user's orders (nested resource) POST /users/{id}/orders → create order for user WRONG — verbs in URLs (RPC over HTTP): POST /createUser ← verb in path GET /getUserById?id=5 ← not resource-oriented POST /users/delete ← using POST for delete GET /users/search?q=bob ← ok for search, but /users?q=bob is better ────────────────────────────────────────────────────────── IDEMPOTENCY — critical for safe retries: Idempotent: GET, PUT, DELETE, HEAD, OPTIONS (safe to retry) NOT idempotent: POST (calling twice creates two resources) PATCH: Depends — "set name to X" is idempotent, "increment counter by 1" is NOT idempotent → Clients SHOULD retry idempotent requests on network failure → POST retries require server-side idempotency keys

Status Codes That Matter

2xx — Success
  • 200 OK — general success
  • 201 Created — POST success, include Location header
  • 204 No Content — DELETE or action with no body
  • 206 Partial Content — range request (file streaming)
3xx — Redirect
  • 301 Moved Permanently — update your bookmarks
  • 302 Found — temporary redirect
  • 304 Not Modified — conditional GET cache hit
4xx — Client Error
  • 400 Bad Request — validation error (include detail)
  • 401 Unauthorized — no valid credentials
  • 403 Forbidden — valid credentials, insufficient permission
  • 404 Not Found — resource doesn't exist
  • 409 Conflict — state conflict (duplicate, version mismatch)
  • 422 Unprocessable — semantic validation failed
  • 429 Too Many Requests — rate limited
5xx — Server Error
  • 500 Internal Server Error — unexpected crash
  • 502 Bad Gateway — upstream service down
  • 503 Service Unavailable — overloaded or maintenance
  • 504 Gateway Timeout — upstream took too long

Pagination Patterns

THREE PAGINATION STRATEGIES ────────────────────────────────────────────────────────── 1. OFFSET / LIMIT GET /posts?limit=20&offset=40 SQL: SELECT * FROM posts ORDER BY created_at LIMIT 20 OFFSET 40 Simple, works for any SQL query Problem: Inserts during pagination cause items to skip or repeat Problem: OFFSET 10000 → full scan of 10,000 rows just to skip them Use for: Admin UIs, non-real-time data, low page numbers 2. CURSOR / KEYSET PAGINATION GET /posts?limit=20&after=eyJpZCI6NDJ9 (base64-encoded cursor) SQL: SELECT * FROM posts WHERE id > 42 ORDER BY id LIMIT 20 Stable: no skip/repeat even with concurrent writes Fast: uses index, constant time regardless of page depth Cannot jump to arbitrary page number Use for: Infinite scroll, feeds, high-volume APIs — this is the right default 3. SEEK / TIME-BASED GET /events?since=2024-01-15T14:32:00Z&limit=100 SQL: SELECT * FROM events WHERE created_at > $1 ORDER BY created_at LIMIT 100 Natural for time-series / event feeds Works well with CDC-style streaming consumers Requires monotonic created_at (duplicates at same timestamp = problem) ────────────────────────────────────────────────────────── Response envelope for paginated APIs: { "data": [...], "pagination": { "next_cursor": "eyJpZCI6NjJ9", "has_more": true, "total": 1250 // optional — expensive to compute, skip if not needed } }
Paradigm 2

GraphQL

GraphQL shifts the contract from server-defined endpoints to a schema that clients query flexibly. This solves over-fetching (getting 50 fields when you need 3) and under-fetching (the N+1 problem hidden inside REST that forces multiple round trips).

Query Shape vs REST

THE OVER/UNDER-FETCHING PROBLEM ────────────────────────────────────────────────────────── REST — mobile client needs user name + first 3 post titles: GET /users/42 → 25-field user object (15 fields unused) GET /users/42/posts → full post objects (content, metadata, comments...) Client picks first 3 post titles out of 50 posts Total: 2 round trips, massive over-fetching GraphQL — mobile client specifies exactly what it needs: POST /graphql { query: " query UserWithPosts($userId: ID!) { user(id: $userId) { # only these fields come back name avatar_url posts(first: 3) { title } } } " } Total: 1 round trip, exactly the fields requested, no more ────────────────────────────────────────────────────────── GraphQL request types: query → read data (like GET) mutation → write data (like POST/PUT/PATCH/DELETE) subscription → real-time push via WebSocket transport

The N+1 Problem & DataLoader

N+1 PROBLEM — the hidden GraphQL killer ────────────────────────────────────────────────────────── Query: { posts { title author { name } } } Naive resolver — 1 + N queries: SQL: SELECT * FROM posts ← 1 query, returns 100 posts For each post: SQL: SELECT name FROM users WHERE id = {post.author_id} Total: 101 queries to render a single GraphQL response DataLoader — batches + deduplicates: SQL: SELECT * FROM posts ← 1 query, returns 100 posts Collect all author_ids: [1, 2, 2, 3, 1, 5, ...] SQL: SELECT * FROM users WHERE id IN (1, 2, 3, 5) ← 1 query (batched) Total: 2 queries regardless of number of posts DataLoader works by: 1. Collecting all IDs queued during a single tick (event loop frame) 2. Calling a batch function once with the deduplicated ID set 3. Returning results mapped back to individual promise resolvers Rule: Any resolver that loads a related entity MUST use DataLoader. Every non-DataLoader resolver in production is a latency time bomb.

Query Cost Limiting & Depth Limiting

GRAPHQL DENIAL-OF-SERVICE via nested queries ────────────────────────────────────────────────────────── Malicious query (exponential cost): { user(id: 1) { friends { ← 100 friends friends { ← 100 × 100 = 10,000 friends { ← 10,000 × 100 = 1,000,000 queries name } } } } } Defenses: 1. Depth limiting: reject queries with nesting > 5 levels 2. Query complexity scoring: each field has a cost weight; reject if total > 1000 3. Persisted queries: only allow pre-registered query hashes from clients 4. Rate limiting per client: complexity budget per user per minute 5. Query timeout: 5-second hard timeout on resolver execution
When NOT to Use GraphQL

GraphQL makes HTTP caching hard (all queries are POST to one endpoint — you lose CDN caching). It adds schema complexity for simple CRUD APIs. File uploads are awkward (multipart workaround). If your API is consumed by a single client with stable requirements, the flexibility cost isn't worth it. Reach for GraphQL when you have many heterogeneous clients or when over-fetching is a real measured problem.

Paradigm 3

gRPC

gRPC uses Protocol Buffers for binary serialization over HTTP/2. Where REST is text-based and human-readable, gRPC is machine-optimized: smaller payload, multiplexed streams, code-generated clients in any language, and strict schema enforcement via the .proto file.

Protocol Buffers Schema

// user_service.proto
syntax = "proto3";
package user;

service UserService {
  // Unary RPC — one request, one response (like HTTP REST)
  rpc GetUser(GetUserRequest) returns (User);

  // Server streaming — one request, stream of responses
  rpc WatchUserEvents(WatchRequest) returns (stream UserEvent);

  // Client streaming — stream of requests, one response
  rpc BatchImportUsers(stream ImportUser) returns (ImportResult);

  // Bidirectional streaming — both sides stream simultaneously
  rpc ChatSession(stream ChatMessage) returns (stream ChatMessage);
}

message GetUserRequest { string user_id = 1; }

message User {
  string user_id    = 1;
  string username   = 2;
  string email      = 3;
  int64  created_at = 4;  // Unix timestamp
  repeated string roles = 5;
}

// protoc compiles this into typed clients in Go, Python, Java, etc.
// Server stub + client stub auto-generated — no hand-written HTTP code

gRPC vs REST Performance

WHY gRPC IS FASTER THAN REST (for internal services) ────────────────────────────────────────────────────────── Serialization: JSON (REST): text encoding, ~400 bytes for a typical user object Protobuf: binary encoding, ~60 bytes same object (6.7× smaller) Parsing: Protobuf deserialization ~5× faster than JSON parsing Transport: HTTP/1.1 (REST): one request per TCP connection (without HTTP/2) head-of-line blocking (request N waits for N-1) HTTP/2 (gRPC): multiplexed streams on one connection request N doesn't wait for N-1 header compression (HPACK) server push capability Code generation: REST: you write the HTTP client, parse JSON, handle errors manually gRPC: protoc generates a type-safe client — just call GetUser(req) Latency at scale: Typical gRPC call (same datacenter): 0.5–2ms Equivalent REST+JSON: 2–10ms At 10k RPS, this difference compounds significantly ────────────────────────────────────────────────────────── gRPC LIMITATION — no native browser support: Browsers cannot make raw HTTP/2 gRPC calls. Solution: gRPC-Web proxy (Envoy/nginx translates gRPC-Web → gRPC) For browser clients: REST or GraphQL is the right choice.
Paradigm 4

WebSocket

WebSocket upgrades an HTTP connection to a persistent, full-duplex TCP channel. The server can push data to the client without the client polling. The cost: stateful connections that don't scale horizontally without a pub/sub backbone.

WebSocket vs SSE vs Long Polling

THREE WAYS TO GET SERVER PUSH ────────────────────────────────────────────────────────── Long Polling: Client sends GET, server holds until event, responds, client immediately sends next GET. No real connection. Works everywhere, high overhead, latency = 1 RTT per event. Use only as last resort (legacy environments). Server-Sent Events (SSE): HTTP/1.1 response body streams indefinitely. Server pushes text events; client reads with EventSource API. One-directional only (server → client) Auto-reconnect built into browser EventSource Works through HTTP/2 multiplexing Best for: live feeds, dashboards, notifications WebSocket: HTTP Upgrade handshake → TCP connection takeover. Full duplex: both sides can send at any time. Binary frames or text frames. Requires stateful server (can't load-balance naively) Best for: chat, collaborative editing, multiplayer games ────────────────────────────────────────────────────────── SCALING WEBSOCKETS — the pub/sub backbone pattern [ Client A ]──WS──► [ Server 1 ] │ subscribe "room:XYZ" [ Client B ]──WS──► [ Server 2 ] │ subscribe "room:XYZ" │ [ Redis Pub/Sub or Kafka ] │ Event from user C ──────►│ publish "room:XYZ" → message │ Server 1 and Server 2 both receive and push to all their subscribed clients → Any server can handle any client's connection → Redis pub/sub fans out to all WebSocket servers → Sticky sessions optional (reduces cross-server overhead)
Paradigm 5

Webhooks

Webhooks invert the request direction: instead of your system polling theirs, their system calls yours when an event happens. The challenge is everything that HTTP polling handled for you — delivery guarantees, retry, ordering, security — becomes your problem to solve.

WEBHOOK RELIABILITY PATTERN ────────────────────────────────────────────────────────── Reliable webhook delivery (Stripe/GitHub approach): Event source creates event │ persists event to DB (status: queued) ▼ [ Webhook Worker ] │ POST {event} to registered endpoint │ timeout: 30s │ ├── 2xx response → mark delivered ✓ │ └── non-2xx / timeout → retry with exponential backoff Attempt 1: immediate Attempt 2: 5 minutes Attempt 3: 30 minutes Attempt 4: 2 hours Attempt 5: 10 hours → mark failed, notify developer ────────────────────────────────────────────────────────── SECURITY — HMAC signature verification: Sender: HMAC-SHA256(secret_key, request_body) → X-Signature-256 header Receiver: expected = HMAC-SHA256(your_secret_key, raw_request_body) if not hmac.compare_digest(expected, received_signature): return 401 ← reject, someone spoofed the webhook → Always verify signature BEFORE processing the payload → Use raw bytes for HMAC, not parsed JSON (order may differ) → Replay attack: include timestamp in signed payload, reject if >5min old ────────────────────────────────────────────────────────── IDEMPOTENCY — handle duplicate deliveries: Webhook may be delivered multiple times (retry after timeout). Your endpoint MUST be idempotent: - Store event_id in DB - On receipt: IF event_id already exists → return 200 immediately - Process event only once, even if called 10 times
Infrastructure Layer

API Gateway

The API gateway is the front door to all your services. It centralizes cross-cutting concerns so individual services don't each have to implement them. Think of it as the load balancer plus the security perimeter plus the traffic cop.

API GATEWAY REQUEST PIPELINE ────────────────────────────────────────────────────────── Client Request │ ▼ [ API Gateway ] │ ├── Step 1: TLS Termination │ Decrypt HTTPS here, forward plain HTTP internally │ ├── Step 2: Authentication │ Validate JWT / API key / OAuth token │ Attach user identity to forwarded request header │ Reject with 401 if invalid │ ├── Step 3: Rate Limiting │ Per-user / per-IP / per-API-key quota │ Reject with 429 + Retry-After header │ ├── Step 4: Request Transformation │ Version routing: /v1/ → legacy service, /v2/ → new service │ Request enrichment: inject tenant_id, correlation_id │ Protocol translation: REST → gRPC backend │ ├── Step 5: Routing │ /users/* → User Service │ /orders/* → Order Service │ /search/* → Search Service │ └── Step 6: Response Transformation Strip internal headers, add CORS headers, compress response ────────────────────────────────────────────────────────── PRODUCTS: Cloud-managed: AWS API Gateway, Kong Gateway, Google Apigee Self-hosted: Nginx + Lua, Envoy, Traefik, Kong (on-prem) Lightweight: nginx with auth_request module

Backend for Frontend (BFF) Pattern

BFF — a dedicated gateway per client type ────────────────────────────────────────────────────────── Problem with a single gateway for all clients: Mobile needs compact responses (bandwidth limited) Web browser needs different auth mechanism (cookie vs token) Smart TV needs simplified API (limited compute for parsing) Solution: Backend for Frontend (BFF) [ Mobile App ] → [ Mobile BFF ] → aggregates: User + Feed + Notifications [ Web Browser] → [ Web BFF ] → full data, server-side rendering support [ Smart TV ] → [ TV BFF ] → simplified, pre-aggregated responses Each BFF: - Calls multiple backend microservices in parallel - Aggregates and shapes the response for its specific client - Handles client-specific auth (mobile: OAuth token, web: session cookie) - Can be GraphQL layer on top of gRPC backend services
Internal Communication

Service-to-Service Communication

Internal microservice calls have different constraints than client-facing APIs: trust level is higher, latency tolerance is lower, and the tooling choice (gRPC vs HTTP vs messaging) has compounding effects across tens of services.

SYNCHRONOUS vs ASYNCHRONOUS SERVICE COMMUNICATION ────────────────────────────────────────────────────────── Synchronous (gRPC / REST): Order Service → gRPC → Inventory Service → gRPC → Warehouse Service Good: Immediate response, simple request-response flow Risk: Chain of dependencies — if Warehouse is down, Order fails Latency compounds: 50ms + 40ms + 60ms = 150ms minimum Requires circuit breakers at every hop (see Reliability pattern) Asynchronous (Message Queue): Order Service → Kafka → [Inventory Consumer, Warehouse Consumer, Email Consumer] Good: Order Service doesn't wait — responds to user immediately Downstream services fail independently without blocking Order Natural buffer for traffic spikes Risk: Eventually consistent — inventory update isn't instant Harder to debug (distributed tracing essential) Decision rule: Need an answer to proceed? → Synchronous (gRPC) Can proceed without waiting? → Asynchronous (Kafka / SQS) Third-party integration? → Webhooks (event-driven HTTP) ────────────────────────────────────────────────────────── SERVICE MESH — Istio / Linkerd Sidecar proxy (Envoy) injected into every service pod Handles: mTLS between services, circuit breaking, retries, load balancing, distributed tracing, traffic shaping Services themselves have no networking code → just business logic Use when: 10+ microservices, need fine-grained traffic control
Evolution Pattern

API Versioning

APIs change. Clients break. Versioning is how you let both evolve independently. The choice of versioning strategy affects your routing logic, documentation tooling, and how long you must maintain old behavior.

THREE VERSIONING STRATEGIES ────────────────────────────────────────────────────────── 1. URL PATH VERSIONING GET /v1/users/42 GET /v2/users/42 Pros: Explicit, easy to route in gateway, visible in logs/browser Cons: URL semantics say "resource identity" — version pollutes it Use for: Public APIs, majority of cases — simple, universally understood 2. HEADER VERSIONING GET /users/42 Accept: application/vnd.myapi.v2+json -- or -- API-Version: 2024-01-01 Pros: Clean URLs, explicit content negotiation Cons: Clients often forget the header, not visible in browser Use for: Internal APIs, Stripe's date-based versioning approach 3. QUERY PARAMETER VERSIONING GET /users/42?version=2 Pros: Convenient for testing in browser Cons: Can conflict with other query params, cache-unfriendly Use for: Development/staging only, not production public APIs ────────────────────────────────────────────────────────── ADDITIVE CHANGES (backward-compatible, no version bump needed): ✓ Add new optional fields to response ✓ Add new optional request parameters ✓ Add new endpoints ✓ Add new enum values (clients should handle unknown values) BREAKING CHANGES (require version bump): ✗ Remove or rename fields ✗ Change field type (string → int) ✗ Change error response format ✗ Remove endpoints ✗ Change authentication scheme
Security Layer

API Security

AUTH MECHANISMS — choosing the right one ────────────────────────────────────────────────────────── API Keys: X-API-Key: sk_live_abc123 Server looks up key → maps to account Simple, good for server-to-server (machine clients) No expiry by default — stolen key is valid forever unless rotated Use for: developer APIs, webhook senders, B2B integrations JWT (JSON Web Token): Authorization: Bearer eyJhbGciOiJSUzI1NiJ9... Self-contained: header.payload.signature (base64-encoded) Server verifies signature without DB lookup → stateless Payload has exp (expiry), sub (subject), roles Cannot invalidate before expiry (use short TTL: 15min, refresh token: 7d) Use for: user auth, stateless APIs, cross-service auth OAuth 2.0: Authorization Code flow: 1. Client redirects user to auth server 2. User logs in, consents to scopes 3. Auth server issues authorization code 4. Client exchanges code for access_token + refresh_token 5. Client uses access_token for API calls Delegated authorization — user grants limited access without sharing password Use for: "Login with Google/GitHub", third-party app access mTLS (mutual TLS): Both client and server present certificates Server verifies client certificate → strong identity Best for internal service-to-service auth (service mesh handles it) High operational overhead — cert rotation, PKI management ────────────────────────────────────────────────────────── AUTHORIZATION — RBAC vs ABAC RBAC (Role-Based): user has role "admin" → can do admin actions Simple, scales well for discrete role sets ABAC (Attribute-Based): policy: "user can READ resource if resource.owner == user.id" Fine-grained, complex policies, audit-friendly Use for multi-tenant SaaS (tenant isolation via policy)
OWASP API Security Top 3

Broken Object Level Authorization (BOLA): GET /orders/123 returns order 123 even if the logged-in user doesn't own it. Always validate that the authenticated user is authorized to access the specific resource ID in the URL — not just that they're logged in. This is the #1 API security failure. Excessive Data Exposure: returning full DB objects and letting clients filter. Send only what the client needs. Mass Assignment: binding all request body fields to model fields — allows clients to set `is_admin: true` in a POST body.

9 Lenses

How Each Team Thinks About APIs

🏗️ Infrastructure Engineer

We care about the operational properties of the API protocol. gRPC over HTTP/2 with persistent connections means connection pooling behaves differently than REST — we tune max concurrent streams and watch for connection exhaustion. WebSocket servers are stateful, which breaks our standard ephemeral auto-scaling model — we provision WebSocket tiers separately with sticky routing.

API gateway selection is partly an infrastructure decision. We prefer gateways that output standard metrics (request rate, latency percentiles, error rate) that feed into our existing Prometheus/Grafana stack. We've seen teams use API gateways with proprietary observability that creates blind spots — metrics trapped in a vendor dashboard we can't alert on.

TLS termination at the gateway boundary is our job. We manage certificates (ACM or Let's Encrypt via cert-manager), rotation schedules, and HSTS headers. Internal service traffic uses mTLS managed by Istio — certificates auto-rotate every 24 hours with zero manual intervention after initial setup.

🌐 Network Engineer

Protocol selection has direct network cost implications. HTTP/2 multiplexing means multiple gRPC streams share one TCP connection — fewer connections, less TCP handshake overhead, more efficient use of connection table entries on load balancers. This matters at 50k+ concurrent users where the load balancer's connection limit becomes a real constraint.

WebSocket traffic doesn't play well with standard HTTP load balancers unless you configure WebSocket passthrough. Sticky sessions (IP hash or cookie-based) are often needed so the same client consistently hits the same WebSocket server. Sticky sessions reduce auto-scaling flexibility — we document this constraint before approving WebSocket architecture.

Long-lived connections (WebSocket, gRPC streams) need aggressive keep-alive tuning on both sides. A mid-path firewall or NAT gateway that silently drops idle connections after 30 seconds will cause mysterious client disconnects in production. We test connection keep-alive behavior against all firewall tiers in staging before any real-time feature launches.

⚙️ Platform Engineer

We provide API standards as a platform capability. Internal teams get a proto file template, a CI pipeline that runs protoc and publishes generated clients to our internal package registry, and a standard health check endpoint (/healthz, /readyz) pattern. This means any service in the company can call any other service without writing HTTP client code by hand.

API contract testing (Pact, or schema validation in CI) prevents breaking changes from reaching production silently. When a team changes a proto definition, our CI runs the consumer contracts against the new schema — if it breaks any registered consumer, the build fails before deployment. This is the single most effective practice we've implemented for preventing service-to-service breakage.

We maintain an internal API registry (Backstage or a simple spec server) where every service publishes its OpenAPI or proto schema. New engineers find APIs by searching the registry, not by asking in Slack. Auto-generated documentation from the schema reduces the chance that docs drift from implementation — a perennial problem with hand-written API docs.

🔐 Security / Cyber Engineer

Every API endpoint is an attack surface. Our minimum baseline: authentication on all non-public endpoints, rate limiting on all endpoints (including authenticated ones — credential stuffing attacks authenticate successfully then hit the API hard), and request size limits to prevent payload-based DoS. We audit new endpoints against OWASP API Security Top 10 before they ship.

JWT validation must happen at the gateway, not in application code — we've seen services accidentally deploy without attaching the auth middleware, exposing the endpoint publicly. The gateway is the mandatory choke point. We require all services to be deployed behind the gateway and block direct ingress to service IPs at the network layer. "Gateway optional" architectures have too many ways to accidentally bypass auth.

Webhook security is chronically underimplemented. We require HMAC signature verification on every webhook receiver we build, replay attack protection (reject events older than 5 minutes), and idempotency keys to prevent double-processing. We run webhook security checks in our code review checklist because developers routinely skip signature verification when prototyping and never add it back.

📊 Data Engineer

APIs are data pipelines with bad lineage. Every API call that returns data is implicitly a data transformation — fields get renamed, filtered, aggregated. We work with backend teams to ensure API response schemas are versioned and documented so we can build reliable data ingestion pipelines on top of them. A schema change with no notice breaks our pipeline silently until an alert fires hours later.

GraphQL is particularly interesting for data work because the query shape tells us exactly which fields were accessed. We've used GraphQL query logs to understand actual field usage patterns — useful for pruning over-fetched data, identifying never-used API fields safe to deprecate, and measuring the actual data footprint of different client types.

Webhooks are a data source we love and hate. They push events to us in real time — great for data freshness. But they're not guaranteed-ordered, can be delivered out of sequence, and may replay events. Our webhook ingestion pipeline always checks event timestamps against the last-seen event and handles out-of-order delivery explicitly rather than assuming chronological order.

🤖 ML / AI Engineer

ML inference APIs have unique SLA requirements: high throughput (batched requests), low tail latency (p99, not just p50), and graceful degradation when the model is overloaded. We design ML serving APIs around gRPC for internal calls (binary protobufs with batching) and REST for external-facing inference endpoints. The request batching pattern — accumulate N requests within a 10ms window, send as batch to GPU — requires async handling that REST alone doesn't elegantly support.

Streaming inference (LLM token streaming) is a real-time API problem. We use Server-Sent Events for streaming model output to browsers — simpler than WebSocket for one-directional server push, and the browser's EventSource API handles reconnection automatically. For internal pipelines that consume model output, gRPC server streaming is the better choice.

Model API versioning is trickier than regular API versioning because the "contract" is often implicit (same input, same response schema) but behavior changes between model versions. We version models with both an API version (schema) and a model version (behavior) — clients can pin to a specific model checkpoint for reproducibility, or use "latest" for the best current model. A/B testing routing at the gateway determines which model version serves which traffic percentage.

⚡ Backend Engineer

I design APIs that I'd enjoy consuming. That means consistent error formats (always {error: {code, message, details}}), never mixing HTTP status codes with in-body success/failure flags, and idempotency keys on all non-idempotent endpoints that clients might retry. The ugliest APIs I've inherited were designed by people who only thought about the happy path — the error handling is an afterthought and every caller has to reverse-engineer what each error condition means.

N+1 queries in GraphQL resolvers are my #1 production concern for GraphQL APIs. Every resolver that fetches a related entity goes through DataLoader — no exceptions. I treat any resolver without DataLoader as a code review blocker. The performance difference between a naive resolver and a DataLoader resolver isn't theoretical: in production I've seen a single GraphQL query drop from 800ms to 12ms purely by adding DataLoader, without changing any business logic.

For gRPC services, I define the .proto first before writing any implementation code. The schema is the contract. We run protoc in CI against a committed version of the proto to generate client stubs for all consuming services. Breaking the proto file fails CI for all consumers simultaneously — this is the intended behavior, it forces breaking changes to be deliberate and coordinated rather than accidental.

🎨 Frontend Engineer

The API protocol choice directly affects my development experience. REST with OpenAPI means I get type-safe client generation (openapi-typescript, orval) — the API schema generates my TypeScript interfaces automatically. GraphQL with codegen gives the same thing but is more flexible about query shape. gRPC from a browser requires gRPC-Web and Envoy proxy, which adds infrastructure complexity — I'd rather not deal with that unless there's a specific reason.

Over-fetching is a real problem I've measured, not a theoretical concern. On mobile, fetching a user profile with 30 fields when the UI shows 4 wastes bandwidth and parsing time. GraphQL lets me specify exactly what I need. But I've also seen teams adopt GraphQL for simple CRUD screens where the "flexibility" advantage doesn't exist — those pages would be simpler with plain REST. The tool fits specific problems.

WebSocket reconnection logic is always harder than it looks. The browser's WebSocket API doesn't reconnect automatically — you have to implement exponential backoff, event queue replay during disconnection, and heartbeat-based dead-connection detection. Libraries like socket.io handle this, but they add overhead. For most "live update" use cases, SSE is simpler to implement correctly and handles reconnection automatically via the EventSource API.

📡 SRE / Site Reliability Engineer

My API SLO is a latency and error rate target: p50 < 50ms, p99 < 200ms, error rate < 0.1% over a 30-day rolling window. When these targets are violated, I page someone. The API gateway gives me per-endpoint metrics, but the gateway only sees requests that pass rate limiting — I also need application-level metrics to catch issues that don't manifest as HTTP errors (slow DB queries, silent data corruption).

Distributed tracing is how I debug cross-service API calls. A Trace-ID header is injected at the gateway, propagated through every gRPC and async call, and emitted to Jaeger or Tempo. When a user reports slow page loads, I search by Trace-ID and see exactly which service and which database query was the bottleneck. Without tracing, debugging in a 15-service architecture means grepping logs across 15 services simultaneously — not viable at 3 AM.

API gateway rate limits are a blast radius control mechanism. A misbehaving client or a bug in our own code that creates a request loop can exhaust downstream service capacity in seconds. Rate limits at the gateway contain the damage to the misbehaving client without taking down the service for everyone else. I set conservative limits, monitor for legitimate clients hitting them, and increase only with evidence — not preemptively.

Problem 01
Real-Time Collaborative Document Editor (Google Docs-style)
WebSocket Operational Transform Pub/Sub Presence

Communication Requirements

  • Multiple users edit the same document simultaneously
  • Edits must appear in near-real-time (<100ms) for all collaborators
  • User presence (cursor positions, names) must be visible live
  • Connection drops must not lose in-progress edits

Protocol Architecture

COLLABORATIVE EDITOR — API LAYER Client A ──WS──► [ WebSocket Server ] ──► [ Redis Pub/Sub ] Client B ──WS──► [ WebSocket Server ] ◄── (broadcast "doc:abc") Client C ──WS──► [ WebSocket Server ] REST (HTTP): GET /docs/{id} → initial document state + version number POST /docs/{id}/ops → persist operation (async, after WS delivery) WebSocket messages: Client → Server: {type: "op", docId: "abc", op: {type:"insert", pos:5, text:"X"}, version: 42} Server → Client: {type: "op", op: {...}, author: "alice", version: 43} Server → Client: {type: "presence", userId: "bob", cursor: {line:3, col:7}} OPERATIONAL TRANSFORM (OT) — conflict resolution: Alice inserts "A" at position 5 (version 42) Bob deletes char at position 3 (version 42) ← concurrent Server receives both: Apply Alice's op first → "B" at position 3 is gone Transform Bob's op relative to Alice's → adjust positions Broadcast transformed ops to all clients All clients converge to identical document state

Handling Reconnection

When a client disconnects, it buffers local operations with a local version counter. On reconnect, it sends all buffered ops with their versions. The server replays missed server ops first, then applies client ops with position transforms. This "catch-up" pattern ensures no edit is lost during a network blip.

DataLoader Implementation

// userLoader.js — one loader per request context
const DataLoader = require('dataloader');
const db = require('./db');

function createUserLoader() {
  return new DataLoader(async (userIds) => {
    // Called once per tick with all queued IDs (deduplicated)
    const users = await db.query(
      'SELECT * FROM users WHERE id = ANY($1)',
      [userIds]  // single IN query regardless of how many tweets we resolve
    );
    // Must return results in same order as input IDs
    const userMap = Object.fromEntries(users.map(u => [u.id, u]));
    return userIds.map(id => userMap[id] || null);
  });
}

Problem 03
Payment Webhook System (Stripe-style)
Webhooks Idempotency HMAC Retry Logic

Architecture

Payment provider sends webhooks to merchants for payment events (payment.succeeded, payment.failed, refund.created). Merchants often have flaky endpoints, and the system must guarantee at-least-once delivery with retry logic.

RELIABLE WEBHOOK DELIVERY SYSTEM Payment Event → DB: INSERT webhook_events (status=queued) → Outbox Worker polls queued events Outbox Worker: 1. SELECT FOR UPDATE events WHERE status='queued' AND next_attempt <= NOW() 2. POST {event} to merchant_url (30s timeout) 3a. Success (2xx): UPDATE status='delivered', delivered_at=NOW() 3b. Failure: UPDATE status='retry', attempts = attempts + 1, next_attempt = NOW() + backoff(attempts) Backoff schedule: attempts=1: +5min | attempts=2: +30min | attempts=3: +2h attempts=4: +10h | attempts=5: +24h → status='failed'

HMAC Verification (Merchant Side)

import hmac, hashlib, time
from flask import request, abort

WEBHOOK_SECRET = "whsec_abc123..."

def verify_webhook(request):
    # 1. Get raw bytes BEFORE JSON parsing (order matters for HMAC)
    payload = request.get_data()

    # 2. Extract signature and timestamp from header
    sig_header = request.headers.get('Stripe-Signature', '')
    parts = dict(p.split('=', 1) for p in sig_header.split(','))
    timestamp = int(parts.get('t', 0))
    received_sig = parts.get('v1', '')

    # 3. Reject stale events (replay attack prevention)
    if abs(time.time() - timestamp) > 300:  # 5 minutes
        abort(400, "Webhook timestamp too old")

    # 4. Compute expected signature
    signed_payload = f"{timestamp}.".encode() + payload
    expected_sig = hmac.new(
        WEBHOOK_SECRET.encode(), signed_payload, hashlib.sha256
    ).hexdigest()

    # 5. Constant-time comparison (prevents timing attacks)
    if not hmac.compare_digest(expected_sig, received_sig):
        abort(401, "Invalid signature")

@app.route('/webhooks/payment', methods=['POST'])
def handle_webhook():
    verify_webhook(request)
    event = request.json

    # 6. Idempotency — check if already processed
    if WebhookEvent.exists(event['id']):
        return '', 200  # already handled, return 200 so no retry

    # 7. Process event
    if event['type'] == 'payment.succeeded':
        fulfill_order(event['data'])

    WebhookEvent.create(event_id=event['id'], processed_at=datetime.utcnow())
    return '', 200
Decision Guide

Trade-offs Table

Decision Option A Option B When to Choose A
REST vs GraphQL REST GraphQL Single client, stable requirements, heavy caching needs (CDN). GraphQL when multiple heterogeneous clients or severe over-fetching is measured
REST vs gRPC (internal) gRPC REST/JSON gRPC for services with high call volume, strict schema, or streaming. REST for low-traffic internal services or when team is unfamiliar with protobufs
WebSocket vs SSE SSE WebSocket SSE when only server-to-client push needed (feed, notifications). WebSocket when client also sends data (chat, collaborative edit, games)
URL vs Header versioning URL (/v1/...) Accept header URL for public APIs (visible, debuggable, routing is trivial). Header for sophisticated internal APIs where clean URL semantics matter
JWT vs API key JWT API key JWT for user-facing auth (stateless, roles embedded). API key for machine-to-machine (simpler, no expiry concerns for trusted internal services)
Single gateway vs BFF Single API gateway Backend for Frontend Single gateway for simple or early-stage systems. BFF when different clients (mobile, web, TV) need substantially different response shapes or auth mechanisms
Sync vs Async service calls gRPC (sync) Kafka (async) gRPC when you need the result before proceeding. Kafka when downstream processing can be deferred and you want blast-radius isolation
Offset vs Cursor pagination Cursor-based Offset/limit Cursor for feeds and infinite scroll (stable, fast at any depth). Offset for admin UIs with page numbers and small datasets (<100k rows)
What Not to Do

Anti-patterns

  • Using POST for everything ("RPC over HTTP") POST /getUser, POST /deleteOrder, POST /searchProducts — this throws away everything HTTP gives you: caching (GET is cacheable), idempotency (PUT/DELETE are defined as idempotent), and meaningful status codes. Also makes your API unreadable to anyone who didn't write it.
  • GraphQL resolvers without DataLoader Any resolver that fetches a related entity in a loop is an N+1 query waiting to destroy your database at scale. This is so common it has a name. Every GraphQL resolver that loads related data must go through DataLoader. Treat this as a hard requirement, not a "nice to have."
  • JWT with no expiry (or multi-year expiry) JWTs are self-contained — you can't revoke them before expiry without a token blacklist (which negates the stateless benefit). Setting exp: "5 years" means a stolen token is valid for 5 years. Standard pattern: access token expires in 15 minutes, refresh token in 7 days. Short-lived access tokens limit the blast radius of token theft.
  • Skipping HMAC verification on webhooks A webhook endpoint that processes any incoming POST without verifying the signature can be exploited: an attacker sends forged payment.succeeded events to your endpoint, triggering order fulfillment for unpaid orders. Always verify HMAC before processing, regardless of how "internal" the webhook seems.
  • Breaking API changes without version bumps Renaming a field, removing a response field, or changing a field type in a deployed API breaks all existing clients silently. They either crash, return wrong data, or fail validation. Backwards-incompatible changes need a version bump (v1 → v2) with a deprecation period, not in-place modification of the existing version.
  • Polling instead of WebSocket/SSE for live data GET /notifications every 2 seconds generates 30 requests per minute per user. At 10k users that's 300k requests/minute — all returning empty results most of the time. A single WebSocket per user delivers events instantly with zero polling overhead. The cost difference at scale is enormous.
  • Exposing internal microservice APIs directly to clients Giving mobile clients direct access to your OrderService, InventoryService, and ShippingService means: every service must implement auth, the client makes 5 round trips for one screen, you can't change internal service boundaries without breaking the client. The API gateway / BFF layer exists to aggregate, transform, and shield internal architecture from external contracts.
  • Not setting a request timeout on outgoing gRPC/HTTP calls An upstream service hanging — not erroring, just hanging — will cause your request goroutines to pile up indefinitely. Without a timeout, a 30-second upstream hang turns into 30 seconds of thread exhaustion, then into a cascading failure across your service. Every external call gets a timeout. Use context deadlines in gRPC (these propagate automatically), explicit timeouts in HTTP clients.
Interview Strategy

Interview Tips for API Design Questions

The Pattern Interviewers Are Testing

API design questions test whether you understand the why behind protocol choices. "We'll use REST" is not an answer — "We'll use REST because the clients are third-party integrators who need familiar tooling, and the data is cacheable at the CDN layer" is the answer that signals senior thinking.

Tip 01

Ask about client types before picking a protocol. "Who calls this API?" is the first question. External developers → REST. Mobile app with varied screens → GraphQL. Internal services → gRPC. Real-time → WebSocket or SSE.

Tip 02

Mention the API gateway as an explicit component. Interviewers like to see that you centralize auth, rate limiting, and routing in a gateway rather than implementing them per-service. Name it (Kong, Nginx, AWS API GW) and list what it does.

Tip 03

For real-time problems, compare WebSocket vs SSE explicitly. One-way push (notifications, feeds) → SSE. Bidirectional (chat, collaborative edit) → WebSocket. Show you know the difference, then pick one and justify it.

Tip 04

Always mention idempotency for write APIs. POST /orders should accept an idempotency key header. Clients retry on network failures — without idempotency keys, retries create duplicate orders. This shows you think about distributed systems failure modes.

Tip 05

Mention cursor-based pagination for large datasets. Never offset pagination for feeds or user-facing infinite scroll. Cursor pagination is O(1) per page regardless of depth, and doesn't have the skip/repeat problem with concurrent writes.

Tip 06

For GraphQL: proactively raise the N+1 problem. "I'd use DataLoader to batch all resolver calls to the same entity type within one query execution." This one sentence signals GraphQL experience. Most interviewers have seen GraphQL APIs destroyed by missing DataLoaders.

Clarifications
+
HTTP Methods
GET: retrieve data — must be safe (no side effects) and idempotent. POST: create a resource — not idempotent (two POSTs create two resources). PUT: replace a full resource — idempotent. PATCH: partially update a resource. DELETE: remove a resource — idempotent. Rule of thumb: PUT/DELETE/GET should be idempotent; POST is not.
+
Idempotency
An operation is idempotent if calling it once vs. 100 times produces the same result. GET /users/1 is idempotent. DELETE /users/1 is idempotent (first call deletes, subsequent calls get 404 — same final state). POST /orders is NOT idempotent — each call creates a new order. Critical for retries: if a network request fails, safe to retry only idempotent operations.
+
HTTP Status Codes
2xx = success: 200 OK, 201 Created, 204 No Content. 3xx = redirect: 301 Permanent, 302 Temporary. 4xx = client error (your fault): 400 Bad Request, 401 Unauthorized (not logged in), 403 Forbidden (logged in but no permission), 404 Not Found, 409 Conflict, 429 Too Many Requests. 5xx = server error (our fault): 500 Internal Server Error, 503 Service Unavailable.
+
GraphQL N+1 Problem
N+1: fetching 10 posts triggers 10 separate DB queries to get each post's author — 1 query for posts + N queries for authors = N+1 queries. In REST, this is solved by JOINs. In GraphQL, solvers (resolvers) run independently, so naive implementations hit the DB once per item. Fix: DataLoader — batches all author lookups into one query using an in-memory queue that flushes between event loop ticks.
+
Protocol Buffers (Protobuf)
Protobuf is a binary serialization format. You define your data schema in a .proto file, and a code generator creates typed classes in your language. JSON: {"user_id": 1234, "name": "Alice"} = 28 bytes as text. Same data in Protobuf: ~5 bytes binary. 5–10x smaller and 10–100x faster to serialize/deserialize. Trade-off: not human-readable, requires schema file to decode.
+
HTTP/2 vs HTTP/1.1
HTTP/1.1: one request per connection at a time (without pipelining). Browsers open 6 parallel connections to work around this. HTTP/2: multiplexing — multiple requests/responses over one TCP connection simultaneously. gRPC requires HTTP/2. HTTP/2 also adds header compression and server push. HTTP/3 replaces TCP with QUIC (UDP-based) for even less connection setup latency.
+
WebSocket vs SSE vs Long Polling
Long polling: client sends a request, server holds it open until there's data or timeout, then client immediately polls again. Works everywhere, wastes connections. SSE (Server-Sent Events): server pushes events to client over HTTP. One-directional (server → client only), simpler than WebSocket. WebSocket: fully bidirectional persistent connection. Use SSE for notifications/feeds (client doesn't send data); WebSocket for chat or gaming (bidirectional).
+
Webhooks vs Polling
Polling: your server asks an external API "do you have updates?" every N seconds. Simple but wasteful. Webhook: the external API calls YOUR endpoint when something happens. Efficient — you're notified only when there's data. Challenge: your endpoint must be publicly accessible, must handle retries (external service will retry if your server is down), and must verify the request is genuine (HMAC signature).
+
Reverse Proxy vs API Gateway
Reverse proxy (Nginx, HAProxy): forwards requests to backend servers. Handles SSL termination, caching, load balancing. No awareness of your API semantics. API Gateway (Kong, AWS API Gateway, Envoy): a smart reverse proxy that additionally handles auth (JWT validation), rate limiting, request transformation, response aggregation, analytics, and developer portal. Every microservices architecture needs one.
+
JWT (JSON Web Token)
A JWT is three Base64-encoded parts separated by dots: Header.Payload.Signature. Header: algorithm used (RS256). Payload: claims — user_id, role, expiry time. Signature: cryptographic proof that the token hasn't been tampered with. The server verifies the signature on every request without hitting the database. Stateless auth. Risk: JWTs can't be invalidated before expiry — use short TTLs (15 minutes) and refresh tokens.
+
OAuth 2.0 Flow
OAuth 2.0 lets a user grant your app access to their data on another service without sharing their password. Example: "Log in with Google." Steps: 1) Your app redirects user to Google with a scope. 2) User consents. 3) Google redirects back with an authorization code. 4) Your server exchanges the code for an access token. 5) Use the token to call Google APIs. The user never gives you their Google password.
+
mTLS (Mutual TLS)
Regular TLS: client verifies the server's certificate (you trust the bank's website). mTLS: both sides verify each other's certificates. In microservices, each service has its own certificate. Service A proves to Service B that it's really Service A, not a malicious insider. Used in zero-trust architectures and service meshes (Istio manages mTLS automatically between all pods).
