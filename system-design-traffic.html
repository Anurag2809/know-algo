Traffic Shaping &
Load Distribution

When your system receives more requests than a single server can handle, you need to distribute load, control flow, and scale horizontally. This pattern is the foundation every system design builds on.

⚡ Trigger: High request volume or single-server bottleneck 🎯 Goal: Even load, controlled flow, elastic capacity 👥 Primary owners: Infra, Network, SRE
When to reach for this pattern A single server is CPU-bound, memory-limited, or you need zero-downtime deployments. Any public service beyond ~500 req/sec, or any system with bursty traffic, needs at minimum: a load balancer, a rate limiter, and a defined scaling policy.

🔴 The Core Problem

Every service starts as a single server. Eventually, incoming requests exceed what one machine can handle. When that happens, you get one of three failure modes:

Without traffic shaping — single server overload: C1 ──────────────────────────────────────────────────► ┌────────────────────────────────┐ C2 ──────────────────────────────────────────────────► │ App Server │ C3 ──────────────────────────────────────────────────► │ CPU: ████████████ 100% │ C4 ──────────────────────────────────────────────────► │ Memory: ████████████ 98% │ ...1,200 req/sec ─────────────────────────────────────► │ Conns: MAXED │ │ Status: ❌ OVERLOADED │ └────────────────────────────────┘ Result: timeouts, OOM kills, or the process crashes entirely. With load balancer + 3 servers: ┌────────────────────────────────────────────────────┐ │ Load Balancer │ │ NGINX / AWS ALB / HAProxy / GCP Load Balancer │ │ Health checks ✓ SSL termination ✓ │ └──────────────┬──────────────┬──────────────────────┘ │ │ │ ▼ ▼ ▼ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ Server 1 │ │ Server 2 │ │ Server 3 │ │ CPU: 33% │ │ CPU: 31% │ │ CPU: 36% │ │ Healthy │ │ Healthy │ │ Healthy │ └──────────┘ └──────────┘ └──────────┘

Three tools solve different dimensions of this problem. You usually need all three:

⚖️

Load Balancer

Distributes requests across multiple servers. Solves the single-machine throughput ceiling.

🚦

Rate Limiter

Controls how fast any one client can make requests. Protects servers from intentional or accidental floods.

📈

Auto-Scaler

Adjusts the number of servers dynamically. Handles growing or spiky traffic without manual intervention.

⚖️ Load Balancing

A load balancer sits in front of your server pool, accepts incoming connections, and forwards each request to a backend server according to its algorithm. The choice of algorithm determines how evenly work is distributed.

Algorithms

── Round Robin ──────────────────────────────────────────────────────── Request 1 ──► Server A Request 2 ──► Server B Request 3 ──► Server C Request 4 ──► Server A (wraps around) Best for: stateless services with homogeneous servers. Weakness: ignores server load — a heavy request and a light one get treated the same. ── Weighted Round Robin ──────────────────────────────────────────────── Server A: weight=3 (larger instance) Server B: weight=1 (smaller instance) Sequence: A, A, A, B, A, A, A, B ... Best for: heterogeneous server pools (mix of instance sizes). ── Least Connections ─────────────────────────────────────────────────── Server A: 150 active conns Server B: 20 active conns ◄── next request goes here Server C: 50 active conns Best for: long-lived connections (WebSockets, streaming, DB proxies) where requests have unequal duration. ── IP Hash ───────────────────────────────────────────────────────────── hash(client_ip) % num_servers = server_index Client 10.0.0.5 → always → Server B Client 10.0.0.9 → always → Server C Best for: stateful apps that store session data in memory. Weakness: one IP behind NAT sends all traffic to one server (hot spot). If that server dies, all sessions for that IP are lost.

Consistent Hashing (for caches and sharded services)

When you add or remove a server from a pool, simple modulo hashing remaps almost all keys. Consistent hashing limits disruption to ~1/N keys.

── Virtual Hash Ring (0° → 360°) ─────────────────────────────────────── Server A (120°) ● ┌───────────────┘ 0° ●─────────────────────────────────────● 360° └───────────────┐ ● Server B (240°) "user:1234" hashes to 175° → next clockwise → Server B (240°) "user:5678" hashes to 80° → next clockwise → Server A (120°) "user:9999" hashes to 300° → next clockwise → Server A (0°/360°) ── Add Server C at 200° ──────────────────────────────────────────────── Keys between 120° and 200° now route to Server C. Everything else stays the same. Only ~1/N keys remapped — not all of them. Used by: DynamoDB, Apache Cassandra, Redis Cluster, Memcached, CDN edge selection.

Layer 4 vs Layer 7

── Layer 4 (Transport) ───────────── ── Layer 7 (Application) ─────────── Sees: TCP/UDP packets only Sees: HTTP headers, URL path, cookies Routing: by IP address + port Routing: by content of the request Client Client │ │ ▼ ▼ GET /api/orders HTTP/1.1 [TCP Proxy LB] [HTTP Proxy LB] │ (opaque stream) │ reads URL, routes smartly ▼ ├──► /api/* → API servers Backend ├──► /static/* → CDN origin └──► /ws/* → WebSocket servers Examples: AWS NLB, HAProxy TCP Examples: AWS ALB, NGINX, Traefik Choose Layer 4 when: Choose Layer 7 when: • Database connection pooling • Microservice routing by URL • Raw UDP (gaming, video) • A/B testing by header/cookie • Ultra-low latency required • SSL/TLS termination needed • Protocol is not HTTP • WebSocket upgrade handling

Sticky Sessions (Session Affinity)

When your application stores session state in local memory (not in Redis), you need the same client to always reach the same server. This is called sticky sessions.

Cookie-based stickiness: 1. First request hits LB → routed to Server B 2. LB inserts cookie: AWSALB=abc123 (encodes Server B's identity) 3. Client sends cookie on every subsequent request 4. LB reads cookie → routes to Server B always The problem with sticky sessions: • If Server B dies → all its sessions are lost • Server B can become a hot spot (popular client → all traffic there) • Makes rolling deployments harder (you need connection draining) Better alternative: stateless services + Redis for session storage Request → Any Server → reads session from Redis → stateless response Works with any LB algorithm. No hot spots. Survives server failure.

Health Checks

Critical design decision A shallow health check (TCP connect succeeds) will mark a server as healthy even if it is deadlocked, stuck in GC, or has a broken database connection. Deep health checks are almost always worth the overhead.
Shallow check (TCP ping): LB ──► TCP connect to port 8080 ──► OK LB thinks: server is healthy ✓ Reality: server is stuck in GC, not processing requests Deep check (HTTP /health endpoint): LB ──► GET /health HTTP/1.1 ──► Server checks: ├── DB connection pool: OK ├── Redis connection: OK ├── Downstream APIs: OK └── Returns HTTP 200 {"status": "ok"} LB: healthy ✓ (the server can actually serve requests) If /health returns 5xx → LB removes server from rotation automatically.

🚦 Rate Limiting

Rate limiting controls how many requests a client (user, IP, API key) can make within a time window. It protects your service from both malicious abuse and accidental floods.

Algorithm 1: Token Bucket

A bucket holds up to C tokens (the burst capacity). Tokens refill at rate r per second. Each request consumes one token. If the bucket is empty, the request is rejected or queued.

Capacity C = 100 tokens | Refill rate r = 20 tokens/sec t = 0s Bucket: [●●●●●●●●●●] 100 tokens (full) t = 1s +20 tokens, 80 requests arrive Bucket: [●●●●●●●●●●] 40 tokens remaining 80 allowed ✓ t = 2s +20 tokens, 70 requests arrive Bucket: [●●●●●●●●●●] 0 tokens 60 allowed ✓ 10 rejected ✗ Incoming request decision: ┌───────────────────────────────────────────────────────────────┐ │ Request arrives │ └────────────────────────┬──────────────────────────────────────┘ ▼ Token available in bucket? / \ YES NO │ │ ▼ ▼ Consume 1 token 429 Too Many Requests Allow request ✓ (or queue if soft limit) Properties: ✓ Allows bursts up to capacity C ✓ Smooth average rate of r req/sec over time ✓ Easy to implement (2 values per client: token_count, last_refill_time)

Algorithm 2: Leaky Bucket

Requests enter a queue. A processor drains the queue at a fixed rate r. If the queue is full, new requests are dropped.

Queue size Q = 50 | Processing rate r = 10 req/sec Requests flood in ──► [Queue: 50 max] ──► Process at 10 req/sec ──► Backend If queue full: drop incoming requests Token Bucket vs Leaky Bucket: ┌─────────────────────────────────────────────────────────────────────┐ │ Token Bucket: allows bursts (bursty client OK up to C requests) │ │ Leaky Bucket: smooth output (always processes at exactly r/sec) │ └─────────────────────────────────────────────────────────────────────┘ Use Leaky Bucket for: • Outbound API calls to a third party with a strict per-second limit • Smoothing egress traffic (prevents bursts toward downstream) Use Token Bucket for: • Inbound API rate limiting where short bursts are acceptable

Algorithm 3: Fixed vs Sliding Window Counter

── Fixed Window (simple, has edge-case burst) ────────────────────────── Window [00:00 ─── 00:59] 100 requests (at limit) Window [01:00 ─── 01:59] 100 requests (at limit) Problem: 100 req at 00:58 + 100 req at 01:02 = 200 req in 4 seconds! The window boundary creates a legal burst of 2× the intended limit. ── Sliding Window Log (accurate, memory-heavy) ───────────────────────── Store timestamp of every request in a sorted log. Count timestamps in [now - 60s, now]. If count ≥ limit → reject. Cost: O(requests) memory per client. Accurate but expensive at scale. ── Sliding Window Counter (approximate, efficient) ────────────────────── Track count for current window and previous window only. Estimate count = prev_count × (1 - elapsed/window) + curr_count Example at 01:15 (25% into the new window, 75% through old window): prev_count = 100 curr_count = 30 elapsed_in_window = 15s / 60s = 0.25 estimated = 100 × (1 - 0.25) + 30 = 75 + 30 = 105 105 > 100 limit → REJECT ← catches the edge-case burst, memory-efficient Used by: Cloudflare, NGINX, most production rate limiters

Distributed Rate Limiting with Redis

A single server can enforce limits with in-memory counters. Multiple servers need a shared counter store — Redis is the standard choice.

Single-server rate limiting (local counter): Client ──► Server A: counter["user:42"] = 47 ← lives in memory Multi-server problem (no shared state): Client ──► Server A: counter["user:42"] = 47 Client ──► Server B: counter["user:42"] = 53 ← different counter! Client ──► Server C: counter["user:42"] = 39 Total requests = 139, but each server thinks limit not exceeded. Fix: centralized counter in Redis (atomic INCR): Client │ ▼ API Gateway │ 1. INCR "rl:user:42" (atomic increment) │ 2. EXPIRE "rl:user:42" 60 (60-second window) │ 3. GET "rl:user:42" ├──► if count > 100 → 429 Too Many Requests └──► if count ≤ 100 → forward to backend ✓ │ ▼ Redis (single source of truth) "rl:user:42" = 74 TTL: 23s remaining
Lua – atomic Redis sliding window (executes atomically) 
-- KEYS[1] = rate limit key   e.g. "rl:user:42"
-- ARGV[1] = window seconds   e.g. "60"
-- ARGV[2] = max requests     e.g. "100"
-- Returns: {current_count, allowed}  (1=allowed, 0=denied)

local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
    return {current, 0}  -- denied
end
return {current, 1}  -- allowed

The Lua script executes atomically on Redis — no race condition between INCR and EXPIRE. This is the standard pattern used by Kong, NGINX rate-limit module, and most API gateways.

📈 Auto-Scaling

Auto-scaling adjusts the number of compute instances based on observed or predicted load. The goal is to have enough capacity to serve traffic without over-provisioning and paying for idle machines.

Horizontal vs Vertical Scaling

── Vertical Scaling (scale up) ───────────────────────────────────────── Before: [4 vCPU / 16 GB RAM] After: [32 vCPU / 128 GB RAM] ✓ No code changes needed ✓ No distributed-systems complexity ✗ Has a hard ceiling (biggest instance available) ✗ Usually requires downtime or live migration ✗ Single point of failure remains Good for: stateful services (databases, Zookeeper, ElasticSearch) where horizontal sharding is complex. ── Horizontal Scaling (scale out) ────────────────────────────────────── Before: [Server 1] [Server 2] After: [Server 1] [Server 2] [Server 3] [Server 4] [Server 5] ✓ No theoretical ceiling ✓ Inherently fault-tolerant (N-1 servers survive) ✓ Cheaper (many small instances vs one huge one) ✗ Requires stateless services (sessions → Redis, files → S3) ✗ Operational complexity increases Good for: stateless web/API servers, worker pools, microservices.

Reactive vs Predictive Auto-Scaling

── Reactive (threshold-based) ─────────────────────────────────────────── Metric: CPU utilization (CloudWatch, Prometheus) Rule: CPU > 70% for 3 minutes → add 1 instance CPU < 30% for 10 minutes → remove 1 instance Traffic ────────────────────────────────────────────────────────────► time ░░░░░░░░░░░▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░ Capacity 1 1 2 3 3 3 2 1 1 Problem: lag New instances take 2–5 min to start. During that lag, your existing servers absorb the spike. For sudden viral spikes, you may not scale fast enough. ── Predictive (ML-based) ──────────────────────────────────────────────── Training: "Every Monday at 9 AM, CPU spikes to 85%" "Every year at Nov 25–30, traffic is 10× baseline" Action: Pre-scale to target capacity 15 min before predicted spike No cold-start lag during the event Monday 8:45 AM: Capacity automatically raised to 5 instances Monday 9:00 AM: Traffic spike hits → servers already ready Tools: AWS Predictive Scaling, GCP Predictive Autoscaler ── Warm Pools (reduces scale-out lag) ────────────────────────────────── Keep N instances pre-warmed in stopped/standby state. On scale-out trigger: start warm instance (30 sec) instead of bootstrapping a new one (3–5 min: AMI launch + software install + warm-up). Trade-off: pays for stopped instance storage, saves on scale-out latency.
Cool-down period Always set a cool-down period after a scale-in event (typically 5–15 minutes). Without it, you get thrashing: the metric drops below threshold → remove instance → metric spikes → add instance → repeat. Cool-down prevents this oscillation.

🌐 Traffic Routing

Geographic & Latency-Based Routing

DNS is your first load balancer for global systems. Users in Tokyo should not connect to servers in Virginia. Route 53 and Cloudflare resolve DNS to the nearest healthy region before the request even leaves the user's network.

User in Tokyo │ 1. DNS lookup: api.myapp.com ▼ [DNS Resolver] │ 2. Route 53 / Cloudflare GeoDNS │ checks: latency to us-east-1 = 230ms │ latency to ap-northeast-1 = 8ms │ │ 3. Returns IP of ap-northeast-1 load balancer ▼ [ap-northeast-1 LB] │ ▼ [Tokyo servers] ← 8ms round-trip instead of 230ms Types: Latency-based: route to region with lowest latency for that client Geolocation: route by client's country (for data residency / GDPR) Geoproximity: route by geographic distance (with traffic bias weights) Failover: primary region → secondary region if primary unhealthy

Canary Deployments & Blue-Green

── Canary Deployment ──────────────────────────────────────────────────── v1.0 (stable) ◄──── 90% of traffic (9 out of 10 requests) v1.1 (canary) ◄──── 10% of traffic (1 out of 10 requests) Week 1: 10% to v1.1 → monitor error rate, p99 latency, business metrics Week 2: 50% to v1.1 → still healthy? Week 3: 100% to v1.1 → v1.0 decommissioned If v1.1 shows elevated errors → route 0% back to v1.1 instantly Implementation: • AWS ALB: weighted target groups • Kubernetes: two Deployments with different replica counts • Istio / Envoy: traffic weight in VirtualService spec • Feature flags: route specific user cohorts to new code ── Blue-Green Deployment ──────────────────────────────────────────────── Blue (v1.0) ◄──── 100% production traffic Green (v1.1) idle (deploy, integration test, load test here) Switch: Blue (v1.0) idle (kept for instant rollback, 15–30 min) Green (v1.1) ◄──── 100% production traffic How to switch: change DNS CNAME, or change LB target group Rollback: switch back in <60 seconds if problems arise Cost: requires 2× compute capacity during transition period.

Consistent Hashing for Distributed Services

When you shard a service (cache, database proxy, session store) across N nodes, consistent hashing minimizes reshuffling when nodes are added or removed. This is distinct from load-balancing HTTP traffic — it applies to key-based routing.

Without consistent hashing (simple modulo): 3 cache nodes: key % 3 Add 4th node: key % 4 75% of keys now map to a different node → cache miss storm With consistent hashing: Virtual hash ring (0 → 2^32): Node A (pos: 1,000,000) ● ┌───────────┘ 0 ●──────────────────────────────────────────● 2^32 └───────────┐ ● Node B (pos: 2,100,000) "session:user_42" hashes to 1,500,000 → next clockwise node → Node B Add Node C at position 1,200,000: → Only keys between 1,000,000 and 1,200,000 move to Node C → ~1/N of all keys remapped, not all Virtual nodes: Each physical node gets 100–200 "virtual" positions on the ring. Ensures even distribution even with few physical nodes. Real-world use: Redis Cluster, Apache Cassandra, DynamoDB, Memcached, CDN edge-node selection, database connection routing.

👥 Engineer Perspectives

The same traffic shaping decision looks entirely different depending on who's in the room. Here's what each role owns and prioritizes.

🖥️
Infrastructure Engineer
Cloud resources · Provisioning · Cost · Auto-Scaling Groups

My first question: ALB or NLB? For HTTP/HTTPS API traffic, ALB is the default — Layer 7 routing, path-based rules, SSL termination, WebSocket support, and per-target health checks. For database connection pooling or any raw TCP workload, NLB is better — it's pass-through TCP with microsecond latency and millions of connections per second.

Cost matters: ALBs charge by the hour plus by LCU (Load Capacity Unit) — a function of new connections, active connections, processed bytes, and rule evaluations. Under heavy traffic, LCU costs can exceed the instance cost. Understand your traffic shape before choosing.

For Auto-Scaling Groups: I define min=2, max=20, desired=4. I attach CloudWatch alarms to scale-out on CPU>70% and scale-in on CPU<30%. The hard-earned lesson: scale-in cooldown must be longer than scale-out cooldown (scale out fast, scale in slow). Set scale-in cooldown to 10–15 minutes. Otherwise you get thrashing — scale in during a lull, then immediately scale back out when the next request wave hits.

🌐
Network Engineer
DNS · Bandwidth · BGP · DDoS · Latency

Before the load balancer even comes up, I'm thinking: single-region or multi-region? If your users are global, DNS is your most impactful load balancer. Route 53 latency-based routing or Cloudflare GeoDNS resolves the API hostname to the closest healthy region. That's a 100–200ms improvement for distant users — much bigger than anything you can do within a single region.

For DDoS: rate limiting at the application LB is too late. I want volumetric attacks absorbed at the CDN/edge layer (Cloudflare Magic Transit, AWS Shield Advanced). TCP SYN flood protection happens at the network layer before your LB even sees the packets. The LB is for application-level distribution, not threat absorption.

DNS TTL design: low TTL (30–60s) enables fast failover when a region goes down, but increases DNS resolver load. High TTL (300s+) reduces resolver traffic but slows failover. For production traffic routing I use 60s TTL; for canary or blue-green switches I temporarily drop to 30s, then raise it back.

🏗️
Platform Engineer
Kubernetes · Ingress · Service Mesh · HPA · CI/CD

In Kubernetes, we don't use a classic LB directly — the Ingress controller handles Layer 7 routing. I choose between NGINX Ingress (battle-tested, wide plugin support) or Traefik (better dashboard, native K8s integration). Rate limiting can be configured at the Ingress level via annotations, or at the API gateway layer (Kong, NGINX Plus, Envoy).

For auto-scaling: HPA (Horizontal Pod Autoscaler) scales pods based on CPU, memory, or custom metrics (queue depth via KEDA — Kubernetes Event-Driven Autoscaling). The critical dependency: HPA only helps if new pods start fast. A JVM service with 3-minute startup time or a model that loads 2GB from S3 on boot will burn during a spike while HPA waits for pods to become ready. For these, I pre-scale or use warm pools.

Service mesh (Istio/Envoy) enables per-service traffic policies: circuit breaking, retries, timeout budgets, and canary splits — all without touching application code. The trade-off is operational complexity: service mesh adds 1–3ms of latency per hop and requires significant expertise to operate correctly.

🔒
Security / Cyber Engineer
DDoS · Bot Detection · SSL/TLS · WAF · Rate Limit as Defense

Rate limiting is my primary defense against credential stuffing (bots trying username/password pairs), API abuse, and scraping. The design of the limit matters enormously: per-IP alone is weak — botnets distribute across thousands of IPs. The right design is tiered: unauthenticated users get 10 req/min, authenticated free tier gets 100 req/min, paid users get 1000 req/min. Different limits for login endpoints (5 req/min) vs read-only endpoints (1000 req/min).

SSL termination at the LB: always terminate TLS at the LB, not at each backend server. This offloads cipher negotiation from every backend (expensive for CPU), enables certificate management in one place, and allows the LB to inspect HTTP headers for routing and WAF rules. Ensure the LB-to-backend path is on a private network (VPC internal, not public internet).

If compliance requires end-to-end encryption (PCI-DSS, HIPAA), use SSL passthrough — the LB routes by SNI without decrypting. But then you lose Layer 7 routing, WAF inspection, and header-based rules. Evaluate whether the compliance requirement actually mandates E2E encryption or just "encryption in transit" (which TLS termination at LB satisfies).

📊
Data Engineer
Read Replicas · Connection Pooling · Replication Lag

Load balancing for read replicas is a pattern I use constantly. Primary database handles writes. Read replicas handle analytics queries, dashboards, and read-heavy API paths. I put a proxy (ProxySQL, PgBouncer, HAProxy) in front of the replicas and route SELECT traffic there. This takes 80–90% of query load off the primary.

The critical caveat: replication lag. Reads from replicas may be 0–30 seconds behind the primary. For analytics dashboards this is fine. For "did my payment go through?" this is not. My routing rule: writes and reads that require read-your-own-write consistency go to primary. All other reads go to replicas.

Connection pooling becomes critical after you add a load balancer. Going from 1 app server to 10 servers, each with a connection pool of 20, means 200 simultaneous DB connections. PostgreSQL starts degrading at ~100–200 connections and fails around 500–1000. Use PgBouncer (for Postgres) or ProxySQL (for MySQL) as a connection pool in front of the DB. They hold hundreds of app-facing connections but maintain only 10–50 connections to the actual database.

🤖
ML / AI Engineer
Inference Cost · Shadow Traffic · Model Version Routing

Model inference is expensive — a single call to a large model can take 50–500ms and saturate a GPU. I rate-limit aggressively at the model serving layer: not by generic API call, but by inference call. Each user gets N inference calls per minute, not N API calls. This prevents one user from monopolizing GPU time.

Shadow traffic for model rollout: I route 1–5% of production requests to the new model version in shadow mode — the response is not shown to users, but the inference runs. This lets me benchmark the new model under real traffic distribution (real inputs, real concurrency) before switching any production traffic. Only after shadow shows acceptable latency and quality do I run a canary split.

For LLM serving: GPU memory is the bottleneck, not CPU or network. Horizontal scaling of GPU instances requires careful batching — serving infrastructure (vLLM, TGI, Triton) handles request batching to maximize GPU utilization. The "load balancer" for LLM serving is actually the batching scheduler inside the serving framework, not a traditional network LB.

⚙️
Backend Engineer
Stateless Design · Graceful Shutdown · Connection Pooling

The LB adds three requirements I must design for. First: statelessness. No in-memory session state. Any data that must survive request routing goes to Redis, a database, or shared storage — not to an instance variable. Second: my /health endpoint must respond quickly (<200ms) with real dependency checks. A health check that queries the DB and takes 2 seconds will cause the LB to mark the server unhealthy under load.

Third: graceful shutdown. When the LB or auto-scaler removes my instance, it sends a SIGTERM. I must: stop accepting new connections, finish in-flight requests (drain), close DB connections, then exit. Without this, the LB removes the instance while it's still processing requests — clients get TCP RST. Kubernetes pod termination grace period (default 30s) + preStop hook give me a window to drain.

After we horizontally scaled from 1 server to 10 servers, our DB started getting connection errors. The culprit: 10 servers × 20 pool connections = 200 connections, exceeding Postgres's default limit of 100. Fix: reduce pool size per server to 5–8, and add PgBouncer. This is the most common gotcha when first scaling horizontally.

🎨
Frontend Engineer
WebSocket Affinity · CORS · Timeout Config · Retry Logic

The LB is mostly invisible to me — until it breaks something. WebSocket connections are the biggest issue: WebSockets are long-lived persistent connections. If the LB doesn't support sticky sessions (or the session cookie expires), the connection gets routed to a different server mid-stream — and the new server has no state for that WebSocket. Fix: configure sticky sessions for /ws/* paths, or better, use a stateless WebSocket router backed by Redis Pub/Sub.

CORS: if the LB terminates SSL and changes the origin domain (e.g., routes api.myapp.com → internal-lb.myapp.com), CORS preflight requests will fail because the Origin header doesn't match. The backend needs to allow the correct origin, or the LB needs to proxy the correct host header.

ALB and NGINX have default timeouts (60s for ALB idle timeout, 60–75s for NGINX). Long file uploads or slow API responses that exceed these timeouts get dropped mid-stream. For large file uploads I configure multipart chunked upload; for long-running API calls I switch to async (202 Accepted + polling) rather than fighting timeout configs across multiple layers.

📈
SRE / Reliability Engineer
SLOs · Health Checks · On-Call · Capacity Planning

My SLO for the load balancer: 99.99% availability (52 minutes downtime/year), p99 added latency <5ms, error rate <0.05%. The LB is our most critical single point of failure — if it fails, everything behind it fails. Solution: multi-AZ LB deployment with anycast or Route 53 health checks. AWS ALB is inherently multi-AZ. Self-managed NGINX needs an active-passive pair with a VIP (virtual IP) and keepalived for failover.

For capacity planning I use: (current p99 latency) × (current throughput) × (safety factor of 1.5). If my p99 is 50ms and I'm processing 1000 req/sec, one server can handle at most 20 requests in flight (1s / 50ms = 20). At 1000 req/sec I need at least 50 servers (1000/20), plus 50% headroom = 75 servers. I run this math before every big event (product launch, Black Friday) and pre-scale manually.

Connection draining (a.k.a. "deregistration delay") is the single most important setting for zero-downtime deployments. When I deregister an instance from the target group, the LB stops sending new requests to it but keeps existing connections alive for the drain period (default: 300 seconds on ALB). Without it, in-flight requests get TCP RST the moment the instance is removed. I set drain to 30s for APIs, 120s for anything with long-lived connections.

🎯 Real Interview Problems

These three problems are asked repeatedly across FAANG and top-tier companies. Each one is primarily a traffic shaping problem — knowing the patterns above gives you the vocabulary to answer them fluently.

Problem 01
Design a Distributed Rate Limiter
Backend Infrastructure Security Redis

The Scenario

Design a rate limiter for a public API serving 10M users. Limit: 100 requests per user per minute. The service runs on 50 servers. Must add <5ms latency overhead. Must handle 100K req/sec at peak.

What Makes It Hard

At 50 servers, local counters don't work — each server has a different count for the same user. You need a shared, atomic counter store. That store becomes a bottleneck and a SPOF unless you design it carefully.

Architecture

Client │ ▼ API Gateway (50 instances) │ │ 1. INCR "rl:{user_id}" ─────────────────────────┐ │ 2. EXPIRE "rl:{user_id}" 60 │ │ 3. GET "rl:{user_id}" ▼ │ Redis Cluster │ (3 primary shards, ├── count > 100 → HTTP 429 3 read replicas, │ Retry-After: 23s persistent AOF) │ └── count ≤ 100 → forward to Backend Services Redis cluster sharding by user_id: user_id % 3 → shard 0, 1, or 2 Each shard handles ~33K req/sec (Redis: 1M ops/sec per node) Read replicas absorb GET calls, primaries handle INCR + EXPIRE

Key Design Decisions

  • Algorithm: Sliding window counter (prev window × overlap + curr window) — more accurate than fixed window, cheaper than log.
  • Atomicity: Lua script on Redis ensures INCR + EXPIRE executes atomically — no race condition.
  • Failure mode: If Redis is down, fail open (allow requests) not fail closed (block everything). Document this in the SLO.
  • Headers: Always return X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset so clients can self-throttle.
  • Tiers: Unauthenticated: 10/min. Free: 100/min. Paid: 1000/min. Login endpoints: 5/min (credential stuffing protection).
Problem 02
Design a Social Media Feed at Scale (Traffic Angle)
Load Balancing Rate Limiting Fan-out Celebrity Problem

The Scenario

Design the tweet delivery system for a Twitter-scale platform. 300M daily active users. Peak: 6,000 new tweets/sec. A celebrity (Lady Gaga, 100M followers) tweets — how do you not bring down the service?

The Celebrity Problem

If you push every tweet to every follower's feed synchronously, one celebrity tweet creates 100M write operations in seconds. No message queue can absorb that without significant delay. The solution is a hybrid push/pull strategy based on follower count.

Architecture

Write Path (tweet is created): User ──► API Gateway [Rate limit: 300 tweets/3hr per user] │ ▼ Tweet Service (stores tweet in DB, gets tweet_id) │ ├──► Tweet Cache (Redis, by tweet_id) │ └──► Fan-out Service │ Is follower_count < 10,000? / \ YES NO (celebrity) │ │ ▼ ▼ Push to each follower's Don't push. Store tweet_id Timeline Cache in celebrity tweets index only. Read Path (user loads their feed): User ──► API Gateway [Rate limit: 100 feed reads/min] │ ▼ Feed Service │ ├── Fetch from personal Timeline Cache (pushed tweets from friends) │ ├── Fetch celebrity tweet_ids this user follows │ └──► lookup tweets from Tweet Cache (pull on read) │ └── Merge + sort + paginate → return feed

Key Decisions

  • Rate limits by operation type: tweet creation (300/3hr), feed reads (100/min), likes (1000/min), follows (400/day).
  • Fan-out threshold: <10K followers → push. >10K → pull on read. This prevents one celebrity tweet from generating 100M write operations.
  • Load balancer for read replicas: Feed service routes to DB read replicas for timeline reads. Replication lag (<1s) is acceptable for feeds.
  • Auto-scaling trigger: Tweet fanout queue depth — if queue backs up, scale fan-out workers horizontally, not vertically.
Problem 03
Design an API Gateway
Load Balancing Rate Limiting Auth Routing Observability

The Scenario

You have 30 microservices. Clients (web app, mobile, third-party partners) are calling each service directly. Design an API Gateway that provides a single entry point, adds auth, rate limiting, and routing — without becoming a bottleneck.

Architecture

Client Request GET /v1/orders/456 │ ▼ ┌──────────────────────────────────────────────────────────────────────────┐ │ API Gateway (horizontally scaled) │ │ │ │ Step 1: Authentication │ │ Validate JWT / API key → reject if invalid (HTTP 401) │ │ Enrich request: inject user_id, tenant_id into headers │ │ │ │ Step 2: Rate Limiting │ │ Check Redis counter per API key / user tier │ │ Reject if over limit (HTTP 429, Retry-After header) │ │ │ │ Step 3: Routing │ │ /v1/users/* ──► User Service (LB across 5 instances) │ │ /v1/orders/* ──► Order Service (LB across 8 instances) │ │ /v1/products/* ──► Product Service (LB + read cache) │ │ /v1/search/* ──► Search Service (separate cluster) │ │ │ │ Step 4: Transform │ │ Request: normalize headers, strip internal headers, add trace ID │ │ Response: aggregate errors, strip internal fields, add CORS headers │ │ │ │ Step 5: Observe │ │ Log: user_id, endpoint, latency, status_code → centralized log store │ │ Metric: p50/p99/p999 latency, error rate per route │ │ Trace: inject X-Trace-ID, propagate to all downstream services │ └──────────────────────────────────────────────────────────────────────────┘ │ │ │ ▼ ▼ ▼ User Service Order Service Product Service

Avoiding the Bottleneck

  • Horizontal scaling: The gateway is stateless. Deploy 10–50 instances behind a cloud LB. Each instance connects to shared Redis for rate limiting.
  • Async auth: Cache validated JWTs in Redis for their TTL period. Don't re-validate the signature on every request — signature verification is CPU-expensive.
  • Timeout budget: Gateway-level timeout of 30s. Each downstream service gets 25s (5s for gateway overhead + network). Services that exceed their budget get a 504 from the gateway.
  • Circuit breaker per route: If Order Service returns 5xx for 50% of requests over 10s, open the circuit — stop forwarding to Order Service, return a cached response or 503. This prevents a slow downstream from backing up the gateway's connection pool.

❌ Anti-patterns at Scale

These are the mistakes that look fine in development and fail catastrophically in production.

  • Single LB with no redundancy The LB itself becomes your single point of failure. If it goes down, nothing works. Use multi-AZ LB deployment (AWS ALB handles this automatically) or active-passive NGINX pair with keepalived.
  • Shallow health checks TCP-level health checks pass even when the server is deadlocked or has a broken database connection. The LB keeps routing traffic to a broken instance. Always implement a deep /health endpoint that checks real dependencies.
  • Rate limiting per IP only Botnets distribute across hundreds of thousands of IPs. IP-only rate limiting is trivially bypassed. Always layer: per-IP (DDoS protection) + per-user/API-key (abuse protection) + per-endpoint (credential stuffing protection).
  • Auto-scaling without a cool-down period Metric drops below threshold → remove instance → brief spike → metric exceeds threshold → add instance → repeat. This "thrashing" wastes money and can cause instability. Set scale-in cooldown to 10–15 minutes.
  • Vertical scaling as primary strategy The instance size has a ceiling. The biggest EC2 instance is still one server — one failure point. Use vertical scaling only for stateful services where horizontal sharding is genuinely infeasible.
  • No connection draining on scale-in Removing an instance from the target group without draining immediately drops all in-flight requests for that instance. Configure deregistration delay (30–120s) and graceful shutdown in your application.
  • Sticky sessions on a single LB Sticky sessions already undermine load balancing by creating hot spots. If you additionally have only one LB, you've built a two-layer SPOF. Prefer stateless services + Redis for session storage.
  • Rate limit counter in application memory Works fine on one server. With 10 servers, each server has a different count for the same user. A user can exceed the limit by routing requests across servers. Use Redis (or another distributed store) for rate limit counters.

💡 Interview Application Tips

01

Ask traffic shape before anything

"What's the expected peak req/sec, and is traffic steady or spiky?" This single question determines your LB type, rate limiting strategy, and scaling policy.

02

Mention rate limiting proactively

Even if the problem doesn't explicitly mention it, add rate limiting. It shows security awareness and operational maturity. State the algorithm and what you're limiting (per user, per IP, per endpoint).

03

Default to horizontal scaling

When asked "how do you scale X?", always say horizontal first and explain why (stateless design, no ceiling, fault tolerance). Then mention when vertical is appropriate (databases, stateful services).

04

Know the L4 vs L7 distinction

"I'd use an ALB for Layer 7 routing since we need path-based routing and SSL termination" impresses interviewers more than "I'd use a load balancer."

05

Consistent hashing for cache nodes

If asked "what happens when you add a cache server?" the answer is "consistent hashing — only 1/N of keys remap, not all of them." Simple modulo hashing would cause a cache miss storm on scale-out.

06

Always mention health checks

"And I'd configure a deep /health endpoint that checks the DB connection pool and any downstream dependencies before the LB considers the instance healthy." This shows operational thinking that many candidates miss.

The pattern → trigger habit Train yourself to identify the trigger before naming the solution. "I see high and spiky traffic (trigger) → I reach for horizontal auto-scaling + rate limiting (pattern)" lands better than jumping to the solution name. Interviewers are evaluating your reasoning process, not just your knowledge of component names.
Clarifications
+
TCP vs UDP
TCP (Transmission Control Protocol) guarantees ordered, reliable delivery — think of it like certified mail. UDP (User Datagram Protocol) is faster but unreliable — like dropping a postcard, no guarantee it arrives. Most web traffic uses TCP. Load balancers operating at Layer 4 route TCP/UDP by IP+port; Layer 7 load balancers read HTTP headers to make smarter decisions.
+
ALB vs NLB (AWS)
ALB = Application Load Balancer — operates at Layer 7 (HTTP). Reads URLs, headers, and cookies to route traffic. Slightly slower but smarter. NLB = Network Load Balancer — operates at Layer 4 (TCP/UDP). Blindingly fast (millions of req/s), preserves source IP, used for gaming, IoT, gRPC. For most web apps: ALB. For extreme throughput: NLB.
+
Load Balancing Algorithms
Round-robin: send request 1 to server A, 2 to B, 3 to C, repeat. Simple but ignores server load. Least-connections: route to whichever server has fewest active connections — better for uneven workloads. Weighted: server A gets 70% of traffic (more powerful hardware). IP hash: same client IP always hits the same server — used for sticky sessions without cookies.
+
Health Checks
A load balancer sends periodic pings to each server (e.g., HTTP GET /health every 5 seconds). If a server fails 3 consecutive checks, it's removed from the pool. When it recovers and passes checks, it's added back. Without health checks, the load balancer sends traffic to dead servers and users get errors.
+
Token Bucket vs Leaky Bucket
Token Bucket: imagine a bucket that refills at a fixed rate (e.g., 10 tokens/second, max 100). Each request consumes one token. If empty, request is rejected. Allows bursting up to bucket size. Leaky Bucket: requests pour in at any rate but leak out at a fixed rate — smooths traffic to a constant output rate. Token bucket is more common in APIs because it allows short bursts.
+
Sliding Window Counter
Fixed window: count requests per minute. Problem: a user sends 100 req at 0:59 and 100 more at 1:01 — technically 200 req in 2 seconds but both windows show 100. Sliding window: track exact timestamps of each request and count those in the last 60 seconds. More accurate but uses more memory. Redis sorted sets make sliding windows efficient.
+
What to Rate Limit By
By IP address: anonymous users, DDoS prevention. Simple but easily bypassed (VPNs, shared IPs in offices). By user ID / API key: authenticated users get their own quota. By endpoint: stricter limits on expensive operations (POST /search) than cheap ones (GET /status). Production systems layer multiple: global IP limit + per-user limit + per-endpoint limit.
+
The Hash Ring
Imagine a clock face (0–360°). Hash each server to a position on the ring. To route a request, hash the request key and find the nearest server clockwise. Adding a server: only the requests between it and the previous server reroute — not everyone. Without consistent hashing, adding one server to N remaps N/(N+1) of all keys.
+
Virtual Nodes
Problem with basic consistent hashing: with 3 servers, each occupies 1/3 of the ring but actual positions may be uneven, causing one server to handle 50% of traffic. Fix: virtual nodes — each physical server gets 150 virtual positions on the ring. Load is distributed far more evenly. Cassandra defaults to 256 virtual nodes per server.
+
Scale-Out vs Scale-Up
Scale-up (vertical): make one server bigger — more CPU, more RAM. Simple, no code changes, but has a ceiling (you can't add infinite RAM to one machine) and has a single point of failure. Scale-out (horizontal): add more servers. More complex (needs load balancer, stateless design) but unlimited ceiling and no single point of failure. Cloud systems prefer scale-out.
+
HPA, VPA, KEDA (Kubernetes)
HPA = Horizontal Pod Autoscaler: scales pod count based on CPU/memory or custom metrics. VPA = Vertical Pod Autoscaler: adjusts CPU/memory requests for existing pods. KEDA = Kubernetes Event-Driven Autoscaler: scales based on queue depth, Kafka consumer lag, or any external metric. Most production Kubernetes uses HPA with KEDA for event-driven workloads.
+
ASG / Auto Scaling Group (AWS)
An ASG is an AWS group of EC2 instances that automatically adds or removes servers based on CloudWatch alarms (CPU > 70% → add one server, CPU < 30% → remove one). Define: min size, max size, desired capacity. Pair with an ALB to automatically add new instances to the load balancer pool. Equivalent: GCP Managed Instance Groups, Azure VM Scale Sets.
