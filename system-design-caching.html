Caching &
Latency Reduction

When response time is dominated by slow data retrieval — database queries, external API calls, disk reads — a cache layer serves hot data from fast memory, turning 50ms round-trips into sub-millisecond lookups.

⚡ Trigger: p99 latency above SLO, DB CPU-bound on reads 🎯 Goal: High hit ratio, low staleness, no stampede 👥 Primary owners: Backend, Infra, Data
When to reach for this pattern Your database is the bottleneck on read queries. The same data is read far more often than it's written. Response time SLOs are being missed. Read traffic is scaling faster than you can vertically scale the database. Any of these is a trigger for a caching layer.

🔴 The Core Problem

Every read path without a cache hits the database. At high read volume, the database becomes the bottleneck — not because writes are too fast, but because reads dominate and the DB is doing the same work repeatedly for the same data.

Without cache — same data fetched from DB on every request: User A ──► API Server ──► Database [SELECT * FROM products WHERE id=42] 50ms User B ──► API Server ──► Database [SELECT * FROM products WHERE id=42] 52ms User C ──► API Server ──► Database [SELECT * FROM products WHERE id=42] 49ms ...10,000 users/sec ↑ identical query, 10,000 times Result: DB CPU at 90%, p99 latency at 800ms, query queue backing up. With cache — DB fetched once, served from memory for all subsequent requests: User A ──► API Server ──► Cache MISS ──► DB ──► Store in cache 50ms User B ──► API Server ──► Cache HIT ──► Return cached value 0.5ms User C ──► API Server ──► Cache HIT ──► Return cached value 0.5ms ...10,000 users/sec 99% hit ratio → DB sees 100 req/sec Result: DB CPU at 8%, p99 latency at 2ms, DB query queue empty.

The key insight: read traffic rarely needs the freshest possible data for every request. A product page that was accurate 10 seconds ago is good enough for 99.9% of use cases. The 10-second staleness window is what the cache exploits.

🏗️ Cache Topology

Modern systems layer multiple caches at different distances from the data source. Each layer trades freshness for speed. Closer to the user = faster but smaller; closer to the DB = slower but larger and more accurate.

User │ ▼ CDN Edge (L3) ← Cloudflare, CloudFront, Fastly │ Miss (first req) Speed: 5–20ms Size: PB range Shared: globally ▼ In-Process Cache (L1) ← Python dict, Guava LoadingCache, caffeine (Java) │ Miss Speed: 0.1ms Size: MB range Shared: per-instance only ▼ Distributed Cache (L2) ← Redis, Memcached, DragonflyDB │ Miss Speed: 1–5ms Size: TB range Shared: all app servers ▼ Database / Origin ← Postgres, MySQL, MongoDB, S3 Speed: 10–200ms Size: unlimited Source of truth

L1: In-Process (Application-Level) Cache

A dictionary or map living in the same process as the application. Zero network overhead — a lookup is a pointer dereference. Used for data that is read extremely frequently, changes very rarely, and is the same for all users.

Example: Cache country list (changes once a year) Application startup: countries = load_from_db() # one DB call at boot _cache = {"countries": countries} # in-process dict, lives forever Every request: return _cache["countries"] # 0.05ms — pure memory access Problems with L1 cache: • Each server has its own copy → 10 servers = 10 different versions of the same data • An update to the DB is not reflected until each server restarts or its local cache expires • Memory leak risk if keys grow unbounded — always set a max size + eviction policy Good for: • Static config (feature flags, country codes, supported currencies) • Compiled regex patterns, parsed templates • Data fetched at startup that changes < once per day

L2: Distributed Cache (Redis / Memcached)

A shared in-memory store reachable by all application servers. The standard cache layer for production systems. Redis is the default choice — it supports rich data structures (strings, hashes, lists, sets, sorted sets, bitmaps, streams) and optional persistence.

All app servers share one Redis cluster: App Server 1 ─┐ App Server 2 ──┤──► Redis Cluster ──► Database (on cache miss) App Server 3 ─┘ (3 shards, 6 nodes) Redis data structures and their use cases: STRING "user:42:name" = "Alice" → simple key-value, serialized JSON HASH "user:42" = {name, email, age} → object fields, partial updates SORTED SET "leaderboard" = {alice:9800, bob:9200} → rankings, top-K queries LIST "user:42:feed" = [post_id_1, post_id_2] → feed, queue, recent items SET "user:42:following" = {user_id_1, ...} → membership checks O(1) BITMAP "daily_active" = bit per user_id → HyperLogLog for unique counts Redis vs Memcached: Redis: data structures, persistence, pub/sub, Lua scripts, cluster mode Memcached: simpler, multi-threaded, pure strings only, slightly faster for simple GET/SET

L3: CDN / Edge Cache

A globally distributed network of edge servers (Points of Presence — PoPs) that cache content close to the user. The first cache hit happens before the request even leaves the user's region.

User in Tokyo │ GET /images/banner.png ▼ Cloudflare Tokyo PoP ← edge server 8ms from user │ Cache HIT → return immediately 8ms total │ │ Cache MISS → forward to origin ▼ Origin Server (US-East) ← 160ms RTT from Tokyo │ Send image + Cache-Control: max-age=86400 ▼ Tokyo PoP caches image ← all subsequent Tokyo requests: 8ms CDN providers: Cloudflare, AWS CloudFront, Fastly, Akamai, GCP CDN Cache hit ratios by content type (typical): Static images/CSS/JS: 99%+ (long TTL, content-addressed URLs) Video segments: 95%+ (large files, re-watched) API responses: 60–85% (depends on how query-specific the response is) HTML pages: 50–75% (if not personalized)

📖 Read Strategies

Cache-Aside (Lazy Loading)

The application manages the cache explicitly. On a read: check the cache. Hit → return. Miss → load from DB, populate cache, return. This is the most common pattern — the application code owns the caching logic.

Cache-Aside read flow: def get_user(user_id): key = f"user:{user_id}" # Step 1: Check cache cached = redis.get(key) if cached: return deserialize(cached) # cache HIT — 0.5ms # Step 2: Cache miss — load from DB user = db.query("SELECT * FROM users WHERE id = ?", user_id) # Step 3: Populate cache for next request redis.setex(key, 300, serialize(user)) # TTL = 5 minutes return user # 50ms first time only Characteristics: ✓ Only caches data that is actually read (no wasted memory) ✓ Cache failure is non-fatal — requests fall back to DB ✓ Application controls exactly what is cached and for how long ✗ First request after cold start / expiry always hits DB (cold start penalty) ✗ Cache can become stale between TTL and event-driven invalidation

Read-Through Cache

The cache itself fetches from the DB on a miss, invisible to the application. The application only ever talks to the cache — it never touches the DB directly for reads.

Read-Through flow: Application ──► Cache Layer ──► Database (on miss only) ↑ Application always reads from here. Cache handles miss → DB fetch → populate → return. Examples: AWS DAX (DynamoDB Accelerator), read-through proxies Cache-Aside vs Read-Through: ┌─────────────────────────────────────────────────────────────────────┐ │ Cache-Aside: App knows about both cache AND DB │ │ Read-Through: App only knows about cache; cache knows about DB │ └─────────────────────────────────────────────────────────────────────┘ When to prefer Read-Through: • Multiple services reading the same data — centralize cache logic • ORM/DAL layer that can abstract the DB access • When you want consistent caching behavior across all readers

✍️ Write Strategies

How you handle writes determines cache consistency. There is no perfect answer — every strategy trades write latency for data freshness or durability risk.

Write-Through

Write-Through: write to cache AND database synchronously Client ──► App ──► Write to Cache ──► Write to DB ──► Response def update_user(user_id, data): db.update("UPDATE users SET ... WHERE id = ?", user_id, data) redis.setex(f"user:{user_id}", 300, serialize(data)) ✓ Cache is always consistent with DB after every write ✓ Subsequent reads always get fresh data from cache ✗ Write latency = DB write time + cache write time (additive) ✗ Writes data to cache even if it will never be read again (wasted memory) Best for: data that is read frequently after writes (user profiles, settings)

Write-Back (Write-Behind)

Write-Back: write to cache immediately, DB write is deferred/async Client ──► App ──► Write to Cache ──► Return immediately (fast!) │ async worker │ ▼ Write to DB (batched, every N seconds) ✓ Extremely fast writes — client sees success after cache write only ✓ DB writes can be batched — fewer, larger writes are more efficient ✗ Data loss risk: if cache crashes before async DB write, data is gone ✗ More complex — requires durable queue or write-behind log ✗ Inconsistency window: DB lags behind cache by seconds to minutes Best for: high-write, loss-tolerant data (view counts, like counts, analytics events) Not for: financial transactions, order records, anything requiring durability

Write-Around

Write-Around: write only to DB, skip the cache entirely Client ──► App ──► Write to DB only ──► Response (cache not touched) Next read for this key: Client ──► App ──► Cache MISS ──► DB ──► Populate cache ──► Return ✓ Prevents polluting cache with data that may never be re-read ✓ Cache memory used only for actually-read data ✗ First read after a write always goes to DB (cold read penalty) ✗ Temporary inconsistency: old cached value may be returned until TTL expires Best for: write-heavy data that is rarely re-read (batch jobs, archive uploads, event logs), or infrequently read items where cache pollution is a concern
Practical rule of thumb Write-through for user-facing data where reads follow writes (profiles, settings). Write-around for batch/bulk data unlikely to be re-read soon. Write-back only when write throughput is the bottleneck and data loss is acceptable (view counts, analytics).

🗑️ Cache Invalidation

"There are only two hard things in computer science: cache invalidation and naming things." The challenge: how do you ensure clients see updated data without hammering the DB on every request?

TTL-Based Expiration

TTL (Time-To-Live): key automatically expires after N seconds redis.setex("user:42:profile", 300, value) # expires in 5 minutes t=0s: Key set, TTL = 300s t=150s: User updates their name in DB Cache still has old value. Stale for up to 150 more seconds. t=300s: Key expires. Next request → DB → fresh value → re-cache Design questions for TTL choice: ┌─────────────────────────────────────────────────────────────────────┐ │ How stale can this data be without affecting user experience? │ │ How often does this data actually change? │ │ What is the cost of a cache miss (DB query time, DB load)? │ └─────────────────────────────────────────────────────────────────────┘ Typical TTLs by data type: User profile: 5–30 min (changes rarely, stale OK for short time) Product inventory: 30–60 sec (changes often, must be fairly fresh) Session token: match auth token lifetime (15–60 min) Trending content: 10–60 sec (freshness matters for relevance) Static config: 1 hour+ (changes very rarely) API rate limit counter: exact window size (60 sec for per-minute limit)

Event-Driven Invalidation

Event-driven: explicitly delete/update cache when data changes Write path: User updates profile ──► User Service │ ┌────────┤ │ │ ▼ ▼ Update DB Delete from Cache (or publish "user_updated" event) │ Cache subscriber deletes key Next read: User reads profile ──► Cache MISS ──► DB ──► fresh value ──► re-cache ──► return ✓ Data is fresh immediately after write (no stale window) ✓ Works with event-driven architectures (Kafka, SNS, Redis Pub/Sub) ✗ Delete-on-write and populate-on-read has a race condition window ✗ If cache delete fails (network error), stale data persists until TTL ✗ More complex — requires coordination between write service and cache Best practice: combine both — event-driven delete + short TTL as safety net "Delete on write, TTL as backstop" is the production-proven pattern

Thundering Herd / Cache Stampede

The problem: a popular key expires → thousands of requests hit DB simultaneously t=0s: "trending:posts" key set, TTL=60s, 10,000 req/sec hitting this key t=60s: Key expires All 10,000 concurrent requests see a cache miss All 10,000 go to DB simultaneously DB overwhelmed → timeouts → cascading failure ── Fix 1: Probabilistic Early Expiration (PER) ──────────────────────── As key approaches expiry, a random % of requests refresh it early. The earlier you check, the higher the chance of early refresh. def get_with_per(key, ttl, beta=1.0): value, expiry = cache.get_with_ttl(key) remaining = expiry - now() if remaining - beta * log(random()) < 0: value = fetch_from_db() # refresh before expiry cache.setex(key, ttl, value) return value ── Fix 2: Mutex / Lock ────────────────────────────────────────────────── On cache miss: Try to acquire Redis lock "lock:trending:posts" (SETNX, expire 5s) If lock acquired: fetch DB → populate cache → release lock If lock NOT acquired: wait briefly, then re-check cache (now populated) ── Fix 3: Background Refresh (Proactive) ─────────────────────────────── A background worker refreshes the cache key before it expires. Application always reads from cache — never experiences a miss. Requires knowing which keys need proactive refresh (precomputed set). Best for: small set of extremely hot keys (top trending, homepage data)

🌐 CDN Patterns

Static Asset Caching

Content-addressed URLs — cache forever, invalidate by changing the URL: app.abc123.js ← Cache-Control: max-age=31536000, immutable (1 year) app.def456.js ← New version → new hash → new URL → new cache entry logo.v3.png ← Same pattern for images Why this works: Content hash in filename ensures URL only changes when content changes. CDN caches the file for 1 year — zero origin hits for returning users. Deploying new version: new hash → new URL → CDN fetches fresh → old URL still cached but app no longer references it. Without content addressing (wrong approach): app.js ← Cache-Control: max-age=3600 Deploy new version → CDN serves old version for up to 1 hour Users see stale JS → broken UI Emergency: purge CDN cache (expensive, not instant, inconsistent)

API Response Caching at CDN

Non-personalized API responses can be cached at the CDN edge: GET /api/trending/posts Response headers: Cache-Control: public, s-maxage=60, stale-while-revalidate=30 Result: CDN caches for 60 seconds. During those 60s: 1 origin request serves millions of CDN cache hits. After 60s + 30s stale window: serve stale, revalidate in background (SWR). What CAN be CDN-cached: • GET /api/products/{id} (product details — same for all users) • GET /api/trending/posts (trending feed — same for all users) • GET /api/countries (static lists) • GET /api/events/upcoming (same for all users in a region) What CANNOT be CDN-cached: • GET /api/me (personalized — use Cache-Control: private) • GET /api/user/42/notifications (user-specific) • Any response that uses Authorization header for user context • POST, PUT, DELETE, PATCH (not idempotent)

Cache-Control Headers

Cache-Control directives: public → CDN AND browser can cache private → browser only (NOT CDN) — for personalized responses no-cache → must revalidate with server before using cache (ETag check) no-store → never cache anywhere — for sensitive data (medical, banking) max-age=300 → browser caches for 300s s-maxage=600 → CDN caches for 600s (overrides max-age for CDNs only) stale-while-revalidate=30 → serve stale for 30s while refreshing async immutable → content will never change — browser never revalidates Decision guide: Is response user-specific? YES → Cache-Control: private, max-age=60 NO → Is content static and content-addressed? YES → Cache-Control: public, max-age=31536000, immutable NO → Is freshness critical? YES → Cache-Control: public, s-maxage=30, stale-while-revalidate=10 NO → Cache-Control: public, s-maxage=300

🗂️ Eviction Policies

When a cache is full, something must be removed to make room for new entries. The eviction policy determines which key gets sacrificed. Choosing the wrong policy causes hot keys to be evicted, destroying your hit ratio.

── LRU (Least Recently Used) ── default for most caches ─────────────── Access history: A → B → C → D → A → B (capacity = 3) Current cache: [A, B, D] C was evicted as least recently used ✓ Excellent for temporal locality (recently used = likely to be used again) ✓ Simple to reason about and implement ✗ A one-time scan of many keys can evict hot keys (scan pollution) Good for: general-purpose caches, hot-data access patterns ── LFU (Least Frequently Used) ───────────────────────────────────────── Access counts: A=500 B=3 C=7 D=45 Evict: B (fewest accesses over its lifetime) ✓ Retains long-term popular items (viral videos, top products) ✗ New items start with count=1 and get evicted even if they become hot ✗ Frequency counts need decay or items from past dominate Good for: recommendation caches, CDN edge caches, long-lived popularity ── FIFO (First In First Out) ──────────────────────────────────────────── Evicts the oldest inserted key regardless of access frequency or recency. Simple but ignores access patterns — often evicts still-hot data. Good for: rate limit windows, event logs, time-bucketed data ── Redis maxmemory-policy options ────────────────────────────────────── allkeys-lru → evict any key using LRU approximation ← most common volatile-lru → evict only keys with TTL set, using LRU allkeys-lfu → evict any key using LFU (Redis 4.0+) ← good for CDN volatile-lfu → evict only keys with TTL using LFU allkeys-random → evict random key (surprisingly OK for uniform access) volatile-random → evict random key with TTL volatile-ttl → evict key with shortest remaining TTL noeviction → return error on writes when full (default — almost always wrong)
Never use noeviction in production The default Redis maxmemory-policy is noeviction — Redis returns an error to the application when memory is full. Your application will crash or throw exceptions at exactly the worst moment (high traffic). Always set an eviction policy explicitly. allkeys-lru is the right default for most caches.

👥 Engineer Perspectives

Every role interacts with caching differently. Here's what each one owns and optimizes for.

🖥️
Infrastructure Engineer
Redis cluster sizing · Persistence · High availability · Cost

My first job is sizing the Redis cluster correctly. Formula: (avg_key_bytes + avg_value_bytes + 64 bytes overhead) × num_keys × 1.2 safety factor. Redis reports memory usage via INFO memory — used_memory_rss is what the OS actually allocates. I provision Redis at no more than 75% of the instance's RAM, leaving headroom for memory spikes and the fork() call during RDB snapshot.

Persistence decisions: for a pure cache, I use RDB snapshots only (save every 5 minutes, accept losing up to 5 minutes of cache data on crash — it's just a cache, the DB is the source of truth). For a cache that doubles as a session store or rate limit counter, I add AOF (append-only file) with appendfsync everysec for better durability with acceptable performance.

For HA: Redis Sentinel for a single shard (primary + 2 replicas + 3 sentinel processes for quorum). Redis Cluster for horizontal scale (6 nodes minimum: 3 primary shards, 3 replicas). Managed services (AWS ElastiCache, Redis Cloud) handle failover automatically at higher cost — worth it for most teams.

🌐
Network Engineer
CDN PoP coverage · Egress cost · Latency · Connection pooling

CDN hit ratio directly controls my egress bill. Every cache miss at the edge → origin pull → egress charges. At scale, the difference between 85% and 95% hit ratio is not 10% more traffic to origin — it's the difference between manageable and catastrophic egress costs. I optimize hit ratio by: increasing TTL where freshness allows, ensuring cache keys don't include query parameters that vary per user, and warming the CDN after deploys.

Redis latency: the round-trip time to Redis should be <1ms for same-AZ co-located caches. If Redis is in a different AZ (cross-AZ latency = 1–2ms), or a different region (10–50ms), the cache stops being fast. I always co-locate Redis and app servers in the same AZ. Connection pooling matters: opening a new TCP connection to Redis per request costs 0.5–1ms. Keep a persistent connection pool — minimum 5 connections per app server thread/goroutine.

CDN cache bypass headers: some debugging tools or bots can send headers that bypass the CDN cache (Cache-Control: no-cache, Pragma: no-cache). In production I configure the CDN to ignore these request headers — only origin response headers should control CDN caching behavior. Otherwise, a crawler with no-cache headers can drain your CDN and hammer origin.

🏗️
Platform Engineer
Cache as a platform service · K8s Redis patterns · Cache warm-up

I provide Redis as a shared platform service — a multi-tenant Redis cluster where each service gets its own key namespace prefix (svc-a:*, svc-b:*). This is cost-effective but requires enforcing key prefixes and memory quotas per service (Redis doesn't natively enforce per-prefix quotas, so I track usage via keyspace notifications and alert when a service exceeds its allocation).

In Kubernetes: Redis is deployed as a StatefulSet (not a Deployment) because it needs stable pod identity and persistent storage (PV/PVC for RDB snapshots). The headless service gives each pod a stable DNS name. For production, I prefer a managed Redis (ElastiCache) over self-managed in K8s — running stateful workloads in K8s adds operational complexity for little gain unless you need very custom Redis configurations.

Cache warm-up on deployment: a new app instance starts with an empty L1 cache and generates extra L2 cache misses. I add a warm-up step in the startup hook that pre-fetches the 100 most-accessed keys from Redis into the local in-process cache before the pod starts accepting traffic. The readiness probe doesn't pass until warm-up completes — prevents a cold instance from getting traffic before it's ready.

🔒
Security / Cyber Engineer
Redis auth · Encryption · Cache poisoning · PII in cache

Redis ships with no authentication and no TLS by default. In any production environment: (1) enable requirepass with a strong password, (2) bind Redis to a private IP only (never 0.0.0.0), (3) enable TLS (tls-port in Redis 6+), (4) put Redis on a private subnet with a security group allowing only app server IPs. A misconfigured Redis open to the internet is one of the most common breach vectors — attackers use Shodan to find open Redis instances and execute arbitrary commands.

PII in cache: what you cache is what you must protect. If you cache user objects containing name, email, and address, the cache needs the same data-at-rest protection as the database. AWS ElastiCache supports encryption at rest. For self-managed Redis: consider encrypting values at the application layer before storing in Redis, using AES-256. Key: the encryption adds latency but removes the risk of cached PII being exposed if Redis memory is dumped.

Cache key injection / poisoning: if the cache key is derived from user input without sanitization, an attacker can craft a key that collides with another user's cached data. Example: if cache key = "user:" + request.headers["X-User-ID"] and the header is user-controlled, the attacker sets the header to another user's ID. Fix: always derive cache keys from authenticated, server-side identity — never from unvalidated request parameters.

📊
Data Engineer
Cache key design · Read patterns · Aggregate caching · Stampede at data scale

Cache is a read concern — design keys around your read access patterns, not your write access patterns. If your API serves user data by user_id, your cache key is user:{user_id}. If it serves by email, you need user_email:{email} → user_id, then user:{user_id}. Storing the same data under multiple keys for different access patterns is normal and expected.

Cache key versioning is how you invalidate the entire cache without flushing it. Instead of user:42:profile, use v1:user:42:profile. When the schema changes, bump the version to v2: — all old keys are now unreachable (they'll expire via TTL) and new reads populate fresh v2 keys. Zero downtime invalidation of potentially millions of keys.

For aggregated data (leaderboards, trending counts, daily active users), I use Redis native data structures rather than caching serialized DB query results. A Redis Sorted Set for a leaderboard is more memory-efficient and query-efficient than caching a JSON array. ZADD, ZRANK, ZRANGE are O(log N) — faster than even a cached SELECT query at scale.

🤖
ML / AI Engineer
Embedding cache · Feature store serving layer · Prediction cache

Embedding caches: computing embeddings is expensive (GPU time, API costs). If the same text input appears multiple times — product descriptions, FAQ entries, support ticket templates — cache the embedding keyed by a hash of the input text. Content hash as key ensures the cache is invalidated automatically when the text changes. Redis string with a 24-hour TTL works well for most embedding caches.

The online feature store is a specialized cache. Feast, Tecton, and similar tools use Redis as the low-latency serving layer for feature vectors. A feature store fetches precomputed features (last 30 purchases, user demographics, real-time event counts) from Redis in <5ms to feed into inference. The alternative — computing features in real-time from raw data — would add 100–500ms to every inference request. The trade-off: feature freshness is bounded by the feature pipeline update frequency (typically minutes to hours).

LLM prediction caching: for deterministic LLM calls (same system prompt + same user input), cache the completion. Hash the full prompt as the key. For user-facing chat, this rarely helps (each conversation differs). For batch processing or API users making identical calls, it can cut inference costs 40–60%. Semantic caching (cache if embeddings of input are similar, not just identical) is a newer pattern — higher complexity, higher cache hit rate for near-duplicate queries.

⚙️
Backend Engineer
Cache-aside pattern · Serialization · Key namespacing · Connection pooling

The cache-aside pattern is my daily implementation. Three rules I always follow: (1) Set a TTL on every key — keys without TTL are a memory leak. (2) Use namespaced keys like v1:user:{id}:profile — the version prefix enables bulk invalidation without FLUSHDB. (3) Handle cache errors gracefully — if Redis is down, fall back to the DB. Never let a cache error propagate to the user as a 500.

Serialization format matters at scale. JSON is human-readable but large. MessagePack is compact binary — 20–40% smaller than JSON, faster to deserialize. Protocol Buffers (protobuf) are even smaller and have schema evolution built-in. For a cache storing millions of objects, switching from JSON to MessagePack can reduce Redis memory usage by 30% and improve hit throughput significantly.

The most common bug I see: caching None/null on DB miss. If the DB returns no result, you must cache a sentinel value (e.g., "__NULL__" with a short TTL). If you don't cache the miss, every request for a non-existent key hits the DB — this is called a cache miss attack. An attacker repeatedly requesting non-existent IDs can bypass your cache entirely and hammer your DB.

🎨
Frontend Engineer
Browser cache · SWR pattern · Service Worker · Cache busting

The browser is a cache. I control it with Cache-Control headers and manage it through asset versioning. For JavaScript and CSS: content-hashed filenames + Cache-Control: max-age=31536000, immutable. The file never changes, so the browser never revalidates. When I deploy, the new hash means a new URL, which the browser fetches fresh. This pattern eliminates the "old JS after deploy" problem entirely.

SWR (stale-while-revalidate) in client-side data fetching (swr.js, React Query, TanStack Query): show the cached data immediately, fetch fresh data in the background, update the UI when it arrives. This makes navigating back to a page feel instant — the user sees old data for milliseconds while the fresh data loads. For most UI contexts, this is the right UX trade-off. The stale data is clearly labeled or the update is seamless.

Service Worker caching for offline-first: the Service Worker intercepts all fetch requests and can serve from a local cache (Cache Storage API) even with no network. Strategy choices: Cache First (serve from cache, update in background — fast, potentially stale), Network First (try network, fall back to cache — fresh but slower), Stale While Revalidate (serve cache, update in background — best of both). For an app that needs to work offline, Cache First for static assets and SWR for API data is the standard combination.

📈
SRE / Reliability Engineer
Cache hit ratio · Cold start playbook · Redis memory alerts · Stampede incidents

Cache hit ratio is the north-star metric for cache health. I alert at <90% hit ratio for a cache that should be running at 95%+. A sudden drop in hit ratio means: (1) Redis restarted (cold cache), (2) new traffic pattern hitting uncached keys, (3) TTLs were made too short, or (4) a code change broke cache key construction. I track hit ratio per cache key prefix to isolate which data type dropped.

The cold cache disaster: Redis restarts, cache is empty, all traffic falls through to the DB. If your DB can't handle the full production read load (which is why you added the cache), this causes a cascade failure. My runbook: (1) immediately throttle incoming traffic or enable graceful degradation (return stale data from backup), (2) warm critical keys from DB in priority order, (3) only open full traffic after hit ratio recovers to 80%+. I test this quarterly with a scheduled Redis flush in staging.

Redis memory alerts: I page at 80% memory usage, investigate at 85%, and treat 90% as a critical incident. Beyond 90%, Redis eviction rate spikes and hit ratio collapses. The fix is either: increase instance size (fast), add a shard (fast for Redis Cluster), or reduce TTL on low-value keys (free but requires analysis). I use redis-cli --bigkeys monthly to identify keys with unexpectedly large values that should be compressed or split.

🎯 Real Interview Problems

Problem 01
Design a News Feed Caching Layer
Cache-Aside Redis Invalidation Thundering Herd

The Scenario

Design the caching strategy for a social media home feed. 300M DAU, each user loads their feed 8–10 times/day. Feed is personalized (different for each user). Feed content changes as new posts arrive. Target: p99 feed load <100ms.

What Makes It Hard

Personalized feeds can't be shared across users like a trending feed can. Each user's cache entry is unique. At 300M users × 8 loads/day = 2.4B requests/day. You can't cache everything in Redis (too expensive), but you also can't compute feeds from scratch on every request (too slow).

Architecture

User │ GET /feed ▼ Feed Service │ ├── 1. Check L1 cache (in-process, 100ms TTL) HIT → 0.1ms │ feeds cached for user's current session │ ├── 2. Check L2 Redis: "feed:{user_id}" (5 min TTL) HIT → 2ms │ stores last N post IDs in a Redis List │ ├── 3. Cache MISS → compute feed │ │ Fetch followed-user post IDs from Post DB │ │ Score by recency + engagement │ │ Store in Redis: LPUSH "feed:{user_id}" post_id_1 post_id_2... │ │ EXPIRE "feed:{user_id}" 300 │ └► Return feed 50–200ms │ └── 4. Hydrate post IDs with post content │ Batch GET from Redis: "post:{id}" for each post ID │ Cache miss per post → fetch from Post DB └► Return hydrated feed Write path (new post arrives): New post published → invalidate cached feeds of all followers But 1M followers → 1M cache deletes (fan-out problem) Fix: don't invalidate on write. Use short TTL (5 min) as backstop. Accept 5-min eventual consistency. High-frequency users see fresher feeds because their L1 TTL is shorter (30s for active sessions).

Key Decisions

  • Two-level TTL: L1 (30s, in-process, session-scoped) + L2 Redis (5min, shared). Active users refresh frequently; inactive users are fine with 5-min staleness.
  • Store IDs, not content: Cache post IDs in the feed, hydrate content separately. Post content is shared across all feeds — one Redis key per post, not per (user, post) pair. Massive memory saving.
  • Stampede on popular accounts: When a celebrity posts, millions of feed caches miss simultaneously. Use Redis Pub/Sub to notify feed services to start warming caches before users request them.
Problem 02
Design YouTube's Video Serving Infrastructure
CDN Cache-Control LFU Eviction Static Assets

The Scenario

YouTube serves 500 hours of video uploaded per minute and 1 billion hours watched per day. Most bandwidth is video. Design the caching and delivery infrastructure that keeps p99 video start time under 3 seconds globally.

Architecture

User GET /videoplayback?vid=abc123&range=0-2097151 │ ▼ CDN Edge PoP (nearest city — ~10ms) │ Key: vid=abc123, range=0-2MB (first segment) │ ├── Cache HIT (popular video) → stream first segment start in <500ms │ └── Cache MISS (new/rare video) │ ▼ Regional CDN (continental — ~50ms) │ ├── Cache HIT → fill edge PoP → stream │ └── Cache MISS │ ▼ Origin (Google data center) (~200ms) ├── Fetch video segment from distributed blob store └── Return with: Cache-Control: public, max-age=86400 CDN fills regional, regional fills edge, edge serves user Eviction at CDN edge (limited storage): Policy: LFU — retain the most frequently accessed videos Viral new video starts at count=1 but quickly surpasses old rarely-watched content Bias toward large files: 1 video serving 10K views/hour beats 1000 images each viewed 10× Cache-Control for video segments: max-age=86400 (1 day) — segments are immutable, URL includes content hash s-maxage=604800 (1 week) — CDN holds for a week for popular content stale-while-revalidate=3600 — serve stale while checking freshness

Key Decisions

  • Segment-based streaming: Videos are split into 2MB segments. CDN caches segments independently. A user watching only the first 10 minutes only warms the cache for those segments — saves storage vs caching full video files.
  • Popularity-aware prefetch: When a video is trending, CDN controllers push its first few segments to all edge PoPs before users in those regions request them. Proactive population eliminates cold-start latency on trending content.
  • Range request caching: CDN must correctly handle HTTP Range requests (Range: bytes=0-2097151) — different ranges of the same video are different cache entries. Each segment URL is unique, simplifying CDN logic.
Problem 03
Design a Real-Time Leaderboard with Redis
Redis Sorted Set Cache Write-Back Aggregation

The Scenario

Design a leaderboard for a mobile game with 10M active players. Players earn points continuously during gameplay. Players view the global top-100 and their own rank. Score updates: 50K/sec. Leaderboard reads: 200K/sec. Must be real-time (rank updates within seconds).

Architecture

Write path (score update): Game Server │ Player 42 earned 500 points ▼ Redis ZADD "leaderboard:global" 9800 "player:42" (atomic update — no race condition, O(log N)) Redis Sorted Set: score=9800 player:42 score=9750 player:77 score=9200 player:13 ...10M entries Read path (top 100): Client GET /leaderboard/top100 │ ▼ Leaderboard API │ ├── ZREVRANGE "leaderboard:global" 0 99 WITHSCORES O(log N + 100) = fast │ Returns top 100 players with scores │ └── Hydrate player names: HMGET "player:{id}:info" for each (batch Redis GET — single round trip with pipeline) Read path (my rank): ZREVRANK "leaderboard:global" "player:42" → 4,823 O(log N) Persistence (write-back pattern): Redis Sorted Set = real-time cache + source of truth for rankings Periodic sync (every 5 min): dump top 1M scores from Redis → PostgreSQL Redis restart recovery: reload last checkpoint from PostgreSQL → ZADD bulk import

Key Decisions

  • Redis as the primary store for rankings: This is write-back caching — Redis is the fast layer, PostgreSQL is the durable backup. Acceptable for a leaderboard because losing 5 minutes of score data on Redis failure is recoverable.
  • Sorted Set vs caching a query result: ZADD + ZREVRANGE is more memory-efficient and faster than caching a JSON array of the top-100. The Sorted Set supports arbitrary rank queries (ZREVRANK for any player) without storing separate data.
  • Sharding at 10M players: A single Redis Sorted Set handles 10M entries fine (~400MB memory). At 100M players, shard by score range (0–1M points → shard 1, 1M–2M → shard 2) and merge top-K from each shard for global rankings.

❌ Anti-patterns at Scale

  • noeviction policy in Redis The default Redis memory policy returns errors when full. Under memory pressure at peak traffic, your application starts getting write errors from Redis, causing cascading failures. Always set an explicit eviction policy — allkeys-lru is the right default.
  • Caching without a TTL Keys without TTL are permanent residents in Redis memory. They grow over time, never evict voluntarily, and eventually cause OOM or trigger mass eviction of other keys. Every cache key must have a TTL, even if it's a long one (24 hours).
  • Not caching null / empty results (cache miss attack) If a key doesn't exist in the DB, you don't populate the cache. An attacker can make millions of requests for non-existent IDs — each bypasses the cache and hits the DB. Cache a sentinel value ("__NULL__") with a short TTL (30–60s) for DB misses.
  • Using the cache as the primary store (no DB backup) Redis is fast but not designed for permanent durability by default. If Redis restarts without a recent RDB/AOF snapshot and your DB doesn't have the canonical data, you've lost data permanently. Cache complements the DB — never replaces it for source-of-truth data.
  • Cache keys derived from user input without sanitization If the cache key includes unvalidated user input, attackers can craft keys that collide with other users' data or inject control characters. Always build cache keys from server-side, authenticated identifiers.
  • No stampede protection on high-traffic keys A popular key expiring during a traffic spike sends thousands of concurrent requests to the DB simultaneously. For any key with >1,000 reads/sec, implement mutex locking or probabilistic early expiration to prevent thundering herd.
  • Caching mutable aggregations without a write-invalidation path Caching a "total order count" computed from a JOIN — then having no mechanism to invalidate it when an order is placed. The count stays stale for its entire TTL. Use write-through or event-driven invalidation for aggregated values that change on writes.
  • One Redis cluster for everything (cache + queues + sessions + rate limiting) When the cache evicts aggressively under memory pressure, it can evict session data (logging users out) or rate limit counters (resetting limits). Separate concerns: use different Redis instances (or at minimum, different databases) for cache, sessions, queues, and rate limiters.

💡 Interview Application Tips

01

Name the cache layer and justify it

Don't just say "add a cache." Say "L2 Redis cache in cache-aside pattern with a 5-minute TTL, because reads are 100× more frequent than writes and 5-minute staleness is acceptable for this use case."

02

Always discuss invalidation

Interviewers probe cache design with "what happens when the data changes?" Have an answer ready: TTL as backstop + event-driven delete on write is the production-proven combination.

03

Bring up the thundering herd problem

Mention it proactively for any high-traffic system: "For popular keys, I'd add probabilistic early expiration or a mutex to prevent a thundering herd when the TTL expires." This signals production experience.

04

Distinguish L1, L2, CDN clearly

"I'd use an in-process L1 cache for config data (sub-millisecond), Redis L2 for user data shared across servers (1–2ms), and CDN for public API responses (serve from edge, no origin hit)."

05

Know when NOT to cache

Personalised data at CDN (use Cache-Control: private), financial transactions (consistency over speed), write-heavy data that is never read (write-around or don't cache). Knowing the limits shows maturity.

06

Redis data structures are a caching superpower

"For the leaderboard I'd use a Redis Sorted Set — ZADD for updates, ZREVRANGE for top-K, ZREVRANK for any player's rank. More efficient than caching a serialised query result."

The cache hit ratio question Interviewers sometimes ask "how do you know if your cache is working?" The answer: cache hit ratio (hits / (hits + misses)). Target >95% for hot data. Monitor it per key prefix, not just globally. A drop in hit ratio is your earliest warning of a cache problem.
Clarifications
+
What is a Cache?
A cache is a fast storage layer that saves the result of expensive operations (DB queries, API calls, complex computations) so future requests get the result instantly instead of re-doing the work. The trade-off: cached data may be stale (out of date). Good caches have strategies for when to expire or invalidate data.
+
Redis vs Memcached
Both are in-memory key-value caches, but Redis is a superset. Redis adds: data structures (lists, sorted sets, hashes), persistence (survive restarts), pub/sub messaging, Lua scripting, and cluster mode. Memcached: simpler, slightly faster for pure get/set, multi-threaded. In 2024, almost everyone uses Redis. Memcached is legacy unless you have a very specific reason.
+
Redis Persistence: RDB vs AOF
Redis is in-memory, so it loses data on crash unless configured for persistence. RDB (Redis Database): snapshot of all data every N minutes. Fast restarts, some data loss between snapshots. AOF (Append-Only File): log every write command. Slower restarts, near-zero data loss. Production: run both — AOF for durability, RDB for fast recovery.
+
CDN: What Is It?
CDN = Content Delivery Network. A global network of servers ("edge servers") positioned close to users. Instead of every user downloading your JavaScript bundle from your server in Virginia, users in Tokyo get it from a CDN edge server in Tokyo — 10ms instead of 200ms. Cloudflare, AWS CloudFront, Fastly, and Akamai are the major CDN providers.
+
Edge Server vs Origin Server
Origin server: your actual backend server where your app runs. Edge server: a CDN server geographically close to the user that stores cached copies of your content. When a user requests a file, the CDN checks its edge server first (cache hit = fast). If not cached (cache miss), the edge fetches from origin, caches it, and returns it. Subsequent requests to that edge are instant.
+
Cache Hit vs Cache Miss
Cache hit: the data is in the cache → return immediately (fast). Cache miss: the data is NOT in the cache → fetch from DB, store in cache, return (slow for this first request). Hit rate = hits / (hits + misses). A well-tuned cache has >95% hit rate. Low hit rate means your cache isn't effective — usually a TTL too short or cache too small.
+
Write-Through vs Write-Back
Write-through: write to cache AND database at the same time. Data is always consistent, but writes are slow (wait for both). Write-back (write-behind): write to cache only, then asynchronously flush to DB later. Writes are fast, but if the cache crashes before flushing, you lose data. Write-through for financial data; write-back for logs or analytics where some loss is acceptable.
+
TTL (Time To Live)
TTL = how long a cached entry lives before expiring. After TTL expires, the next request is a cache miss and fetches fresh data. Short TTL (seconds): fresh data but more DB load. Long TTL (hours/days): stale data risk but fewer DB hits. There's no universal right answer — pick TTL based on how often the underlying data actually changes.
+
LRU / LFU / FIFO
When the cache is full and a new item arrives, something must be evicted. LRU (Least Recently Used): evict the item not accessed for the longest time. Most common — works well for most workloads. LFU (Least Frequently Used): evict the item accessed the fewest times total. Better for skewed access patterns. FIFO: evict the oldest item regardless of access. Simple but often wrong choice.
+
Cache Warming
Cold cache: after a deploy or server restart, the cache is empty. Every request is a miss → DB is hammered → service may be slow or crash. Cache warming = pre-loading the cache with data before going live. Strategies: replay recent traffic logs, batch-load hot keys on startup, or use a separate warming process that runs before traffic is routed to the new instance.
+
Cache-Control HTTP Header
The Cache-Control header tells browsers and CDNs how to cache a response. max-age=3600 = cache for 1 hour. no-cache = always revalidate with server before using cache. no-store = never cache (sensitive data). public = CDNs can cache this. private = only the browser should cache (user-specific data). This is how you control CDN behavior per-resource without touching CDN config.
+
Hot Key Problem
A hot key is a single cache key that gets millions of requests per second (e.g., a celebrity's profile). Even Redis can struggle with a single key getting too much traffic. Solutions: local in-process cache for ultra-hot keys (L1 cache for the celebrity's data), key replication (store the same data under N keys and randomly pick one), or add a short sleep before the request to spread timing.
