Foundation

Global Architecture Overview

Distributing a system globally means placing compute, data, and network resources close to users across continents. The fundamental constraints are physics (speed of light ≈ 200 km/ms in fiber), regulatory divergence (GDPR, China Cybersecurity Law, India PDPB), and the CAP theorem at planetary scale. Every global architecture decision is a trade-off between latency, consistency, and operational complexity.

Global multi-region architecture overview User → Anycast/CDN Edge (200+ PoPs worldwide) ├── Static assets: S3/GCS + CDN (cache-hit → 5ms response) ├── Dynamic API: Route 53 latency-based → nearest region └── WebSocket/long-poll: Anycast to nearest edge, tunnel to origin Region A (us-east-1) Region B (eu-west-1) Region C (ap-southeast-1) Primary (writes) Secondary (reads + failover) Secondary (reads + failover) ├── App tier (K8s) ├── App tier (K8s) ├── App tier (K8s) ├── RDS Primary ├── RDS Read Replica ├── RDS Read Replica ├── Redis Primary ├── Redis replica └── Redis replica └── Kafka source └── Kafka mirror (MirrorMaker 2) Cross-region replication flows Database: async replication (RPO ~1s), sync optional (RPO=0, +15ms write latency) Cache: TTL-based invalidation or event-driven (Kafka → invalidation topic) Blob/Object: S3 Cross-Region Replication, GCS Object Replication Data Sovereignty Boundaries EU data: pinned to eu-west-1 / eu-central-1 (GDPR compliance) US data: us-east-1 / us-west-2 China: isolated vpc + ICP license required (separate deployment) Tenant-level routing: shard key includes region → always land on correct region
⚡

Speed of Light Constraint

New York → London RTT is ~70ms (fiber). You cannot beat physics — the only win is reducing the distance between user and data. Every CDN and regional edge deployment is an attempt to get closer.

🗺️

Region vs Availability Zone

A region is a geographic area (us-east-1 = Virginia). An AZ is an isolated data center inside a region. Multi-AZ protects against data center failure; multi-region protects against regional failure or regulatory requirements.

⚖️

CAP at Global Scale

Global systems can't be both strongly consistent and always available under network partitions. Most choose AP (eventual consistency) for reads with strong consistency only where required (financial writes). CockroachDB and Spanner are CP — they sacrifice availability for correctness.

🏛️

Regulatory Isolation

GDPR mandates EU personal data stays in the EU. China requires data residency + ICP license. India PDPB, Brazil LGPD, and others add more boundaries. Many global systems maintain isolated deployments per regulatory zone with no cross-border data flow.

Networking

Anycast Routing

Anycast assigns the same IP address to multiple servers in different locations. BGP routes each user's request to the topologically nearest server. This is how Cloudflare, Google (8.8.8.8), and modern CDNs route traffic with zero application-layer logic.

How Anycast works Traditional Unicast User (Tokyo) ──────────────────────────────→ Server IP 203.0.113.10 (Virginia) 70ms RTT across ocean Anycast Same IP 203.0.113.10 announced from 5 PoPs via BGP: Tokyo PoP → announced 203.0.113.10 (AS 12345) Frankfurt PoP → announced 203.0.113.10 (AS 12345) Virginia PoP → announced 203.0.113.10 (AS 12345) Singapore PoP → announced 203.0.113.10 (AS 12345) São Paulo PoP → announced 203.0.113.10 (AS 12345) User (Tokyo) → BGP selects nearest → Tokyo PoP (5ms RTT) User (London) → BGP selects nearest → Frankfurt PoP (8ms RTT) No DNS resolution needed — routing is at the IP layer Anycast use cases DNS resolvers: 8.8.8.8, 1.1.1.1, authoritative nameservers DDoS mitigation: attack traffic absorbed by 200+ PoPs, no single target CDN ingestion: Cloudflare, Fastly, Akamai all use anycast for TCP termination Load balancing: ECMP (Equal-Cost Multi-Path) distributes within a PoP Anycast limitation Stateful TCP: BGP can reroute mid-connection during network events → session drop Mitigation: QUIC (UDP-based) handles rerouting better; or use anycast only for TCP termination at edge, then proxy to origin over stable tunnel
📡

BGP & AS Numbers

Border Gateway Protocol (BGP) is the routing protocol of the internet. Each network operator has an Autonomous System Number (ASN). Anycast works by advertising the same IP prefix from multiple ASes — BGP shortest-path selection routes each packet to the nearest announcement.

🛡️

Anycast DDoS Mitigation

A 10 Tbps DDoS attack distributed across 200 PoPs with 50 Gbps capacity each is manageable — no single PoP sees more than a fraction. Cloudflare's 321 Tbps global network absorbs volumetric attacks that would saturate any single data center.

Performance

CDN Strategy

Content Delivery Networks cache content at edge PoPs close to users. The key decisions are what to cache, for how long, and how to invalidate. A well-configured CDN can serve 95%+ of traffic without hitting your origin, reducing both latency and cost.

CDN caching hierarchy & invalidation Cache hierarchy (L1 → L2 → Origin) Browser cache (user's machine, private) └── CDN Edge PoP (e.g., Cloudflare Frankfurt) ← L1 cache └── CDN Regional cache (e.g., Cloudflare EU hub) ← L2 cache └── Origin server (your data center) Cache-Control header strategy Static assets (JS/CSS/images with content hash): Cache-Control: public, max-age=31536000, immutable → Cache for 1 year; filename changes on deploy (hash in filename) HTML pages (SSR or SPA shell): Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate=300 → CDN caches 60s; serves stale up to 5min while background-revalidating API responses (user-specific): Cache-Control: private, max-age=0 → Never cache at CDN; browser may cache briefly Vary: Accept-Encoding, Accept-Language → CDN maintains separate cache entries per language Cache invalidation strategies Purge by URL: instant, precise — call CDN API on deploy for changed URLs Purge by tag/surrogate key: tag objects with entity IDs → purge all pages showing Product #42 Cache-key normalization: strip UTM params from cache key to avoid cache fragmentation Stale-while-revalidate: serve stale immediately, refresh in background (best UX) Edge compute (CDN Workers) A/B testing at edge: no origin round-trip for experiment assignment Auth token validation: verify JWT at edge, reject before hitting origin Geolocation-based redirect: CF-IPCountry header → redirect to localized URL Image optimization: resize/format-convert at edge (WebP for Chrome, AVIF for new browsers)
Traffic Management

Geo-Routing & Traffic Steering

Geo-routing directs users to the geographically or topologically closest server. DNS-based geo-routing (Route 53, Cloudflare DNS) operates at resolution time. Load-balancer-level geo-routing (Global Load Balancing) operates at connection time for finer control.

Route 53 routing policy comparison Latency-based routing (recommended default) Route 53 measures RTT from each AWS region to DNS resolvers globally. User DNS query → Route 53 picks region with lowest measured latency. Not the same as geographic proximity! A user in South Africa might be routed to eu-west-1 (Ireland) if that has lower latency than af-south-1. Geolocation routing Routes based on where DNS query originates (country / continent / US state). Use case: serve localized content, enforce data residency (EU → eu-west-1 only). Fallback: must define a "default" record for unmatched locations. Weighted routing (for canary / gradual rollout) Record A: us-east-1, weight 90 Record B: us-west-2, weight 10 → 10% of traffic to new region; increase weight as confidence grows. Geoproximity routing (Traffic Flow required) Like latency-based but you can add a "bias" — expand or shrink a region's effective coverage area. Useful when a new region opens and you want to gradually shift users away from an old one. Failover routing Primary record: active region. Secondary: standby region. Health check monitors primary → if unhealthy, all traffic shifts to secondary. Warm standby vs cold standby: warm keeps capacity running (faster RTO); cold shuts down (cheaper but slower to bring up). Global Load Balancer alternatives Cloudflare Load Balancing: anycast + health checks, sub-second failover GCP Global Load Balancer: single Anycast IP, Google's backbone routing Azure Traffic Manager: DNS-based, similar to Route 53 AWS Global Accelerator: Anycast entry, fixed IPs, routes over AWS backbone
🏥

Health Checks

Route 53 health checks probe your endpoints every 10–30s. A region is removed from DNS when 3 consecutive checks fail (~1 min). Combine with CloudWatch alarms for application-level health (not just TCP connectivity).

⏱️

DNS TTL Trade-offs

Low TTL (30s) enables fast failover but increases DNS query volume and costs. High TTL (300s) reduces DNS load but means users are stuck on a failed endpoint longer. Typical production: 60s for geo-routed records, 300s for stable records.

🔄

Warm Standby Pattern

Keep a small but running capacity (e.g., 20% of primary) in the standby region. On failover, autoscaling kicks in to reach full capacity. RTO is minutes rather than hours of a cold standby. Cost: ~20% premium on compute in standby region.

Compliance

Data Sovereignty & Compliance

Data sovereignty means that data is subject to the laws of the country where it is stored or processed. GDPR (EU), PDPB (India), PIPL (China), LGPD (Brazil), and dozens of other regulations impose geographic restrictions on personal data. Failure to comply results in fines up to 4% of global annual revenue (GDPR Art. 83).

Data Layer

Global Database Deployment

Global databases must balance consistency guarantees with write latency (strong consistency requires cross-region round trips). The main options span from single-region with replicas (simple, eventual reads) to fully distributed ACID databases (complex, but strong guarantees everywhere).

Global database options compared Option 1: Single-region primary + read replicas Write path: all writes → us-east-1 primary (strong consistency) Read path: reads → nearest read replica (eventual, ~100ms lag) Failover: promote replica to primary (minutes of downtime or data loss) Best for: apps where writes concentrate in one region, reads are global Tools: RDS Multi-AZ + read replicas, MySQL + Vitess with follower reads Option 2: Active-active with regional primaries (partitioned by key) Shard by tenant/geography: EU writes → eu-west-1, US writes → us-east-1 Each region is primary for its shard — no cross-region write latency Cross-region: async replication for reporting; no cross-shard transactions Risk: hot-shard if user distribution is uneven; no cross-region joins Tools: Cassandra, DynamoDB Global Tables, custom sharding + Vitess Option 3: NewSQL — globally distributed ACID CockroachDB: PostgreSQL-compatible, serializable isolation, geo-partitioning - Pin a table's ranges to specific regions (data residency built-in) - Consensus via Raft across 3+ replicas spanning regions - Write latency ≈ 2× RTT to quorum region (~150ms cross-continent) Google Spanner: TrueTime (atomic clocks + GPS) for external consistency - Globally consistent reads at any timestamp without locking - Write latency ~10ms within a region, ~80ms multi-region - Expensive; used by Google Ads, Stripe, and others at global scale Option 4: Event sourcing + CQRS multi-region Event log (Kafka or Kinesis) is source of truth — replicated globally. Each region maintains its own read model (projection) from the event log. Writes go to the user's home region event log; other regions consume asynchronously. Consistency: eventual for cross-region reads; strong within home region. Good for: audit-heavy systems, financial ledgers, collaboration tools.

Replication

Active-Active vs Active-Passive

Active-active means every region can accept writes. Active-passive (or active-standby) means only one region takes writes; others are read-only replicas that can be promoted. Active-active dramatically reduces write latency for globally distributed users but introduces conflict risk.

Active-passive vs active-active comparison Active-Passive us-east-1 (PRIMARY) ──async repl──→ eu-west-1 (STANDBY) ──async repl──→ ap-southeast-1 (STANDBY) Pros: no conflicts possible, simple consistency model Cons: global write latency (Tokyo user → Virginia → reply: 300ms+) failover takes minutes; RPO depends on replication lag Use when: writes must be strongly consistent; user base concentrated in one region Active-Active (same data, multi-master) us-east-1 ←──────────────────────────── ap-southeast-1 ↕ bidirectional replication ↕ eu-west-1 ──────────────────────────────────── Every region accepts writes to any record → conflict risk! Conflict resolution needed: LWW (last-write-wins), CRDTs, or custom logic Pros: local writes for all users (~5ms vs 300ms), regional isolation Cons: operational complexity; conflict resolution bugs are insidious Active-Active (partitioned writes — best practice) Partition writes by owner: EU user's data is ONLY written in eu-west-1. Other regions can read that data (via replication) but won't write it. No conflicts possible — each record has a canonical home region. Failover: if eu-west-1 goes down, route EU writes to us-east-1 temporarily. This is the most common "active-active" in practice — it avoids true multi-master. Replication topology Full mesh: every region replicates to all others (N² connections, most resilient) Hub-and-spoke: one hub region replicates to all (simpler, hub is SPOF) Ring: us-east → eu-west → ap-southeast → us-east (simple, 2-hop lag) Recommended: full mesh for ≤4 regions; hub-and-spoke for 5+ with secondary hubs
🎯

RTO vs RPO

RTO (Recovery Time Objective): how long can you be down? Active-passive: minutes. Active-active: seconds (no failover needed — users rerouted to another live region). RPO (Recovery Point Objective): how much data can you lose? Sync replication: RPO=0. Async: RPO = replication lag (often <1s).

🔀

Replication Lag Monitoring

Always monitor replication lag — a stale replica serving reads leads to stale data bugs that are hard to debug. Alert at 5s lag, page at 30s. Use `pg_stat_replication` (Postgres) or CloudWatch `ReplicaLag` (RDS) metrics.

Consistency

Conflict Resolution

When two regions concurrently write to the same record, you have a conflict. Resolution strategies range from blindly picking a winner (LWW) to mathematically correct data structures (CRDTs) to domain-specific logic. The right choice depends on data semantics — not one size fits all.

Conflict resolution strategies 1. Last-Write-Wins (LWW) Compare timestamps; highest wins. Simple to implement. Problem: clock skew between regions (NTP accuracy ±1ms, not enough for sub-ms writes) Solution: Hybrid Logical Clocks (HLC) — combine wall clock + logical counter. DynamoDB Global Tables uses LWW. Cassandra uses LWW by default. Risk: concurrent writes in different regions silently lose one write — no error returned. 2. CRDTs (Conflict-free Replicated Data Types) Math-based structures that merge automatically with no conflicts: G-Counter: grow-only counter. Merge = max per replica. Sum = sum all replicas. PN-Counter: positive + negative counters. Merge each separately. G-Set: grow-only set. Merge = union. (no deletes) OR-Set (Observed-Remove Set): supports deletes with unique tags per add. LWW-Register: single value with timestamp. Merge = highest timestamp. LWW-Map: map of LWW-Registers. Good for user profile-like data. Used by: Riak, Redis (CRDT module), collaborative editors (Yjs, Automerge) 3. Operational Transformation (OT) Transform concurrent operations to be compatible before applying. Used by Google Docs, Etherpad for collaborative text editing. Complex to implement correctly; mostly replaced by CRDTs in new systems. 4. Application-level conflict resolution Store conflicting versions (siblings in Riak, vector clocks in Dynamo). Expose conflict to application layer → business logic decides. Example: shopping cart — union of all versions (don't lose items). Example: bank balance — reject concurrent debits via optimistic locking. 5. Avoid conflicts via design Single-writer per entity: each entity has a home region (partitioned active-active). → No concurrent cross-region writes to same record → no conflicts. Fencing tokens: distributed lock (ZooKeeper, DynamoDB conditional writes). Saga pattern: break multi-step operations into compensatable steps.
🕰️

Vector Clocks

A vector clock tracks causality across nodes: {A:3, B:1, C:2} means node A has seen 3 events, B seen 1, C seen 2. If two versions have incomparable vectors, they're concurrent (conflict). Amazon Dynamo pioneered using vector clocks to detect conflicts and present them to the application layer.

🔢

G-Counter CRDT Example

Shopping site page-view counter across 3 regions. Each region increments its slot: A=1000, B=500, C=300. Total = 1800. On merge, take max per slot — works even if regions have diverged for hours. No coordination needed.

🔐

Optimistic Locking

Include a version number in writes: `UPDATE accounts SET balance=900, version=6 WHERE id=1 AND version=5`. If another region already wrote version 6, this update fails with 0 rows affected → retry from application. Safe for financial data; higher write latency under contention.

Viewpoints

Engineer Perspectives

Solutions Architect

Start with latency goals per region and work backwards. If P99 API latency must be under 100ms globally, static assets must be CDN-cached, API servers must be in each region, and the database either accepts eventual reads or uses a NewSQL like Spanner. Never promise "global" without knowing where users actually are.

Backend Engineer

Partition writes by owner region from day one — retrofitting single-region code to handle multi-region conflicts is enormously painful. Use a region field in every tenant record, enforce it at the ORM layer, and make cross-region reads explicit in code (not transparent). Transparency hides bugs.

SRE

Multi-region doubles your operational surface. Automate failover but gate it behind a manual approval step for production — fully automated region failover has caused more incidents than it prevented when triggered by monitoring false positives. Practice failover drills quarterly. Track cross-region replication lag as an SLI.

Security Engineer

Data sovereignty is not just about where data lives at rest — it's about where it's processed, logged, and who has access. Ensure audit logs are also region-isolated. Use AWS KMS Regional keys (not multi-region) for GDPR-sensitive data. Prohibit cross-region replication of PII by IAM policy, not just documentation.

Data Engineer

Global analytics pipelines need to handle timezone normalization, regional schema divergence, and GDPR restrictions on EU data leaving the EU. Use a data lakehouse per region and aggregate only anonymized/pseudonymized metrics cross-region. Never pull EU PII into a US data warehouse — even for analytics.

Platform Engineer

Treat each region as an independent deployment target in your CD pipeline. GitOps (ArgoCD) per region with separate cluster configs. Use Terraform workspaces or Atlantis per-region state files. Config drift between regions causes subtle production bugs — enforce config-as-code strictly and diff regions in CI.

Frontend Engineer

Geo-routing is only as good as the user's perceived latency. CDN cache-hit rate is the metric to watch — if it's below 80%, investigate cache key fragmentation (too many query params, missing normalization). Use the `Timing-Allow-Origin` header to expose PerformanceResourceTiming data from CDN edge servers.

ML Engineer

Training data aggregation across regions must respect sovereignty. Use federated learning for models that require EU + US data: train local models per region, aggregate gradients (not data) centrally. For inference, deploy model replicas per region — a single inference endpoint across regions adds 100-200ms latency unnecessarily.

Mobile Engineer

On mobile, network switches (WiFi → LTE, region border crossing) can cause TCP connection resets. Use QUIC (HTTP/3) where possible — it handles path migration without reconnecting. Implement a local cache with optimistic updates for offline-first behavior; sync to the nearest region's API on reconnect.

Multi-Region Active-Active with Geo-Partitioned Writes

Scenario

B2B SaaS platform with 5,000 enterprise tenants across US, EU, and APAC. EU customers require GDPR-compliant data residency (no data outside EU). US customers want sub-50ms API latency. You currently have a single us-east-1 PostgreSQL cluster — EU customers see 200ms+ latency and you're at risk of GDPR fines.

Architecture

Deploy CockroachDB across three regions with geo-partitioning to pin EU tenant data to EU nodes. Use Route 53 geolocation routing to direct EU users to eu-west-1 API servers and US users to us-east-1 servers, each connecting only to their local CockroachDB leaseholders.


# CockroachDB geo-partitioning setup and tenant routing

import psycopg2
from typing import Optional

REGION_DSN = {
    "us": "postgresql://user:pass@cockroachdb-us.internal:26257/saas?sslmode=verify-full",
    "eu": "postgresql://user:pass@cockroachdb-eu.internal:26257/saas?sslmode=verify-full",
    "ap": "postgresql://user:pass@cockroachdb-ap.internal:26257/saas?sslmode=verify-full",
}

# SQL: create geo-partitioned tenant table
SETUP_SQL = """
-- Partition tenants table by region; each partition's range leases stay in that region
ALTER TABLE tenants PARTITION BY LIST (region) (
    PARTITION us_tenants VALUES IN ('us'),
    PARTITION eu_tenants VALUES IN ('eu'),
    PARTITION ap_tenants VALUES IN ('ap')
);

-- Pin each partition's range leases to the matching region
ALTER PARTITION us_tenants OF TABLE tenants
    CONFIGURE ZONE USING lease_preferences = '[[+region=us-east-1]]';
ALTER PARTITION eu_tenants OF TABLE tenants
    CONFIGURE ZONE USING lease_preferences = '[[+region=eu-west-1]]';
ALTER PARTITION ap_tenants OF TABLE tenants
    CONFIGURE ZONE USING lease_preferences = '[[+region=ap-southeast-1]]';

-- Same for all tenant-data tables (partitioned by tenant_region FK)
ALTER TABLE orders PARTITION BY LIST (tenant_region) (
    PARTITION eu_orders VALUES IN ('eu'),
    PARTITION us_orders VALUES IN ('us'),
    PARTITION ap_orders VALUES IN ('ap')
);
ALTER PARTITION eu_orders OF TABLE orders
    CONFIGURE ZONE USING lease_preferences = '[[+region=eu-west-1]]';
"""

class TenantRouter:
    """Routes DB connections to the correct regional CockroachDB leaseholder."""
    def __init__(self):
        self._conns: dict[str, psycopg2.extensions.connection] = {}

    def conn(self, region: str) -> psycopg2.extensions.connection:
        if region not in self._conns:
            self._conns[region] = psycopg2.connect(REGION_DSN[region])
        return self._conns[region]

    def get_tenant(self, tenant_id: str, requesting_region: str) -> Optional[dict]:
        """Always read from tenant's home region to ensure strong consistency."""
        # First, determine tenant's home region from global metadata
        # (tiny metadata table replicated globally — no PII)
        meta_conn = self.conn(requesting_region)
        with meta_conn.cursor() as cur:
            cur.execute(
                "SELECT region FROM tenant_meta WHERE tenant_id = %s",
                (tenant_id,)
            )
            row = cur.fetchone()
            if not row:
                return None
            home_region = row[0]

        # Route to tenant's home region for actual data
        home_conn = self.conn(home_region)
        with home_conn.cursor() as cur:
            cur.execute(
                "SELECT tenant_id, name, plan, created_at FROM tenants WHERE tenant_id = %s AND region = %s",
                (tenant_id, home_region)
            )
            row = cur.fetchone()
            if not row:
                return None
            return {"tenant_id": row[0], "name": row[1], "plan": row[2], "region": home_region}

    def write_order(self, tenant_id: str, home_region: str, order_data: dict) -> str:
        """Write order to tenant's home region — avoids cross-region writes entirely."""
        conn = self.conn(home_region)
        with conn.cursor() as cur:
            cur.execute(
                """INSERT INTO orders (order_id, tenant_id, tenant_region, amount, status, created_at)
                   VALUES (gen_random_uuid(), %s, %s, %s, 'pending', now())
                   RETURNING order_id""",
                (tenant_id, home_region, order_data["amount"])
            )
            conn.commit()
            return cur.fetchone()[0]


# FastAPI middleware: inject tenant region from JWT claim
# (Region claim set during login based on tenant metadata)
from fastapi import Request, HTTPException
import jwt as pyjwt

async def tenant_region_middleware(request: Request, call_next):
    token = request.headers.get("Authorization", "").removeprefix("Bearer ")
    if token:
        try:
            claims = pyjwt.decode(token, options={"verify_signature": False})
            request.state.tenant_region = claims.get("tenant_region", "us")
            request.state.tenant_id = claims.get("sub")
        except Exception:
            raise HTTPException(status_code=401, detail="Invalid token")
    return await call_next(request)

Result

EU tenant writes land on eu-west-1 CockroachDB leaseholders (data never leaves EU). Latency for EU customers drops from 210ms to 18ms. US customers unchanged. GDPR audit shows zero cross-border PII transfers. CockroachDB handles the replication topology; the application layer only needs to know "which region is this tenant's home?"

Problem 2 of 3
Global CDN with Intelligent Cache Invalidation
Cloudflare WorkersCache Tags Stale-While-RevalidateEdge Auth

Scenario

E-commerce platform with 50M daily active users across 40 countries. Product pages are server-side rendered and must show real-time inventory ("Only 3 left!"). Currently every page request hits origin — CDN cache-hit rate is 12% because the inventory count breaks caching. You need to serve product pages in <50ms globally while keeping inventory accurate.

Architecture

Separate page shell (cacheable for 5 min) from inventory count (fetched client-side from a regional API). Use Cloudflare Cache Tags to surgically invalidate only the affected product's cached pages when inventory changes, rather than purging everything. Add a Cloudflare Worker to validate auth tokens at the edge without hitting origin.

import hashlib, json, time

# Edge auth token validation (avoids origin round-trip for auth)
def validate_session_token(token: str, public_key: bytes) -> dict | None:
    """Called at edge — verifies JWT signature locally. No origin call needed."""
    try:
        import jwt
        return jwt.decode(token, public_key, algorithms=["RS256"])
    except Exception:
        return None

# Origin server: set Cache-Control + Surrogate-Key (Cloudflare Cache Tag) headers
from fastapi import FastAPI, Response

app = FastAPI()

@app.get("/products/{product_id}")
async def product_page(product_id: str, response: Response):
    product = await db.get_product(product_id)
    category_id = product["category_id"]

    # Cache for 5 minutes; serve stale for 1 hour while revalidating in background
    response.headers["Cache-Control"] = "public, max-age=300, stale-while-revalidate=3600"
    # Cloudflare Cache Tags — allows surgical invalidation
    response.headers["Cache-Tag"] = f"product-{product_id},category-{category_id},site-products"
    # Vary only on Accept-Encoding (not Cookie — logged-in state handled client-side)
    response.headers["Vary"] = "Accept-Encoding"

    # Return page WITHOUT inventory count — inventory fetched client-side
    return {
        "product_id": product_id,
        "name": product["name"],
        "price": product["price"],
        "description": product["description"],
        # inventory_count intentionally omitted — makes page cacheable
    }

PostgreSQL Sync ReplicationRoute 53 Failover Fencing TokensRTO < 60s

Scenario

Payments platform processing $2M/hour. Primary region us-east-1 goes down. You have async replication to eu-west-1 (typical lag 800ms) and need RPO=0 (no financial transactions lost) and RTO<60s (back online in under a minute). Current setup uses async replication and manual failover — last DR test took 12 minutes with 2 lost transactions.

Architecture

Switch to synchronous replication for the write path (at the cost of +15ms write latency). Implement automated health-check-based DNS failover with a distributed lock (fencing token) to prevent split-brain writes during the transition window.


import asyncio, time, boto3, psycopg2
from dataclasses import dataclass

# PostgreSQL synchronous replication config (postgresql.conf on primary)
# synchronous_standby_names = 'FIRST 1 (eu_replica)'
# → writes only commit after eu_replica acknowledges write to WAL
# Cost: +RTT to EU (~80ms) on every write. Accept this for RPO=0.

@dataclass
class FailoverConfig:
    primary_dsn: str       = "postgresql://...@us-east-1-db:5432/payments"
    standby_dsn: str       = "postgresql://...@eu-west-1-db:5432/payments"
    primary_health_url: str = "https://us-east-1-api.payments.com/healthz"
    route53_zone_id: str   = "Z1234567890"
    payments_record: str   = "api.payments.com"
    primary_ip: str        = "203.0.113.10"
    standby_ip: str        = "198.51.100.20"
    lock_table: str        = "failover_lock"     # in standby DB
    failover_token_ttl: int = 300                 # 5 min; primary must renew or yield

class FailoverManager:
    def __init__(self, cfg: FailoverConfig):
        self.cfg = cfg
        self.r53 = boto3.client("route53")
        self._consecutive_failures = 0
        self._required_failures = 3   # 3 × 10s = 30s before failover

    async def health_check_loop(self):
        import httpx
        while True:
            await asyncio.sleep(10)
            try:
                async with httpx.AsyncClient(timeout=5) as client:
                    r = await client.get(self.cfg.primary_health_url)
                    if r.status_code == 200:
                        self._consecutive_failures = 0
                        await self._renew_primary_lock()  # heartbeat
                        continue
            except Exception:
                pass

            self._consecutive_failures += 1
            print(f"Primary health check failed ({self._consecutive_failures}/{self._required_failures})")

            if self._consecutive_failures >= self._required_failures:
                await self.execute_failover()
                break  # stop loop after failover; manual runbook to fail back

    async def _renew_primary_lock(self):
        """Primary continuously renews its lock — standby watches for expiry."""
        conn = psycopg2.connect(self.cfg.standby_dsn)
        with conn.cursor() as cur:
            cur.execute(
                """INSERT INTO failover_lock (lock_key, holder, expires_at)
                   VALUES ('primary', 'us-east-1', NOW() + INTERVAL '5 minutes')
                   ON CONFLICT (lock_key) DO UPDATE SET expires_at = EXCLUDED.expires_at""",
            )
            conn.commit()
        conn.close()

    async def execute_failover(self):
        print("Executing failover: us-east-1 → eu-west-1")
        # Step 1: Verify the standby lock has expired (primary is truly gone)
        conn = psycopg2.connect(self.cfg.standby_dsn)
        with conn.cursor() as cur:
            cur.execute("SELECT expires_at FROM failover_lock WHERE lock_key = 'primary'")
            row = cur.fetchone()
            if row and row[0].timestamp() > time.time():
                print("Lock still valid — primary may still be alive. Aborting failover.")
                conn.close()
                return  # fencing: don't failover if lock is unexpired

            # Step 2: Claim the lock for eu-west-1 (becomes new primary)
            cur.execute(
                """INSERT INTO failover_lock (lock_key, holder, expires_at)
                   VALUES ('primary', 'eu-west-1', NOW() + INTERVAL '5 minutes')
                   ON CONFLICT (lock_key) DO UPDATE SET holder='eu-west-1', expires_at=NOW()+INTERVAL '5 minutes'"""
            )
            conn.commit()
        conn.close()

        # Step 3: Promote standby to primary in PostgreSQL
        import subprocess
        subprocess.run(["pg_ctl", "promote", "-D", "/var/lib/postgresql/data"], check=True)
        print("PostgreSQL standby promoted to primary")

        # Step 4: Update Route 53 DNS to point to eu-west-1
        self.r53.change_resource_record_sets(
            HostedZoneId=self.cfg.route53_zone_id,
            ChangeBatch={
                "Changes": [{
                    "Action": "UPSERT",
                    "ResourceRecordSet": {
                        "Name": self.cfg.payments_record,
                        "Type": "A",
                        "TTL": 30,   # short TTL set proactively for faster failover
                        "ResourceRecords": [{"Value": self.cfg.standby_ip}]
                    }
                }]
            }
        )
        print(f"Route 53 updated: {self.cfg.payments_record} → {self.cfg.standby_ip}")
        # DNS propagates in ~30s (TTL was pre-set to 30s during steady state)
        # Total RTO: 30s (health check detection) + 30s (DNS TTL) = ~60s

Result

Synchronous replication guarantees RPO=0 — no committed transaction is lost even if us-east-1 disappears instantaneously. Automated failover detects failure in 30s (3×10s checks) and updates DNS. With TTL pre-lowered to 30s in steady state, total RTO is ~60s. The fencing token prevents split-brain: even if us-east-1 recovers mid-failover, it can't reclaim the lock until eu-west-1 releases it. Write latency penalty: +15ms (London RTT), acceptable for a payments system prioritizing correctness.

What to Avoid

Anti-patterns

Transparent Read-from-Replica

Routing reads silently to replicas without the application knowing means your code assumes strong consistency but gets eventual. One bad assumption ("read what I just wrote") causes hard-to-reproduce bugs. Make replica reads explicit in code or accept 100% strong reads.

LWW on Financial Data

Last-write-wins is inappropriate for bank balances, inventory counts, or any data where both concurrent writes matter. A £500 debit and a £200 debit happening simultaneously in two regions — LWW silently drops one. Use optimistic locking or a single primary for financial records.

High DNS TTL During Failover

Setting DNS TTL to 3600s (1 hour) to save query costs means users are stuck on a failed region for up to an hour after failover. Keep TTL at 30–60s for records behind health checks. The DNS query cost is negligible compared to an hour of outage.

GDPR Compliance by Policy Only

Writing in the runbook "EU data stays in EU" without technical enforcement means one misconfigured replication job causes a GDPR breach. Enforce residency via IAM policies that block cross-region DB replication, not documentation alone.

Manual Failover in 2025

If your DR runbook says "engineer SSHes into standby and runs pg_ctl promote," your RTO is determined by how fast an on-call engineer can wake up and not make mistakes at 3am. Automate the detection and promotion; keep human approval only for fail-back (restoring original primary).

Cross-Region Joins

A query that joins a table in us-east-1 with a table in eu-west-1 has 200ms of irreducible latency in the query path. If your ORM makes cross-region joins transparent, you'll only discover them in production. Shard your schema so joined tables always live in the same region.

Caching User-Specific Content at CDN

Accidentally serving User A's cached response to User B. Happens when you forget to add Cache-Control: private or when auth headers are stripped at the CDN. Always validate that authenticated endpoints return private cache headers; test with two different users.

Ignoring Replication Lag

Async replication that's usually 200ms can spike to 30s during heavy write load or network issues. If your application doesn't monitor lag and alert, you'll discover it when a user sees data from 30 seconds ago and files a bug. Monitor lag as a first-class SLI.

Interview Readiness

Interview Tips

Lead With Latency Goals

When asked to design a global system, immediately ask: "Where are users located and what's the latency requirement?" The answer determines everything — whether you need multi-region at all, whether CDN alone solves it, or whether you need active-active with local writes.

Know the CAP Trade-off Cold

Interviewers love this. For reads: eventual consistency is almost always fine (users tolerate 1-second stale data). For writes: explain that strong consistency requires a round-trip to quorum, and quote the latency cost (80ms cross-continent). Financial writes need strong consistency; social feeds don't.

Distinguish Active-Active From Multi-Master

Most "active-active" in practice is partitioned active-active (each record has one home region — no conflicts possible). True multi-master (any region can write any record) requires conflict resolution and is rarely the right choice. Say "partitioned active-active" in interviews — it shows depth.

Address Data Sovereignty Proactively

For any global design with user data, mention GDPR before the interviewer asks. Say: "EU personal data must stay in the EU — I'd use geo-partitioning or isolated regional deployments, enforced at both the DB and IAM layer." It signals operational maturity.

Quantify the Physics

New York → London = ~70ms RTT. NY → Singapore = ~200ms. These numbers matter — if you claim "global active-active with strong consistency," an interviewer will ask about write latency. Sync replication to a quorum in another region adds one RTT to every write. Know these numbers and cite them.

Always Have a Failover Story

Interviewers expect you to describe failure modes. For every region you add, explain: (1) how traffic is rerouted when it fails (Route 53 health check + failover routing), (2) what the RTO is (DNS TTL + detection time), and (3) what the RPO is (async = non-zero, sync = zero). RTO and RPO show you understand operations.

Key Concepts
+
Anycast vs Unicast
Unicast: one IP → one server. Anycast: same IP → multiple servers; BGP routes to nearest. Used by all major CDNs and DNS resolvers. Works at IP layer — no application changes needed.
+
Surrogate Keys / Cache Tags
Tag cached objects with entity IDs (e.g., "product-42"). When product 42 changes, purge all tagged entries across every CDN PoP with one API call. Cloudflare, Fastly, and Varnish all support this pattern.
+
Route 53 Routing Policies
Latency-based: lowest RTT (most common). Geolocation: by country (for residency). Weighted: for canary rollouts. Failover: primary + standby with health checks. Geoproximity: with bias adjustment.
+
GDPR Key Numbers
Fine: up to 4% of global annual revenue or €20M (whichever higher). Breach notification: 72 hours to notify the DPA. Right to erasure: 30 days to comply. Data portability: must provide machine-readable export.
+
TrueTime (Spanner)
Google Spanner uses atomic clocks + GPS receivers to bound clock uncertainty to ±7ms. This gives external consistency: a transaction committed at time T is visible to any subsequent read anywhere in the world. No other public cloud DB has this.
+
RTO vs RPO
RTO = how long you can be offline. RPO = how much data you can lose. Sync replication → RPO=0 (no data loss) at cost of write latency. Async replication → lower latency but RPO = replication lag (often 1s, can spike to minutes).
+
Vector Clocks & Causality
A vector clock {A:3, B:1} tracks causal history. Two events are concurrent if neither vector dominates the other → conflict. Amazon Dynamo and Riak use vector clocks to detect conflicts and expose them to the application layer for resolution.
+
Split-Brain & Fencing
Split-brain: two nodes both think they are primary → both accept writes → data diverges. Fencing token (a monotonically increasing lock version) prevents this: the old primary's writes are rejected by storage if a newer token exists.
