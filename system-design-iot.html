Foundation

IoT Architecture Overview

IoT systems connect physical devices — sensors, cameras, industrial machines, vehicles — to cloud infrastructure. The challenge is scale (billions of devices), heterogeneity (different hardware, protocols, connectivity), and the unique constraints of resource-limited devices.

IoT architecture: 4 layers Layer 1: Devices (sensors, actuators, cameras, PLCs) Constraints: limited CPU/RAM/battery, intermittent connectivity Protocols: MQTT (primary), CoAP (constrained), HTTP (capable devices), AMQP Security: hardware attestation, certificate-based auth (X.509) Layer 2: Edge (gateways, on-premise servers, CDN edge nodes) Purpose: aggregate device data locally, reduce cloud bandwidth Filter: only send anomalies or summaries to cloud (not raw 100Hz sensor data) Local ML: run inference close to the device (< 10ms) Offline mode: buffer data when cloud connection lost, sync when restored Hardware: AWS Greengrass, Azure IoT Edge, NVIDIA Jetson, Raspberry Pi Layer 3: Connectivity & Ingestion IoT Gateway / Broker: AWS IoT Core, Azure IoT Hub, HiveMQ, EMQX Scale: millions of concurrent device connections Protocol translation: MQTT → internal Kafka topics Device registry: track all devices, their state, last heartbeat Layer 4: Cloud Processing & Storage Stream processing: Flink / Kinesis for real-time telemetry Batch: Spark on S3 for historical analysis Time-series DB: TimescaleDB, InfluxDB, Amazon Timestream Command & Control: send commands back to devices OTA: manage firmware update campaigns
🌡️

Sensor Data Characteristics

High frequency (1Hz to 10kHz), time-stamped, often floating-point. Most raw data is noise — edge filtering and downsampling reduce cloud egress by 100×.

🔋

Power Constraints

Battery devices must sleep between transmissions. MQTT's persistent session lets devices disconnect and reconnect without losing subscriptions. LoRa and NB-IoT enable long-range, low-power connectivity.

🔒

Device Security

Devices can't rotate passwords manually. Use X.509 certificates provisioned at manufacturing. Certificate rotation must be automated via OTA. Compromised device certificates revoked in device registry.

📶

Connectivity Reality

IoT devices have intermittent connectivity: vehicles in tunnels, industrial networks with gaps. Design for offline operation: local buffer, store-and-forward, conflict resolution on reconnect.

IoT Protocol

MQTT Protocol

MQTT (Message Queuing Telemetry Transport) is the dominant IoT protocol. It's a lightweight publish-subscribe protocol designed for unreliable networks and resource-constrained devices. A 250-byte MQTT packet vs a 2KB HTTP request makes a significant difference at scale.

MQTT: broker-mediated pub/sub Device (Publisher) MQTT Broker Backend (Subscriber) │ │ │ │── CONNECT (client_id, │ │ │ clean_session=False, │ │ │ keepalive=60s) ───────────►│ │ │◄─ CONNACK ───────────────────│ │ │ │◄─ SUBSCRIBE ─────────────────│ │ │ "devices/+/telemetry" │ │── PUBLISH ──────────────────►│ topic: devices/abc/telemetry │ │ topic: devices/abc/telemetry│ {"temp": 72.3, "ts": ...} │ │ payload: {"temp": 72.3} │──► PUBLISH ─────────────────►│ │ QoS: 1 (at least once) │ │ Topic hierarchy: devices/{device_id}/telemetry devices/{device_id}/commands (cloud → device) devices/{device_id}/status (online/offline) QoS levels: QoS 0: at most once (fire and forget) — fastest, may lose messages QoS 1: at least once — broker ACKs, may duplicate QoS 2: exactly once — 4-way handshake, slowest, guaranteed once Use QoS 1 for telemetry (tolerate duplicate), QoS 2 for commands (must execute once) Last Will and Testament (LWT): broker publishes on behalf of device if it disconnects ungracefully Retained message: broker stores last message on a topic, new subscribers get it immediately
import paho.mqtt.client as mqtt
import json, time, ssl

# Device-side MQTT client (runs on embedded device)
class IoTDevice:
    def __init__(self, device_id: str, broker_host: str):
        self.device_id = device_id
        self.client = mqtt.Client(client_id=device_id, clean_session=False)

        # Mutual TLS: device authenticates with certificate
        self.client.tls_set(
            ca_certs="/certs/root-ca.pem",
            certfile=f"/certs/{device_id}.pem",
            keyfile=f"/certs/{device_id}-key.pem",
            tls_version=ssl.PROTOCOL_TLS,
        )

        # Last Will: published if device disconnects without DISCONNECT packet
        self.client.will_set(
            topic=f"devices/{device_id}/status",
            payload=json.dumps({"status": "offline"}),
            qos=1, retain=True
        )

        self.client.on_connect = self._on_connect
        self.client.on_message = self._on_message
        self.client.connect(broker_host, port=8883)  # 8883 = MQTT over TLS
        self.client.loop_start()

        # Announce online
        self.client.publish(f"devices/{device_id}/status",
                           json.dumps({"status": "online"}), qos=1, retain=True)

    def _on_connect(self, client, userdata, flags, rc):
        # Subscribe to command topic (cloud → device)
        client.subscribe(f"devices/{self.device_id}/commands", qos=2)

    def _on_message(self, client, userdata, msg):
        command = json.loads(msg.payload)
        if command["action"] == "set_sampling_rate":
            self.sampling_interval = command["interval_ms"] / 1000.0
        elif command["action"] == "reboot":
            import os; os.system("reboot")

    def publish_telemetry(self, sensor_data: dict):
        payload = json.dumps({**sensor_data, "ts": int(time.time() * 1000)})
        self.client.publish(
            topic=f"devices/{self.device_id}/telemetry",
            payload=payload,
            qos=1           # at-least-once: tolerable for sensor data
        )

Data Ingestion

Telemetry Ingestion at Scale

1M devices sending data every second = 1M messages/sec. The ingestion pipeline must be horizontally scalable, handle backpressure, and route data to the right storage (time-series for recent, cold storage for historical).

Telemetry pipeline: device → processing → storage Devices (1M devices × 1 msg/sec = 1M msg/sec) │ MQTT (TLS) ▼ IoT Broker Cluster (HiveMQ / AWS IoT Core) │ Bridge/Rules Engine → Kafka ▼ Kafka (partitioned by device_id) │ 100 partitions → parallel consumers ├──────────────────────────────────────────────────────────────┐ │ │ │ ▼ ▼ ▼ Flink (stream processor) Timescale / InfluxDB S3 / Iceberg Windowed aggregations (recent: last 30 days) (all history) Anomaly detection fast queries for dashboards Parquet columnar Alert generation downsampled metrics Spark batch analysis Enrichment (device meta) Downsampling: raw 1Hz → 1-minute averages in TSDB → 1-hour averages in S3 Hot path: Kafka → Flink → Redis (real-time dashboard, alert state) Cold path: Kafka → S3 (Kafka Connect) → Spark (batch ML training)
from pyflink.datastream import StreamExecutionEnvironment
from pyflink.datastream.connectors.kafka import FlinkKafkaConsumer
from pyflink.common.typeinfo import Types
import json, statistics

env = StreamExecutionEnvironment.get_execution_environment()

# Flink job: consume telemetry, compute 1-min windowed stats, detect anomalies
def process_iot_telemetry():
    kafka_consumer = FlinkKafkaConsumer(
        topics="iot.telemetry",
        deserialization_schema=SimpleStringSchema(),
        properties={"bootstrap.servers": "kafka:9092", "group.id": "flink-iot"},
    )

    stream = (
        env.add_source(kafka_consumer)
        .map(lambda x: json.loads(x))            # parse JSON
        .key_by(lambda msg: msg["device_id"])    # partition per device
        .window(TumblingEventTimeWindows.of(Time.minutes(1)))
        .process(DeviceWindowFunction())
    )

    # Write to TimescaleDB (1-min aggregates)
    stream.add_sink(timescale_sink)

    # Anomaly stream → alert topic
    stream.filter(lambda r: r["anomaly"]).add_sink(alert_kafka_sink)

    env.execute("IoT Telemetry Processing")

class DeviceWindowFunction(ProcessWindowFunction):
    def process(self, device_id, context, elements, out):
        readings = [e["temperature"] for e in elements]
        mean = statistics.mean(readings)
        stddev = statistics.stdev(readings) if len(readings) > 1 else 0

        # Z-score anomaly: value more than 3 std devs from mean
        anomaly = any(abs(r - mean) > 3 * stddev for r in readings)

        out.collect({
            "device_id": device_id,
            "window_start": context.window().start,
            "mean_temp": round(mean, 2),
            "min_temp": min(readings),
            "max_temp": max(readings),
            "sample_count": len(readings),
            "anomaly": anomaly,
        })
Processing at the Edge

Edge Computing

Edge computing moves computation from the cloud to the edge — near the devices. This reduces latency, cuts bandwidth costs, and enables operation when cloud connectivity is unavailable.

Cloud vs Edge processing decision Process at EDGE when: • Latency matters: safety system must respond in < 10ms (no time for round trip) • Bandwidth is expensive: 100 cameras × 4K video = 400 Mbps, too much for cloud • Privacy required: video processed on-premises, only metadata sent to cloud • Intermittent connectivity: factory floor with periodic outages Edge can do: local ML inference, data filtering, aggregation, buffering, local SCADA control Process in CLOUD when: • Compute-intensive: training ML models, complex analytics across all devices • Cross-device: correlation across 100K devices requires global view • Long-term storage: S3 for years of historical data • Cost: GPU in cloud cheaper than GPU in every factory AWS Greengrass: runs Lambda functions and ML models at the edge Azure IoT Edge: Docker containers deployed to edge devices from Azure NVIDIA Jetson: GPU-accelerated edge nodes for computer vision inference Edge deployment pattern (GitOps to edge): Cloud: build new ML model → push to model registry OTA: download model to edge nodes via delta update Edge: hot-swap model without service restart Rollback: if edge validation fails → revert to previous version
Fleet Updates

OTA (Over-the-Air) Firmware Updates

Updating firmware on 1M devices without breaking them is an engineering challenge. OTA updates must be atomic, verifiable, rollback-safe, and bandwidth-efficient.

Delta updates: often < 500KB → 95% savings A/B partition: device has 2 firmware partitions. Update writes to inactive partition. On success: mark new partition active. If boot fails 3 times: auto-rollback to old partition.
Inference at the Edge

Edge ML Inference

Running ML models directly on IoT devices or edge nodes eliminates cloud round-trips for time-sensitive decisions. Model quantization and hardware-specific compilation are key to fitting models on constrained devices.

📱

TFLite (TensorFlow Lite)

Optimized for mobile and embedded devices. Supports quantization (INT8), hardware delegates (GPU, DSP, NPU). Used for: keyword spotting, image classification on MCUs and phones.

🎯

ONNX Runtime

Cross-platform inference engine. Export PyTorch/TF → ONNX → run on CPU, GPU, NPU. Works on: x86 servers, ARM edge devices, NVIDIA Jetson. No Python required at inference time.

⚡

Quantization

Convert FP32 weights → INT8 (4× smaller, 2-4× faster, 1-2% accuracy loss). Post-training quantization requires a calibration dataset. Used when model must fit in 4MB device flash.

🔧

TensorRT

NVIDIA's inference optimizer. Compiles ONNX model for specific GPU hardware → 2-5× speedup over PyTorch. Layer fusion, precision calibration, kernel auto-tuning. Used on Jetson AGX for real-time video AI.

9 Viewpoints

Engineer Perspectives

Backend Engineer

IoT device IDs are global identifiers. Design APIs idempotent by device_id + sequence_number — devices retry on network failure, and you may receive duplicates days later when devices come back online.

SRE

Monitor fleet health as a distribution: % of devices online, % reporting in last 5 minutes. A single metric ("total messages/sec") hides mass device failures if total volume stays the same with different devices reporting.

Security Engineer

Devices in the field can't be manually patched. Certificate expiry, firmware vulnerabilities, and supply chain attacks are critical concerns. Design for remote remediation from day one — OTA is a security control, not just a feature.

Data Engineer

IoT time-series data is write-heavy, read-rarely. Partition by device_id + day. Downsample aggressively: 1Hz raw data → 1-min aggregates for queries → 1-hour summaries for dashboards. Raw data costs 100× more to store than summaries.

ML Engineer

Edge ML models must be validated on the same hardware they run on. INT8 quantization on ARM vs x86 can have different accuracy profiles. Test on representative device hardware, not just your laptop.

Platform Engineer

OTA updates are deployments — apply the same rigor: staged rollout, canary devices, automatic halt on failure rate threshold. A bad firmware update bricking 1M devices is a major incident.

Frontend Engineer

IoT dashboards often display live data from thousands of devices. Virtual scrolling and WebSocket fan-out from a backend aggregator (not one WS per device) are essential — don't open 10K WebSocket connections from the browser.

Mobile Engineer

Phones are IoT devices too. Bluetooth Low Energy (BLE) connects phones to nearby sensors. Core Bluetooth (iOS) and BLE API (Android) enable proximity-based device management without needing the device to have a cloud connection.

Architect

Design the edge-cloud split from day one. Retrofitting edge processing into a cloud-first architecture is painful. Decide upfront: what data stays at edge, what goes to cloud, and what actions are autonomous vs cloud-directed.

from pyflink.datastream import StreamExecutionEnvironment
from pyflink.datastream.window import TumblingEventTimeWindows
from pyflink.common.time import Time

def detect_harsh_braking(telemetry_stream):
    return (
        telemetry_stream
        .key_by(lambda x: x["vehicle_id"])
        .window(SlidingEventTimeWindows.of(Time.seconds(2), Time.milliseconds(200)))
        .process(HarshBrakingDetector())  # speed drop > 20 km/h in 2 seconds
    )

class HarshBrakingDetector(ProcessWindowFunction):
    def process(self, vehicle_id, ctx, elements, out):
        speeds = sorted(elements, key=lambda x: x["ts"])
        if len(speeds) >= 2:
            speed_drop = speeds[0]["speed_kmh"] - speeds[-1]["speed_kmh"]
            if speed_drop > 20:
                out.collect({
                    "vehicle_id": vehicle_id,
                    "event": "harsh_braking",
                    "speed_drop_kmh": speed_drop,
                    "ts": speeds[-1]["ts"]
                })

Problem 02 · Smart Factory
Design an edge computing system for a factory with 500 machines and intermittent connectivity
Edge ComputingStore-and-ForwardLocal ML

Requirements

500 CNC machines, each with 50 sensors at 100Hz. Factory WiFi drops for 30 min daily. Need: real-time anomaly detection (stop machine in < 100ms), predictive maintenance, production analytics.

"""
Edge Node (per factory floor section: 50 machines):
  Hardware: Intel NUC i7, 32GB RAM, 2TB NVMe
  OS: Ubuntu 22.04 LTS, Docker
  Software stack:
    - EMQX (local MQTT broker for 50 machines)
    - Flink (stream processing for anomaly detection)
    - ONNX Runtime (ML inference: predictive maintenance model)
    - TimescaleDB (local time-series: 7 days of raw data)
    - Kafka (local buffer: 48h of data for store-and-forward)
    - AWS Greengrass (sync with cloud when connected)
"""

class EdgeAnomalyDetector:
    """Runs on edge node. Detects anomalies in < 10ms without cloud."""

    def __init__(self, model_path: str):
        import onnxruntime as ort
        self.session = ort.InferenceSession(model_path,
            providers=["CPUExecutionProvider"])  # or CUDAExecutionProvider if GPU
        self.thresholds = self._load_thresholds()

    def analyze(self, machine_id: str, sensor_window: list[dict]) -> dict:
        # Build feature vector from 100 sensor readings (1 second window)
        features = self._extract_features(sensor_window)
        anomaly_score = self.session.run(None, {"features": features})[0][0]

        if anomaly_score > self.thresholds[machine_id]["critical"]:
            # IMMEDIATE ACTION: send stop command to machine PLC (< 10ms)
            self.send_plc_command(machine_id, "EMERGENCY_STOP")
            self.alert_cloud_async(machine_id, anomaly_score, sensor_window[-1])
            return {"action": "stopped", "reason": "critical_anomaly", "score": anomaly_score}

        elif anomaly_score > self.thresholds[machine_id]["warning"]:
            # Predictive maintenance: schedule inspection
            self.queue_maintenance_notification(machine_id, anomaly_score)

        return {"action": "none", "score": anomaly_score}

class StoreAndForwardBuffer:
    """Buffers data locally when cloud unavailable. Syncs when connection restored."""

    def __init__(self, kafka_bootstrap: str, cloud_kafka: str):
        self.local = KafkaProducer(bootstrap_servers=kafka_bootstrap)
        self.is_connected = True

    def write(self, topic: str, data: bytes):
        self.local.send(topic, data)  # always write locally first

    async def sync_to_cloud(self):
        # When cloud connection available: replay buffered messages
        last_synced_offset = await self.get_cloud_offset()
        async for batch in self.local_consumer.consume_from(last_synced_offset):
            await self.cloud_producer.send_batch(batch)
Problem 03 · OTA System
Design an OTA update system for 5M IoT devices with staged rollout
OTADelta UpdatesCanary

Requirements

5M devices, firmware updates every 2 weeks. Update size: 8MB. Total bandwidth if all at once: 40TB. Need staged rollout with automatic rollback on failure. Devices have 16MB flash, A/B partition.

import boto3, hashlib, subprocess

class OTAUpdateManager:
    def __init__(self):
        self.s3 = boto3.client("s3")
        self.iot = boto3.client("iot")
        self.dynamodb = boto3.resource("dynamodb").Table("ota_campaigns")

    def create_campaign(self, new_version: str, firmware_path: str, prev_version: str = None):
        # Generate delta if possible (saves 90% bandwidth)
        if prev_version:
            delta_path = f"/tmp/delta_{prev_version}_to_{new_version}.bin"
            subprocess.run(["bsdiff", f"firmware_{prev_version}.bin",
                           firmware_path, delta_path], check=True)
            upload_path = delta_path
            update_type = "delta"
        else:
            upload_path = firmware_path
            update_type = "full"

        # Sign and upload
        sha256 = hashlib.sha256(open(upload_path, "rb").read()).hexdigest()
        s3_key = f"firmware/{new_version}/{update_type}.bin"
        self.s3.upload_file(upload_path, "iot-firmware", s3_key)

        # Staged rollout: groups defined by device attributes
        stages = [
            {"name": "canary", "target_pct": 0.01, "wait_hours": 24, "max_failure_pct": 0.5},
            {"name": "early", "target_pct": 0.05, "wait_hours": 48, "max_failure_pct": 0.3},
            {"name": "majority", "target_pct": 0.50, "wait_hours": 72, "max_failure_pct": 0.1},
            {"name": "all", "target_pct": 1.00, "wait_hours": 0, "max_failure_pct": 0.05},
        ]

        campaign_id = f"campaign_{new_version}_{int(time.time())}"
        self.dynamodb.put_item(Item={
            "campaign_id": campaign_id, "version": new_version,
            "s3_key": s3_key, "sha256": sha256, "stages": stages,
            "current_stage": 0, "status": "active",
        })
        return campaign_id

    def check_campaign_health(self, campaign_id: str) -> dict:
        campaign = self.dynamodb.get_item(Key={"campaign_id": campaign_id})["Item"]
        stage = campaign["stages"][campaign["current_stage"]]

        # Count successes/failures from device telemetry
        metrics = self.query_device_metrics(campaign_id, hours=24)
        failure_pct = metrics["failures"] / metrics["total"] * 100

        if failure_pct > stage["max_failure_pct"]:
            # HALT and rollback
            self.halt_campaign(campaign_id)
            self.send_rollback_command(campaign_id)
            return {"action": "halted", "failure_pct": failure_pct}

        return {"action": "healthy", "failure_pct": failure_pct}

What Not to Do

IoT Anti-patterns

Polling Instead of MQTT

Having 1M devices HTTP poll the server every second = 1M req/sec for status checks. MQTT pub/sub delivers to devices instantly when state changes, with zero polling overhead.

Sending Raw High-Frequency Data

Streaming 100Hz sensor data to the cloud without edge filtering. 100Hz × 100 bytes × 1M devices = 10GB/sec. Edge downsampling (send 1-min averages + anomalies) reduces this to manageable volume.

Hardcoded Credentials on Devices

Shared API keys or passwords embedded in firmware. One extracted key compromises all devices. Use per-device X.509 certificates provisioned at manufacturing with hardware-based key storage.

Big Bang Firmware Rollouts

Pushing firmware to all 1M devices simultaneously. A bad update bricks the entire fleet. Staged rollout with canary devices and automatic halt on failure rate threshold is mandatory.

Storing Raw IoT Data Forever

1 year of 1Hz data from 1M devices = 30 trillion rows. Implement tiered storage: hot (TSDB, 30 days), warm (S3 Parquet, 1 year), cold (S3 Glacier, 7 years) with automatic downsampling at each tier.

No Offline Mode

Assuming devices always have cloud connectivity. Industrial networks, vehicle tunnels, and cellular dead zones make this a guarantee of failure. Design store-and-forward from the start.

Single MQTT Topic for All Devices

All devices publish to "iot/telemetry" — the broker must fanout to all subscribers for every message. Use hierarchical topics (devices/{id}/telemetry) so subscribers can filter by device or group.

Cloud-Dependent Safety Logic

Machine stops only when cloud sends a stop command after detecting anomaly. Round-trip latency of 100ms+ is unacceptable for safety-critical responses. Safety logic must run at the edge, autonomously.

Interview Prep

Interview Tips

Explain MQTT vs HTTP

MQTT is designed for IoT: pub/sub, persistent sessions, QoS levels, Last Will and Testament, tiny overhead (2-byte fixed header). HTTP is designed for web. Know why MQTT wins on constrained networks and devices.

Address Scale Math

When given "10M devices," calculate: messages/sec, bandwidth, storage growth/day. Then show how the architecture handles it (Kafka partitioning, downsampling, tiered storage). The math shows you're thinking about real constraints.

Edge vs Cloud Isn't Binary

The best answer is usually "both, for different things." Edge for latency-sensitive and bandwidth-expensive. Cloud for global analytics and long-term storage. Describe the data flow between the two layers.

Mention Device Shadow

Device shadow (desired vs reported state) is the standard pattern for cloud-to-device configuration. It handles offline devices elegantly. Interviewers at IoT-heavy companies specifically look for this pattern.

OTA is a Security System

Don't describe OTA purely as a feature — it's a critical security mechanism. Firmware signing, certificate rotation, and vulnerability patching all depend on OTA. Frame it as security infrastructure.

Store-and-Forward for Resilience

Always mention offline resilience when designing IoT systems. "What happens when connectivity drops?" is a common follow-up. Local buffering + cloud sync on reconnect is the standard pattern.

Clarifications
+
What is publish-subscribe (pub/sub)?
In pub/sub, publishers send messages to named channels (topics) without knowing who will receive them. Subscribers listen on topics they care about. A broker in the middle routes messages. This decouples producers from consumers: devices publish telemetry without knowing which services consume it, and new consumers can subscribe without changing device code.
+
What is an X.509 certificate?
An X.509 certificate is a digital identity document for a device or server. It contains: the device's public key, who issued it (Certificate Authority), and what it identifies (device ID). The private key stays on the device (never transmitted). When the device connects to the IoT broker, it proves it holds the private key matching the certificate — this authenticates the device without passwords.

What is a time-series database?
A time-series database (TSDB) is optimized for data that arrives as (timestamp, value) pairs. It excels at: ingesting millions of data points per second, querying "show me temperature over the last 24 hours," computing aggregations (min, max, avg) over time ranges. TimescaleDB, InfluxDB, and Amazon Timestream are examples. Regular databases are too slow for IoT-scale time-series queries.

What is a PLC?
A PLC (Programmable Logic Controller) is an industrial computer that controls physical machinery. It reads sensors (temperature, pressure, position) and controls actuators (motors, valves, conveyors) in real time. PLCs operate on deterministic timescales (microseconds) — they cannot tolerate the variable latency of cloud communication. Edge nodes talk to PLCs via industrial protocols (OPC-UA, Modbus) and relay data to the cloud.

What is A/B partitioning for firmware?
Devices with A/B (dual-bank) flash storage have two firmware slots. The device boots from the active slot. During OTA, the new firmware is written to the inactive slot while the device keeps running. On success, the device reboots into the new slot (marking it active). If the new firmware fails to boot 3 times, the bootloader reverts to the old slot. This makes OTA updates atomic and recoverable.
