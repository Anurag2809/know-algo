Foundation

The ML System Landscape

An ML system is not just a model — it's the data pipelines that feed it, the infrastructure that trains it, the store that serves its features, the registry that versions it, and the monitoring that detects when it degrades. Most ML projects fail not because of bad models, but because of broken infrastructure around the model.

Feature Engineering

Feature Stores

A feature store is the central repository for ML features. It solves two critical problems: (1) training-serving skew — the features used during training differ from features at inference time; (2) feature reuse — multiple models can share the same features without recomputing them.

Feature Store: offline (training) + online (serving) stores Feature Engineering (runs on schedule — hourly/daily) │ │ Compute: user_30d_purchase_count, item_avg_rating, etc. │ ├──────────────────────────────────────────────────────────┐ │ │ ▼ ▼ Offline Store (historical features) Online Store (latest features) S3 / BigQuery / Redshift Redis / DynamoDB / Bigtable Columnar format (Parquet) Key-value: user_id → feature_vector Used for: model training Used for: real-time inference Can query "what was this user's state at T?" Low latency (< 5ms) Point-in-time correct joins (offline): critical for training correctness When training, use the features as they existed AT prediction time, not today's values Without point-in-time joins: future leakage → model looks great offline, fails in prod Real-time serving flow: Request: "score user 123 for item 456" 1. Fetch user features from Redis (online store): O(1), ~2ms 2. Fetch item features from Redis: ~2ms 3. Concatenate → feature vector → model inference: ~20ms 4. Return prediction Tools: Feast (open-source), Tecton (managed), Databricks Feature Store, Vertex AI Feature Store

Inference

Model Serving

Getting predictions from a model at production scale is an engineering challenge distinct from training. Latency, throughput, cost, and reliability all require deliberate design.

Online inference vs batch inference Online (real-time) Inference Request → Model Server → Prediction (< 100ms p99) • User-facing: recommendation, fraud detection, search ranking • Serving: TorchServe, TF Serving, Triton, BentoML, vLLM (LLMs) • GPU vs CPU: GPU for deep learning, CPU for tree models (XGBoost) • Batching: group 32 requests into one forward pass (GPU efficiency) • Model caching: keep model in GPU VRAM — loading takes seconds Batch Inference Precompute predictions for all users daily / hourly Store in DB → app reads from DB (not model server) • Cheaper: no GPU idle time between requests • Works for: daily recommendation lists, email targeting, risk scores • Spark / Databricks for large-scale batch scoring • Cannot handle new items (no record until next batch run) Hybrid: Streaming Inference Kafka consumer → model → write result to DB Latency: seconds to minutes (not milliseconds) Good for: fraud scoring after transaction, content moderation Triton Inference Server: NVIDIA's multi-framework server Supports: PyTorch, TF, ONNX, TensorRT, XGBoost, LightGBM, Python Features: dynamic batching, concurrent model execution, model ensembles vLLM: optimized LLM serving with PagedAttention, continuous batching

Model Optimization

Quantization (FP32 → INT8): 4× speedup, slight accuracy loss. TensorRT: compiles model to GPU-optimized kernels. ONNX: model format that runs on any runtime. Pruning: remove weights near zero.

Latency vs Throughput

Online inference: optimize for p99 latency (SLO: 100ms). Batch scoring: optimize for throughput (records/hour). The same model needs different serving configs for each use case.

Model Caching

Loading a PyTorch model from disk takes 2-10 seconds. Keep models warm in GPU memory. Use Kubernetes HPA on GPU pods to scale with traffic. Cold start is a real problem in serverless ML.

RAG & Vector Databases

RAG (Retrieval-Augmented Generation) enhances LLMs with external knowledge. Instead of fine-tuning the model (expensive), you retrieve relevant documents at query time and include them in the prompt context. Vector databases enable semantic search over document embeddings.

RAG pipeline: index time + query time Index time (run once, or incrementally as docs change): Documents (PDFs, wiki, Notion, Confluence) │ ▼ Chunking (split into 512-token chunks with overlap) │ ▼ Embedding Model (text → 1536-dim vector) (OpenAI ada-002, sentence-transformers, E5-large) │ ▼ Vector Database (store vectors with metadata) Pinecone / Weaviate / Chroma / pgvector (Postgres extension) Index type: HNSW (hierarchical navigable small world) for ANN search Query time (every user request): User Question: "How do I reset my 2FA?" │ ▼ Embed question → 1536-dim vector │ ▼ ANN search: top-5 most similar chunks from vector DB (~10ms) Result: [docs about 2FA reset, account recovery, auth settings] │ ▼ Prompt construction: "Answer using this context:\n[chunks]\n\nQuestion: How do I reset 2FA?" │ ▼ LLM inference (GPT-4, Claude, Llama) → grounded answer │ ▼ Hallucinations reduced: model answers from retrieved facts, not training memory

import chromadb

# Index documents (run once)
def index_documents(docs: list[dict]):
    collection.add(
        documents=[d["content"] for d in docs],
        metadatas=[{"source": d["source"]} for d in docs],
        ids=[d["id"] for d in docs],

# RAG query pipeline
def rag_query(question: str, n_results: int = 5) -> str:
    # 1. Retrieve relevant chunks
    results = collection.query(query_texts=[question], n_results=n_results)
    context = "\n\n".join(results["documents"][0])

    # 2. Build grounded prompt
    prompt = f"""Answer the question using ONLY the context below.
If the answer is not in the context, say "I don't know."

Context:
{context}

Question: {question}"""

    # 3. Generate answer
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        temperature=0,  # deterministic for factual QA
    )
    return response.choices[0].message.content

Model Validation

A/B Testing ML Models

Offline metrics (AUC, RMSE) often don't translate to business metrics (revenue, engagement). A/B testing in production is the only way to measure true model impact on user behavior.

Model A/B test (champion vs challenger) Traffic Splitter │ ├─ 90% ──► Model A (champion, production) └─ 10% ──► Model B (challenger, new version) Critical: assignment must be deterministic per user hash(user_id + experiment_id) % 100 < 10 → Group B Same user always gets same model (no flickering) Metrics logged per prediction: { user_id, model_version, prediction, timestamp } Later joined with: { user_id, purchased, revenue, timestamp } Statistical significance: After N days: compute p-value for revenue difference (A vs B) p < 0.05 + minimum detectable effect met → promote B to champion If inconclusive after max duration → abandon experiment Guardrail metrics (must not regress even if primary metric improves): Latency p99, error rate, customer support contacts A/B test is invalid if guardrail metrics degrade significantly
9 Viewpoints

Engineer Perspectives

ML Engineer

Training-serving skew is the #1 silent killer. Recompute features in your serving code using the exact same logic as training. Even a rounding difference causes invisible accuracy degradation.

Data Engineer

Point-in-time correct joins are non-negotiable for classification models. Training on "current" features instead of "features at prediction time" leaks future information. The model looks great offline and fails in production.

Backend Engineer

Treat model predictions like any other service call: set timeouts, add circuit breakers, have a fallback (heuristic or cached prediction). Model servers have latency spikes too.

SRE

Monitor input distributions, not just model accuracy. Data drift alerts are often the first signal of an upstream data problem. Accuracy degrades silently; input distribution changes are detectable immediately.

Platform Engineer

GPU pods are expensive. Use preemptible/spot instances for training (save 70%). Set up Cluster Autoscaler to spin up GPU nodes only when training jobs run. Idle GPU instances are pure waste.

Security Engineer

ML models can leak training data (membership inference attacks). Differential privacy during training limits this. Feature stores with PII need column-level access control — not all engineers should see all features.

Architect

Separate the ML system from the application system with a well-defined API. The application calls "get recommendation" and doesn't know if it's a model, a heuristic, or a cache. This lets you swap backends without touching app code.

Frontend Engineer

Predicted results should degrade gracefully. If the recommendation service times out, show popular items. If the search model fails, fall back to keyword search. Users don't see model versions; they see broken experiences.

Mobile Engineer

On-device ML (TFLite, Core ML) eliminates latency and works offline. Tradeoff: model size limited to ~50MB, update requires app release. Use for: face detection, text autocorrect, wake word detection. Use cloud inference for complex models.

Problem 01 · Recommendation System
Design a real-time product recommendation system at 100K req/s
Feature StoreTwo-Stage RetrievalOnline Serving

Requirements

Return 20 personalized product recommendations in under 100ms p99. 100K requests/second. 10M users, 1M items. Personalized by user history, trending items, and user context.

import asyncio
from feast import FeatureStore
import faiss, numpy as np

# Two-stage architecture: Recall → Ranking
# Stage 1 (Recall): retrieve candidate set fast (1000 items in < 10ms)
# Stage 2 (Ranking): score candidates with a more complex model (< 50ms)

class RecommendationService:
    def __init__(self):
        self.feature_store = FeatureStore(repo_path=".")
        self.faiss_index = faiss.read_index("item_embeddings.faiss")  # pre-built
        self.item_ids = np.load("item_ids.npy")
        self.ranking_model = load_model("ranking_model.onnx")

    async def get_recommendations(self, user_id: str, n: int = 20) -> list[str]:
        # Parallel: fetch user features + trending items
        user_features, trending = await asyncio.gather(
            self._get_user_features(user_id),
            self._get_trending_items(n=200),
        )

        # Stage 1: ANN search in item embedding space (< 10ms)
        user_embedding = user_features["embedding"]  # 64-dim vector
        _, candidate_indices = self.faiss_index.search(
            user_embedding.reshape(1, -1), k=500  # top-500 nearest items
        )
        candidates = self.item_ids[candidate_indices[0]].tolist()

        # Merge candidates: ANN results + trending + diverse categories
        all_candidates = list(set(candidates + trending))[:1000]

        # Stage 2: Ranking model scores each candidate (< 50ms for 1000 items)
        item_features = self.feature_store.get_online_features(
            features=["item_features:avg_rating", "item_features:purchase_rate_7d"],
            entity_rows=[{"item_id": iid} for iid in all_candidates]
        ).to_dict()

        scores = self.ranking_model.run(None, {
            "user_features": np.tile(user_embedding, (len(all_candidates), 1)),
            "item_features": np.array([
                [item_features["avg_rating"][i], item_features["purchase_rate_7d"][i]]
                for i in range(len(all_candidates))
            ]),
        })[0]

        # Top-N by score
        top_indices = np.argsort(scores)[-n:][::-1]
        return [all_candidates[i] for i in top_indices]

    async def _get_user_features(self, user_id: str) -> dict:
        return self.feature_store.get_online_features(
            features=["user_features:embedding", "user_features:age_bucket"],
            entity_rows=[{"user_id": user_id}]
        ).to_dict()

FAISS ANN search is CPU-bound and thread-safe. Deploy 50+ pods with HPA on CPU utilization. Ranking model on GPU pods (batching 32 requests per forward pass). Feature store reads from Redis cluster.

Problem 02 · RAG Chatbot
Build an enterprise knowledge chatbot using RAG over 100K internal documents
RAGVector DBChunkingReranking

Requirements

100K documents (PDF, Confluence, Notion). Answer questions accurately with citations. Latency under 5 seconds. Access control: users only see documents they're authorized for.

from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.embeddings import OpenAIEmbeddings
from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams, PointStruct
import cohere

# Index pipeline
def index_documents(docs: list[dict], user_permissions: dict):
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=512,
        chunk_overlap=64,    # overlap prevents losing context at boundaries
        separators=["\n\n", "\n", ". ", " "],
    )
    embedder = OpenAIEmbeddings(model="text-embedding-3-small")
    qdrant = QdrantClient("http://qdrant:6333")

    points = []
    for doc in docs:
        chunks = splitter.split_text(doc["content"])
        embeddings = embedder.embed_documents(chunks)

        for i, (chunk, emb) in enumerate(zip(chunks, embeddings)):
            points.append(PointStruct(
                id=f"{doc['id']}_{i}",
                vector=emb,
                payload={
                    "text": chunk,
                    "source": doc["source"],
                    "doc_id": doc["id"],
                    "allowed_groups": doc["access_groups"],  # ACL embedded in vector
                },
            ))

    qdrant.upsert(collection_name="enterprise_docs", points=points)

# Query pipeline with access control
co = cohere.Client("...")

def query(question: str, user_groups: list[str]) -> dict:
    embedder = OpenAIEmbeddings(model="text-embedding-3-small")
    q_emb = embedder.embed_query(question)

    # Access-controlled search: only return docs user can see
    results = qdrant.search(
        collection_name="enterprise_docs",
        query_vector=q_emb,
        query_filter={"must": [{"key": "allowed_groups", "match": {"any": user_groups}}]},
        limit=20,  # over-fetch for reranking
    )

    # Rerank: cross-encoder scores relevance more precisely than cosine similarity
    docs = [r.payload["text"] for r in results]
    reranked = co.rerank(query=question, documents=docs, top_n=5, model="rerank-english-v3.0")
    top_chunks = [docs[r.index] for r in reranked.results]
    sources = [results[r.index].payload["source"] for r in reranked.results]

    context = "\n\n".join(top_chunks)
    answer = chat_with_context(question, context)
    return {"answer": answer, "sources": list(set(sources))}
Problem 03 · Model Monitoring
Design a data drift detection and automated retraining system
Data DriftEvidentlyAutomated Retraining

Scenario

Fraud detection model trained on Q1 data. In Q3, fraud patterns changed — model accuracy dropped from 94% to 78% without anyone noticing for 3 weeks. Build a system to detect drift and trigger retraining automatically.

from evidently.report import Report
from evidently.metric_preset import DataDriftPreset, ClassificationPreset
import pandas as pd, mlflow, subprocess

class ModelMonitor:
    def __init__(self, model_name: str, drift_threshold: float = 0.1):
        self.model_name = model_name
        self.threshold = drift_threshold

    def check_drift(self, reference_data: pd.DataFrame, current_data: pd.DataFrame) -> dict:
        report = Report(metrics=[
            DataDriftPreset(),          # feature distribution drift (KS test, PSI)
            ClassificationPreset(),     # model performance metrics
        ])
        report.run(reference_data=reference_data, current_data=current_data)
        result = report.as_dict()

        drift_detected = result["metrics"][0]["result"]["dataset_drift"]
        drift_share = result["metrics"][0]["result"]["drift_share"]
        current_accuracy = result["metrics"][1]["result"]["current"]["accuracy"]

        return {
            "drift_detected": drift_detected,
            "drift_share": drift_share,           # fraction of features drifted
            "current_accuracy": current_accuracy,
        }

    def should_retrain(self, monitoring_result: dict) -> bool:
        # Retrain if: significant drift OR accuracy dropped below threshold
        return (
            monitoring_result["drift_share"] > self.threshold
            or monitoring_result.get("current_accuracy", 1.0) < 0.90
        )

    def trigger_retraining(self):
        # Kick off training pipeline (Airflow DAG trigger)
        subprocess.run([
            "airflow", "dags", "trigger",
            f"train_{self.model_name}",
            "--conf", '{"trigger_reason": "drift_detected"}'
        ])

# Scheduled monitoring (run daily via Airflow)
def daily_monitor():
    monitor = ModelMonitor("fraud-detection", drift_threshold=0.15)

    # Load reference data (training data from last model)
    reference = pd.read_parquet("s3://ml-data/reference/fraud_train.parquet")

    # Load current production data (last 7 days of predictions + actuals)
    current = pd.read_parquet(f"s3://ml-data/production/last_7d.parquet")

    result = monitor.check_drift(reference, current)

    # Log monitoring metrics
    mlflow.log_metrics({
        "drift_share": result["drift_share"],
        "current_accuracy": result["current_accuracy"],
    })

    if monitor.should_retrain(result):
        monitor.trigger_retraining()
        alert("Model drift detected — retraining triggered", severity="warning")

What Not to Do

ML Systems Anti-patterns

Training-Serving Skew

Feature computation differs between training and serving code. The model sees different inputs at inference time, silently degrading accuracy. Use a shared feature computation library or feature store.

Future Data Leakage

Training with features computed after the label timestamp. The model learns from information that wouldn't exist at prediction time. Always use point-in-time correct feature retrieval.

No Model Versioning

Deploying new models by overwriting the old artifact. When something breaks, there's no rollback. MLflow/W&B model registry gives every version a unique artifact with metrics and lineage.

Evaluating Only on Accuracy

AUC = 0.92 does not mean the model is ready for production. Also evaluate: fairness across demographic groups, latency at p99, and business metrics (revenue, engagement) via A/B test.

RAG Without Chunking Strategy

Splitting documents into fixed 200-token chunks ignores semantic boundaries. A sentence split mid-paragraph loses context. Use recursive character splitting with overlap, and tune chunk size per document type.

No Data Drift Monitoring

Deploying a model and forgetting it. Models degrade as the world changes. Set up weekly distribution checks between training data and production data. Alert before accuracy visibly degrades.

Random Train/Val/Test Split for Time-Series

A random split for fraud detection or recommendations mixes future data into training. Always split by time: train on past, validate on recent past, test on the most recent period.

Embedding Everything in a Vector DB

Vector search is approximate and may miss exact keyword matches. Hybrid search (BM25 + vectors) outperforms pure semantic search for most enterprise use cases. Don't throw away keyword search.

Interview Prep

Interview Tips

Explain the Two-Stage Architecture

Recall (fast ANN, returns 1000 candidates) → Ranking (expensive model, scores 1000 → returns top 20). This pattern underlies YouTube, Netflix, LinkedIn recommendations. Name it explicitly.

Always Mention Training-Serving Skew

When designing any ML system, proactively mention this risk and how you'd prevent it (feature store, shared library). It shows production experience that distinguishes senior candidates.

Offline vs Online Metrics

Offline metrics (AUC) validate model quality. Online metrics (revenue, CTR) validate business impact. Always A/B test before declaring a model "better." Interviewers want to see this distinction.

RAG vs Fine-tuning

Know when each applies. RAG: dynamic knowledge, citations needed, no retraining budget. Fine-tuning: specific writing style, domain vocabulary, low latency inference with smaller model. This trade-off comes up often.

Mention Data Drift Monitoring

Most candidates design the training and serving pipeline but skip monitoring. Adding "we'd run weekly drift checks comparing production input distributions to training data" shows operational maturity.

Cold Start Problem

New users have no history — what do you recommend? New items have no ratings. Address this explicitly: popularity-based fallback, content-based matching, onboarding quiz. Ignoring cold start signals incomplete design.

Clarifications
+
What is an embedding vector?
An embedding is a dense list of numbers (e.g., 1536 floats) that represents the semantic meaning of text, an image, or a user's behavior. Similar things have similar vectors. OpenAI's text-embedding-3-small converts "help me log in" and "I forgot my password" to nearby vectors — so a search for one finds the other. They're the engine behind semantic search and recommendations.
+
What is data leakage?
Leakage happens when information that wouldn't be available at prediction time sneaks into your training data. Example: predicting fraud using "was account suspended within 7 days of transaction?" — that's future information. The model learns a perfect signal that doesn't exist in production. Result: perfect offline accuracy, terrible production accuracy.

What is ONNX?
ONNX (Open Neural Network Exchange) is an open format for ML models. You can export a PyTorch model to ONNX and run it with any ONNX runtime (ONNX Runtime, TensorRT, CoreML). Benefit: train in PyTorch (flexible), serve with ONNX Runtime (fast, no Python overhead). It's a portability layer for ML models.

What is ANN search?
Approximate Nearest Neighbor (ANN) search finds the K vectors in a database most similar to a query vector — but approximately, not exactly. Exact search is O(N·D) — too slow for millions of vectors. ANN algorithms (HNSW, IVF) build a graph or index structure that reduces search to O(log N). FAISS (Facebook AI Similarity Search) is the most popular ANN library. Accuracy vs speed is tunable.

What is statistical significance in A/B tests?
If model B shows higher revenue than model A, is that real or random luck? A p-value measures the probability of observing this difference if there were no real effect. p < 0.05 means there's less than 5% chance the result is random. You also need a minimum detectable effect (MDE) — if you're measuring a 0.1% revenue lift, you need millions of samples to be confident. Run A/B tests long enough to reach statistical significance.

What is hyperparameter tuning?
Hyperparameters are settings you choose before training (learning rate, tree depth, regularization strength) — the model doesn't learn them from data. Tuning finds the best combination. Optuna uses Bayesian optimization (tries promising combinations based on previous results). Ray Tune distributes the search across many machines. Grid search (try all combinations) is only feasible for small search spaces.
