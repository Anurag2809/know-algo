Foundation

CAP Theorem

CAP states that a distributed system can guarantee at most two of three properties simultaneously during a network partition. The key insight: partitions are not optional — networks fail. So the real choice is what to sacrifice when a partition occurs.

CAP THEOREM — the three properties ────────────────────────────────────────────────────────── Consistency (C): Every read returns the most recent write (or an error). All nodes see the same data at the same time. "There is one true value and everyone sees it." Availability (A): Every request receives a (non-error) response. The system keeps serving requests even if some nodes are down. "The system never refuses to answer." Partition Tolerance (P): The system continues operating when the network splits. Messages between nodes may be lost or delayed. "The system keeps running even with network failures." The practical constraint: Partitions WILL happen (network is unreliable). Therefore P is non-optional → choose between C and A during partitions. ────────────────────────────────────────────────────────── CP SYSTEMS — sacrifice availability for consistency During partition: reject requests rather than return stale data. Example: HBase, Zookeeper, etcd (Raft-based) Behavior: "I'd rather say 'I don't know' than give you wrong data." AP SYSTEMS — sacrifice consistency for availability During partition: continue serving, accept stale reads. Example: Cassandra, CouchDB, DynamoDB (tunable) Behavior: "I'll give you something, even if it's not perfectly fresh." ────────────────────────────────────────────────────────── COMMON MISCONCEPTION: "CA systems" (no partition tolerance) don't exist in practice. A single-node PostgreSQL is "CA" only because it has no distributed component to partition — it's not a distributed system at all. Once you have replication, you have P (and lose CA as a unified option).
CAP is a Partition-Time Choice, Not a System Design Choice

In normal operation (no partition), you can have both C and A. CAP only forces a trade-off during a network partition. The real question is: when a partition occurs and I can't guarantee both, which do I prioritize? This is a product decision as much as a technical one: financial transactions demand C, social media feeds can accept A.

Extended Model

PACELC — Beyond CAP

CAP only describes partition behavior. PACELC extends it: even when the system is running normally (no partition), there's a trade-off between latency (L) and consistency (C). Lower consistency → lower latency. Higher consistency → higher latency. This is the trade-off you live with every day, not just during failures.

PACELC FRAMEWORK ────────────────────────────────────────────────────────── IF Partition: choose between Availability or Consistency ELSE Normal op: choose between Latency or Consistency System classifications: System P behavior E behavior Classification ────────────── ──────────── ──────────── ────────────── DynamoDB Avail (AP) Low latency PA/EL Cassandra Avail (AP) Low latency PA/EL (tunable) Zookeeper/etcd Consist (CP) Consistency PC/EC Google Spanner Consist (CP) Consistency PC/EC (strong) MongoDB Consist (CP) Low latency PC/EL (tunable) PostgreSQL Consist (CP) Consistency PC/EC (single node) ────────────────────────────────────────────────────────── THE LATENCY/CONSISTENCY TRADE-OFF (normal operation): Strong consistency requires: 1. Primary node processes write 2. Write replicates to all replicas (sync) 3. All replicas confirm receipt 4. Primary acknowledges to client Time: network RTT × number of replicas At 3 replicas in same DC: +5-20ms latency per write Eventual consistency requires: 1. Primary node processes write 2. Client immediately gets success 3. Write replicates async in background Time: minimal write latency, replicas catch up within seconds
Spectrum

Consistency Models

Consistency is not binary — it's a spectrum from strict linearizability to eventual consistency. Each level has different performance implications and use cases.

Linearizability (Strict)
Reads always return the most recent write. Operations appear instantaneous and sequential. Real-time ordering guaranteed.

Cost: Highest latency (consensus required per op)
Use: Financial transactions, distributed locks, leader election
Sequential Consistency
All processes see the same order of operations. Each process's operations appear in order, but may not reflect wall-clock time.

Cost: High latency
Use: Multi-player game state, collaborative tools
Causal Consistency
Causally related operations seen in order. Concurrent operations may be seen in different orders by different nodes.

Cost: Medium latency (vector clocks or DAG)
Use: Comments, social feeds, collaborative editing
Eventual Consistency
Given no new writes, all replicas converge to the same value eventually. No ordering guarantees. Highest performance.

Cost: Lowest latency, conflict resolution needed
Use: DNS, shopping cart, user preferences, social likes

Read Your Own Writes (RYOW)

READ-YOUR-OWN-WRITES — a practical consistency guarantee ────────────────────────────────────────────────────────── Problem with async replication: User writes profile picture update App reads from replica (async lag: 500ms) User sees OLD profile picture → confusing UX RYOW solutions: 1. Read from primary after writes (simple but increases primary load) Track per-user "last_write_timestamp" If time_since_write < 1 minute → read from primary 2. Monotonic read + sticky session User always reads from same replica Replica may be stale but their reads are monotonically consistent Implement via session-based replica affinity 3. Client-side merge Cache the user's own writes in client state Overlay locally on top of server response Used by Facebook, Twitter for optimistic UI 4. Version token Write returns a version: {user_id, version: 42} Next read includes "read-after: version 42" header Load balancer routes to replica that has replicated version 42+
Consensus Algorithm

Raft Consensus

Raft is the consensus algorithm that powers etcd (and therefore Kubernetes), CockroachDB, TiKV, and most modern distributed databases. It solves a fundamental problem: how do multiple nodes agree on a single value (or sequence of values) when any node can fail or messages can be lost?

RAFT — THREE ROLES ────────────────────────────────────────────────────────── Leader: Receives all client writes. Replicates to followers. One leader at a time (per Raft term). Sends heartbeats every 150ms to maintain authority. Follower: Accepts log entries from leader. Votes in elections. If no heartbeat for election timeout (150-300ms) → candidate. Candidate: Requests votes from all nodes. If majority → new leader. ────────────────────────────────────────────────────────── RAFT LOG REPLICATION (happy path): Client → Leader: "set x = 5" Leader appends to own log: [... | {term:3, cmd: "set x=5"}] Leader → Follower A, Follower B: AppendEntries RPC Followers append to their logs, reply OK Leader receives majority (2 of 3): entry committed Leader applies to state machine, replies to client Leader notifies followers: "entry 42 committed, apply it" Commit rule: An entry is committed once stored on a majority of nodes. With 3 nodes: commit after 2 store it. With 5 nodes: commit after 3 store it. → Tolerate (n-1)/2 failures: 3-node cluster survives 1 failure. ────────────────────────────────────────────────────────── LEADER ELECTION: Leader fails → no heartbeat → followers time out (random delay) Candidate increments term, votes for self, requests votes from others Majority vote (2 of 3) → becomes new leader for new term Random election timeout (150-300ms) prevents split votes Split vote: 2 candidates simultaneously, each gets 1 vote → retry Random timeouts statistically prevent repeated splits
Raft vs Paxos

Paxos is the original consensus algorithm (Lamport, 1989) but is notoriously difficult to understand and implement correctly. Raft was designed specifically to be understandable — it produces equivalent results but structures the algorithm around leader-based log replication with explicit leader election. Production systems use Raft (etcd, CockroachDB, TiKV); Paxos is largely academic at this point or used in legacy Google systems (Chubby, Spanner uses a Paxos variant).

Coordination Primitive

Distributed Locks

A distributed lock ensures only one process in a distributed system holds a resource at a time. The challenge: the lock holder can fail mid-operation without releasing the lock. Every distributed lock implementation must handle this case.

Redis-based Lock (Redlock)

REDIS DISTRIBUTED LOCK (SETNX + EXPIRE) ────────────────────────────────────────────────────────── Acquire lock: SET lock:resource_id {unique_token} NX PX 30000 NX = only set if key doesn't exist (atomic acquire) PX 30000 = expire in 30 seconds (safety net if holder crashes) Release lock (Lua for atomicity): if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end → Check-then-delete is atomic via Lua script → Only the holder with the correct token can release → If holder crashes: lock auto-expires after 30s THE CRITICAL EXPIRY PROBLEM: Process A acquires lock (30s TTL) Process A does work... takes 35s (long GC pause, slow DB) Lock expires after 30s Process B acquires the same lock (thinks it's free) Process A finishes, does the write (lock already held by B!) → Two processes think they hold the lock simultaneously Solution: Fencing tokens (see next section)

etcd / Zookeeper Locks (Strongly Consistent)

ETCD DISTRIBUTED LOCK — Raft-backed, no expiry race ────────────────────────────────────────────────────────── etcd uses leases (TTL-based, auto-renewed by holder): 1. Create lease: lease_id = etcd.grant(ttl=30) 2. Acquire lock: etcd.put(key="/lock/resource", lease=lease_id, prev_kv=nil) → Only succeeds if key doesn't exist (atomic via Raft) 3. Holder renews lease every 10s (keepAlive goroutine) 4. If holder crashes: lease expires, etcd deletes the key 5. Waiters watch the key: notified when it's deleted → re-acquire Why etcd > Redis for critical locks: Raft-backed: lock operations are serialized through consensus No split-brain: only one leader can commit the lock grant Session expiry detected immediately (watch mechanism) Used by: Kubernetes leader election, distributed job schedulers When Redis SETNX is fine: Best-effort mutual exclusion where occasional double-execution is OK Rate limiting (not critical correctness) Cache population locks (thundering herd prevention) Short-duration locks where expiry is very unlikely
Safety Mechanism

Fencing Tokens

Fencing tokens solve the lock expiry race condition: even if a lock holder believes it holds the lock, the storage system rejects its writes if a newer lock holder has superseded it.

FENCING TOKEN PATTERN ────────────────────────────────────────────────────────── Lock service issues monotonically increasing token per grant: Process A acquires lock → token = 33 Process A takes too long → lock expires Process B acquires lock → token = 34 (higher number) Process A (delayed) tries to write: WRITE data WHERE lock_token >= 33 → rejected! Storage sees current token is 34 → 33 < 34 → reject stale write Process B writes successfully: WRITE data WHERE lock_token >= 34 → accepted Implementation in storage: Each protected resource stores last_seen_token Any write must include its token Storage: if write.token < resource.last_seen_token → reject (stale lock holder) Storage: if write.token >= resource.last_seen_token → accept, update token → Storage itself enforces exclusivity, not just the lock service → Network partitions, GC pauses, and lock expiry can't cause split writes → Used in: HDFS NameNode lease tokens, etcd compare-and-swap
Causality Tracking

Vector Clocks

Physical clocks in distributed systems cannot be trusted — clocks drift, NTP synchronization is imperfect. Vector clocks track causality between events using logical timestamps, enabling systems to determine if event A happened before B, after B, or concurrently with B.

VECTOR CLOCK — causality tracking ────────────────────────────────────────────────────────── 3 nodes: A, B, C. Each maintains a vector [A_count, B_count, C_count] Initial state: A=[0,0,0], B=[0,0,0], C=[0,0,0] A writes x=1: A=[1,0,0], sends to B B receives: B=[1,1,0], writes y=2 C writes z=3: C=[0,0,1] (concurrent with B — C doesn't know about A's write) Now B and C both want to update the same key "foo": B's value: "hello" with clock [1,1,0] C's value: "world" with clock [0,0,1] Compare clocks: Is [1,1,0] < [0,0,1]? → NO (B is ahead in B_count) Is [0,0,1] < [1,1,0]? → NO (C is ahead in C_count) → Concurrent writes — CONFLICT Resolution strategies: 1. Last-Write-Wins: Pick higher timestamp (requires physical clock — imprecise) 2. Multi-value return: Return both values, let client resolve (Amazon shopping cart) 3. CRDT merge: Merge automatically based on data type semantics 4. Application merge: Business logic decides winner (Google Docs OT) ────────────────────────────────────────────────────────── HAPPENED-BEFORE RULES (→ means "happened before"): A=[1,0,0] → B=[1,1,0] (B has seen A's write) Two clocks are concurrent if neither dominates the other Concurrent = neither knows about the other's changes
Conflict-Free Replication

CRDTs (Conflict-free Replicated Data Types)

CRDTs are data structures designed so that concurrent modifications can always be merged automatically without conflicts. The data type itself embeds the merge function, making eventual consistency achievable without application-level conflict resolution.

CRDT TYPES AND USE CASES ────────────────────────────────────────────────────────── G-Counter (Grow-only counter): Each node has its own count. Global value = sum of all. Node A increments its slot: [A:5, B:3, C:2] → total = 10 Concurrent increments auto-merge: take max per slot. Use: Page view counts, like counts, event tallies PN-Counter (Positive-Negative counter): Two G-counters: one for increments, one for decrements. Value = G-Counter(P) - G-Counter(N) Use: Inventory counts, bank balances (simplified) G-Set (Grow-only set): Elements can only be added, never removed. Merge = union of both sets. No conflicts possible (union is always valid). Use: Tags, metadata collections where items are never removed OR-Set (Observed-Remove set): Each element tagged with unique ID on insert. Remove marks the specific instance (by ID) as deleted. Supports add-and-remove with concurrent modifications. Use: Shopping cart, collaborative whiteboard items LWW-Register (Last-Write-Wins register): Scalar value with timestamp. Merge: take value with higher timestamp. Simple but requires synchronized clocks (problematic). Use: User preferences, configuration settings ────────────────────────────────────────────────────────── CRDT IN PRACTICE — Redis Shopping Cart: User adds item A on device 1: cart = {A: 1} User adds item B on device 2 (offline): cart = {B: 1} Network reconnects → merge: OR-Set merge: {A: 1, B: 1} ← no conflict, both additions preserved User removes A on device 1: cart = {B: 1} Concurrently, user also increments A on device 2: cart = {A: 2, B: 1} Merge: conflict — was A added or removed? OR-Set rule: if a remove is concurrent with an add, the add wins Result: {A: 2, B: 1} ← this is the "add wins" CRDT semantics Real systems: Riak uses CRDTs natively. Redis has CRDT modules. Figma uses CRDTs for collaborative design multiplayer.
Distributed Transactions

Two-Phase Commit (2PC)

2PC is the classic protocol for coordinating writes across multiple nodes in a distributed transaction. It guarantees atomicity (all commit or all abort) but is blocking and has a known failure scenario that makes it unsuitable for high-availability systems.

2PC PROTOCOL ────────────────────────────────────────────────────────── PHASE 1 — Prepare: Coordinator → all Participants: "Can you commit transaction T?" Each Participant: Writes undo/redo log to durable storage Acquires all necessary locks Replies VOTE_COMMIT or VOTE_ABORT PHASE 2 — Commit/Abort: If ALL voted COMMIT: Coordinator → all Participants: GLOBAL_COMMIT Participants commit, release locks, reply ACK If ANY voted ABORT: Coordinator → all Participants: GLOBAL_ABORT Participants rollback using undo log, release locks ────────────────────────────────────────────────────────── THE BLOCKING PROBLEM — why 2PC is avoided in production: 1. Participant votes COMMIT (locks held, can't proceed without coordinator) 2. Coordinator crashes before sending phase 2 3. Participant is stuck: committed? aborted? Don't know. 4. Locks are held indefinitely until coordinator recovers. 5. Other transactions waiting on those locks are blocked. → 2PC is a "blocking" protocol — one crash can block the system indefinitely Why 2PC is still used: Most databases use 2PC internally for XA transactions (JDBC distributed transactions, JTA in Java EE) Acceptable when coordinator recovery is fast and MTTR is low Not acceptable when you need millisecond-level availability Better alternatives: Saga pattern (see Async pattern) — non-blocking, compensating txns Google Spanner — external consistency via TrueTime + 2PC hybrid
9 Lenses

How Each Team Thinks About Consistency

🏗️ Infrastructure Engineer

Consistency guarantees are only as strong as the underlying infrastructure. Synchronous replication across AZs adds network latency — we measure the round-trip time between our AZs and factor it into write latency budgets before committing to a consistency model. A promise of "synchronous replication" between AZs 50ms apart means every write has at minimum 50ms added to its tail latency.

etcd clusters (which back Kubernetes) require careful capacity planning and network isolation. etcd is latency-sensitive — disk I/O jitter during Raft log writes can cause leader elections and transient unavailability. We run etcd on dedicated nodes with SSDs (not network storage), reserved CPU, and isolated network interfaces. A noisy neighbor on the same host as the etcd leader has caused Kubernetes control plane instability in past incidents.

We never allow quorum-based systems (Raft, Paxos) to have even numbers of nodes. Even numbers create split-brain risk where neither half can reach majority. Three nodes, five nodes, or seven nodes — never two, four, or six. When someone requests a "two-node HA setup," we push back: two nodes can't achieve consensus when one fails. You need three or an external tiebreaker.

🌐 Network Engineer

Network partitions are the forcing function of CAP theorem. We design network topology to minimize the probability of partitions within a cluster: redundant switch paths, LACP bonding on physical servers, dedicated cluster network segments separate from user traffic. But partitions can still occur — split-brain between two AZs during a routing loop, packet loss causing Raft leader heartbeat failures. We cannot eliminate partitions, so we design systems that handle them gracefully.

The choice between CP and AP has network throughput implications. CP systems (Raft-based) require all writes to flow through the leader — this creates an ingress bottleneck at the leader's network interface. AP systems (Cassandra-style) accept writes at any node — write traffic is distributed across all nodes and their network interfaces. At 10 GB/s write throughput, this difference is significant for network capacity planning.

MTU and packet fragmentation matter for consensus algorithms. Raft AppendEntries RPCs carry log entries that can be large (multi-KB batch entries). Packets fragmented by MTU mismatches cause reassembly delays that look like latency spikes, which can trigger false leader elections. We verify MTU consistency across all nodes in the cluster and disable TCP segmentation offload (TSO) in environments where it causes issues with Raft timing.

⚙️ Platform Engineer

We provide consistency level as a configurable parameter, not a fixed property. Teams declare their consistency requirement in the service manifest: "strong" (routes to primary-only reads), "bounded-staleness" (reads from replica with max 5s lag), or "eventual" (reads from any replica). The platform enforces this routing — teams don't configure database connection strings manually and accidentally bypass consistency guarantees.

Distributed lock management is a platform service we operate. Teams request a named lock via a gRPC API; we handle the etcd lease management, TTL renewal, and failure detection. Application code calls `lock.acquire()` and `lock.release()` — the distributed systems complexity is hidden. This avoids teams writing their own buggy Redis-based locking code and having the associated incidents.

Leader election for stateful services (job schedulers, singleton workers) goes through our platform's leader election service (backed by etcd). We expose a simple API: register as a candidate, watch for leadership changes, resign gracefully on shutdown. The Kubernetes leader election library is our reference implementation — it handles all the edge cases that hand-rolled implementations miss.

🔐 Security / Cyber Engineer

Consistency models have security implications that aren't obvious. Eventual consistency means a permission revocation might not be immediately reflected across all nodes. If we revoke a user's access token and the system is eventually consistent, they might still succeed in making API calls to nodes that haven't received the revocation yet. For auth and permissions, we require strong consistency — revocations take effect immediately, not eventually.

Distributed locks protect critical sections, and lock implementations have known vulnerabilities. Redis SETNX with no TTL creates deadlock if the holder crashes — we've seen this happen with a CPU spike killing a lock holder before it could release. We audit all distributed lock usage in code review: every lock must have a TTL, the release must be guarded against releasing someone else's lock (unique token check), and the lock scope must be as narrow as possible.

The consensus layer (etcd, Zookeeper) must be secured as tightly as the database. etcd contains every Kubernetes secret, configuration, and state — it's the single most sensitive datastore in the cluster. We enforce: mTLS between etcd nodes and between API server and etcd, restricted network access (only the API server communicates with etcd, not application pods), and encrypted etcd storage at rest (EBS encryption + encryption-at-rest flag).

📊 Data Engineer

Consistency models determine what data pipelines can assume. If we're reading from a Cassandra table with eventual consistency, our pipeline might see different values for the same key across different reads in the same batch. We handle this by reading from a single coordinator node with LOCAL_QUORUM, or by deduplicating by primary key and taking the highest timestamp within our pipeline. We never assume an eventually consistent source gives us a clean, point-in-time snapshot.

The "exactly-once" processing guarantee in Kafka Streams and Flink is a consistency guarantee at the processing level. It relies on exactly-once semantics from the source (Kafka transactional producer) and idempotent writes to the sink (upsert by primary key rather than append). The entire pipeline must support exactly-once for the end-to-end guarantee to hold — a single non-idempotent step breaks the chain.

Vector clocks appear in our change data capture pipelines. Debezium attaches the WAL LSN (log sequence number) to each event — this is effectively a monotonic vector timestamp for the Postgres WAL. We use LSN ordering to deduplicate events and ensure our pipeline processes changes in the correct causal order. An event with a lower LSN always happened before one with a higher LSN on the same Postgres instance.

🤖 ML / AI Engineer

Feature consistency is our version of the distributed consistency problem. When we train a model, each training example uses a consistent snapshot of features at a point in time. When we serve the model, we need to reconstruct those features from the online store in real time. If the online feature store is eventually consistent, a prediction at time T might use a feature value that was actually computed at T-2 minutes — a consistency skew. For time-sensitive features (current cart value, recent activity), this skew can significantly degrade prediction quality.

ML training requires consistent snapshots. We use a two-phase snapshot: first, copy all table metadata and record current timestamps; second, export data where created_at <= snapshot_time. This gives a consistent view even if new rows are being written during the export. Using a read replica with a known replication lag and exporting from it with lag offset is another approach. Inconsistent training data produces non-reproducible experiments — a consistency problem that shows up as statistical noise.

Distributed hyperparameter search (Optuna, Ray Tune) uses a shared trial database with concurrent writes from many workers. The consistency model here is best-effort: workers occasionally see slightly stale trial results and may explore the same hyperparameter region twice. This is acceptable because the loss from inconsistency is bounded (slightly redundant trials), not catastrophic (wrong model deployed). Eventual consistency with deduplication on the completed trial ID is the correct choice here.

⚡ Backend Engineer

Choosing a consistency level is a per-query decision in Cassandra, and I make it consciously. Read-after-write consistency for a user's own data: LOCAL_QUORUM (strong within the datacenter). Background analytics reads that can be slightly stale: ONE (fastest). Cross-DC reads where we need global consistency: QUORUM (majority of all replicas across DCs). Defaulting to ONE everywhere is a bug waiting to become an incident.

Optimistic concurrency control (OCC) is my preferred approach over distributed locks for write conflicts. Instead of acquiring a lock before writing, I include a version field in the row. The UPDATE statement includes WHERE version = $expected_version. If another writer updated the row between my read and my write, the version won't match and the UPDATE affects 0 rows — I detect the conflict and retry. No locks, no distributed coordination, much simpler failure modes.

Compare-and-swap (CAS) operations are the building block for coordination primitives in my application code. Redis SETNX is CAS. Postgres UPDATE WHERE version=$expected is CAS. DynamoDB conditional writes are CAS. etcd compare-and-swap is CAS. All distributed coordination reduces to CAS at some level. When I see complex locking code, I ask: can this be expressed as a CAS loop instead? The CAS version is almost always simpler and has clearer failure semantics.

🎨 Frontend Engineer

Consistency is a UX problem as much as a technical one. When a user edits their profile and immediately navigates to the profile page, seeing the old data is jarring even if it's "technically correct" under eventual consistency. I implement client-side read-your-own-writes by caching recent writes locally and overlaying them on server responses. The server is eventually consistent; the client shows the user their own writes immediately regardless.

Conflict resolution UX in collaborative tools is the frontend manifestation of distributed consistency. Google Docs resolves conflicts invisibly via operational transforms. Figma shows "this layer was moved by Alice" when a conflict occurs. Linear shows a "conflict" state when two people edit the same issue simultaneously. The choice of CRDT vs OT vs last-write-wins determines what conflict UI is even possible — CRDTs allow invisible merges, LWW requires showing who won.

Offline-first apps are a consistency design challenge. When the user is offline, they write to a local store (IndexedDB). When they reconnect, changes must be merged with the server state. If another user edited the same data while they were offline, there's a conflict. The merge strategy must be designed upfront: last-write-wins (data loss risk), three-way merge (complex), or CRDT (data-type-specific auto-merge). Most apps choose last-write-wins because it's simple, but this silently discards data that users care about.

📡 SRE / Site Reliability Engineer

Consistency anomalies are hard to detect with standard monitoring. Error rates and latency look fine; the system appears healthy. But stale reads, phantom reads, or lost updates are silently corrupting business state. We instrument data consistency checks: periodic reconciliation jobs that compare expected vs actual state across replicas, alert if divergence exceeds thresholds. For critical data (financial balances, inventory counts), we run these checks every 5 minutes.

Raft leader elections show up in our metrics as latency spikes. The election window (150-300ms timeout + voting + new leader establishing authority) causes requests to queue or fail during leader transitions. We alert on Raft leader change frequency — more than 2 leader changes per hour indicates a sick cluster (network instability, overloaded leader, disk latency). etcd provides `/metrics` with leader change rate via Prometheus.

Distributed lock contention is a capacity signal. When many processes compete for the same lock, lock acquisition time increases and throughput drops. We instrument lock acquisition latency and contention rate (how often acquire fails because lock is held). High contention is usually a design smell — the lock is protecting a hot resource that should be partitioned or redesigned to avoid the serialization point. We surface this to the backend team before it becomes a performance incident.

Real Problems

Applied Consistency Design

Problem 01
Design a Distributed Counter for Real-Time Leaderboard (100M writes/day)
CRDT G-Counter Eventual Consistency Redis Sorted Set

Requirements

  • Users earn points for completing actions. Points update in real time.
  • Leaderboard shows top 100 players, refreshed every second.
  • 100M point-award events per day = ~1200 writes/second peak.
  • Leaderboard may show slightly stale values (1-2s lag acceptable).

Why Not Strong Consistency

Serializing all point-award writes through a single strongly consistent source (a single Postgres primary) creates a write bottleneck. At 1200 writes/second, each touching the same leaderboard data structure, lock contention becomes severe. The business tolerance for 1-2 seconds of stale leaderboard values makes eventual consistency the right choice.

Architecture: CRDT G-Counter + Redis Sorted Set

LEADERBOARD CONSISTENCY DESIGN Events → Kafka: game.points.awarded │ partitioned by user_id (all events for user go same partition) ▼ [ Points Consumer ] │ ZINCRBY leaderboard {points} {user_id} (Redis Sorted Set) │ atomically increments — no lock needed ▼ [ Redis Sorted Set: "leaderboard" ] ZADD uses score = cumulative points per user ZREVRANGE leaderboard 0 99 WITHSCORES → top 100 Durability: Redis is the hot view (fast, eventually consistent) Postgres is the source of truth (all events persisted before Kafka) If Redis flushes → rebuild from Postgres in minutes Periodic Postgres→Redis sync every 60s (catch any drift) Partition-by-user ensures ordering: All point events for user X processed in sequence No race condition on user X's score Concurrent events for different users are independent (no shared lock) 
import redis

r = redis.Redis(host='redis', decode_responses=True)

def award_points(user_id: str, points: int, event_type: str) -> float:
    pipe = r.pipeline(transaction=True)
    pipe.zincrby('leaderboard:global', points, user_id)
    pipe.zincrby(f'leaderboard:daily:{today()}', points, user_id)
    results = pipe.execute()
    return results[0]  # new total score

def get_top_100() -> list:
    return r.zrevrange('leaderboard:global', 0, 99, withscores=True)

def get_user_rank(user_id: str) -> int:
    rank = r.zrevrank('leaderboard:global', user_id)
    return rank + 1 if rank is not None else None

def get_user_score(user_id: str) -> float:
    return r.zscore('leaderboard:global', user_id) or 0
Problem 02
Implement a Distributed Job Scheduler (Run Job Exactly Once)
Distributed Lock Fencing Tokens Leader Election

The Problem

A cron-style job must run exactly once per scheduled interval across 10 instances of a service. Without coordination, all 10 instances run the job simultaneously — 10× the side effects (duplicate emails, double charges, redundant index builds).

Architecture: etcd-based Leader Election + Fencing

import etcd3
import uuid

etcd = etcd3.client()

def try_acquire_job_lock(job_name: str, ttl: int = 60) -> tuple:
    """Returns (acquired: bool, token: str)"""
    token = str(uuid.uuid4())
    lock_key = f"/job-locks/{job_name}"

    # Create lease — auto-expires if this process crashes
    lease = etcd.lease(ttl)

    # Atomic compare-and-swap: only set if key doesn't exist
    success, _ = etcd.transaction(
        compare=[etcd.transactions.version(lock_key) == 0],
        success=[etcd.transactions.put(lock_key, token, lease=lease)],
        failure=[]
    )

    if success:
        # Start background lease keepalive
        lease.keepalive()
        return True, token, lease
    return False, None, None

def run_scheduled_job(job_name: str, job_fn):
    """Only one instance in the cluster runs this."""
    acquired, token, lease = try_acquire_job_lock(job_name)
    if not acquired:
        return  # Another instance holds the lock — skip

    try:
        # Pass fencing token to job — storage layer checks it
        job_fn(fencing_token=token)
    finally:
        # Release lock: only delete if our token still matches
        etcd.transaction(
            compare=[etcd.transactions.value(f"/job-locks/{job_name}") == token],
            success=[etcd.transactions.delete(f"/job-locks/{job_name}")],
            failure=[]
        )
        lease.revoke()
Problem 03
Design a Multi-Region Shopping Cart (Offline-First, CRDT)
OR-Set CRDT AP System Conflict Resolution

Requirements & Trade-offs

Users add/remove items from a shopping cart. The cart must work offline (mobile app). Conflicting edits (item added on device 1 while removed on device 2) must be resolved without data loss. The cart is not a financial instrument — availability trumps strict consistency.

CRDT OR-Set Cart

SHOPPING CART AS OR-SET CRDT Each add assigns a unique tag: {item_id, device_id, timestamp} Device 1 (online): adds "Book" → {book, dev1, T1} Device 2 (offline): adds "Pen" → {pen, dev2, T2} Device 2 (offline): removes "Book" ← removes {book, dev1, T1} Reconnect → merge: Device 1 has: {book, dev1, T1}, removes={} Device 2 has: {pen, dev2, T2}, removes={book, dev1, T1} OR-Set merge: union of adds, union of removes Effective items = adds - removes = { {book,dev1,T1}, {pen,dev2,T2} } - { {book,dev1,T1} } = { {pen,dev2,T2} } → Cart: ["Pen"] If Device 2 concurrently added a new tag for "Book": = { {book,dev1,T1}, {pen,dev2,T2}, {book,dev2,T3} } - { {book,dev1,T1} } = { {pen,dev2,T2}, {book,dev2,T3} } → Cart: ["Pen", "Book"] Add wins over concurrent remove — acceptable for shopping carts

What Not to Do

Anti-patterns

  • Assuming eventual consistency means "eventually correct" Eventual consistency means replicas converge to the same value if no new writes occur. It does NOT mean the value will eventually be the one you wrote — it means the last write wins. If two nodes receive conflicting writes, one will be discarded. "Eventually consistent" data can permanently lose writes without error if conflict resolution (LWW or CRDT) discards your value.
  • Redis distributed lock without TTL (deadlock risk) SETNX without EXPIRE creates a permanent lock if the holder crashes before releasing it. The lock key lives forever in Redis, blocking all future lock holders. Always use atomic SET key value NX PX ttl_ms — never SETNX followed by a separate EXPIRE (non-atomic, crashes between the two commands leave no TTL).
  • Even-number Raft cluster (2, 4, 6 nodes) A 2-node Raft cluster cannot elect a leader if either node fails — neither can reach majority (1 of 2 = 50%, not >50%). Always use odd numbers: 3, 5, or 7. Three nodes tolerate 1 failure. Five nodes tolerate 2. The "two-node HA" pattern for cost savings is a latent split-brain waiting to happen.
  • Using distributed locks as a substitute for proper data modeling A distributed lock around a shared counter prevents concurrent modification. But so does an atomic INCR in Redis, or an UPDATE WHERE version=$v in Postgres. Reaching for a distributed lock first is a code smell — often there's a simpler atomic primitive (CAS, INCR, conditional write) that avoids the coordination entirely. Locks serialize throughput; atomic operations don't.
  • Ignoring the lock expiry window in critical operations If a lock holder experiences a GC pause, network delay, or CPU throttle and the lock expires, another process acquires the lock. Both processes now believe they hold the lock. Without fencing tokens, the first holder's write will corrupt data after the second holder has already proceeded. Critical sections that modify external state must use fencing tokens or Raft-backed locks that don't expire while the session is alive.
  • Strong consistency everywhere "to be safe" Strong consistency requires consensus per write — adding latency and reducing write throughput. Applying it to all data regardless of business need is waste. User preferences, analytics events, and read counts don't need linearizability. Measure the actual cost (latency, throughput) of consistency at each storage layer and choose the weakest consistency that meets the business requirement.
  • Two-phase commit in a microservices architecture 2PC across microservice boundaries requires all services to implement the XA protocol and coordinate through a single transaction coordinator. Any service that doesn't support XA breaks the protocol. Any coordinator failure leaves all participants blocked with locks held. The Saga pattern solves this correctly for microservices — local transactions with compensating actions, no distributed coordinator.
  • Relying on physical timestamps for event ordering NTP synchronization can drift by 100ms or more between nodes. Two events written 1ms apart at different nodes can appear in the wrong order when sorted by wall-clock time. For event ordering, use Kafka partition offsets (monotonic within partition), Postgres LSN (monotonic within WAL), or logical timestamps (vector clocks). Physical timestamps are for humans to read, not for machines to order events.
Interview Strategy

Interview Tips for Consistency Questions

The Consistency Interview Signal

When interviewers ask about distributed systems design, the consistency question is usually implicit: "What if two users update the same thing simultaneously?" or "What if the database replica is slightly behind?" Proactively raising this question and providing a nuanced answer (not just "we'll use strong consistency everywhere") is what separates senior candidates.

Tip 01

Lead with CAP's practical framing. "Partitions happen, so the choice is: do we sacrifice consistency (serve stale data) or availability (reject requests) when a partition occurs?" This shows you understand CAP is a partition-time decision, not an architectural one.

Tip 02

Classify each data type separately. "Financial data needs strong consistency. User profile photos can be eventually consistent. The leaderboard can be eventual with 2s staleness." Don't pick one consistency model for the whole system — different data has different requirements.

Tip 03

For concurrent writes, name your resolution strategy. "If two users edit the same document simultaneously, we need a conflict resolution strategy — last-write-wins with timestamps, operational transforms, or a CRDT based on the data type." Naming the options shows distributed systems depth.

Tip 04

For distributed locks, mention fencing tokens. "I'd use a distributed lock via etcd with a fencing token — even if the lock expires, the storage layer rejects writes from stale lock holders via the token comparison." This is the detail that shows you've thought about failure modes.

Tip 05

Mention Raft for "how does this coordinate" questions. etcd, CockroachDB, TiKV, and Kubernetes control plane all use Raft. Saying "I'd use etcd for leader election — it's Raft-backed and handles network partitions correctly" shows awareness of production tools.

Tip 06

Use "read-your-own-writes" as a concrete consistency discussion. "After a user saves their profile, they should see their own changes immediately — I'd ensure this via sticky routing to the primary for that user's next read, or client-side caching of the write." This is concrete, testable, and shows you think about UX impact of consistency choices.
